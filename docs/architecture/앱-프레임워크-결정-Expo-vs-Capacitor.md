# 앱 프레임워크 결정 — Expo(React Native) vs Capacitor

작성: 2026-10-13. 전제: 네이티브 앱 100만 다운로드 규모, "앱으로 할 수 있는 건 다 한다". 판단 기준은 효율·개발속도가 아니라 **운영 안정성과 확장성**. 짝 문서: `모노레포-정석구조-설계.md`.

## 결론 먼저

- 권고: **Expo(React Native)**. 100만 DL + "앱 기능 전부" 전제에서 정석에 더 가깝다.
- 이유 한 줄: 지금 Capacitor는 "앱"이 아니라 **라이브 사이트를 그대로 띄우는 웹뷰 셸**이라, 사용자의 목표("앱으로 할 수 있는 건 다")와 구조적으로 어긋난다.
- 단, 이건 되돌리기 어려운 결정(전환비용 큼, 전문 인력 필요)이므로 근거를 아래에 다 편다. 반대 선택(Capacitor 유지)이 맞는 조건도 명시한다.

## 지금 Capacitor의 실체 (2026-10-13 실측)

| 항목 | 사실 | 함의 |
|---|---|---|
| 모드 | **원격 URL 모드** — `server.url: https://ailens.sedaily.ai` | 로컬 번들 없음. 앱이 라이브 웹을 그대로 띄움 |
| 커스텀 네이티브 코드 | 7개 파일 전부 보일러플레이트(MainActivity, AppDelegate 등) | 네이티브 기능 0 |
| 설치된 플러그인 | `@capacitor/{core,android,ios,cli,assets}`뿐 | **푸시 플러그인 없음**. 네이티브 플러그인 0 |
| iOS 빌드 | Xcode 미설치로 실제 빌드 미검증(README 명시) | iOS는 사실상 미완 |
| 상태 | Play 미발행, `appId: ai.sedaily.lens` | 아직 출시 전 — 되돌릴 비용이 가장 쌀 때 |

핵심: 현재 Capacitor 앱은 **브라우저 창에 AI LENS 사이트를 띄운 것**이다. 홈 인디케이터·스플래시·아이콘만 앱이고 내용물은 100% 웹. "앱으로 할 수 있는 건 다"(오프라인, 네이티브 제스처, 백그라운드, 생체인증, 인앱결제, 네이티브 공유 등)와는 반대 지점에 있다.

## 두 접근의 본질 차이

- Capacitor = **웹뷰 래퍼**. 웹 코드를 네이티브 컨테이너에 담는다. UI는 WebView가 렌더.
- Expo(React Native) = **JS→네이티브 브릿지**. React로 작성하되 실제 네이티브 뷰(UIView/android.view)를 렌더. Expo는 그 위의 빌드·OTA·푸시·모듈 생태계.

## 비교표 (운영 안정성·확장성 기준)

| 기준 | Capacitor | Expo(RN) | 100만 DL 관점 승자 |
|---|---|---|---|
| 렌더링 | WebView(웹 성능에 종속) | 네이티브 뷰 | **Expo** — 긴 리스트·스크롤·전환이 네이티브 |
| 복잡 애니메이션/제스처 | 웹 한계 | Reanimated 등 네이티브 | **Expo** |
| 오프라인/백그라운드 | 플러그인 의존, 원격 URL 모드면 사실상 불가 | 1급 지원 | **Expo** |
| 푸시 | 플러그인(FCM/APNs) 가능하나 미구현 | Expo Notifications + FCM/APNs | **Expo**(생태계 성숙) |
| 네이티브 기능 전부 | 플러그인 있으면 가능, 없으면 직접 | 모듈+Config Plugin, 직접 네이티브 모듈 | **Expo**(천장이 높음) |
| OTA 업데이트 | 플러그인(Capgo 등) | EAS Update 1급 | **Expo**(심사 없이 JS 핫픽스) |
| 웹 코드 재사용 | UI까지 100% | UI 제외 전부(계약·타입·로직·인증) | Capacitor(단 UI 공유가 100만서 독) |
| 개발 인력 | 웹 개발자 그대로 | RN 전문성 필요 | Capacitor |
| 전환 비용(지금) | 0(이미 있음) | 중~대(UI 재작성) | Capacitor |
| 플랫폼 변경 내성 | 영향 적음 | 주기적 breaking change | Capacitor |
| 안정성 운영 성숙도 | 콘텐츠·폼 앱에 충분 | 소셜·미디어 대규모 앱 표준 | **Expo** |

## 쟁점별 심층

### 1. 성능 — 100만 DL에서 WebView가 병목이 되는 지점
일반 콘텐츠 앱은 WebView로 "충분"하다는 게 통설이다. 그러나 AI LENS는 긴 레터 스크롤, 타임머신, 웹툰·영상·오디오 혼합, 무한 리스트가 핵심이다. 이 영역은 WebView에서 스크롤 지연·메모리·제스처 충돌이 체감된다. 100만 사용자의 저사양 단말까지 포함하면 네이티브 렌더의 이점이 커진다.

### 2. 푸시 — 둘 다 FCM/APNs가 종착지, 차이는 성숙도
- Capacitor: `@capacitor/push-notifications` 플러그인으로 가능. 미구현 상태라 지금 붙이면 신규 작업.
- Expo: Expo Notifications가 토큰 발급·권한·수신 핸들링을 추상화. 단 SDK 53부터 Expo Go에서 Android 푸시 테스트 불가 → **development build 필요**(인증서·네이티브 설정은 어차피 해야 함).
- 100만 발송은 프레임워크보다 **백엔드 팬아웃**(SNS/FCM 배치·토큰 수명주기)이 본체다. 이 부분은 프레임워크 선택과 독립 → 짝 문서 `services/push` 설계로 분리.

### 3. "앱으로 할 수 있는 건 다" — 천장의 차이
Capacitor도 플러그인/직접 네이티브로 많은 걸 하지만, **원격 URL 모드에서는 대부분 불가**(웹이 외부 URL이라 네이티브 브릿지 접점이 좁음). 로컬 번들 모드로 바꾸면 가능해지지만, 그 순간 "재빌드 없이 즉시 반영"(README가 원격 모드를 택한 이유)이 깨진다. 즉 Capacitor로 네이티브 기능을 다 하려면 **지금 구조를 버려야** 한다 — 전환비용이 Expo와 수렴한다.

### 4. 인력/유지보수
- Capacitor: 지금 웹 팀이 그대로. 신규 역량 0.
- Expo: RN 역량 필요. 100만 DL 서비스를 장기 운영하려면 어차피 모바일 전담이 필요해지는 지점 — 조직 관점에선 지금이 그 투자 시점일 수 있다.

## 권고와 조건

**Expo 권고.** 근거: ①현 Capacitor는 웹뷰 셸이라 목표와 어긋남 ②미출시 상태라 전환비용이 가장 쌀 때 ③Capacitor로 네이티브 기능을 다 하려 해도 원격 URL 모드를 버려야 해 비용이 수렴 ④100만 DL·미디어 혼합 UX에 네이티브 렌더가 유리 ⑤공유 코드(계약·타입·인증)는 `packages/`로 승격하면 Expo도 그대로 재사용.

**반대로 Capacitor 유지가 맞는 조건:**
- 앱을 "사이트의 스토어 배포 채널" 정도로만 쓸 것이고, 네이티브 기능 욕심이 사실상 푸시 하나다.
- 모바일 전담 인력을 둘 수 없고 웹 팀만으로 간다.
- 빠른 출시가 100만 DL 품질보다 우선한다.
→ 이 셋 중 하나라도 참이면 Capacitor 유지 + 푸시 플러그인이 합리적이다. 사용자의 "앱으로 할 수 있는 건 다 / 안정성·확장성 우선"과는 상충하므로, 지금 명시된 전제에선 Expo를 택한다.

## 결정이 바꾸는 범위

- 바뀌는 것: `apps/mobile/` 내부 전체(프레임워크·UI 코드).
- 안 바뀌는 것: `모노레포-정석구조-설계.md`의 폴더 정석, `packages/`(계약·타입·인증·도메인 로직), `services/push` 백엔드. 이들은 프레임워크 중립.

## 안 하는 것

- 성능 일반론으로 결정하기(AI LENS의 실제 UX·실측 상태로 판단).
- UI 공유를 이유로 Capacitor를 택하기(100만 DL에서 웹·앱 UI 공유는 양쪽을 함께 제약).
- 출시 후 전환 미루기(미출시 지금이 전환비용 최소 시점).
