# v1.5 — 이관 전/후 베이스라인 비교 (2026-09-08)

**왜**: 마이그레이션 계획 §4(검증). 데이터 이관(v1.4)까지 끝난 Postgres
dev 인스턴스에서, 이관 전 DynamoDB 베이스라인(dynamodb 트랙
[2026-09-08 이관전-베이스라인](../dynamodb/2026-09-08-이관전-베이스라인.md))
과 같은 성격의 쿼리를 재실행해 비교.

**방법론 차이 (숨기지 않고 명시)**: DynamoDB 쪽은 실제 프로덕션 API
(`curl`, Lambda+API Gateway 포함 종단 간)를 쟀지만, Postgres 쪽은 아직
그 앞단이 없어 **Python→DB 직접 쿼리**를 쟀다. 완전히 동일한 조건 비교가
아니라 "DB 계층 자체의 참고 성능"으로 읽어야 한다.

**결과**:

| 요청 | Postgres | DynamoDB(이관 전) |
|---|---|---|
| webtoon limit=20 | 0.39s / 7.2KB | 2.10s / 14.3KB |
| publications(lens 대응) limit=20 | 0.19s / 13.8KB | 4.25s / 68.8KB |
| webtoon limit=1000 | 0.77s / 300.6KB | 2.89s / 603.3KB |
| publications limit=1000 | 0.39s / 603.4KB | 5.57s / 2.47MB |

**EXPLAIN ANALYZE 확인**: 현재 986건 규모에서 플래너가 인덱스가 아니라
Seq Scan을 선택함(Execution Time 0.38ms) — 데이터가 적어서 나온 정상
판단이지, 인덱스가 안 걸리는 문제가 아니다. 프로덕션 규모(수만 건)에서
재확인 필요.

**성과**: 측정된 모든 항목에서 Postgres 쪽 응답시간이 더 짧았다. 다만
앞서 밝힌 방법론 차이(Lambda/API 계층 부재) 때문에 이 격차를 곧바로
"이관하면 N배 빨라진다"로 해석하지 않는다 — 실제 백엔드가 Postgres로
전환된 뒤 종단 간으로 다시 재는 게 진짜 비교다.

**다음**: 실제 서비스 백엔드(Lambda)가 Postgres를 쓰도록 전환된 뒤,
DynamoDB 때와 동일하게 `curl`로 종단 간 재측정 — 이게 나와야 진짜
이관 성공 여부를 판단할 수 있다.
