# v1.31 — lens 게시물 4포맷(레터/웹툰/팟캐스트/영상) 대량 누락 백필 + 정규 순서 정렬 (2026-09-09)

**왜**: v1.30 확인 중 사용자가 "동영상이 없네"라고 재신고. 확인해보니
단순 정렬 문제가 아니라 **원본 마이그레이션 자체가 대부분의 lens
게시물에서 1개 이상의 포맷을 통째로 빠뜨렸다**는 훨씬 큰 문제였다.
사용자가 "이전 작업할 때 데이터 안 가져온 거 아니냐"고 정확히 짚었다.

## 진단 — 근본 원인

DynamoDB 원본(`sedaily-mbti-cms-posts-dev`, channel='lens', 913건)을
직접 스캔한 결과 **913건 전부 예외 없이 레터/웹툰/팟캐스트/영상 4개
포맷을 완전하게 갖고 있었다**(영상도 실제 S3 mp4 URL 포함). 그런데
Postgres `renditions` 테이블엔 레터 872건, 영상 208건, 팟캐스트 152건,
웹툰 136건이 누락돼 있었다 — 콘텐츠가 없는 게 아니라 이관이 안 된 것.

원본 마이그레이션 스크립트 2개(세션 초반 작성분)를 재분석해 정확한
원인을 찾았다:

1. **`migrate_cms_posts.py`(v1.4)** — `channel='lens'` DynamoDB 항목
   자체에서는 렌디션을 아예 안 만들었다(코드 주석: *"lens 등 rendition
   없는 채널은 publications 메타데이터만 기여"*, 당시 "본문은 articles
   테이블에 이미 있다"고 오판). 대신 **같은 `source_url`을 공유하는
   다른 채널(webtoon/video/home_player/letters) DynamoDB 항목을 lens
   게시물에 병합**하면서 그 형제 항목의 렌디션을 대신 붙이는 설계였다.
2. **형제 채널의 건수 불균형이 누락 패턴을 만들었다**: webtoon 886건,
   video 814건, home_player 870건에 비해 **letters는 겨우 64건** —
   그래서 lens 글 대부분(913건 중 872건)이 매칭되는 "레터" 형제를
   못 찾아 레터 렌디션 자체가 안 생겼고, 나머지 3개 포맷은 형제 채널
   건수에 비례해 덜 누락됐다(정확히 관찰된 패턴과 일치).
3. **`backfill_lenses.py`(v1.12)**가 이 문제를 고치려 시도했지만,
   `WHERE NOT EXISTS(렌디션이 하나도 없는 글만)` 조건 때문에 **렌디션이
   1개라도 있으면(형제한테서 받은 것) 통째로 건너뛰었다** — "3개는
   있는데 1개 빠진" 대다수 케이스가 이때도 고쳐지지 않고 남았다.

부수 발견: `media_assets.thumbnail_url`(v1.30에서 읽기 경로만 연결)의
쓰기 경로(`admin_posts_repo.py::_write_format_body`)도 이 값을 한 번도
쓴 적이 없었다 — DynamoDB엔 실제 영상 프레임 캡처 URL이 있었는데
누락됐던 것.

## 수정

`service/lens-cms-api/admin_posts_repo.py::_write_format_body`(video
분기) — `media_assets` INSERT에 `thumbnail_url` 컬럼 추가(v1.30이
연결한 읽기 경로에 이제 진짜 데이터가 들어갈 수 있게).

`service/lens-cms-api/cms_posts_repo.py` — lens 아이템 배열 정렬을
DB 삽입 순서(`ORDER BY r.id`)에서 **정규 포맷 순서**(레터→웹툰→
팟캐스트→영상)로 변경(`_LENS_RENDITIONS_SELECT`, `list_published_posts`
의 렌디션 조회 둘 다). 프론트(`shared/constants/lensPerspectives.ts`)
가 lens 아이템을 `label` 문자열이 아니라 **배열 인덱스로** 포맷
카드에 매핑하는 설계라서(라벨 텍스트가 admin에서 바뀌면 문자열 매칭이
조용히 깨질 수 있다는 이유로 의도적으로 인덱스 기반 채택, 코드 주석에
"순서는 레터→웹툰→팟캐스트→영상으로 고정"이라 명시) 백엔드가 이
계약을 지켜야 했는데 안 지키고 있었다.

## 백필

`admin_posts_repo.py`의 실제 쓰기 헬퍼(`_get_or_create_rendition`/
`_write_format_body`)를 그대로 재사용하는 스크립트로, DynamoDB 913건을
다시 스캔해 **포맷별로 개별 확인**(v1.12 스크립트의 "글 전체를
건너뛴다" 결함을 고침) — 렌디션이 없으면 생성+콘텐츠 삽입, 렌디션은
있지만 자식 콘텐츠가 비어있으면 콘텐츠만 채움, 이미 콘텐츠가 있으면
절대 안 건드림(중복 삽입 방지 + 실제 admin 편집 결과 보존).

결과: 신규 렌디션 888건 생성, 이미 콘텐츠 있어 스킵 2484건,
publications 슬러그 매칭 실패 22건(v1.29와 같은 소수 잔여 gap).
백필 전후 "4개 포맷 다 갖춘 게시물" 826/986건(84%, 이전엔 2/986건
=0.2%)으로 대폭 개선.

## 검증

- 사용자가 신고한 정확히 그 게시물("성장판 누르는 노동시스템…55%가
  '산업 뒷받침 미흡'")로 재현·확인 — 백필 전 3개(웹툰/팟캐스트/영상,
  레터 없음)만 있던 것이 백필 후 4개(레터/웹툰/팟캐스트/영상) 전부,
  실제 프로덕션 API로 정규 순서(레터→웹툰→팟캐스트→영상) 확인.
- 홈페이지 상위 5개 게시물 전부 4개 포맷 정규 순서로 정상 반환 확인.
- EC2 배포 전, 별도 `/tmp` 경로에 올려 실 서버는 안 건드리고 실제
  DB로 직접 실행해 결과 확인 후 배포(기존 세션 관례 유지).
- 백필 스크립트는 로컬 DynamoDB 접근 권한 + EC2의 Postgres 네트워크
  접근이 둘 다 필요해, STS 임시 세션 토큰(1시간 유효)을 발급해 EC2
  쉘에 환경변수로 주입하는 방식으로 실행(장기 자격증명 노출 없음,
  세션 종료 시 자동 만료).

## 배포

lens-cms-api EC2 재배포 2회(`admin_posts_repo.py` thumbnail_url 수정 →
백필 스크립트 실행 → `cms_posts_repo.py` 정규 순서 정렬).

## 남은 항목

- 여전히 1개 포맷만 있는 160건 — 슬러그에 `-podcast` 같은 접미사가
  붙어 있어(예: `...-800선-내줘-podcast`) 슬러그 충돌 처리 과정에서
  생긴 별도 중복 행으로 추정(v1.13 "publications.slug 유일성 이슈"와
  연관 가능성) — 실제 콘텐츠 손실이 아니라 데이터 정리 이슈일 가능성이
  높음, 원인 미조사.
- publications 슬러그 매칭 실패 22건(v1.29부터 반복 관찰되는 소수
  잔여 gap) — 원인 미조사.
- `media_assets.thumbnail_url`은 이번에 새로 만든 영상 렌디션에만
  채워졌고, 이미 존재하던 777건의 예전 video media_assets 행은
  `ON CONFLICT DO NOTHING`으로 보호돼 그대로 비어있음(v1.30의
  `photo_image_url` 폴백이 여전히 이 케이스를 커버).
