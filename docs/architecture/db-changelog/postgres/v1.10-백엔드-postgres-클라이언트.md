# v1.10 — 백엔드 Postgres 클라이언트 작성 + 검증 (2026-09-09)

**왜**: dev 환경 검증(v1.1~v1.9)이 끝난 뒤, 실제 서비스 백엔드가
Postgres를 쓰도록 전환하는 작업에 착수. 전체 백엔드(10개 이상 클라이언트
파일)를 한 번에 바꾸는 대신, 가장 많이 벤치마크한 대표 경로(`GET /api/v2/posts`,
`cms_posts_ddb_client.py`)부터 안전하게 전환 가능한 형태로 작성.

## 실행 중 발견한 것 — 라이브 데이터 모델이 이미 바뀌고 있었다

작업 착수 직전 실제 API 응답 shaping 코드(`cms_posts_shaping.py::shape_lens`)를
확인하다가, 'lens' 채널 글이 `body_inline.lenses[]`에 레터·웹툰·팟캐스트·
영상 4포맷을 **통째로 내장**하는 구조임을 발견했다 — v1.4 마이그레이션
당시엔 이 필드를 몰라서 'lens' 채널을 메타데이터만 이관했다. 샘플 45건
전수 확인 결과 100%가 이 필드를 갖고 있어 실제 콘텐츠 손실이었다.

더 나아가, 2026-09-08에 채널 4개(lens/webtoon/video/home_player)로 나뉘어
있던 것으로 기록했던 것과 동일한 `source_url`을 2026-09-09에 재조회하니
**`lens` 채널 1건만 남아있고 나머지 3개 채널 row가 사라져 있었다** —
DynamoDB `cms-posts` 테이블이 지금도 실제 파이프라인이 계속 쓰고 스키마
자체를 바꾸는 **라이브 테이블**이라는 뜻이다. 사용자 확인(데이터 유실
허용, 과감히 진행) 하에 이 차이는 미해결로 남기고 진행했다.

## 한 것

1. `service/backend/clients/cms_posts_pg_client.py` 신규 작성 —
   `cms_posts_ddb_client.py`와 동일한 인터페이스(`list_published_posts`,
   `get_published_post_by_slug`), 같은 dict 반환 shape. `publications`+
   `renditions`+`webtoon_panels`+`media_assets`+`rendition_blocks`를
   JOIN해서 원본 DynamoDB 아이템 모양으로 재구성.
2. 실제 dev DB에 대고 5개 채널(webtoon/video/home_player/letters/lens) +
   slug 단건 조회를 실행해 검증. 시행착오 2건 발견·수정:
   - `media_assets` JOIN 누락(`ma` 테이블 참조 오류)
   - video와 podcast가 같은 `media_assets.file_url` 컬럼을 쓰는데 채널
     구분 없이 `body_inline.video_url`에 몰아넣던 오류 — video는
     `body_inline.video_url`, home_player(podcast)는 최상위
     `media_embed_url`로 분리(원본 마이그레이션 스크립트의 매핑과 일치시킴)
3. `lens_service_app` 역할에 SELECT 권한 부여(`publications`/`renditions`/
   `webtoon_panels`/`media_assets`/`rendition_blocks`/`articles`/`categories`/
   `sections`/`quizzes`/`users`/`v_live_renditions` 등) — `14-operations.md`
   §3에 정의된 역할이었지만 컬럼별 권한만 있고 일반 SELECT가 없었음.
4. `service/backend/handlers/cms_posts_public.py`에 `CMS_DB_BACKEND`
   컷오버 스위치 추가 — 2026-09-07 `CMS_LIST_INDEX_MODE`와 같은 패턴,
   기본값은 기존 DynamoDB 그대로라 **이 커밋을 배포해도 동작이 안 바뀐다**.
   `postgres`로 설정해야만 새 클라이언트가 쓰인다.
5. 기존 테스트 스위트 전체 재확인 — 104 passed, 무관한 사전 실패 6건
   동일(CLAUDE.md에 이미 기록된 것과 일치) — 이번 변경으로 인한 신규
   실패 0건.

## 알려진 한계 (문서화, 해결 안 함)

- ~~`lens` 채널의 `lenses[]` 콘텐츠 미이관~~ → **v1.12에서 해소**
  (기존 renditions 구조 재사용, 스키마 확장 불필요했음).
- DynamoDB 원본이 계속 바뀌는 라이브 테이블이라, 이 Postgres 데이터는
  2026-09-08 스냅샷 기준 — 실제 컷오버 전 재동기화 필요.
- Lambda 배포 패키지에 `psycopg2-binary`가 없음(`deploy.sh`의 pip
  install 목록에 미포함) — `CMS_DB_BACKEND=postgres`로 실제 전환하려면
  Lambda(Amazon Linux) 호환 빌드로 추가해야 함. 지금 상태로 배포해도
  안전한 이유: 이 조건부 import라 플래그를 안 켜면 로드 자체가 안 됨.
