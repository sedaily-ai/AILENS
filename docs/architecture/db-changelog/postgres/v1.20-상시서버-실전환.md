# v1.20 — CMS posts 읽기를 상시 서버로 실제 전환 완료 (2026-09-09)

**왜**: v1.19까지 Postgres 백엔드는 기능적으로 완성됐지만 `CMS_DB_BACKEND`
전환 스위치는 Lambda 아키텍처 위에서 검토 중이었다. 실제로 Lambda를
RDS와 통신시키려던 시도가 **실제 장애**로 이어지면서(아래 §1), 사용자
지시("근본적으로 해결... 디센터 사례처럼")에 따라 컴퓨트 계층 자체를
상시 서버로 바꾸는 방향으로 전환했다.

## §1. 인시던트 — Lambda VPC 부착으로 인한 일시 장애 (01:26~01:36 UTC)

`sedaily-mbti-v2-posts-dev` Lambda를 RDS 접근용 VPC(서브넷
`subnet-0b8c902571faafab8`/`subnet-0430a7468d7d796e9`)에 붙였는데 이
서브넷에 NAT 경로가 없어, VPC 부착 직후 이 Lambda가 쓰던 DynamoDB(공인
API) 호출이 막혀 30초 타임아웃 → 503이 간헐적으로 발생했다. 발견 즉시
VPC 연결 해제(`SubnetIds=[]`)로 되돌리고 반복 헬스체크로 정상화
확인했다. 첫 curl 2회가 우연히 200을 반환해 "정상"으로 오판했던 것도
원인 중 하나 — 웜 컨테이너 재사용 때문이었고, 환경변수 변경으로
콜드스타트를 강제한 순간 실제 네트워크 경로가 드러났다.

## §2. 아키텍처 결정 — Lambda 대신 상시 서버(decenter 패턴)

Lambda+RDS 조합의 근본 문제(호출마다 새 커넥션, VPC 붙이면 NAT/엔드포인트
필요)를 사용자가 지적, 참조 사례(`1_ai_link/globe/decenter` — PM2로
EC2에 상시 구동되는 서버, 진짜 커넥션 풀 사용)를 보고 같은 패턴으로
전환하기로 결정. 언어는 Node 대신 Python(FastAPI+psycopg2)을 선택 —
`cms_posts_pg_client.py`/`cms_posts_shaping.py` 로직이 이미 검증돼 있어
재작성 없이 포팅 가능.

**배치 위치 조사 중 발견한 정정 사항**: 처음엔 기존 `ailens-ssr-prod`
EC2(PM2로 `ailens-frontend` 프로세스 구동 중)를 "이미 있는 상시 서버
패턴"으로 재사용/참고하려 했으나, ALB(`sedaily-lens-frontend-alb`)
타겟 그룹을 확인한 결과 실제 헬시 타겟은 IP `172.31.4.112:3000`(ECS
Fargate 태스크)였고 `ailens-ssr-prod`(사설 IP 172.31.75.225)는 대상이
아니었다 — 이 EC2는 **2026-09-04 ECS Fargate 전환 이후 폐기된 채
PM2 프로세스만 계속 돌고 있던 유령 인스턴스**였다(`service/frontend/
deploy.sh` 상단 주석에 그 전환 이력이 있었음, 처음엔 못 보고 지나침).
실제로 새로 만든 인프라는 이 EC2와 무관하게 독립적으로 구축했으므로
결과에는 영향 없음 — 서술만 정정.

  `13.223.179.151`. IAM 인스턴스 프로파일은 `ailens-ssr-ec2-profile`

- **CloudFront**: `ailens.sedaily.ai`를 서빙하는 배포(`E1QS7PY350VHF6`)에

  (`/api/v2/posts*` → 이 오리진, CachingDisabled + AllViewer 정책, 기존
  SSR/saju 라우팅은 그대로 유지) 추가. 이렇게 해서 새 도메인·인증서
  없이 기존 HTTPS를 그대로 재사용.

## §4. 배포 중 발견·수정한 버그 2건

1. **`lens_service_app`에 `publication_slug_history` SELECT 권한 누락**:
   v1.15에서 이 테이블을 신설했지만 v1.10 시점의 권한 부여 목록에는
   없었다. 지금까지의 모든 Postgres 검증은 admin 계정으로 했었어서
   놓쳤다가, 실제 서비스 계정으로 처음 돌려본 이 배포에서 "permission
   denied for table publication_slug_history"로 드러남 — `GRANT SELECT`
   로 해결(DB 전역 수정이라 dormant였던 Lambda 경로도 같이 해소됨).
2. **`fetchHomePlayerBySlug()`가 `channel` 파라미터 없이 호출**:
   `service/frontend/src/shared/lib/api/homePlayerApi.ts`의 단건 조회
   함수가 유일하게 `?channel=`을 안 붙이고 있었다(다른 함수들은 전부
   붙임, 2026-09-09 이전 라우팅 조사에서 놓쳤던 예외 케이스) —
   DynamoDB에선 slug가 아이템별로 고유해 문제 없었지만, Postgres에서는
   한 slug가 여러 렌디션을 가질 수 있어 임의의(이 경우 video) 포맷이
   반환됐다. 프론트 빌드 중 `/listen/[slug]` prerender가
   `TypeError: Cannot read properties of undefined (reading 'match')`로
   실패하면서 발견 — `channel=home_player` 명시로 수정.

## §5. 검증

- 새 서버 단독(HTTP, 직접 IP): 전 채널(letters/webtoon/video/lens/
  home_player) 200, slug 단건 조회(직접/slug_history 폴백/channel
  disambiguation/lens 조립/404) 전부 정상, 응답시간 0.37~0.4초대
  (Lambda 콜드스타트 1.9~4초 대비 대폭 개선 — 커넥션 풀 재사용 효과).
- HTTPS 경유(`https://ailens.sedaily.ai/api/v2/posts`, CloudFront 새
  behavior): 전 채널 재확인 200, 기존 SSR(`/`) 라우팅 무영향 확인.
- 프론트엔드: `CMS_API_URL`(신규, `ailens.sedaily.ai`)로 `cmsPostsApi.ts`
  8곳 + `homePlayerApi.ts` 3곳 전환, 기존 `API_URL`(Lambda API Gateway,
  다른 모든 엔드포인트)은 그대로 유지 — 서로 다른 오리진이라 분리했다.
  `tsc --noEmit` 통과, `npm run build` 186페이지 전부 성공(1차 시도는
  §4-2 버그로 실패, 수정 후 재빌드 성공).
- 실제 배포: Docker(arm64) 빌드 → ECR push → ECS 태스크 정의 리비전 2 →
  `force-new-deployment` 롤링 배포 완료. 배포 후 실사이트 확인:
  `/`(메인) 200, `/api/v2/posts`(신규 경로) 200, `/letters`(→308
  `/archive` 정상 리다이렉트) 200, `/webtoon`·`/video`·`/lens`·`/listen`
  전부 200, 실제 발행물 slug로 상세 페이지(`/webtoon/{slug}`) 200 확인.

## 현재 상태

**CMS 글 공개 조회(`GET /api/v2/posts`, `GET /api/v2/posts/{slug}`)가
2026-09-09부로 실제 프로덕션 트래픽 기준 DynamoDB+Lambda에서
PostgreSQL+상시 서버(EC2/PM2)로 전환 완료됐다.** 이 마이그레이션
프로젝트(v0.1부터 시작)의 핵심 목표가 달성됨. Lambda 쪽
`CMS_DB_BACKEND` 스위치는 이제 이 경로에서 무의미해짐(프론트가 더는
그 API Gateway 경로를 이 용도로 호출하지 않음) — 해당 Lambda 함수
자체는 여전히 배포돼 있으나 이 트래픽에서는 제외됨.

## §6. 후속 정리 — 유령 인프라 제거

- `sg-0c665d3e8aec706ab`(Lambda용으로 만들었다가 안 쓰게 된 보안그룹) —
  ENI 참조 0건 확인 후 RDS 보안그룹 규칙 회수 + 삭제 완료.
- `ailens-ssr-prod` EC2(`i-077eb96afcc2597d4`) — §2에서 발견한 대로
  2026-09-04 ECS Fargate 전환 이후 완전히 고아 상태였다(어떤 ALB 타겟
  그룹에도 없음). 추가 조사 결과 `origin-ailens.sedaily.ai`라는 전용
  DNS A레코드가 이 인스턴스의 공인 IP를 직접 가리키고 있었으나, 이
  도메인을 오리진으로 쓰는 CloudFront 배포가 0건이었다 — 이것도 같은
  전환 때 남은 잔재. 사용자 확인 후 **완전 종료**: 인스턴스 terminate,
  DNS A레코드 삭제, 전용 보안그룹(`sg-026385217d66ed9e1`) 삭제. 6일간
  실사용 트래픽 없이 t3.small이 돌고 있었다(월 추정 $15~20 낭비).
  종료 후 실사이트(`ailens.sedaily.ai` 메인·API) 재확인 정상.

## §7. 신뢰성 점검·보강

- **재부팅 생존 확인**: `systemctl cat pm2-root` 확인 결과
  `ExecStart=pm2 resurrect`가 enabled 상태로 등록돼 있고,
  `/root/.pm2/dump.pm2`에 `lens-cms-api`가 저장돼 있음을 확인 —
  인스턴스가 재부팅돼도 PM2가 자동으로 앱을 복원한다(프로비저닝 로그의
  `pm2 startup` 관련 stderr 노이즈는 실제 결과에 영향 없었음).
- **하드웨어 장애 자동 복구 추가**: CloudWatch 알람
  `lens-cms-api-prod-system-status-check-failed`(`StatusCheckFailed_System`
  2회 연속 시 `arn:aws:automate:us-east-1:ec2:recover` 액션 — 같은
  하이퍼바이저 장애 시 AWS가 자동으로 새 하드웨어로 인스턴스를 이전)
  신설. 비용 없음, 표준 단일 인스턴스 관행.

## 남은 항목

- `list_published_posts`의 lens 채널 라벨 배치 조회(v1.18)는 성능
  검증됐으나, 실제 프로덕션 트래픽 규모에서의 장기 모니터링은 아직
  없음.
- 새 EC2는 여전히 단일 인스턴스(수평 이중화 없음) — §7로 하드웨어
  장애·재부팅 복구는 커버되지만, 애플리케이션 레벨 이중화(ALB+Auto
  Scaling Group)는 트래픽 증가 시 별도 검토 필요.
- CloudWatch Logs 연동(현재 PM2 로컬 로그만) — IAM 역할에
  `CloudWatchAgentServerPolicy`는 이미 있어 에이전트 설치만 하면 되나,
  이번 범위에서는 보류.
