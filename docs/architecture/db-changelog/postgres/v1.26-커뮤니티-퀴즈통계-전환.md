# v1.26 — 커뮤니티 게시판·퀴즈 응답 통계 Postgres 전환, engagement 테이블 라이브 write 완전 소거 (2026-09-09)

**왜**: articles(v1.25)에 이어 다음 대상 스코핑 중, v1.8("게시판·뱃지 스키마
확장")이 "게시판 실사용 데이터 0건"이라고 결론냈던 것을 재검증하다가
**그 결론이 이미 틀렸다는 걸 발견**했다 — `services/community_post_service.py`
가 지금도 라이브(`sedaily-mbti-post-dev`, 인증 필요)로 그 테이블에 쓰고
있었다. v1.8 스냅샷 시점엔 정말 테스트 픽스처 1건뿐이었지만, 이후 실제
투표/댓글 활동이 쌓였다.

## 조사 요약 (Explore 에이전트 2개 병렬 조사)

- `sedaily-mbti-admin-config-dev`(667건)/`sedaily-mbti-admin-prompts-dev`
  (76건)도 같이 조사했으나 이번 버전 범위 밖(다음 버전에서 다룸).
- `sedaily-mbti-engagement-dev`(198건) 실제 구성: `USER#.../READ·DAILY·
  PROFILE`, `ARTICLE#.../REACTIONS·RATING_STATS·USER_RATING`, `STATS#day·
  all-time` — 전부 2026-07-30 폐기된 `engagement_handler.py`의 잔재(코드
  자체가 저장소에 없음, `infrastructure/decommission-2026-07-30/`에 기록만
  남음). **완전히 죽은 데이터**로 확인, 마이그레이션 대상에서 제외.
- `COMMUNITY_POSTS`/`POST#{id}/COMMENT·VOTE`는 **라이브**
  (`community_post_service.py`, `sedaily-mbti-post-dev`, JWT 인증 필요,
  `deploy.sh`의 `API_FUNCTIONS`에 포함돼 매 배포마다 갱신됨).
- `QUIZ#{id}/STATS`(익명 응답 집계)도 **라이브** — `handlers/quiz_public.py`
  가 씀, v1.22에서 이미 Postgres로 전환된 퀴즈 기능과 물리적으로 같은
  DynamoDB 테이블(engagement)을 우연히 공유하고 있었을 뿐.
- `sedaily-mbti-ws-connections-dev`는 순수 `connectionId` 단건 put/delete
  뿐(get/query/scan 없음, 0건 상시) — 관계형 쿼리 필요성 없어 **DynamoDB에
  그대로 둔다** — 스키마 작업 없음.

## 스키마 변경

- `community_post_votes(post_id, user_id, vote_type, created_at)`,
  PK=(post_id, user_id) — DynamoDB `POST#{id}/VOTE#{user_id}` 토글 로직의
  사용자별 중복투표 방지 대응 신설. `community_posts.upvotes`는 여전히
  비정규화 집계 카운터(빠른 정렬용), 이 테이블이 실제 근거.
  `community_posts`/`community_comments` 자체는 v1.8에서 이미 스키마와
  FK(`article_no→articles`, `user_id→users`)까지 갖춰져 있어 그대로 사용.
- `quizzes.total_count`/`correct_count` INTEGER 컬럼 신설 — DynamoDB
  `QUIZ#{id}/STATS`의 익명 집계 대응.
- 댓글 좋아요(DynamoDB `COMMENT_LIKE` 항목 1건 발견)는 **대응 스키마를
  만들지 않았다** — 실제 라이브 코드에 그 항목을 만드는 엔드포인트 자체가
  없다(2026-07-30 폐기된 옛 핸들러의 잔재로 확인). `community_comments.
  likes` 컬럼은 이미 있으니 나중에 좋아요 기능이 부활하면 그때 중복방지
  테이블을 추가하면 된다.

## 구현

`service/lens-cms-api/community_repo.py`(신설) — `create_post`(article_id가
실제 `articles.article_no`와 매칭되는지 검증 후 없으면 NULL로 저장, FK 위반
방지), `list_posts`(KST 날짜 기준, 태그 필터, upvotes desc·recency desc
정렬), `vote_post`(토글/전환 로직 SQL 트랜잭션으로 재현 — 신규/토글오프/
전환 3가지 delta 케이스), `add_comment`, `list_comments`. `article_title`
은 컬럼에 안 두고(v1.24와 동일 패턴) `articles` LEFT JOIN으로 항상 최신
제목 반환 — DynamoDB는 작성 시점 제목을 그대로 박제했었다. `user_mbti`는
저장 안 함(MBTI 페르소나 프로젝트 전체 폐지, DynamoDB 쪽도 항상 빈
문자열이었음) — API 응답 키는 하위호환으로 유지하되 항상 빈 문자열.

`quiz_repo.py`에 `record_attempt(quiz_id, correct)` 추가 — `quiz_id`가
`admin_post_id`(UUID) 또는 `id`(bigint) 중 어느 형태로 와도 매칭
(`list_published_quizzes()`가 둘 중 있는 쪽을 문자열로 내려주므로).

`main.py`에 공개 라우트(`GET /api/v2/community/posts*`, 원본 DynamoDB
핸들러도 GET은 무인증) + 내부 라우트(`POST /internal/community/posts*`,
`POST /internal/quiz/attempt`, `X-Internal-Token`) 추가.

Lambda 쪽 `clients/community_pg_client.py`(신설, articles_pg_client.py와
같은 패턴)로 `services/community_post_service.py` 전체 rewiring — 응답
shaping(`to_post_response`/`to_comment_response`, camelCase 변환,
`timeAgo` 계산)은 그대로 두고 저장 계층만 교체. `post_id`가 문자열
(`cp_YYYYMMDDHHMMSS_hex`)에서 Postgres bigint(문자열 직렬화)로 바뀜 —
dev 단계라 옛 ID 형식과의 하위호환은 고려하지 않음.

`handlers/quiz_public.py`의 `_handle_attempt`도 `common.secrets.get_secret
('/sedaily-mbti/v2/lens-cms-api-token')` 경유로 rewiring — 이 Lambda
(`sedaily-mbti-v2-quiz-dev`)는 `sedaily-mbti-v2-collector-dev-role`을 써서
`V2SecretsAccess` 정책으로 `/sedaily-mbti/v2/*` SSM 경로에 이미 접근
가능했다(newsletter_subscribers_pg_client.py, v1.23과 같은 토큰 재사용)
— articles/personal 때처럼 평문 env var로 우회할 필요가 없었던 첫
케이스.

## IAM 역할 확인

- `sedaily-mbti-post-dev`는 `sedaily-mbti-lambda-execution-dev`(AI LENS
  밖 다른 프로젝트와 공유하는 광범위 실행 역할) — articles/personal과
  같은 이유로 평문 환경변수(`LENS_CMS_API_TOKEN`)로 토큰 직접 주입.
- `sedaily-mbti-v2-quiz-dev`는 `sedaily-mbti-v2-collector-dev-role`을 써서
  `/sedaily-mbti/v2/*` SSM 경로 접근이 이미 가능 — SSM SecureString
  경유로 깔끔하게 처리(이번 세션에서 평문 env var가 필요 없었던 유일한
  케이스).

## 발견한 버그(수정 안 함) — nginx location 빠뜨림

`main.py`에 `/internal/quiz/attempt` 라우트를 추가했지만 `nginx.conf`에
대응 `location` 블록을 처음에 빠뜨려 배포 직후 로컬 curl 검증에서 nginx
레벨 404로 걸렸다 — 즉시 발견·수정(재배포 1회 추가). 실제 사용자
트래픽에 노출된 적 없음(같은 검증 사이클 안에서 잡힘).

## 검증

- `community_repo.py`/`quiz_repo.py` 로컬 스크립트(마스터 커넥션): 글
  생성·목록(태그 필터)·투표 토글/전환(delta 수학 직접 검증: 1-1+1-1-2=-2)·
  댓글 작성/조회·퀴즈 집계 증가/존재하지 않는 quiz_id 처리 전부 실제
  데이터로 확인.
- EC2 배포 후 서버 로컬 curl로 공개/내부 라우트 재확인, nginx 라우트
  누락 발견 즉시 수정 후 재확인.
- **Lambda 코드 경로 직접 호출**(JWT는 Cognito RS256이라 위조 불가 —
  v1.24와 동일하게 인증 계층만 우회): `services/community_post_service.py`
  의 5개 함수(create/list/vote/comment/list_comments) 전부 실제 lens-cms-api
  서버에 대고 호출해 확인.
- **실제 Lambda 직접 invoke**: `sedaily-mbti-v2-quiz-dev`의
  `/api/quiz/attempt`(200)·`/api/quiz/today`(200) 둘 다 실제 배포된
  함수로 확인.
- `service/backend` 전체 테스트 104 passed(기존 무관 에러 6건 동일).
- 테스트 데이터(게시글/댓글/투표, 퀴즈 카운터)는 전부 검증 직후 정리.

## 배포

lens-cms-api EC2 재배포 3회(엔드포인트 추가 → nginx 라우트 누락 수정 →
퀴즈 집계 엔드포인트 추가). service 22개 Lambda 재배포 2회
(community 전환 1회, 퀴즈 집계 전환 1회).

## 남은 항목

- `sedaily-mbti-engagement-dev`(DynamoDB) 테이블은 삭제 안 함 — 이번
  버전으로 라이브 writer는 완전히 없어졌지만(community·퀴즈 둘 다
  Postgres로 이전), 죽은 잔여 데이터(ratings/reactions/read/daily/stats)
  자체는 그대로 남아있음.
- `sedaily-mbti-ws-connections-dev`는 스키마·마이그레이션 작업 대상에서
  제외 — DynamoDB가 계속 맞는 선택이라는 기존 판단 재확인.
- 댓글 좋아요 기능이 나중에 부활하면 `community_comment_likes` 같은
  중복방지 테이블 추가 필요(이번엔 라이브 엔드포인트가 없어 스킵).
- 다음 대상: admin-config(`feature_flags`는 쉬움, `threshold`/`AUTH
  lockout`/`WEBTOONLAB job`은 전용 테이블 없음, `audit_logs`는
  `flag_name REFERENCES feature_flags`로만 좁게 설계돼 재설계 필요)와
  admin-prompts(`prompt_versions.created_by REFERENCES editors`가 실제
  "editor" 개념 부재와 안 맞음 — admin_extra JSONB 우회 후보).
