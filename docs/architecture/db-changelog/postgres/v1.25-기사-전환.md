# v1.25 — 뉴스 기사(articles) 읽기·쓰기 Postgres 전환, 크론 포함 완전 전환 (2026-09-09)

**왜**: cms-posts/퀴즈/뉴스레터/개인화에 이어 계속 진행. 사용자가 명시적으로
"글이 안 보여도 되니 원래 하려던 전체 전환을 다 하자"고 확인 — 이번엔
읽기만이 아니라 **쓰기(매일 23시 KST EventBridge 크론이 돌리는 실 수집기
포함)까지 한 번에** 전환하기로 범위를 정했다.

## 조사 요약

- 읽기 호출자 5곳 확인: `services/article_service.py`(단건 조회·날짜별
  목록), `services/search_service.py`(카테고리·기간·키워드 검색,
  `handlers/search_handler.py`가 호출), `services/chatbot_context_service.py`
  (최근기사·연관기사, raw boto3로 `dynamodb_client.py`를 거치지 않고
  직접 GSI 쿼리), `handlers/question_handler.py`(오늘의 질문 생성용
  기사 제목 수집, 역시 raw boto3 직접 쿼리).
- 쓰기 호출자 1곳: `services/article_collection_service.py`
  (`dynamodb_client.save_article`/`batch_check_exists`/
  `batch_get_articles_with_hash`/`save_collection_log`) —
  `sedaily-mbti-article-collector-dev` Lambda가 EventBridge
  `cron(0 14 * * ? *)`(23시 KST)로 매일 실행.
- DynamoDB는 본문을 S3에 분리 저장(`s3_body_uri`)하지만 Postgres
  `articles.body`는 v1.6/v1.19에서 이미 100% 백필돼 있어 그
  인다이렉션이 필요 없다 — 읽기 쪽이 오히려 DynamoDB보다 단순해졌다.

## 스키마 변경 — raw_category 컬럼 추가

원본 Postgres 스키마엔 `article_categories`(AI LENS 자체 7분류, 52%만
커버)와 `section_id`(뉴스레터 지면 분류, 마이그레이션 때 안 채워짐) 두
분류 체계만 있었는데, 현재 검색/목록/챗봇 컨텍스트 전부가 실제로 쓰는
분류 키는 **DynamoDB의 원본 `category` 필드**(GSI
`category-published_at-index`의 파티션 키)였다 — 이 컬럼 자체가 없어서
그대로는 기존 조회 동작을 재현할 수 없었다.

```sql
ALTER TABLE articles ADD COLUMN raw_category VARCHAR(32);
GRANT INSERT, UPDATE ON articles TO lens_service_app;
GRANT INSERT, UPDATE, DELETE ON article_images, article_related_news TO lens_service_app;
GRANT USAGE, SELECT ON SEQUENCE article_images_id_seq, article_related_news_id_seq TO lens_service_app;
```

`sedaily-mbti-articles-dev`를 다시 스캔(`news_id, category`만
projection)해 18,157건 전부 `raw_category` 채움(NULL 0건). 분포:
경제 6555, 사회 4379, 정치 2073, 국제 1822, 문화 1099, 스포츠 868,
IT_과학 855 — 7개 표준값이 97%를 차지하고, 나머지는 "Signal,Deal,ECM"·
"피플,피플일반,피플일반" 같은 세분화된 레거시 분류 문자열 약 50종이
소량씩 있다. 이건 **이번 마이그레이션이 만든 문제가 아니라 DynamoDB에도
원래 있던 데이터 특성**이다 — 현재 모든 조회가 GSI의 7개 표준 카테고리로만
쿼리하기 때문에 이 장꼬리 값들은 DynamoDB 시절에도 이미 도달 불가능했다.
그대로 보존하고 손대지 않았다.

## 구현

`service/lens-cms-api/articles_repo.py`(신설) — 공개 조회:
`get_article`(단건, S3 merge 불필요), `list_articles_by_date`,
`get_recent_articles`(카테고리별), `search_paged`(카테고리 alias 확장은
Lambda 쪽이 하고 이미 확장된 리스트를 받아 `WHERE raw_category = ANY(...)`
+ `COUNT(*)`/`LIMIT`/`OFFSET`으로 페이지네이션), `query_category_keywords`
(챗봇의 카테고리+OR-키워드+`since` 쿼리 프리미티브). 내부 쓰기:
`batch_check_exists`, `batch_get_hash`, `save_article`(UPSERT,
`article_images`/`article_related_news`는 완전 교체 — DynamoDB
`put_item`의 전체 교체 의미와 동일).

`main.py`에 공개 라우트(`/api/v2/articles*`, 인증 없음 — 기존 DynamoDB
경로도 공개 API였음) + 내부 라우트(`/internal/articles/*`,
`X-Internal-Token`) 추가. **라우트 순서 버그 하나 발견·즉시 수정**:
FastAPI가 등록 순서로 매칭해서 `/api/v2/articles/{article_no}`를 먼저
등록해뒀더니 `/api/v2/articles/category-query` 같은 정적 경로를
article_no="category-query"로 오인해 삼켰다 — 정적 경로를 파라미터
경로보다 앞에 두는 것으로 해결.

Lambda 쪽 `clients/articles_pg_client.py`(신설, `personal_pg_client.py`
와 같은 패턴)로 5개 호출자 전부 rewiring:
- `services/article_service.py` — `DynamoDBClient`/`S3ArticleClient`
  의존 제거, `ArticleHandler` 생성자에서 클라이언트 인자 자체를 없앰.
- `services/search_service.py` — GSI 쿼리 루프+dedup(카테고리 alias
  중복, `version_` 접두사 레코드) 전부 제거. Postgres는 article_no당
  행이 하나뿐이라 애초에 중복이 안 생긴다. `published_from`/
  `published_until`는 DynamoDB 시절 `Key.between()`의 문자열 사전식
  비교(끝 날짜가 "2026-09-09"처럼 시각 없는 짧은 문자열이면 그 날 실제
  타임스탬프보다 사전순으로 작아 당일 기사가 새는 미세한 기존 동작이
  있었을 수 있음)를 그대로 재현하지 않고 `published_at::date BETWEEN`
  (양끝 날짜 포함)으로 구현 — 더 직관적인 쪽으로 판단, 발견했지만 굳이
  버그까지 재현하지 않기로 결정.
- `services/chatbot_context_service.py` — 카테고리별 top-3 병합, 불용어
  필터링, broad-keyword fallback 등 비즈니스 로직은 그대로 두고 boto3
  GSI 쿼리만 서버 호출로 교체. `_fetch_article_body`(S3) 제거 —
  Postgres body가 이미 인라인.
- `handlers/question_handler.py` — 카테고리별 GSI 쿼리(카테고리당
  Limit=10, 총 30개)를 날짜 하나로 한 번에 가져오는 호출 1번 + 클라이언트
  쪽에서 카테고리당 10개 상한 재현으로 대체.
- `services/article_collection_service.py`(크론 쓰기 경로) —
  `dynamodb_client.save_article`/`batch_check_exists`/
  `batch_get_articles_with_hash` → `articles_pg_client`의 동명 함수로
  교체. `save_collection_log`는 Postgres에 대응 테이블이 없어(수집
  실행 로그, 관측용 저가치 데이터) CloudWatch 로그만 남기는 스텁으로
  대체.

## 발견한 (재현하기로 한) 버그 — batch_get_hash의 published_at은 원래 죽은 코드

`article_collection_service.py`가 `existing.get('published_at')`으로
"수정된 기사는 원래 발행 시각을 보존"하려 했는데, DynamoDB
`batch_get_articles_with_hash`가 애초에 `published_at`을 반환한 적이
없어(`ProjectionExpression='news_id, content_hash, content_ko'`) 이
보존 로직이 **한 번도 실행된 적 없는 죽은 코드**였다 — 항상 XML의 새
발행 시각을 쓰고 `updated_at`은 항상 None. Postgres `batch_get_hash`도
`published_at`을 반환하지 않게 만들어 이 (버그 있는) 동작을 의도적으로
그대로 재현했다 — 마이그레이션과 버그 수정을 같은 변경에 섞지 않기
위한 결정. 고치려면 별도 작업으로.

## IAM 역할 확인

읽기 4개(`article-dev`/`search-dev`/`chatbot-dev`/`question-dev`)와
쓰기 1개(`article-collector-dev`) 전부 `sedaily-mbti-lambda-execution-dev`
(bigkinds/ga4 등 AI LENS 밖 프로젝트와 공유하는 광범위 실행 역할, v1.24
에서 archive-dev/user-dev로 이미 확인된 것과 동일 역할)를 쓴다 —
같은 이유로 SSM 미경유, 평문 환경변수 `LENS_CMS_API_TOKEN`을 5개
함수 모두에 직접 주입(기존 환경변수는 보존하며 병합).

## 검증

- `articles_repo.py` 로컬 스크립트(마스터 커넥션): 단건 조회·날짜별
  목록·카테고리별 최근기사·검색·`batch_check_exists`·`batch_get_hash`·
  `search_paged`(페이지네이션+총건수)·`query_category_keywords` 전부
  실제 데이터로 확인. `save_article` UPSERT(이미지/관련기사 완전교체
  포함) 테스트 후 정리.
- EC2 배포 후 서버 로컬 curl로 공개/내부 라우트 재확인, 라우트 순서
  버그 발견 즉시 수정 후 재확인. 내부 라우트 토큰 미제공 시 401 확인.
- `service/backend` 전체 테스트 104 passed(기존 무관 에러 6건 동일).
- **실제 API Gateway/Lambda 직접 호출**: `sedaily-mbti-article-dev`
  단건 조회·날짜별 목록 200, `sedaily-mbti-search-dev` 카테고리
  검색 200(`total_hits` 정상), `chatbot_context_service`/
  `question_handler`의 함수를 로컬에서 실제 토큰으로 직접 호출해 확인.
- **쓰기 경로(크론) 실제 검증**: `sedaily-mbti-article-collector-dev`를
  `{"target_date":"20260909"}`로 5회 수동 호출해 오늘자 백로그를
  전부 처리(`pending_remaining` 0까지). 신규 저장(첫 호출 50건, 이후
  배치들 합계 203건)·기존 판별(`cached_articles`가 호출마다 정확히
  누적)·변경분 갱신(마지막 호출에서 34건 `updated_articles`) 전부
  Postgres에 실제로 반영됐는지 직접 쿼리로 확인 — 이미지까지 정상
  저장. 실 크론(23시 KST) 정규 실행을 기다리지 않고 수동 invoke로
  전체 경로(신규/중복/수정 3가지 분기 모두) 검증 완료.

## 배포

lens-cms-api EC2 재배포 2회(엔드포인트 추가 → 라우트 순서 버그 수정
재배포). service 22개 Lambda 전부 재배포(1회, deploy.sh).

## 남은 항목

- `sedaily-mbti-articles-dev`(DynamoDB) 테이블은 삭제 안 함.
- `search_service.py`의 날짜 범위 비교를 DynamoDB의 문자열 사전식
  비교에서 `::date BETWEEN`(포함)으로 바꾼 것 — 기능적으로는 개선이지만
  기존 동작과 미세하게 다를 수 있음, 문제 생기면 여기부터 볼 것.
- `search_paged`의 키워드 매칭은 `title`/`body`는 대소문자 무시
  (`ILIKE`)지만 `keywords`/`hashtags` 배열은 대소문자 구분 정확매칭
  (DynamoDB `Attr.contains()`가 원래 `keywords`는 소문자화된 쿼리로,
  `hashtags`는 원본 케이스로 비교하던 걸 단순화) — 실사용 영향은
  낮다고 판단, 필요해지면 재검토.
- `article_collection_service.py`의 `original_published_at`
  보존 로직(위 "발견한 버그" 참조)은 여전히 죽은 코드 상태로 남아있음
  — 고칠지는 별도 결정.
