# v1.21 — admin CMS 글 쓰기를 Postgres로 전환, 동기화 버그 해소 (2026-09-09)

**왜**: 사용자 질문("포스트그레로 전환한다고 한거 아닌가요?")을 계기로
확인한 결과, v1.20 컷오버 이후 admin은 여전히 DynamoDB(`sedaily-mbti-
cms-posts-dev`)에만 글을 쓰고 있었고 라이브 사이트는 Postgres 스냅샷만
읽고 있어서 **admin이 새 글을 발행해도 라이브에 영원히 안 보이는**
상태였다. 사용자가 "개발 단계라 사용자 없음, 원래 하려던 대로 전체
전환하라"고 확인 후 이 문제를 근본적으로 해소했다.

## 아키텍처 결정 — admin Lambda가 RDS에 직접 안 붙는 이유

admin Lambda(`sedaily-mbti-admin-api-dev`)를 RDS와 같은 VPC에 직접
붙이는 방안도 검토했다(실제로 이미 같은 VPC `vpc-07a3a75110d6594aa`에
있었고 pg8000도 이미 의존성에 있어 기술적으로는 가능했다). 하지만
오늘(v1.20) Lambda+RDS 조합의 근본 문제(호출마다 새 커넥션)를 이미
한 번 해결한 마당에 같은 문제를 admin 쪽에서 재현하는 대신, **RDS
접근을 이미 만든 상시 서버(`lens-cms-api-prod`) 하나로 집중**시키기로
했다 — admin Lambda는 이 서버의 새 내부 API(`/admin/posts*`)를
호출하는 얇은 HTTP 클라이언트가 된다.

## 스키마 변경

DynamoDB의 admin 쓰기 모델(문서 = "채널 하나")과 기존 Postgres 스키마
(source_url UNIQUE, "발행물 하나에 여러 포맷 렌디션")가 근본적으로
안 맞는 지점을 발견 — admin은 실제로 형제 채널(웹툰/영상/팟캐스트
버전)마다 **독립된 문서**를 쓰고, 같은 source_url을 공유하는 경우가
있다. 원래 스키마의 `UNIQUE(source_url)`은 이 실제 쓰기 패턴과
충돌한다.

- `ALTER TABLE publications DROP CONSTRAINT publications_source_url_key`
  — 형제 채널이 같은 source_url을 공유할 수 있게 허용.
- `admin_post_id UUID UNIQUE` 추가 — admin CmsPost 문서의 원래 id(uuid)를
  보존, get/update/status/delete가 이 값으로 주소를 찾는다.
- `admin_channel VARCHAR(32)` 추가 — admin의 channels[0] 스칼라 원본값
  (공개 읽기 API가 쓰는 renditions.format 역산출 로직과는 별개).
- `admin_publish_date DATE` 추가 — admin이 지정하는 발행 예정일
  (published_at=실제 상태 전환 시각과는 다른 개념).
- `admin_extra JSONB` 추가 — editor_id/closing_line/display_order/
  created_by/media_embed_url/**원본 body_inline 전체**를 그대로 보존.
  **이 컬럼이 admin 쓰기의 진실의 원천**이다 — renditions/webtoon_panels/
  media_assets/rendition_blocks는 공개 읽기 API만을 위한 파생
  프로젝션으로 쓰기 시점에 같이 생성할 뿐, admin의 get/update
  라운드트립은 admin_extra만 본다(완벽한 필드 보존 보장).
- `lens_service_app`에 INSERT/UPDATE/DELETE + 시퀀스 USAGE 권한 부여
  (지금까지 SELECT만 있었음 — admin 쓰기 첫 실행에서 permission denied로
  발견).

## 구현

- `service/lens-cms-api/admin_posts_repo.py`(신규) — create/get/
  list_posts/update/set_status/soft_delete. lens 채널은 body_inline.
  lenses[]를 최대 4개 렌디션으로 분해(v1.12/v1.17과 같은 원칙), 그 외
  채널은 1개 렌디션. update 시 채널/body_inline이 바뀌면 기존 렌디션을
  삭제(CASCADE)하고 다시 씀.
- `service/lens-cms-api/main.py` — `/admin/posts*` 라우터 추가,
  `X-Internal-Token` 공유 시크릿 헤더로 보호(무토큰 401 확인).
  아직 HTTP(EC2 공인 IP:80) 직접 호출 — HTTPS 미적용(TODO, 아래 참조).
- `admin/backend/repo/posts_repo.py` — DynamoDB(boto3) 코드를 전부
  제거하고 `urllib.request` 기반 HTTP 클라이언트로 교체. 함수 시그니처
  동일 유지 — `routes/posts.py`는 무수정.
- 공유 시크릿은 SSM SecureString(`/sedaily-mbti/admin/lens-cms-api-token`)
  — 기존 `JWT_SECRET_PARAM`과 같은 패턴. admin Lambda의 IAM 역할이
  이미 `/sedaily-mbti/admin/*` 전체에 대한 `ssm:GetParameter` 권한을
  갖고 있어 IAM 변경 불필요.

## 흥미로운 발견 — admin Lambda가 이미 RDS와 같은 VPC에 있었다

`sedaily-mbti-admin-api-dev`는 이미 `vpc-07a3a75110d6594aa`(RDS와 동일)
에 VPC 연결돼 있고 `AWSLambdaVPCAccessExecutionRole`도 붙어 있었다 —
그리고 이 Lambda는 이미 `https://ailens.sedaily.ai/api/revalidate`
(공인 인터넷)로 실제 webhook을 성공적으로 호출해온 전례가 있어, 이
VPC/서브넷 조합이 실제로 아웃바운드 인터넷이 되는 것으로 확인된다
(오늘 초 `sedaily-mbti-v2-posts-dev`를 다른 서브넷 조합에 붙였다가
NAT 부재로 장애가 났던 것과는 다른 서브넷). 이론적으로는 admin
Lambda가 RDS에 직접 붙을 수도 있었다는 뜻이지만, 이미 만든 내부 API
경로가 검증까지 끝나 그대로 유지했다 — 상시 서버 하나로 RDS 접근을
집중시키는 게 더 깔끔한 설계이기도 하다.

## 검증

- `service/lens-cms-api/admin_posts_repo.py` 단위 스크립트로 create→
  get→list→update→publish→delete 전체 사이클 확인, webtoon/lens(4개
  렌디션 분해) 양쪽 다 쓰기 직후 공개 읽기 API로 정확히 조회됨을 확인.
- 새 서버 HTTP 엔드포인트 직접 테스트(무토큰 401, 전체 CRUD 200).
- **실제 admin API Gateway 경유 end-to-end**: JWT 발급 → `POST /admin/
  posts`(201) → `POST /admin/posts/{id}/publish`(200) → 즉시
  `https://ailens.sedaily.ai/api/v2/posts/{slug}?channel=webtoon`으로
  조회 시 방금 쓴 내용 그대로 확인 — **admin 발행이 지연 없이 라이브에
  반영된다(동기화 버그 해소 확인)**. 테스트 데이터는 delete로 정리.
- 기존 테스트: `test_posts_repo.py`를 HTTP mock 기반으로 재작성(9/9
  통과), admin/backend 전체 스위트 156 passed(webtoon_lab 관련 무관
  에러 1건은 다른 세션 작업물).

## 남은 항목

- `/admin/posts*`가 아직 HTTP(평문, EC2 공인 IP:80)로만 노출됨 —
  CloudFront behavior를 추가해 HTTPS화하지 않음(dev 단계라 리스크
  낮다고 판단, TODO로 남김).
- admin Lambda가 이미 RDS와 같은 VPC에 있다는 걸 감안하면, 장기적으로
  admin이 RDS에 직접 붙는 편이 내부 API 계층(중복 유지보수 부담)보다
  간단할 수도 있다 — 지금은 바꾸지 않음, 향후 재검토 대상.
- `letters_repo.py`/`quiz_repo.py`/`subscribers_repo.py` 등 나머지
  admin 쓰기 경로는 여전히 DynamoDB 그대로(각각 별도 전환 필요).
