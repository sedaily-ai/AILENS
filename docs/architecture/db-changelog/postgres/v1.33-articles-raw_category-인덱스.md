# v1.33 — articles.raw_category 인덱스 추가 (실측 전/후 비교) (2026-09-10)

**왜**: 사용자 요청으로 DB 인덱스·쿼리 튜닝 상태를 감사했다. `pg_stat_user_tables`
실측 결과 `articles`(18,491행, 148MB)가 순차스캔 125회 누적 202만 튜플 읽음
— 테이블 크기와 거의 맞먹는 양이라 뭔가가 매번 풀스캔을 타고 있다는 신호였다.

## 진단

`service/lens-cms-api/articles_repo.py`가 카테고리 페이지마다
`WHERE raw_category = %s`(또는 `= ANY(...)`) `ORDER BY published_at DESC
LIMIT ... [OFFSET ...]`, 그리고 페이지네이션용 `SELECT count(*) ... WHERE
raw_category = %s`를 반복 호출하는데, `raw_category`(v1.25 신규 컬럼)에
인덱스가 전혀 없었다 — `LIMIT`이 작고 최신순 정렬과 맞아떨어지는 경우만
`articles_published_idx`(published_at DESC)를 타고 우연히 빠르게 끝났고,
`count(*)`나 깊은 페이지네이션(`OFFSET` 큼)은 매번 전체 테이블을 훑었다.

## 수정

```sql
CREATE INDEX articles_raw_category_idx ON articles (raw_category, published_at DESC);
```
`publications_category_idx`(카테고리+published_at DESC 복합, partial)와
같은 패턴 — 이 프로젝트가 이미 쓰던 관례를 그대로 따랐다. RDS
`lens_service_app` 계정엔 DDL 권한이 없어(v1.21 이후 INSERT/UPDATE/DELETE만)
마스터 계정으로 직접 실행(사용자가 시크릿 조회를 승인·실행, 세션에
직접 노출 안 함).

## 실측 — EXPLAIN (ANALYZE, BUFFERS), 흔한 카테고리("경제", 6,689건) 기준

| 쿼리 패턴 | 인덱스 전 | 인덱스 후 | 비고 |
|---|---|---|---|
| `count(*) WHERE raw_category='경제'` | 6.407 ms, buffers 3625(Seq Scan) | 2.392 ms, buffers 1448(Index Only Scan) | 실행시간 **약 63% 감소** |
| `... ORDER BY published_at DESC LIMIT 20 OFFSET 500`(깊은 페이지) | 1.266 ms, buffers 1482(Index Scan on published_idx, 필터로 955행 버림) | 0.481 ms, buffers 522(Index Scan on 신규 인덱스) | 실행시간 **약 62% 감소** |
| `count(*) WHERE raw_category = ANY('{스포츠}')`(877건, 희귀 카테고리) | 미측정(같은 패턴이라 seq scan 확실) | 0.288 ms, buffers 194(Index Only Scan) | |
| `... ORDER BY published_at DESC LIMIT 20`(흔한 카테고리, 얕은 페이지) | 0.117 ms(이미 published_idx로 빠름) | 변화 없음(이미 빨랐음) | 인덱스 유무와 무관 |

테이블이 지금 148MB라 절대 시간차는 몇 ms 수준이지만, `articles`는 매일
크론으로 계속 늘어나는 테이블이라(v1.25) 이 격차는 테이블이 클수록
더 벌어진다 — count(*)는 이미 테이블 크기에 비례해 최악의 경우였다.

## 남은 항목 — pg_stat_statements

사용자가 상시 켜두자고 요청했으나, 이 Aurora 클러스터가 AWS 기본
파라미터 그룹(`default.aurora-postgresql16`, 수정 불가)을 쓰고 있어
`shared_preload_libraries`를 못 바꾼다 — 전용 파라미터 그룹 신설 +
클러스터에 연결 + **재부팅**이 필요하다(재부팅 없이는 적용 안 됨).
지금(v1.33 작성 시점) mustknow_auto 정기 실행이 한창 진행 중이라
재부팅하면 그 실행이 끊길 위험이 있어, 완료 후로 미뤘다 — 별도 항목으로
후속 진행 예정.
