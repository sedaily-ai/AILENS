# v1.15 — publication_slug_history 백필 + slug 폴백 조회 (2026-09-09)

**왜**: v1.13에서 발견하고 미해결로 남긴 문제 — v1.4 마이그레이션이
`publications.slug` UNIQUE 제약 때문에 형제 채널(같은 source_url)의
slug를 대표 채널 것 하나만 남기고 버렸다. 그 결과 개별 채널 slug로
들어오는 기존 URL(북마크·검색엔진 색인)이 `get_published_post_by_slug()`
에서 404가 났다.

## 백필: DynamoDB 재스캔으로 유실된 slug 복원

`scratchpad/backfill_slug_history.py` — v1.4의 `migrate_cms_posts.py`와
동일한 그룹핑 로직(source_url 기준, `BASE_PRIORITY`로 대표 채널 선정)을
재실행해서, 그룹 내 대표가 아닌 채널들의 slug 중 이미 `publications.slug`
로 살아있는 값과 다른 것들을 `publication_slug_history(old_slug,
publication_id)`에 삽입했다. DynamoDB 원본은 읽기만 함(수정 없음).

**결과** (cms-posts 4,116건 재스캔, 985개 그룹):
- 삽입: **2,495건** (824개 서로 다른 publication에 걸쳐 분포)
- 형제 slug가 대표 slug와 동일: 17건 → 건너뜀(중복 불필요)
- 대표 slug의 publications 행 없음: 0건
- 형제 slug가 다른 살아있는 publications.slug와 충돌: 0건(무결성 확인)

## 코드: get_published_post_by_slug()에 폴백 추가

`service/backend/clients/cms_posts_pg_client.py` — `publications.slug`
직접 조회가 실패하면 `publication_slug_history.old_slug`로 재조회해서
`publication_id`를 얻고, 그 걸로 같은 JOIN 쿼리를 다시 실행하도록 확장.
폴백 시에도 어떤 렌디션을 반환할지는 기존과 동일하게 `ORDER BY r.id
LIMIT 1`로 임의 선택한다 — 포맷 구분 없이 조회하는 기존 한계(v1.13
문서화, 아직 미해결)를 그대로 유지할 뿐이고, 이번 변경으로 새로
나빠지는 지점은 없다(이전엔 404였던 게 조회는 되게 바뀜).

**검증** (dev DB against pg8000 driver):
- 직접 slug 조회: 정상 동작 유지 확인
- 형제 slug(`...-video` 등)로 조회 시 history 폴백을 거쳐 같은 publication을
  정상 반환하는 것 실측 확인
- 존재하지 않는 slug: `None` 정상 반환(404 유지) 확인
- 테스트 스위트 재확인: 104 passed, 기존 무관 에러 6건 동일(신규 실패 0건)

## 배포

22개 Lambda 함수 전부 업데이트 성공(0건 스킵). 배포 전 확인: 대상
Lambda 마지막 배포 시각이 v1.14와 일치(`2026-09-08T22:19:43Z`) — 그 사이
다른 배포 없음 확인, 워킹트리 클린 확인. 배포 후 실 API 확인
(`https://chzwwtjtgk.execute-api.us-east-1.amazonaws.com/dev/api/v2/posts`):
`channel=lens` 200(4.05초), `channel=webtoon` 200(1.88초) — v1.14 기록값과
비슷한 응답시간대, `CMS_DB_BACKEND` 미설정 상태 그대로라 여전히 기존
DynamoDB 경로로 정상 서빙 중.

## 남은 미해결

- `get_published_post_by_slug()`가 포맷 구분 없이 아무 렌디션이나
  반환하는 문제 자체는 이번에 해결하지 않음(v1.13에서 이미 식별,
  프론트엔드가 채널별 slug를 실제로 URL에 쓰는지 확인 필요 — 별도 작업).
- `CMS_DB_BACKEND=postgres`는 여전히 어디에도 설정 안 됨 — Postgres
  경로는 계속 dormant.
