# v1.3 — 스키마·운영 결정 실제 적용 및 검증 (2026-09-08)

**왜**: v1.2에서 만든 Aurora dev 인스턴스에 원본 스키마와 `14-operations.md`의
결정 4가지를 실제로 적용해 동작을 검증. 여기까지가 마이그레이션 계획
§2(스키마 적용)의 실행.

**한 것**:

1. `lens` 데이터베이스 생성, 확장 5종 설치 확인:
   `pg_trgm 1.6`, `btree_gin 1.3`, `vector 0.8.2`, `pg_bigm 1.2`,
   `pg_partman 5.4.3` — 전부 `CREATE EXTENSION` 성공(AWS 지원 여부를
   추측이 아니라 실제 설치로 확인).
2. `lens_schema_2026-08-26.sql` 원본 DDL 전체를 단일 트랜잭션으로 적용,
   커밋 성공. 결과: 기본 테이블 50개 + 파티션 자식 테이블 4개
   (`ai_usage_logs_2026_09/10`, `view_events_2026_09/10`) + pg_partman
   메타테이블 2개(`part_config`, `part_config_sub`) = 56개, 뷰
   `v_live_renditions` 1개 + pg_partman 뷰 `table_privs` 1개.
3. `14-operations.md` §1(pg_bigm) 적용: `articles`/`publications`/
   `glossary_terms`/`media_assets`/`rendition_blocks`의 `search_vector`
   컬럼 제거, `gin_bigm_ops` 인덱스 10개 생성 확인.
4. `14-operations.md` §2(pg_partman) 적용 — 시행착오 2건 발생:
   - pg_partman 5.4.3은 구버전 문법 `'monthly'`를 더 이상 지원하지 않음
   → 표준 interval `'1 month'`로 교체.
   - 원본 DDL이 수동으로 만든 파티션(`_2026_09`/`_2026_10`)과
   pg_partman의 자동 명명 규칙(`_p20260901`)이 겹쳐 `create_parent()`가
   실패 → 데이터가 없는 빈 파티션을 확인 후 삭제하고 재실행해 해결.
   결과: `view_events`는 `retention='90 days'`, `ai_usage_logs`는
   `retention=NULL`(무기한)로 `part_config`에 반영됨을 조회로 확인.
5. `14-operations.md` §3(권한분리) 적용: `lens_service_app`/
   `lens_admin_app`/`lens_batch` 역할 생성, `view_counts`에 대해
   `information_schema.column_privileges` 조회로 컬럼별 권한 실제 확인 —
   `lens_admin_app`만 `adjustment` UPDATE 가능, `lens_batch`만
   `real_count` UPDATE 가능, `lens_service_app`은 SELECT만 가능함을
   확인.
6. §4(탈퇴 정책)는 설계상 스키마 변경이 없어 별도 DDL 적용 없음.

**환경 참고**: Aurora 인스턴스가 기본값 `PubliclyAccessible=false`였고
로컬 연결이 안 돼, 검증 목적으로 `PubliclyAccessible=true`로 전환(보안그룹은
작업자 단일 IP로 제한된 상태 유지). 검증 종료 후 다시 `false`로 되돌리는
작업이 남아있음.

**성과**: 원본 설계(v0.1)와 그 이후 결정(v1.0·v1.1·`14-operations.md`)이
전부 실제 DB에서 오류 없이 동작함을 확인 — 종이 위 설계가 아니라 실행
가능한 스키마임이 증명됨. 마이그레이션 계획 §2까지 완료.

28,970건을 이 스키마로 옮기는 작업.
