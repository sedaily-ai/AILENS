# v1.34 — user_archives.article_no FK를 articles→publications(slug)로 수정 (2026-09-11)

**왜**: 사용자가 "서랍에 담기" 기능이 500 에러로 실패한다고 브라우저
콘솔 로그를 직접 공유(`POST .../api/archive` 500).

## 진단

`user_archives.article_no`는 옛 스크래핑 전용 `articles` 테이블(짧은
영숫자 코드, 예: `2KDJYBDOKD`, `VARCHAR(32)`)을 가리키는 FK였다.
DynamoDB→Postgres CMS 마이그레이션 이후 "서랍에 담기"의 실제 호출부
(`SentenceSelectionPopover.tsx`, letters/lens 상세 페이지)는 CMS
슬러그(예: `2026-09-10-채무조정-실패해도-1조-추가로-빚탕감`)를
`article_id`로 보내고 있었다 — `articles`와는 완전히 다른 콘텐츠
체계라, 실제로는 한 번도 성공한 적이 없었다(`user_archives` 기존 11건
전부 `article_no`/`rendition_id` 둘 다 NULL로 이관돼 있었음). 실측한
에러 3종:

1. `permission denied for table user_archives`(2026-09-09, 권한 문제 —
   이후 사라짐)
2. `violates foreign key constraint "user_archives_article_no_fkey"` —
   CMS 슬러그가 `articles.article_no`에 없음
3. `value too long for type character varying(32)` — CMS 슬러그가
   짧은 코드 기준 32자 제한을 넘음

`user_archives.rendition_id`(CMS 렌디션 참조용, v1.24 exclusive arc로
같이 추가됨)를 쓰는 게 스키마 설계 의도에는 더 맞지만, 그러려면
프론트가 렌디션 ID를 알아야 해서 프론트·백엔드 여러 계층을 같이
고쳐야 한다. 실제 호출부가 이미 보내고 있는 슬러그를 그대로 받아주는
쪽이 훨씬 작은 변경이면서 정확히 같은 문제를 없애 — 이쪽을 택했다.

## 수정

```sql
ALTER TABLE user_archives DROP CONSTRAINT user_archives_article_no_fkey;
ALTER TABLE user_archives ALTER COLUMN article_no TYPE VARCHAR(255);
ALTER TABLE user_archives ADD CONSTRAINT user_archives_article_no_fkey
  FOREIGN KEY (article_no) REFERENCES publications(slug) ON DELETE CASCADE;
```

`VARCHAR(255)`는 `publications.slug` 컬럼과 동일 — 실측 최대 슬러그
길이는 80자(`slugify()`의 `[:80]` 절단)라 여유 있게 맞췄다. 마이그레이션
직전 `user_archives` 11건 전부 `article_no IS NULL`이라 FK 위반 없이
안전하게 적용됐다(직접 확인 후 진행).

`service/lens-cms-api/personal_repo.py`의 `_ARCHIVE_SELECT`·
`list_popular_archived_sentences()` 두 조회 쿼리의 `LEFT JOIN articles
a ON a.article_no = ua.article_no`도 `LEFT JOIN publications a ON
a.slug = ua.article_no`로 같이 수정 — 안 고치면 저장은 되지만 "내 서랍"
목록에 기사 제목이 항상 빈 문자열로 뜬다. `user_readings`(읽은 기록)는
다른 호출부가 `publication_id` 경유로 정상 동작 중이라 이번엔
손대지 않았다.

RDS `lens_service_app` 계정엔 DDL 권한이 없어(v1.21 이후 INSERT/
UPDATE/DELETE만) 마스터 계정으로 직접 실행(사용자가 시크릿 조회를
승인·실행, 세션에 직접 노출 안 함) — v1.33과 동일한 절차.

## 검증

`lens-cms-api` EC2에 SSM으로 배포 후, `/internal/personal/archives`를
실제 사용자 ID + 실제 발행 슬러그로 직접 호출해 저장 성공(id 68) +
`article_title`이 `publications.title`로 정상 조인되는 것까지 확인,
테스트 데이터는 바로 삭제.
