# v1.4 — DynamoDB → Postgres 데이터 마이그레이션 실행 (2026-09-08)

**왜**: 마이그레이션 계획(`docs/worklog/2026-09/2026-09-08-postgres-migration-plan.md`
§3, 일괄 이관)의 실제 실행. 스키마(v1.3)는 이미 검증됐고, 실행 전 계획
단계에서 9개 DynamoDB 테이블을 Explore 에이전트 3개로 조사해 이관 대상/
제외 대상을 코드 근거로 확정했다(승인된 계획: `/Users/yeong-gwang/
.claude/plans/adaptive-napping-quasar.md`).

## 실행 중 발견한 것 — 계획 수정

계획 수립 단계에서는 `lens`/`webtoon`/`video`/`home_player` 채널을 각각
독립적인 것으로 가정했으나, 실행 직전 실측 결과 **cms-posts 968개 고유
`source_url` 중 921개가 여러 채널에 걸쳐 반복**됨을 확인했다(예: 같은
기사가 lens+webtoon+video+home_player 4개 row로 존재). 이는 스키마의
"발행물 하나에 형식콘텐츠 여러 개"(`publications`+`renditions` 1:N)
구조와 정확히 일치 — 계획을 `source_url` 기준 그룹핑으로 수정해 실행함
(1 그룹 = 1 `publications` + N개 `renditions`).

## 제외한 것 (근거와 함께)

- `articles`: news_id/title_ko/published_at 중 하나라도 없는 6,482건
  제외("[통합테스트]" 픽스처 37건 포함). 제외 사유(빈 필드)의 근본 원인은
  조사 범위 밖 — 후속 확인 필요.
- `articles.body`: DynamoDB에 없고 S3(`s3_body_uri`)에 있어 **메타데이터만
  1차 이관**. 본문 백필은 계획대로 별도 후속 작업.
- `article_images`/`article_related_news`/`article_categories`:
  DynamoDB `images`/`related_news`/`category` 필드가 실제로 존재하지만
  이번 실행 범위에서는 이관하지 않음 — 후속 작업으로 남김.
- `personal.reading_record`(97건): `article_id`가 원본 기사를 가리키는데
  새 스키마의 `user_readings.publication_id`와 개념이 달라(연결 데이터
  없음) 계획 단계에서 이미 제외 확정.
- `personal`의 `DATE#` 레거시 MBTI 퀴즈(69건): 코드에 없는 유형, 폐기된
  기능으로 판단해 제외.
- `podcast`(3건 중 2건): `status='failed'`(빈 스크립트·오디오, MBTI 실험
  잔재) — 완료된 1건만 이관.
- `cms-posts`의 `trend_card`(4건), 채널 누락(462건): 계획대로 제외.
- `engagement`(198건), `external-content`(51건), `newsletter-subscribers`
  (3건), `daily-letters`(0건): 계획 단계에서 코드 근거로 이관 불필요
  확정(폐기/미병합/배정 불가 — `adaptive-napping-quasar.md` 참조).

## 검증 결과 (전부 실측 확인, 가정 없음)

- FK 무결성: `renditions`→`publications`, `webtoon_panels`→`renditions`
  orphan **0건**
- 테스트 픽스처 유입: `articles.title LIKE '%통합테스트%'` **0건**
- `v_live_renditions` 뷰: **2,520행** 정상 반환, 실제 JOIN된 제목·포맷
  데이터 확인(예: "트럼프 알래스카 언급에… TCC스틸·부국철강 등 관련주
  급등" — podcast/video/webtoon 3개 렌디션 모두 확인)

## 스키마 공백 (계획 단계에서 발견, 이번 실행에서도 미해결)

1. **뱃지 기능** — `users` 테이블에 컬럼 없음, `engagement`/`personal`
   양쪽에 살아있는 데이터 존재하나 이관 안 함
2. **커뮤니티 게시판** — 대응 테이블 자체가 없음, 이관 안 함

두 항목 다 원본 스키마를 임의로 확장하지 않는다는 원칙에 따라 손대지
않았다 — 별도 제품/설계 결정이 나오면 그때 스키마 확장 + 데이터 이관을
진행한다.
