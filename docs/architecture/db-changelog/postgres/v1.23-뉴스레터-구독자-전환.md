# v1.23 — 뉴스레터 구독자 읽기·쓰기 Postgres 전환 (2026-09-09)

**왜**: cms-posts(v1.20/v1.21), 퀴즈(v1.22)에 이어 "원래 하려던 대로
전체 전환" 계속 진행.

## 조사 요약

- 쓰기: `handlers/subscribe.py`(`POST /api/v2/subscribe`,
  `GET /api/v2/unsubscribe`) — 이메일 검증, CAN-SPAM consent 강제,
  가입 즉시 SES 환영 발송까지 담당하는 단일 정본 Lambda(2026-09-04
  리팩토링 감사로 중복 구현 통합됨).
- admin: 통계 전용(`GET /admin/newsletter/stats`), 쓰기 능력 없음.
- Postgres `subscriptions`(v1.9에서 이미 뼈대 이관됨)에는 원본
  DynamoDB item의 `consent`/`status`(3단계)/`name`/`onboarding_format`/
  `onboarding_interests` 컬럼이 없었다 — `cancelled_at`만으로는
  "탈퇴"와 "발송 제외(suppressed)"를 구분 못 함.

## 스키마 확장

- `consent BOOLEAN DEFAULT TRUE` — 발송 대상 필터링에 직접 쓰여 실 컬럼.
- `status VARCHAR(16) DEFAULT 'active' CHECK IN ('active','suppressed','unsub')`
  — 3단계 유지. `cancelled_at`은 계속 "발송 제외 여부" 판단용으로 남기고
  (active가 아니면 항상 채움), `status`는 "왜 제외됐는지"(suppressed vs
  자발적 unsub) 구분용으로 추가.
- `extra JSONB` — name/onboarding_format/onboarding_interests(원본
  스키마에 컬럼 자체가 없던 개인화 필드).
- `lens_service_app`에 subscriptions INSERT/UPDATE/DELETE + 시퀀스
  USAGE, newsletters/subscriptions SELECT 권한 부여(지금까지 아예
  없었음 — v1.10 grant 목록에 이 두 테이블이 빠져 있었음).

## 구현 — 저장만 이전, 비즈니스 로직은 그대로

cms-posts/퀴즈와 다른 점: 공개 HTTP 표면(검증·SES 발송)을 lens-cms-api로
옮기지 않았다. `handlers/subscribe.py`는 그대로 두고 **저장 계층만**
`clients/newsletter_subscribers_pg_client.py`(신규, HTTP 클라이언트)로
위임 — SES 발송·CAN-SPAM 검증 같은 비-DB 로직을 상시 서버로 옮길
이유가 없었다.

- `service/lens-cms-api/subscribers_repo.py`(신규) — subscribe(upsert,
  기존 토큰/온보딩값 보존)/get_by_email/unsubscribe_by_token/
  list_active_subscribers/list_all.
- `service/lens-cms-api/main.py` — `/internal/subscriptions*` 라우터
  추가. `/api/v2/posts`·`/api/quiz/today`와 달리 **전부 내부 전용**(공개
  노출 안 함, 토큰 보호) — 공개 검증·발송 로직은 여전히 기존 Lambda가
  맡으므로 이 서버는 순수 저장소 역할만.
- `handlers/subscribe.py` — DynamoDB(boto3) 제거, HTTP 클라이언트 호출로
  교체. 검증·발송 로직·응답 shape 전부 무변경.
- `newsletter/subscribers.py::load_active_subscribers()`도 같이 이전 —
  조사 결과 **현재 어떤 발송 파이프라인도 호출하지 않는 죽은 코드**
  (Editor Pick 자동생성 파이프라인이 2026-08-05 폐기된 이후, 가입 즉시
  환영 발송은 이 함수를 안 거치고 개별 `send()`를 호출)로 확인됐지만,
  새 호출자가 생겼을 때 두 저장소가 갈리지 않도록 함께 옮겼다.
- `admin/backend/repo/subscribers_repo.py` — 마찬가지로 HTTP 클라이언트로
  교체(통계 전용, 쓰기 없음).

## 공유 시크릿 — 역할별로 다른 SSM 경로에 같은 값 복제

`subscribe.py`가 속한 공용 Lambda 실행 역할
(`sedaily-mbti-v2-collector-dev-role`)의 IAM 정책(`V2SecretsAccess`)이
`/sedaily-mbti/v2/*`만 허용해서, admin 쪽이 쓰던
`/sedaily-mbti/admin/lens-cms-api-token`을 그대로 못 읽는다. 이 공용
역할은 22개 함수가 같이 쓰므로 IAM 정책 범위를 넓히는 대신, 같은 토큰
값을 `/sedaily-mbti/v2/lens-cms-api-token`에도 복제 저장 — 배포 영향을
`newsletter_subscribers_pg_client.py` 한 파일로 좁혔다.

## 검증

- `subscribers_repo.py` 단위 스크립트: subscribe(신규)→재구독(토큰 보존
  확인)→활성 목록 포함 확인→unsubscribe→활성 목록 제외 확인→전체 목록엔
  남아있음(soft 상태) 확인.
- 새 서버 HTTP 엔드포인트 직접 테스트(subscribe/unsubscribe/active-list
  필터 전부 200).
- **실제 API Gateway 경유 e2e**: `POST /api/v2/subscribe`(200, `ok:true`)
  → Postgres에 실제로 행 생성 확인 → `GET /api/v2/unsubscribe?token=`
  (200) → `status='unsub'`로 전환 확인. 테스트 데이터는 삭제로 정리.
  이 과정에서 SES 발송이 `AccessDeniedException`으로 실패하는 걸
  발견했으나 **이번 마이그레이션과 무관한 기존 IAM 권한 문제**로 확인
  (저장 자체는 정상— `ok:true`, `send_status`만 별개로 실패). 별도
  이슈로 남김, 이번 범위에서 고치지 않음.
- 테스트: service/backend 104 passed, admin/backend 156 passed(기존
  무관 에러만 동일).

## 배포

admin Lambda, service 22개 Lambda 전부 재배포 완료.

## 남은 항목

- SES `ses:SendRawEmail` IAM 권한 누락(`sedaily-mbti-v2-collector-dev-role`)
  — 이번 마이그레이션과 무관하게 이미 있던 문제, 환영 이메일이 계속
  못 나가는 중. 별도 확인·수정 필요(이번 세션 범위 밖으로 기록만).
- `sedaily-mbti-newsletter-subscribers-dev`(DynamoDB) 테이블 자체는
  삭제 안 함 — 안정화 후 정리 검토.
- 진짜 지면별 뉴스레터 구독 분리(현재 전부 newsletter_id=1 임시 배정,
  v1.9부터의 미해결 사항)는 여전히 별도 과제.
