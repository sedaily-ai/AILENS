# v1.27 — admin 프롬프트·감사 로그 Postgres 전환 (2026-09-09)

**왜**: articles(v1.25)·커뮤니티/퀴즈통계(v1.26)에 이어 admin-config/
admin-prompts 스코핑 조사(두 Explore 에이전트 병렬 조사) 결과를 바탕으로
계속 진행. admin-prompts는 라이브(관리자가 지금도 편집 중)에 스키마도
`prompts`/`prompt_versions`로 거의 준비돼 있어 우선순위가 높았다.
admin-config(feature_flags/threshold/AUTH lockout/WEBTOONLAB job)는
이번 범위 밖 — 남은 항목에 정리.

## 조사에서 확정한 스키마 갭

- `prompts.name`이 name 단독 UNIQUE였는데, 실제 DynamoDB 키스페이스는
  `category/name` 조합이 유일 단위였다(예: `mustknow/published`과
  `video/published`이 둘 다 name="published"로 겹침) — 그대로면 두 번째
  카테고리의 첫 저장에서 UNIQUE 위반이 났을 것.
- 관리자 화면의 섹션 편집기 구조(`sections_json`, 설명/구조/지침 3섹션 +
  첨부)가 원본 설계엔 없었다 — content(모델이 읽는 산문)와는 별개로
  편집기 폼 복원용으로만 쓰인다.
- `prompt_versions.created_by REFERENCES editors(employee_no)` — 실제로
  "editor" 개념이 존재한 적이 없다(단일 공유 관리자 계정, `editors` 테이블
  0행). 모든 쓰기가 `"actor": "admin"` 리터럴이었다 — v1.21/v1.22가 이미
  같은 문제를 `admin_extra JSONB`로 우회한 전례가 있지만, 여긴 그 값이
  상수 하나뿐이라 컬럼 자체를 만들 실익이 없다고 판단 — `created_by`는
  항상 NULL로 남기고 응답 쪽만 `"admin"`으로 하드코딩.
- 버전 쓰기가 `v#N` put + `LATEST` update 2개의 non-atomic write였다 —
  Postgres 트랜잭션(단일 `get_cursor()` 블록)으로 원자성 확보.
- `audit_logs`가 `flag_name REFERENCES feature_flags(name)`로만 좁게
  설계돼 있었는데, 실제 감사 로그(`admin/backend/shared/audit.py::log()`)
  는 feature-flag/threshold/driver/login/password-change/webtoon-lab/
  prompt/quiz/posts/letters/media 전부를 담는 범용 이벤트 로그였다(DynamoDB
  실 데이터로 `action`/`detail`/`actor`/`session`/`source_ip` 5개 필드
  구조 확인) — 테이블이 비어있어(0행) 안전하게 전면 재설계.

## 스키마 변경

```sql
ALTER TABLE prompts DROP CONSTRAINT prompts_name_key;
ALTER TABLE prompts ADD CONSTRAINT prompts_category_name_key UNIQUE (category, name);

ALTER TABLE prompt_versions ADD COLUMN sections JSONB;

DROP TABLE audit_logs;  -- 0행, 안전
CREATE TABLE audit_logs (
    id          BIGSERIAL PRIMARY KEY,
    action      VARCHAR(64) NOT NULL,
    detail      JSONB,
    actor       VARCHAR(32),
    session_id  VARCHAR(64),
    source_ip   VARCHAR(64),
    logged_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX audit_logs_logged_at_idx ON audit_logs (logged_at DESC);
```

## 구현

`service/lens-cms-api/prompts_repo.py`(신설) — `get_active_content`(공개
읽기 전용, content만), `list_prompts`, `get_prompt`(활성 버전 + 최근
이력, `ORDER BY version DESC` — 버전이 진짜 INTEGER라 admin/backend의
`_load_version_history`가 워크어라운드하던 사전식 정렬 버그(v#10이
v#2보다 앞에 오던 것)가 구조적으로 재발 불가), `update_prompt`(단일
트랜잭션으로 이전 활성 버전 비활성화 + 새 버전 삽입 + prompts 행 없으면
생성).

`service/lens-cms-api/audit_repo.py`(신설) — `log_event`, `list_events`
(id 내림차순 keyset 페이지네이션, DynamoDB의 base64-JSON `LastEvaluatedKey`
커서 대신 `audit_logs.id`를 그대로 opaque 커서로 사용).

`main.py`에 공개 라우트(`GET /api/v2/prompts/{category}/{name}`, 원본
DynamoDB GetItem도 사실상 무인증이었음) + 내부 라우트(`/internal/admin/
prompts*`, `/internal/audit/*`, `X-Internal-Token`) 추가.

Lambda 쪽:
- `admin/backend/repo/prompts_repo.py`/`repo/audit_repo.py`(신설,
  posts_repo.py/quiz_repo.py와 같은 패턴) — `routes/prompts.py`
  (`handle_list`/`handle_get`/`handle_update`, DDB 특유의 워크어라운드
  코드 `_load_version_history`/`_version_of`/`_strip_prefix`/
  `_parse_sections` 전부 삭제) rewiring.
- `admin/backend/shared/audit.py::log()` — **이 파일 하나만 고치면
  posts/quiz/letters/media/drivers/auth/admin_password/webtoon_lab/
  prompts 전부의 `audit.log()` 호출이 자동으로 새 저장소를 쓴다**(20여
  호출부 개별 수정 불필요 — 이미 존재하던 얇은 추상화 계층 덕분).
  `routes/audit.py`(조회 화면)도 같은 패턴으로 rewiring, 커서 검증(정수
  문자열인지)을 라우트 레벨에 다시 추가(예전 base64-JSON dict 검증의
  대체물).
- `service/backend/services/prompt_loader.py` — DynamoDB GetItem 2회를
  `GET /api/v2/prompts/{category}/{name}` 1회 HTTP 호출로 교체, 5분
  TTL+stale-cache+파일시스템 폴백 3단 구조는 그대로. 공개 무인증
  엔드포인트라 IAM(`dynamodb:GetItem`) 걱정이 없어졌다.
- `pipelines/common/ddb_prompt.py` — 같은 방식으로 rewiring, AWS
  자격 증명(boto3 세션)이 아예 필요 없어졌다.

## 발견·수정한 버그 — 리뷰 중 발견한 테스트 오염 사고

admin/backend 테스트를 다시 쓰는 과정에서 `test_prompts_routes.py`의
`monkeypatch.setattr(prompts.prompts_repo, "update_prompt", ...)`가
어느 한 시점(파일을 3개 동시에 고치던 중간 상태)에 제대로 안 먹혀 **실제
lens-cms-api 서버에 테스트 데이터(`letters/draft`, `transform/nt` 등
가짜 content)가 실제로 쓰인 사고가 있었다** — 전체 스위트를 두 번 이상
독립 재실행해 재현 안 됨을 확인(현재 코드는 정상 격리됨), 오염된 4개
버전 행을 직접 정리했다. 근본 원인은 명확히 특정 못 했음(중간 편집 상태의
일시적 문제로 추정) — 재발하면 다시 조사할 것.

## IAM 역할 확인

- `admin/backend`(admin Lambda)는 이미 `/sedaily-mbti/admin/*` SSM 경로
  접근 가능(posts_repo.py/quiz_repo.py가 v1.21/v1.22부터 써온 것과 동일
  역할) — 추가 IAM 작업 없음.
- `service/backend`의 prompt_loader 호출자(chatbot/question 등)는 이제
  공개 무인증 엔드포인트를 부르므로 IAM/SSM 자체가 필요 없어짐.
- `pipelines/frontpage_auto/task-policy.json`·`pipelines/mustknow_auto/
  task-policy.json`이 부여하던 프롬프트 테이블 `dynamodb:GetItem` 권한은
  이제 안 쓰지만, 굳이 회수하지 않음(과다권한 방치가 즉시 위험하지 않고
  IAM 변경 자체가 더 조심스러운 작업이라 판단) — 필요시 후속 정리.

## 백필

`sedaily-mbti-admin-prompts-dev` 전체 스캔(76건) → `prompts` 24개 +
`prompt_versions` 52개(활성 24개, 정확히 프롬프트당 1개) 백필. 원본
어떤 행도 `sections_json`을 쓴 적이 없어(실 데이터 0건 확인) 전부
`sections IS NULL`로 이관. `mustknow/published` 등 실제 콘텐츠를
DynamoDB 원본과 바이트 단위로 대조해 정확성 확인.

## 남은 항목

- `sedaily-mbti-admin-prompts-dev`(DynamoDB) 테이블은 삭제 안 함.
- admin-config(`sedaily-mbti-admin-config-dev`)는 이번 범위 밖:
  - `feature_flags`는 기존 Postgres 테이블로 쉽게 커버 가능(읽기
    `common/feature_flag.py`, 쓰기 `admin/backend/routes/drivers.py`).
  - `threshold`(같은 CONFIG pk 공유)는 전용 테이블이 없음 — 신설 필요.
  - `AUTH#lockout/global`(관리자 로그인 잠금, 라이브)·`WEBTOONLAB#job`
    (2026-09-05 신설, 아직 API Gateway 미연결)도 전용 테이블 없음.
  - `pipelines/frontpage_auto`·`mustknow_auto`의 IAM 과다권한(안 쓰는
    `dynamodb:GetItem`) 회수는 후속 결정.
