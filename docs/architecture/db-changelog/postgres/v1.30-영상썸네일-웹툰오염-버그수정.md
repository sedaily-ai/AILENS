# v1.30 — "영상으로 보는 이슈" 썸네일이 웹툰 컷 이미지로 나오던 버그 수정 (2026-09-09)

**왜**: v1.29(lens 지면 코너 빈 화면) 수정 직후, 사용자가 바로 아래 있는
"영상으로 보는 이슈" 위젯을 보고 "웹툰거를 가져와서 쓰고 있네"라고 신고 —
카드 썸네일이 AI 생성 웹툰풍 인물 초상화였다.

## 진단

Explore 에이전트로 역추적: `service/frontend/.../VideoPreviewSection.tsx`
→ `GET /api/v2/posts?channel=video` → `cms_posts_repo.py::list_published_posts`
→ `cms_posts_shaping.py::shape_video()`.

`channel=video`는 사실 독립 콘텐츠가 아니라 **lens 4포맷 번들과 같은
`publications` 행**을 `renditions.format='video'` 자식이 있는 것만
걸러서 보여주는 것 — 그래서 카드 헤드라인이 "지면 1면" 그리드와
바이트 단위로 같았다.

`shape_video()`는 썸네일을 `cover_image_url`(모든 4포맷이 공유하는
"인스타 카드뉴스"용 완성 그래픽, `shape_lens` 주석이 명시적으로
"웹 카드의 사진 칸에 쓰면 안 된다"고 경고하던 바로 그 필드) 하나만 보고
있었다. 실제 프로덕션 API 778건 전수 확인 결과 **760건(97.7%)의
`cover_image_url`이 실제로는 웹툰 렌디션의 첫 컷 이미지**였다
(`pipelines/common/publish_utils.py`의 커버 이미지 할당 로직 —
`"cover_image_url": webtoon_images[0]["url"] if webtoon_images else None`
— S3 키 자체가 `...-webtoon-cut001.png`). v1.29에서 고친 `admin_extra`
미투영 버그(그때는 lens 채널만 고쳤음)가 `channel=video`에도 똑같이
있어서, 진짜 대안인 `photo_image_url`("텍스트 없는 순수 기사 사진")도
항상 비어 있었다 — `cover_image_url`이 유일한 폴백이라 매번 웹툰 컷이
뜬 것.

부수 발견: 스키마엔 `media_assets.thumbnail_url`(진짜 영상 프레임
캡처용) 컬럼이 이미 있지만, 쓰기 경로(`admin_posts_repo.py`)가 이 값을
채운 적이 없고(관리자 화면에 입력란 자체가 없음) 읽기 경로도 이 컬럼을
SELECT조차 안 하고 있었다 — 있으나 마나 한 죽은 컬럼이었다.

## 수정

`service/lens-cms-api/cms_posts_repo.py`:
- `_apply_lens_admin_extra()`를 `_apply_admin_extra()`로 일반화 — v1.29
  에서 lens 채널에만 걸었던 `admin_extra`(category/paper_section/
  photo_image_url/display_order/editor_id) 투영을 **모든 채널**
  (letters/webtoon/video/home_player)로 확장.
- `_BASE_SELECT`/`_BY_PUBLICATION_ID_SELECT`에 `p.admin_extra` SELECT
  추가(lens 채널 전용 쿼리에만 있던 것).
- `_BASE_SELECT`/`_LENS_RENDITIONS_SELECT`/`_BY_PUBLICATION_ID_SELECT`에
  `ma.thumbnail_url` SELECT 추가, `_row_to_post()`가
  `media_thumbnail_url`로 노출 — 죽어있던 컬럼을 읽기 경로에 연결(쓰기
  경로는 아직 안 채워서 대부분 비어있지만, 나중에 채우기 시작하면 바로
  동작하도록 미리 배선).
- `_fetch_lens_items()`의 lens 상세 페이지 "영상" 탭용 `thumbnail_url`도
  하드코딩 `None`에서 실제 컬럼값으로 교체(부수 수정 — 같은 원인의
  다른 증상).

`service/lens-cms-api/cms_posts_shaping.py::shape_video()`:
- 우선순위를 `cover_image_url` 단독 → `media_assets.thumbnail_url`
  (진짜 영상 프레임, 현재 거의 항상 비어있음) → `photo_image_url`(진짜
  기사 사진, 이제 대부분 채워짐) → `cover_image_url`(최후 폴백)로 변경.

이번엔 새 백필이 필요 없었다 — v1.29에서 이미 913건의 `admin_extra`
(photo_image_url 포함)를 백필해뒀고, `channel=video` 게시물이 그
lens 번들과 같은 행이라 데이터는 이미 준비돼 있었다. 읽기 경로 연결만
빠져 있었을 뿐.

## 검증

- EC2에 배포 전, `/tmp` 임시 경로에 수정본을 올려 실 서버 프로세스는
  안 건드리고 실제 DB로 직접 호출 — `list_published_posts('video', ...)`
  가 `photo_image_url`을 실제로 채우는지, `shape_video()`가 최종적으로
  `wimg.sedaily.com`(진짜 기사 사진 CDN) URL을 고르는지 확인. 사용자가
  스크린샷에서 신고한 바로 그 4개 게시물(단기국채 ETF/프랑크푸르트
  K컬처/LG디스플레이/대용량 소용량)로 직접 재현·확인.
- EC2 배포 후 **실제 프로덕션 API** `channel=video&limit=1000`(778건
  전수) — 웹툰 컷 잔존 10건(1.3%, 원래부터 photo_image_url 자체가 없던
  소수 게시물로 추정), 진짜 기사 사진 746건(95.9%), 빈 값 10건. 수정
  전 760건(97.7%)이 웹툰 컷이었던 것과 대비.

## 배포

lens-cms-api EC2 재배포 1회(`cms_posts_repo.py`, `cms_posts_shaping.py`).

## 남은 항목

- 여전히 웹툰 컷/빈 값으로 남은 20건(778건 중)은 원본 `admin_extra`에
  `photo_image_url` 자체가 없던 게시물 — v1.29의 "slug 매칭 실패 22건"과
  겹칠 가능성이 있음, 원인 미조사.
- `media_assets.thumbnail_url`(진짜 영상 프레임 캡처)은 읽기 경로만
  연결했을 뿐 여전히 아무도 안 채운다 — 파이프라인이나 관리자 화면에
  캡처 로직/입력란을 추가하는 건 이번 범위 밖(백엔드 DB 마이그레이션이
  아니라 프론트엔드/파이프라인 기능 추가가 필요한 작업).
- v1.29에서 남겨둔 우려("letters/webtoon/home_player도 같은 admin_extra
  미투영 문제가 있을 것")가 이번에 확인·해소됐다 — `_apply_admin_extra`
  일반화로 4개 채널 전부 `category`/`photo_image_url` 등이 이제 정상
  투영된다. 다만 각 채널의 shaper(`shape_letter`/`shape_webtoon`/
  `shape_home_player_item`)가 이 필드들을 실제로 어떻게 쓰는지(예:
  카테고리 필터 페이지가 지금까지 어떻게 동작해왔는지)는 개별 검증
  안 함 — 회귀 소지는 낮다고 판단(항상 None이던 값이 이제 실제 값으로
  채워지는 방향이라, 필터링 로직이 "값 있으면 그것대로, 없으면 전체"
  식이면 자연히 개선되고 깨질 이유가 없음).
