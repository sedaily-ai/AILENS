# v1.24 — 개인화(내 서랍·읽은 기록·프로필) 읽기·쓰기 Postgres 전환 (2026-09-09)

**왜**: cms-posts/퀴즈/뉴스레터에 이어 계속 진행. 지금까지 중 가장 복잡한
기능(3개 하위 기능이 단일 DynamoDB 테이블에 PK=user_id/SK=sk로 얽혀있음).

## 조사 요약

- `PersonalDBClient`(DynamoDB, PK=user_id/SK=sk)가 5개 primitive
  (get/put/delete/query_by_user/update_item)를 노출하고 `PersonalRepository`
  가 그 위에 아카이브·프로필·읽은기록 3개 하위 기능의 비즈니스 로직을
  얹는 구조.
- `users`(Cognito sub, 11행)/`user_archives`(11행)는 v1.4에서 이미
  일부 이관됐지만, `user_readings`는 "article_id가 publication_id에
  안 맞는다"는 이유로 **당시 이관 자체를 제외**했었다.
- 뱃지(`users.badges`)는 v1.8에서 이미 컬럼이 추가돼 있었음(재확인).

## 핵심 발견 — article_id는 CMS가 아니라 뉴스 기사(articles)를 가리킨다

원본 Postgres 스키마의 `user_archives.rendition_id`/`user_readings.
publication_id`는 CMS 렌디션(cms-posts 유래)만 참조할 수 있게 설계돼
있었는데, 실제 "내 서랍"·"읽은 기록" 기능은 **뉴스 기사**
(`articles`, 24,682건)에서 문장을 담고 기사를 읽는 것이었다 — CMS
콘텐츠와는 완전히 다른 대상. 이 불일치를 v1.4 계획 문서도 이미
알고 있었다(`user_readings` 제외 사유가 정확히 이것).

### 스키마 변경 — exclusive-arc FK 추가

- `user_archives.article_no VARCHAR(32) REFERENCES articles(article_no)`
  추가, `CHECK (num_nonnulls(rendition_id, article_no) <= 1)` — **"최대
  1개"**(정확히 1개가 아님). 기존 11건이 마이그레이션 당시 연결정보
  없이 이관돼 둘 다 NULL이라 "정확히 1개"로 하면 위반됨을 실측 중
  발견, 완화.
- `user_readings`: 복합 PK `(user_id, publication_id)` 제거 →
  `id BIGSERIAL PRIMARY KEY`로 교체(NULL 허용 컬럼과 복합 PK가 공존
  불가), `publication_id` nullable화, `article_no` 추가,
  `CHECK (num_nonnulls(publication_id, article_no) = 1)`(이쪽은 기존
  행 0건이라 엄격하게), 부분 유니크 인덱스 2개
  (`(user_id,publication_id) WHERE ... IS NOT NULL`,
  `(user_id,article_no) WHERE ... IS NOT NULL`)로 대체.
- `article_title`/`article_published_at`은 컬럼으로 중복 저장하지 않고
  조회 시 `articles` 테이블과 JOIN해서 채운다(정규화 유지).
- `lens_service_app`에 user_archives/user_readings 전체 권한, users
  INSERT/UPDATE 권한 부여.

## 구현 — 저장만 이전, 스트릭·뱃지 로직은 그대로

- `service/lens-cms-api/personal_repo.py`(신규) — 아카이브/프로필/
  읽은기록 CRUD, `list_popular_archived_sentences`(전체 유저 집계,
  2건 이상만 노출).
- `service/lens-cms-api/main.py` — `/internal/personal/*` 라우터(전부
  내부 전용, 토큰 보호).
- `service/backend/clients/personal_pg_client.py`(신규) — HTTP 클라이언트.
- `service/backend/repositories/personal_repository.py` — 전면 재작성.
  메서드 시그니처·반환 타입(`ArchivedSentence`/`UserProfile`/
  `ReadingRecord` 모델)은 무변경 — 호출부(`archive_service.py`/
  `user_service.py`)가 거의 무수정으로 그대로 동작.

## 발견·수정한 버그 3건

1. **`archive_service.py::handle_delete`의 워크어라운드 제거** —
   DynamoDB sk가 `{article_id}#{timestamp}` 합성값이라 opaque한
   `archive_id`만으로 못 지우고, 목록 전체를 긁어 id 매칭 후
   article_id/timestamp를 재조합해야 했다. 관계형 PK로는 이 우회가
   불필요 — `archive_id`로 직접 삭제(소유자 확인은 `WHERE user_id=`
   로 대체).
2. **로그인 시각 갱신 회귀** — `PersonalRepository.update_user_profile`
   이 `{'last_login': ...}` 갱신 요청을 "get_or_create_user가 대신
   처리하니 무시해도 된다"고 잘못 판단해 드롭하도록 짰다가, 실제로는
   기존 유저 로그인 경로가 `update_user_profile`만 부르고
   `get_or_create_user`(서버쪽)는 안 거쳐서 **로그인 시각이 영원히
   안 갱신**되는 회귀였음을 로컬 통합 테스트 중 발견 — `last_login`
   키가 있으면 서버의 get_or_create_user(터치 목적)를 같이 호출하도록
   수정.
3. **RETURNING 절 권한 오류** — `INSERT ... RETURNING *`이 SELECT
   권한을 요구한다는 걸 놓쳐, INSERT/UPDATE/DELETE만 부여하고 배포한
   첫 실 API 호출에서 "permission denied for table user_archives" 발생
   (평범한 INSERT 자체는 되는데 RETURNING만 막힘 — 직접 재현해서 원인
   특정). SELECT 권한 추가로 해결.
4. **공유 IAM 역할 문제** — archive-dev/user-dev Lambda가 AI LENS
   프로젝트 밖 다른 서비스(bigkinds/ga4 등 인라인 정책 이름으로 확인)
   와 공유하는 광범위 실행 역할(`sedaily-mbti-lambda-execution-dev`)을
   써서, 다른 클라이언트들처럼 SSM SecureString으로 토큰을 읽으면 그
   공유 역할에 SSM 권한을 추가해야 했다 — 영향 범위가 프로젝트 밖으로
   새는 걸 피하기 위해 이 두 함수에만 평문 환경변수(`LENS_CMS_API_TOKEN`)
   로 토큰을 직접 주입.

## 검증

- `lens-cms-api/personal_repo.py` 로컬 스크립트: 프로필 생성/조회,
  아카이브 저장(article_no 있음/없음 둘 다)/조회/삭제, 읽은기록
  저장·증가, `article_title` JOIN 값 확인.
- Lambda 쪽 `PersonalRepository`를 실제 서버에 대고 직접 호출(인증
  계층 우회, 코드 경로 자체는 동일) — 전체 사이클 + 로그인 시각 갱신
  버그 수정 검증까지 완료.
- **실제 API Gateway 경유**: `GET /api/archive/popular`(공개, 무인증)
  200 확인. 그 외 엔드포인트는 Cognito JWT가 필요해 이번 세션에서는
  직접 호출 검증 대신 위 Lambda 코드 경로 직접 테스트로 대체.
- `service/backend` 테스트 104 passed(기존 무관 에러만 동일 — 이
  3개 서비스 전용 유닛 테스트 자체가 원래 없었음).

## 배포

service 22개 Lambda 전부 재배포(2회 — 토큰 조달 방식 수정 후 재배포).

## 남은 항목

- `sedaily-mbti-personal-dev`(DynamoDB) 테이블은 삭제 안 함.
- 인증 필요 엔드포인트(아카이브 저장/조회/삭제, 프로필, 읽은기록,
  뱃지)의 실 API Gateway e2e는 Cognito JWT 조달 방법을 찾으면 후속
  검증 권장.
- `temperature`/`title`(UserProfile 필드)는 폐기 판단해 컬럼을 안
  만듦 — 다시 필요해지면 admin_extra류 JSONB 재도입 검토.
