# v1.28 — feature flag·threshold·admin 로그인 잠금 Postgres 전환 (2026-09-09)

**왜**: v1.27(admin 프롬프트·감사 로그)에 이어 admin-config 스코핑 조사의
나머지 항목 진행. `feature_flags`는 원본 설계에 이미 있었고, `threshold`/
`AUTH lockout`은 전용 테이블이 없어 신설이 필요했다. `WEBTOONLAB job`은
2026-09-05 신설 기능이지만 아직 API Gateway에 라우트가 안 붙어 프로덕션
도달 불가 상태라 이번 범위에서 제외(남은 항목 참조).

## 조사에서 확정한 사실

- `admin/backend/common/feature_flag.py`(읽기)와 `admin/backend/routes/
  drivers.py`(쓰기)는 feature-flag/threshold를 같은 DynamoDB 테이블
  (admin-config, pk='CONFIG')에서 sk 접두사(`feature-flag/`|`threshold/`)
  로만 구분해왔다 — 원본 Postgres 설계는 `feature_flags` 테이블만 있고
  threshold 대응이 없었음.
- `AUTH#lockout/global`은 실제 라이브 admin 로그인 잠금 기능
  (`admin/backend/auth.py`) — 단일 공유 관리자 계정이라 전역 싱글턴 1행
  으로 충분(여러 계정이 생기면 그때 확장).
- `common/feature_flag.py`의 실제 프로덕션 호출자는 `handlers/
  chatbot_handler.py`/`handlers/question_handler.py` 둘뿐(`is_enabled`만
  사용, `get_threshold`는 프로덕션 호출자 0 — 테스트 conftest.py만 참조).
  둘 다 v1.25에서 이미 `LENS_CMS_API_TOKEN` 평문 env var가 설정돼 있어
  추가 IAM 작업이 필요 없었다.

## 스키마 변경

```sql
CREATE TABLE thresholds (
    name        VARCHAR(64) PRIMARY KEY,
    value       INTEGER     NOT NULL,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE admin_login_lockout (
    id             SMALLINT PRIMARY KEY DEFAULT 1 CHECK (id = 1),
    fail_count     INTEGER NOT NULL DEFAULT 0,
    lockout_until  TIMESTAMPTZ
);
```

`feature_flags`는 기존 테이블 그대로 사용(스키마 변경 없음).

## 구현

`service/lens-cms-api/config_repo.py`(신설) — `list_feature_flags`/
`get_feature_flag`/`set_feature_flag`(UPSERT), `list_thresholds`/
`get_threshold`/`set_threshold`(UPSERT), `check_lockout`/
`record_login_fail`/`reset_login_fail`(전부 UPSERT, id=1 싱글턴). 행이
없을 때 `get_feature_flag`/`get_threshold`는 `None`을 반환하고 기본값
판단은 호출부에 맡긴다 — DynamoDB 시절 서로 다른 호출부가 서로 다른
fail-open 기본값(항상 True vs 호출자가 준 default)을 썼기 때문에 이
계층에서 기본값을 고정하지 않는 게 맞다고 판단.

`main.py`에 전부 내부 라우트(`/internal/config/feature-flags*`,
`/internal/config/thresholds*`, `/internal/auth/lockout/*`,
`X-Internal-Token`) 추가 — DynamoDB 시절도 공개 노출이 아니라 Lambda
IAM 권한으로 막혀있던 운영 설정값이라 공개 엔드포인트로 바꾸지 않았다.

Lambda 쪽:
- `service/backend/common/feature_flag.py` — DynamoDB get_item 2종을
  `GET /internal/config/{feature-flags,thresholds}/{name}` HTTP 호출로
  교체. 5분 TTL+stale-cache fallback 구조, fail-open 철학 전부 그대로.
- `admin/backend/repo/config_repo.py`(신설, posts_repo.py와 같은 패턴)
  — `routes/drivers.py`(`_load_feature_flags`/`_load_thresholds`
  DynamoDB Query 헬퍼 삭제, `handle_feature_flag_update`/
  `handle_threshold_update`가 이제 UPSERT 결과의 `updated_at`을 그대로
  씀 — 라우트에서 직접 타임스탬프를 만들 필요가 없어짐)와
  `auth.py`(`_check_lockout`/`_record_fail`/`_reset_fail` 3개 함수가
  각각 DynamoDB read-modify-put 구현에서 `config_repo` 위임 한 줄로
  축소) rewiring.

## 발견·수정한 버그 — 또 한 번의 테스트 오염 사고

`test_drivers_routes.py`의 `set_feature_flag`/`set_threshold` monkeypatch
가 v1.27 때의 `prompts_repo` 사고와 똑같은 패턴으로 다시 한번 실제
lens-cms-api에 테스트 값(`name="f"`, `name="t"`)을 실제로 썼다 — 역시
전체 스위트 재실행 2회로 재현 안 됨을 확인, 오염된 2개 행 정리. 근본
원인은 이번에도 명확히 특정 못 했음(v1.27과 같은 결론) — 세 번째
발생하면 pytest 격리 메커니즘 자체를 더 깊게 조사할 것.

## IAM 역할 확인

- `sedaily-mbti-chatbot-dev`/`sedaily-mbti-question-dev`는 v1.25에서
  이미 `LENS_CMS_API_TOKEN` 평문 env var가 설정돼 있어 추가 작업 없음.
- `admin/backend`는 v1.21부터 `/sedaily-mbti/admin/*` SSM 경로 접근
  가능 — 추가 IAM 작업 없음.

## 검증

- `config_repo.py` 로컬 스크립트(마스터 커넥션): feature flag/threshold
  UPSERT+조회, 로그인 실패 5회 → lockout 발동 → 잔여시간 계산 →
  reset까지 전부 실제 데이터로 확인.
- EC2 배포 후 서버 로컬 curl로 내부 라우트 재확인(무토큰 401 포함).
- `service/backend/common/feature_flag.py` 로컬에서 직접 호출 —
  미존재 flag(fail-open True)·미존재 threshold(default 반환)·명시적
  값(false/55) 둘 다 정확히 반영 확인.
- `admin/backend` 전체 테스트 146 passed(무관한 사전 존재 에러 1건은
  v1.27과 동일). `test_drivers_routes.py`/`test_auth_routes.py`
  FakeTable→config_repo 함수 스텁으로 재작성.
- `service/backend` 전체 테스트 104 passed(기존 무관 에러 6건 동일).
- **실제 API Gateway 경유**(admin 자체 HS256 JWT): `GET /admin/drivers`
  (rules 4개 + 빈 flags/thresholds), `POST /admin/drivers/feature-flag/
  e2e-gateway-test`(enable) → 재조회로 반영 확인, `POST /admin/drivers/
  threshold/e2e-gateway-threshold`(77) → 재조회로 반영 확인,
  `POST /admin/login`(실제 틀린 비밀번호로 실패 1회) → `admin_login_
  lockout.fail_count`가 실제로 1 증가함을 직접 쿼리로 확인(진짜 프로덕션
  보안 카운터가 살아있다는 뜻이라 테스트 직후 즉시 리셋).
- **실제 Lambda 직접 invoke**: `sedaily-mbti-question-dev`의
  `/api/questions/today` 200, 로그에 feature_flag 관련 에러 없음.
- 테스트 데이터(`e2e-gateway-test`/`e2e-gateway-threshold`, lockout
  카운터, 오염된 `f`/`t` 행)는 전부 검증 직후 정리.

## 배포

lens-cms-api EC2 재배포 1회. service 22개 Lambda 재배포 1회
(deploy.sh). admin API Lambda 재배포 1회(deploy-admin-api.sh).

## 남은 항목

- `sedaily-mbti-admin-config-dev`(DynamoDB) 테이블은 삭제 안 함.
- `WEBTOONLAB#job/*`(웹툰 실험 기능, 2026-09-05 신설)은 아직 API
  Gateway에 라우트가 안 붙어 프로덕션 도달 불가 — 라이브 기능이 아니라
  이번 범위에서 계속 제외. 실제로 API Gateway에 연결되는 시점에 스키마
  설계·마이그레이션 진행할 것.
- `pipelines/frontpage_auto`·`mustknow_auto`의 admin-prompts 관련 IAM
  과다권한(v1.27에서 발견, 회수 안 함) — 이번에도 별도 결정 대기.
- 이것으로 이번 세션에서 스코핑한 admin-config/admin-prompts/engagement/
  community/ws-connections 5개 중 4개(admin-prompts, community, quiz
  통계, feature-flag/threshold/lockout) 완료 — ws-connections는 작업
  불필요로 확인, WEBTOONLAB job만 "아직 라이브 아님"으로 보류.
