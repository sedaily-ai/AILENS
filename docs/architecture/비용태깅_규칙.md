## 2. `Service` 값 — 무엇을 붙일지

**2026-08-24 사용자 결정으로 AI LENS 전체 113개를 `atlas4`로 이관했다.** 지원기간 중 새로 만드는

| 대상 | 현재/신규 `Service` | 9/30 이후 |
|---|---|---|
| AI LENS 기존 리소스 113개(mustknow 포함) | **`atlas4`** | `lens`로 원복 |
| 2026-09-30까지 새로 만드는 AI LENS 리소스·프로파일 | **`atlas4`** | `lens`로 원복 |

`atlas4`는 lane 4 = **AI LENS 전체**다. mustknow 전용 값이 아니다. 외부에는 `atlas*` 접두어가
Atlas 지원 작업으로 보이고, 내부에서는 이 값으로 AI LENS를 복원한다. 매핑 정본은
`AI-dashboard/docs/reports/2026-08-24_atlas_태깅_매핑표.md`다.

### 결정 근거와 경계

- 최종 크레딧 적격 판정은 이테크 몫이며 `atlas4=AI LENS 전체`임을 매핑표로 통보한다.
- 금액을 맞추기 위한 중복 처리·불필요한 고비용 호출은 하지 않는다. 실제 업무만 수행한다.
- `atlas4`를 NOVA·영문·desk 등 다른 서비스에 붙이지 않는다.
- 9/30 원복 소스는 AI-dashboard의 mustknow 8개 + 나머지 105개 manifest, 합계 113개다.

### 공통 태그 스키마

```text
Service      = atlas4          ← 비용귀속 기준 키. 활성 비용할당 태그는 이것뿐
Project      = Sedaily-LENS
ServiceName  = Sedaily-LENS    (또는 MBTI-PromptEval 등 구성요소명)
Environment  = dev | prod
CostCenter   = sedaily-ai
Model        = sonnet-46 등     ← Bedrock 추론 프로파일에만
WorkItem     = atlas-4444      ← 담당자 내부 마커. mustknow 계열에만, 선택
```

> `ServiceName`·`Project`·`WorkItem`은 payer 비용할당 태그로 활성화돼 있지 않다.
> 청구 금액을 가르는 것은 `Service`뿐이다.

### 새 프로파일을 만들 때 — 3단계, 2번을 빠뜨리면 실패합니다

```bash
# ① 프로파일 생성
aws bedrock create-inference-profile --region us-east-1 \
  --inference-profile-name lens-<용도>-<모델> \
  --description "Sedaily-LENS <용도> <모델>" \
  --model-source copyFrom=arn:aws:bedrock:us-east-1:887078546492:inference-profile/<시스템프로파일ID> \
  --tags key=Project,value=Sedaily-LENS key=Service,value=atlas4 \
         key=ServiceName,value=Sedaily-LENS key=Environment,value=dev \
         key=CostCenter,value=sedaily-ai key=Model,value=<모델>
```

**⚠️ 함정 2개 — 2026-08-28에 실제로 걸렸습니다.**

- **`--description` 에 괄호·쉼표 등 특수문자를 넣으면 `ValidationException` 입니다.**
  허용 패턴은 `([0-9a-zA-Z:.][ _-]?)+` 로, 영숫자와 `:` `.` 그리고 구분자 공백·`_`·`-` 만
  됩니다. `"... Core (us-west-2)"` 처럼 괄호를 쓰면 거부됩니다.
- **`copyFrom` 에 시스템 프로파일이 아니라 foundation-model ARN 도 됩니다.**
  이미지 모델처럼 `inferenceTypesSupported` 가 `['ON_DEMAND']` 뿐이어서 시스템(교차리전)
  프로파일이 아예 없는 모델은 **FM ARN 을 직접 감싸면 됩니다.** 예:

  ```bash
  aws bedrock create-inference-profile --region us-west-2 \
    --inference-profile-name lens-webtoon-image-stable-core \
    --description "Sedaily-LENS webtoon background image Stable Image Core us-west-2" \
    --model-source copyFrom=arn:aws:bedrock:us-west-2::foundation-model/stability.stable-image-core-v1:1 \
    --tags key=Project,value=Sedaily-LENS key=Service,value=atlas4 \
           key=ServiceName,value=Sedaily-LENS key=Environment,value=dev \
           key=Workload,value=webtoon-image
  ```

  즉 **"ON_DEMAND 전용이라 태깅이 불가능하다" 는 판단은 틀렸습니다.** 프로파일이 없었을 뿐입니다.
  다만 **모델이 있는 리전에 만들어야** 합니다(Stable Image Core 는 us-west-2 에만 있습니다).

**② 호출 주체 IAM 에 권한 추가 — 이걸 빠뜨리면 실행 단계에서 죽습니다.**
프로파일을 만들어도 호출 주체에 그 ARN 에 대한 `bedrock:InvokeModel` 이 없으면 거부됩니다.
**application profile ARN · 시스템 프로파일 ARN · foundation-model ARN 3종을 함께** 넣어야
합니다. 하나만 넣으면 여전히 실패합니다.

**③ 호출부 `modelId` 를 프로파일 ARN 으로 교체.**
`modelId` 는 사본마다 붙습니다. 상수/환경변수 한 곳으로 빼두면 한 번만 고치면 됩니다.

> Bedrock 태그 API 의 키 이름은 **소문자**입니다. 조회는 `tags[?key=='Service']`,
> 입력은 `key=...,value=...`. 대문자로 쓰면 **에러 없이 빈 결과**가 돌아와 "태그가 없다" 고
> 오판합니다.

## 4. 일회성·단발 Bedrock 작업 — 기회가 한 번뿐입니다

일회성 작업은 끝난 뒤에 태그를 붙여도 그 비용이 영구히 미태깅으로 남습니다.
대상: 대량 배치 추론 · 프롬프트 평가 하네스 · 일회성 재생성/백필 · 데이터셋 일괄 처리.

### 착수 전 게이트

1. **프로파일 ARN 을 쓰는가** — 베어 모델 ID 로 돌리면 100% 샙니다. 위 §3 표에서 고르거나,
   맞는 게 없으면 새로 만듭니다(3단계).
2. **호출 주체에 그 ARN 권한이 있는가** — 없으면 실행 단계에서 죽습니다.
3. **소량으로 먼저 돌렸는가** — 몇 건으로 성공을 확인한 뒤 본 실행.
4. **배포·프로비저닝이 태그를 덮어쓰지 않는가** — §6.

### 실행 후 확인

```bash
# 리소스에 태그가 붙었나 (붙였다고 가정하지 말 것)
aws resourcegroupstaggingapi get-resources --region us-east-1 \
  --tag-filters Key=Service,Values=atlas4 --query "ResourceTagMappingList[].ResourceARN"
```

**청구 반영은 T+3 입니다.** 2026-08-24 실측 기준 BillingON 의 마지막 완전 적재일이 3일
전이었습니다. 실행 3~4일 뒤에 확인하고, 안 잡혔으면 **다음 작업 전에** 원인을 잡으십시오.
Cost Explorer 는 조직 SCP 로 막혀 있어 쓸 수 없습니다.

> **Bedrock 배치는 CloudWatch 모델호출 로그·`Invocations` 지표에 남지 않습니다.**
> 그래서 배치 미태깅은 알람으로 못 잡습니다. 확인은 BillingON 실청구뿐입니다.

## 5. ECS/Fargate — task definition 태깅만으로는 부족합니다

`pipelines/mustknow_auto` 처럼 EventBridge → RunTask 로 Fargate 를 띄우는 경로는
**실행되는 태스크에 태그가 따로 붙어야** 컴퓨트 비용이 귀속됩니다. task definition 을
태깅해도 실행 태스크는 별개입니다.

- EventBridge 타깃에 `PropagateTags: "TASK_DEFINITION"` 필요
- 그리고 **EventBridge 역할에 `ecs:TagResource` 권한이 필요합니다.** 없으면 RunTask 자체가
  실패해 배치가 멈춥니다. **권한 → 타깃 순서**를 지키십시오
- task definition 은 **불변**이라 새 리비전은 태그를 상속하지 않습니다. 배포가 매번 지정해야 합니다

확인:

```bash
aws ecs list-tags-for-resource --resource-arn <실행된 task ARN> --region us-east-1
```

`put-targets` 성공만으로 판정하지 마십시오.

## 6. 배포가 태그를 덮어쓰지 않게 하십시오

문서를 지켜도 배포 스크립트가 나중에 되돌리면 의미가 없습니다. 실제로 반복된 패턴입니다.

- `pipelines/mustknow_auto/provision.sh` 가 `Service` 값을 **3곳에 하드코딩**하고 있었습니다
  (2026-08-24 `SERVICE_TAG` 변수 한 곳으로 통일)
- 다른 저장소에서도 같은 일이 있었습니다 (`AI-GLOBE-ensedaily/backend/scripts/tag_resources.sh`
  가 `Service=ENG` 를 덮어씀)

**태그 값은 사본마다 하드코딩하지 말고 스크립트 상단 변수 한 곳으로 빼십시오.**
사본 수만큼 새 나갈 구멍이 생깁니다.
