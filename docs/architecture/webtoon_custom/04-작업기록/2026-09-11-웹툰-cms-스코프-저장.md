# 2026-09-11 웹툰(4가지 시선 번들) CMS 스코프 저장 기능

작성: Claude Code
관련: service/lens-cms-api/admin_posts_repo.py, main.py, admin/backend/routes/posts.py,
admin/backend/repo/posts_repo.py, admin/frontend webtoon·video·home-player 편집 화면

## 배경

"웹툰 CMS에 데이터가 안 쌓인다" 신고로 시작 — 자동 파이프라인이 만드는
글은 전부 admin_channel='lens'(4가지 시선 번들)라 웹툰/영상/홈플레이어
관리 화면의 완전일치 필터에 하나도 안 걸렸다. 목록/열람은 고쳤는데, 그
다음 사용자가 명확히 요구한 것: "저장도 할 수 있어야하는겁니다... 웹툰을
완성하고 저장누르면 웹툰 카테고리쪽에 데이터쌓이고 웹사이트쪽에는 웹툰
카테고리에만 게재가 되는겁니다." — 처음엔 통째 덮어쓰기로 다른 3포맷이
유실되는 걸 막으려 저장 자체를 잠갔었는데, 그 설계를 뒤집고 "이 포맷
슬라이스만 스코프해서 저장"하는 기능을 새로 만들었다.

## 한 것

- `admin_posts_repo.py`에 `_update_lens_bundle_slice()` 신설 — lens
  번들의 `admin_extra.body_inline.lenses[]`에서 해당 포맷(레터/웹툰/
  팟캐스트/영상) 항목 하나만 바꾸고 나머지는 그대로 둔다. 파생
  렌디션(webtoon_panels/media_assets)도 그 포맷 것만 지우고 다시 쓴다.
- `update()`가 `edit_channel` 인자를 받아 lens 번들 + 단일 포맷 채널이면
  위 함수로 분기. `main.py`의 `PUT /admin/posts/{id}`가 `channel` 쿼리
  파라미터를 받아 `edit_channel`로 전달, `ValueError`는 400으로 변환.
- `admin/backend`(Lambda) — `repo/posts_repo.py::update()`와
  `routes/posts.py::handle_update()`가 `channel` 쿼리 파라미터를
  읽어 lens-cms-api까지 흘려보내도록 수정(GET에서 이미 한 번 겪은
  것과 같은 종류의 "중간 계층이 파라미터를 흘린다" 버그를 PUT에서도
  미리 막음). 안전장치 400 에러의 메시지를 프런트까지 그대로 전달하기
  위해 `posts_repo._request()`가 400을 `ValueError`로 다시 던지도록
  바꿨다(HTTPError의 body는 한 번 읽으면 다시 못 읽어서 원래 코드로는
  라우트 쪽에서 메시지를 못 꺼냈다).
- `adminClient.ts::updatePost()`에 `channel?` 파라미터 추가.
- `webtoon/edit`, `video/edit`, `home-player`(Row) 편집 화면 — 저장
  버튼을 lens 번들이어도 항상 활성화하고 `channel`을 실어 보내게 바꿈.
  발행/내리기/삭제는 여전히 lens 번들에서 막아둠(이 publications 행
  전체·4포맷 공유 상태라 한 화면에서 건드리면 다른 포맷까지 같이
  바뀌거나 전부 삭제됨 — 이번 요청 범위 밖).
- 홈플레이어 팟캐스트 스코프 저장에서 실제 버그 하나 발견·수정: 그
  화면은 오디오 URL을 `body_inline.media_url`이 아니라 최상위
  `media_embed_url`로 보내는데, `_update_lens_bundle_slice()`가
  `body_inline.media_url`만 보고 있어서 그대로 두면 진실의 원천
  (admin_extra)이 "저장 전" URL로 되돌아가 버리는 문제였다. `media_embed_url`을
  우선하도록 고침.
- `_update_lens_bundle_slice()`가 반환할 때 `get()`으로 재조회하면 다른
  DB 커넥션이라 커밋 전 값을 못 보는 버그도 로컬 테스트 중 발견 —
  같은 트랜잭션(같은 cursor)에서 재조회하도록 수정.
- 실 프로덕션 글(a1f2e048-e358-4b77-9acc-59fe34a45d60, "채무조정
  실패해도 1조 추가로 빚탕감") 대상으로 웹툰/팟캐스트 스코프 저장을
  각각 테스트 데이터로 썼다가 즉시 원복, 매번 나머지 3포맷이 완전히
  그대로인지(`==` 비교) 확인한 뒤 배포.

## 결정

- 발행/내리기/삭제는 이번에 안 풀었다 — publications 행 하나가 4포맷을
  공유해서, 이 상태 전환은 웹툰 화면 하나에서 보고 누르면 사용자가
  예상 못 한 범위(레터·팟캐스트·영상까지)에 영향을 준다. 사용자가
  명시적으로 요청한 건 "저장"이지 발행 상태 변경이 아니었다.

## 다음

- 사용자가 실제 admin 화면에서 웹툰 저장 → 재확인해보는 게 최종 검증.
- 홈플레이어 화면은 웹툰/영상과 달리 원래도 저장 버튼만 잠겨 있었고
  발행/삭제는 애초에 안 잠겨 있었다 — 이번에 그 비대칭을 그대로 뒀다
  (건드리면 범위가 넓어짐).
