## 목표

*(2026-09-20 대화 정리 — 사용자 원문 인용 포함, 확인·수정 필요)*

> "백엔드.. cms 단에서.. 관리자가 설정한값이... 자동화파이프라인에
> 실시간으로 적용이 되는 구조를 설계하는 것을 원합니다... 웹툰 cms
> 관리자 페이지에서, 관리자가 설정한 프롬프트와 모델, 등의 설정값을
> 설정한다,. 그리고, 그것을 저장하면, 자동화 파이프라인에 실시간으로
> 적용된다."

1. **구조적 목표** — 관리자가 admin 화면에서 (1) 프롬프트 내용, (2)
   이미지 모델 선택, (3) 파이프라인 동작 옵션(인물고정·화풍전이 등)을
   저장하면, **코드 수정·재배포 없이** 다음 자동화 파이프라인 실행부터
   그 값이 그대로 쓰여야 한다.
2. **선행 원칙**(이미 여러 세션에 걸쳐 반복 확인된 요구) — "관리자가
   화면에서 저장한 프롬프트만이 생성을 통제해야 하고, 화면에 안 보이는
   곳에서 내용이 바뀌면 안 된다." 이번 목표는 이 원칙을 admin 실험
   패널 밖의 **실제 발행 파이프라인까지** 넓히는 것.
3. **작업 순서 지시**(2026-09-20) — 설계보다 정리(리팩토링)가 먼저.
   "불필요한 과정이나 중복된것이나, 헤비한 코드들을 심플하게
   리팩토링하고 clean 하게 만드는걸 먼저" 한 뒤, 그 위에서 설계를
   고정한다.

## 이상적인 사용자 흐름 (기획 관점)

*(2026-09-20 대화 정리 — 개발 용어 대신 관리자가 겪는 경험 기준. 여기서
"사용자"는 서비스 최종 독자가 아니라 **웹툰 CMS를 운영하는 관리자**를
가리킨다.)*

### 기존 방식 — 지금 관리자가 실제로 겪는 경험

시나리오: 관리자가 "요즘 웹툰 인물 그림체가 별로다, 다른 AI 모델로
바꿔보고 싶다"고 생각한다.

1. admin 화면의 실험 패널에서 여러 AI 모델로 이것저것 그려보고 비교한다.
2. "이거다" 싶은 조합을 찾는다.
3. 여기서 끝난다 — **이 발견을 실제 자동 발행에 반영할 방법이 관리자에게
   없다.** 개발자에게 요청해 코드를 고치고 재배포해야 실제 기사에
   반영된다.
4. 즉 "관리자가 찾아낸 답"과 "실제로 서비스에 쓰이는 답" 사이에 사람
   (개발자)과 배포 과정이 끼어 있다.

프롬프트 문구(대사 톤, 화풍 설명)는 이미 이 문제가 없다 — 저장하면 다음
기사부터 바로 반영된다. **문제는 "어떤 AI 모델을 쓸지", "인물을
고정할지" 같이 문구가 아닌 설정값만 여전히 개발자를 거쳐야 한다는 것.**

### 이상적인 파이프라인 — 관리자 여정

1. 관리자가 CMS의 웹툰 설정 화면에 들어간다.
2. 프롬프트 문구뿐 아니라 "어떤 모델로 그릴지", "인물을 고정할지"
   같은 항목을 화면에서 버튼·드롭다운으로 직접 고른다 — 코드를 몰라도
   되는 화면.
3. "저장"을 누른다.
4. 그 순간부터 자동화 시스템이 다음 기사부터 그 설정을 그대로 쓴다 —
   개발자 호출도, 재배포도, 대기 시간도 없다.
5. 며칠 써보고 "역시 아니다" 싶으면 다시 화면에서 바꾸고 저장만 하면
   된다.

### 왜 이래야 하는가

- 웹툰은 사람이 한 건씩 확인·발행하는 게 아니라 **자동으로 계속
  찍혀나오는 서비스**다. 관리자가 더 나은 설정을 찾아도 반영까지
  시간이 걸리면, 그 사이 나오는 기사는 계속 낮은 품질로 발행된다.
- "실험은 화면에서, 반영은 개발자가"라는 구조는 관리자를 병목으로
  만든다. 콘텐츠 품질 판단은 관리자가 하는데, 그 판단을 실행에 옮기는
  열쇠는 개발자가 쥔 셈이다.
- 원칙: **"CMS 화면이 곧 제어판이고, 자동화 파이프라인은 그 제어판이
  지금 가리키는 값을 그대로 따라가는 실행기여야 한다."** 지금은
  파이프라인이 제어판의 절반(문구)만 보고, 나머지 절반(모델·옵션)은
  제어판과 무관하게 코드에 박힌 대로 움직인다.

## 구조 도식화

관리자가 CMS에 저장한 값이 실제로 어디까지 흘러가는지 — "이미
실시간인 경로"(실선)와 "저장할 곳조차 없는 경로"(점선)를 나눠 그린다.
2026-09-20 코드 직접 대조로 확인(추측 없음, 근거는 [01-현재구조] 참고).

```text
[admin CMS 화면] 관리자가 프롬프트/모델/옵션을 저장
   │
   ├─(프롬프트 텍스트 — 스크립트 22챕터, STYLE, CHARACTER_FEMALE/MALE)
   │  ▼
   │  lens-cms-api(PostgreSQL, "published"로 저장)
   │  │
   │  ├──▶ [admin 챗랩] 매 기사 처리마다 prompts_repo.get_prompt()로
   │  │      fresh 조회, 캐시 없음                        ✅ 실시간
   │  │
   │  └──▶ [발행 파이프라인] ddb_prompt.load_prompt()가 lens-cms-api
   │         공개 엔드포인트를 매 기사 처리마다 HTTP로 직접 조회      ✅ 실시간
   │
   └╌(이미지 모델 선택 / 인물고정·화풍전이 옵션)
      ╌▶ ★ 저장할 곳 자체가 없음 — DB 문서·설정 테이블 미존재
         │
         ├──▶ [admin 실험 패널] 요청 body 파라미터로만 존재(저장 안
         │      됨) — 매 요청마다 프론트가 값을 실어 보내야 함        △ 요청 단위
         │
         └╌╌▶ [발행 파이프라인] pipelines/webtoon/pipeline.py:86
                IMAGE_PROVIDER = "bedrock-style-transfer" (코드 상수)
                바꾸려면: 코드 수정 → Docker 재빌드(ARM64) → ECR push
                → ECS task definition 새 리비전                    ❌ 코드+재배포 필요
```

**요약**

| 값 | 저장 위치 | admin 챗랩 | 발행 파이프라인 |
|---|---|---|---|
| 스크립트 프롬프트(22챕터) | lens-cms-api(PostgreSQL) | ✅ 실시간 | ✅ 실시간 |
| STYLE / CHARACTER 텍스트 | lens-cms-api(PostgreSQL) | ✅ 실시간 | ✅ 실시간 |
| 참조 이미지(화풍/인물) | S3 정본 키 | ✅ 실시간(화풍 60초 캐시) | ✅ GPU 기동 시 재동기화 |
| 이미지 모델 선택 | 없음 | △ 요청 파라미터(저장 안 됨) | ❌ 코드 상수 |
| 인물고정/화풍전이 옵션 | 없음 | △ 요청 파라미터(저장 안 됨) | ❌ 코드에 옵션 자체가 없음 |

[정리후보 A](02-정리후보/01-모델디스패치중복.md)가 이 표의 마지막 두 행이
막힌 근본 원인(admin과 발행 파이프라인의 모델 디스패치 로직이 서로 다른
구현) — 03_설계는 이 표를 전부 ✅로 만드는 게 목표.
