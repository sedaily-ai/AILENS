# CHANGELOG — AI LENS DB 설계 버전 이력

이 폴더(`lens-erd-src/`) 전체가 어떤 순서로, 왜, 어떤 성과를 내며
쌓여왔는지 한눈에 보는 문서다. 각 항목의 "근거"는 `docs/worklog/`의 해당
날짜 파일 — 여긴 요약만, 전체 경위는 worklog에서 읽는다.

**규칙**: 의미 있는 설계 변화(스키마 결정, 실측 결과, 방향 전환)가 생기면
이 파일 맨 위(최신이 위)에 항목을 추가한다. 지나간 항목은 고치지 않는다 —
"그때는 이렇게 판단했다"가 기록의 가치라, 나중에 틀린 게 밝혀져도 취소선
+ 정정 링크만 추가하고 원문은 남긴다.

## v1.1 — DynamoDB 베이스라인 확보 (2026-09-08 오후)

**왜**: Postgres 이관 후 "빨라졌다"를 숫자로 증명하려면 이관 전 기준선이
있어야 하는데 없었다.

**한 것**: 실 프로덕션 DynamoDB(계정 887078546492, us-east-1) 실측 — 테이블
규모, CloudWatch 지연시간, curl 종단간 응답, 2일 소비 용량. → `15-baseline-benchmark.md`

**성과(비포 수치 확보)**:
| 측정 | 값 |
|---|---|
| DynamoDB 자체 처리(Query, 평균) | 15~22ms |
| 종단간 API 응답(`channel=lens&limit=1000`) | 5.57초 |
| 종단간 API 응답(`channel=webtoon&limit=1000`) | 2.89초 / 603KB |
| cms-posts 2일 소비 | 읽기 20,431 / 쓰기 23,137 |

**배운 것**: DB 엔진 지연(15~30ms)과 종단간 응답(1.2~5.6초) 사이 100배
가까운 격차 — 병목이 DynamoDB가 아니라 애플리케이션 레이어(스캔 후 필터링,
큰 페이로드)에 있다는 09-07 항목의 결론을 실측으로 재확인. **이 격차가
Postgres 이관 후 줄어드는지가 이관 성공의 실질 지표**로 채택.

관련 커밋: `02cf0ea` · worklog: `2026-09-08-postgres-schema-단계별-설계.md` (후속 3)

## v1.0 — 논리·물리 설계 확정 (2026-09-08)

**왜**: 09-01 ERD 초안이 "추정" 40여 곳을 안은 채였고, 작성자 본인이 미해결
이슈 2건(웹툰 시리즈, ai_usage_logs 배타 CHECK)을 남겨뒀다. 정석 순서
(개념→논리→물리)로 검증해달라는 요청.

**한 것 (시행착오 포함, 숨기지 않고 남긴다)**:
1. 처음엔 원본 정의서 없이 논리적 추론만으로 이슈 2건에 "해결책"을 만들어
   커밋(`2251642`) — **이게 오류였다**. `ai_usage_logs`를 배타 FK로 잘못
   전제해 `subject_type+subject_id`로 구조를 바꿨고, `users.deleted_at`을
   임의로 추가했다.
2. 로컬에서 원본 `lens_schema_2026-08-26.sql`(50테이블 완성 DDL)을 찾아냄 —
   탐색 중 이름이 비슷한 다른 프로젝트 정의서(en.sedaily.com)를 잘못
   짚었다가 테이블 구성으로 걸러냄.
3. 원본 전체와 12개 도메인 파일을 1:1 대조 — 1번의 오류 2건 원복 +
   이전 작성자의 "추정" 작업에서 나온 실제 오류 다수 발견·수정(컬럼명 오류,
   컬럼 누락, `prompts`/`audit_logs` 등 테이블 목적 자체를 잘못 추측한
   경우까지). 원본 SQL을 레포에 영구 보관(`lens_schema_2026-08-26.sql`).
   → 커밋 `1057956`
4. 물리 설계 — 원본에 이미 정의된 인덱스·파티셔닝 전체를 옮기고 실제
   DynamoDB 접근 패턴(2026-09-07 조사)과 대조 검증. → `13-physical-design.md`
5. 원본에 조건부로 남아있던 기술 결정 3건을 AWS 확장 지원 확인 후 확정
   (pg_bigm, pg_partman, view_counts 권한분리). → `14-operations.md`,
   커밋 `27d96f0`

**성과**: 개념·논리·물리 3단계 설계가 원본과 완전히 일치하는 상태로 확정.
미해결은 회원 탈퇴 삭제 정책 1건(법무 판단 필요)만 남음.

**배운 것**: 원본 문서 없이 "논리적으로 맞는 것 같은" 결정을 내리면 있지도
않은 문제를 고치게 된다 — 정의서 대조 작업은 반드시 원본 확보가 먼저다.

## v0.3 — DynamoDB 성능 사고와 실제 개선 (2026-09-07)

**왜**: 발행글이 쌓일수록 모든 목록 조회가 느려지는 구조적 문제 — GSI가
채널 구분 없이 발행글 전체를 읽은 뒤 애플리케이션에서 필터링하고 있었다.

**한 것**: `channel-publish_date-index` 신규 GSI 생성 + 기존 3,551건 백필,
`CMS_LIST_INDEX_MODE` 환경변수로 즉시 롤백 가능한 컷오버.

**비포/애프터 (실측)**:
| 지표 | 이관 전 | 이관 후 | 개선율 |
|---|---|---|---|
| `channel=lens` 응답 | 9.8초 | 6.0~6.2초 | ~40% |
| webtoon 목록 응답 | 8~10초 | 2.9~4.4초 | 60~70% |
| webtoon 페이로드 | 3.2MB | 604KB | ~81% |

**부수 사고**: IAM 정책에 신규 GSI ARN을 빠뜨려 전체 목록 API 500 사고 발생
→ env 스위치 덕에 즉시 롤백. (이게 나중에 "AI로 DB 작업할 때 사람 승인
필요" 원칙의 실증 사례가 됨.)

**이 프로젝트에서 갖는 의미**: 이 시점 실측이 지금 Postgres 설계의 물리
설계 절(§v1.0)이 참조하는 "실제 DynamoDB 접근 패턴"의 원천 데이터다 —
채널+발행일 범위 조회 패턴이 여기서 처음 정량적으로 확인됐다.

관련 커밋: `5b55aa9` · worklog: `2026-09-07-cms-posts-channel-gsi-migration.md`

## v0.2 — PostgreSQL ERD 문서화 (2026-09-01)

**왜**: `lens_schema_2026-08-26.sql`(원본 DDL)이 있었지만 테이블별 컬럼
명세는 촘촘한 데 비해 관계(FK·카디널리티·삭제정책)가 글로만 정리돼 있어
파악이 어려웠다.

**한 것**: Mermaid ERD 소스 14개(도메인별 12장 + 전체 위상도 + 렌더설정) +
SVG 인라인 HTML 열람본 작성. 작성자(minyoung0303)가 두 가지 논의 필요
이슈를 커밋 메시지에 직접 남김: 웹툰 시리즈 엔터티 부재, `ai_usage_logs`
배타 CHECK와 탈퇴 정책의 잠재 충돌.

**성과**: "정의서는 있지만 관계가 안 보인다"는 문제를 시각 자료로 해결.
다만 원본 SQL과의 전수 대조는 이 시점엔 없었다(→ v1.0에서 발견된 40여 곳
오류의 원인).

관련 커밋: `7d836dd`(ERD 소스), `a0c6559`(HTML)

## v0.1 — PostgreSQL 스키마 원본 설계 (2026-08-26)

**왜**: DynamoDB 오버로드 단일 테이블 구조를 관계형으로 정규화 이관하기
위한 6단계 설계 산출물.

**한 것**: `lens_schema_2026-08-26.sql` — 50테이블·뷰1·확장3(pg_trgm,
btree_gin, vector). 이 레포 밖(외부 정의서 작성 과정)에서 만들어졌고,
2026-09-08에 레포로 편입됨(`lens_schema_2026-08-26.sql`, 커밋 `1057956`).

**설계 당시 이미 반영된 실무 판단**:
- 파티션 키를 PK에 포함(`ai_usage_logs`, `view_events`) — Postgres
  네이티브 파티셔닝 제약을 정확히 앞서서 반영
- 한국어 검색·파티션 운영 자동화를 "확인 필요" 조건부로 명시적으로
  남겨둠(추측으로 채우지 않음) → v1.0에서 확정
- `view_counts.real_count`를 "제약으로 표현 불가, DB 권한으로 처리"라고
  명시 → v1.0에서 구체 GRANT문으로 완성

이 원본이 이후 모든 버전의 기준선이다 — v0.2~v1.1은 전부 이 파일을
검증·시각화·완성해가는 과정이었다.
