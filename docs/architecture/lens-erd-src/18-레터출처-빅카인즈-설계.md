# 18. 이슈 레터 출처 — 빅카인즈 검색 + 보관 기사 (설계 + 구현 완료·미배포, 2026-10-09)

## 1. 문제와 결정

| | 내용 |
|---|---|
| 문제 | 레터 출처를 우리 기사 DB(`articles`)에서만 찾을 수 있었다. 그런데 이 DB는 2026-02-02부터 19,932건뿐이고, 하루 50건 저장 상한(매일 원본 450건 안팎 중 50건)과 2026년 3월 공백이 있다. 라네즈 레터의 핵심 근거 기사(`20099230`)도 이 DB에 없어 발행하지 못했다 |
| 기존 | 후보 검색 = 우리 DB 키워드 검색(최신순). 출처 = `articles` 참조 또는 승인된 외부 URL |
| 결정 | 후보 검색은 **빅카인즈 하나로 픽스**(1990~어제, provider=서울경제, 관련도순). 편집자가 고른 기사를 `external_archives`에 보관하고, 레터 출처는 그 보관 기사를 가리킨다. 빅카인즈가 서울경제로 돌려준 기사는 서울경제 기사로 인정 |
| 이유 | 범위·정렬이 우위, 이미 운영 중인 검색(타임머신)이 있어 새로 만들 것이 적음, 레터가 `articles`에 의존하지 않게 되어 그 테이블을 나중에 폐기할 수 있음 |

## 2. 흐름

```
편집자 → (1) 키워드·기간 검색 ──► 빅카인즈(타임머신 공개 API, 관련도순)
       → (2) 결과에서 고르기 ──► "후보로 담기": 서버가 external_archives 에 보관 (제목·날짜·원문 링크·미리보기)
       → (3) "제목 | 주소" 복사 ──► 템플릿 v2 의 후보 기사 목록에 붙여 넣기 → AI 가 저장용 JSON 생성
       → (4) JSON 붙여넣어 저장 ──► 서버가 출처 주소를 보관 기사(url_key)와 대조해 연결, 없으면 거부
```

(4)의 대조가 안전장치다. 검색 단계를 거쳐 보관된 기사만 출처가 되므로, AI가 지어낸 주소는 저장되지 않는다.

## 3. 저장 대응

| `external_archives` 컬럼 | 빅카인즈 응답 |
|---|---|
| `provider` | 고정값 `bigkinds` |
| `external_id` | `news_id` |
| `published_at` | `published_at` |
| `title` | `title` |
| `press` | `서울경제` |
| `reporter_name` | `byline` |
| `summary` | `content` 앞 150자 미리보기(본문 전문 아님) |
| `source_url` | `provider_link_page` |
| `url_key` (신규, 생성 컬럼) | `source_url`에서 `?ref=…` 제거 — 대조 키 |

## 4. DB 변경 (v1.40, 추가만)

- `external_archives.url_key` + 인덱스, 앱 권한(SELECT·INSERT·UPDATE)
- `issue_letter_sources.archive_provider`, `archive_id` + `external_archives` FK(RESTRICT)
- 출처 종류 제약: 기존(articles / 외부 URL) 또는 보관 기사 중 정확히 하나
- 로컬 Postgres 16에서 적용·재적용·위반 거부·앱 권한 검증 완료. 운영 적용은 마스터 계정으로 사용자 실행
- **2단계 전환**: v1.40은 추가만 한다. 부캉이의 출처 4건(현재 `articles` 참조)을 보관 기사로 옮긴 뒤, v1.41에서 `articles`·외부 URL 칸을 제거한다

## 5. API·화면 변경

| 영역 | 변경 |
|---|---|
| 서버 | `POST /admin/issue-letters/archives`(고른 기사 보관, upsert, 건당 검증·최대 30건). 출처 해석: 주소 → `external_archives.url_key`. 기존 `articles` 참조는 전환 기간에만 유지. 공개 상세의 출처는 보관 기사의 제목·주소를 읽음(매체명 "서울경제") |
| 관리자 API | `POST /admin/issue-letters/archives` 라우트 추가, `GET /candidates`(우리 DB 검색) 삭제 — API Gateway 라우트도 같이 교체 |
| 관리자 화면 | 검색 칸이 빅카인즈를 호출(검색어, 기간 프리셋 최근 1·3·6년 + 직접 입력, 정렬 관련도/최신, 최대 20건). 선택 → "후보로 담고 복사" 한 번에. 6년을 넘는 과거는 기간을 옮겨 다시 검색 |
| 오류 처리 | 빅카인즈 장애·오류는 화면에 사유 표시(대체 검색 없음) |

## 6. 위험·한계

| 항목 | 내용 |
|---|---|
| 외부 의존 | 빅카인즈 장애·호출 한도(한도는 미확인). 이미 보관한 기사는 장애 중에도 레터에 쓸 수 있다 |
| 주소 형식 | 과거 기사의 원문 링크는 `http://www.sedaily.com/NewsView/<ID>` 형식이고 최근 기사는 `https://www.sedaily.com/article/<번호>?ref=…` 형식이다. 모두 서울경제 도메인(2026-10-09 80건 표본 확인). 처음에 "이데일리 주소"라고 적은 것은 출력의 끝 30자만 보고 `sedaily.com`을 `edaily.com`으로 오독한 것이어서 정정한다. 기사 번호를 주소에서 뽑는 코드는 두 형식을 모두 처리해야 한다 |
| 본문 | 보관은 제목·미리보기·링크뿐. 레터 작성 AI는 링크를 직접 열어 읽는다 |
| 신뢰 경계 | 보관 요청은 로그인한 관리자만 가능. 서버는 빅카인즈를 직접 호출하지 않아(키 없음) 관리자가 검색 결과를 보냈다는 것을 신뢰한다 |

## 7. 구현 순서

1. v1.40 적용(사용자, 마스터 계정)
2. 서버: 보관 API + 출처 해석 + 공개 상세 읽기 + 테스트 → 배포
3. 관리자 백엔드 라우트 교체 + API Gateway 라우트 교체
4. 관리자 화면: 검색 칸 교체
5. 부캉이 출처 4건을 빅카인즈 검색으로 보관 후 재연결, 라네즈를 `20099230`·`20099214` 등으로 다시 구성
6. v1.41: 정리(`articles` 의존 제거)
