# lens-erd-src — PostgreSQL 스키마 설계 소스

DynamoDB에서 PostgreSQL로의 이관을 검토하며 만드는 스키마 설계 소스. 아직
프로덕션에 반영된 스키마가 아니다 — `docs/architecture`의 다른 문서와 달리
"지금 시스템"이 아니라 "이관 대상으로 검토 중인 설계"를 담는다. 렌더 결과물은
`../lens-postgres-erd.html`.

## 설계는 세 단계로 나눠 진행한다

교과서적 DB 설계 순서(개념 → 논리 →물리)를 그대로 따른다. 단계를 섞으면
"이 결정이 비즈니스 규칙인지 성능 최적화인지" 구분이 안 돼서 나중에 왜
이렇게 됐는지 추적이 안 된다.

| 단계 | 다루는 것 | 소스 | 상태 |
|---|---|---|---|
| **개념 설계** | 엔터티·관계만. DBMS 종류에 안 묶임 | `00-map.mmd`(영역 지도) + `01-12` 도메인별 다이어그램 | 12개 도메인 확정. 원본 정의서(`lens_schema.sql`, 2026-08-26) 대조는 미완료 |
| **논리 설계** | 정규화, PK/FK, CHECK 제약 | `01-12`(컬럼·제약) + `99-full.mmd`(전체 위상도) | 진행 중 — 해결된 이슈와 미해결 이슈는 아래 참조 |
| **물리 설계** | 인덱스, 파티셔닝, 페이지네이션 | `13-physical-design.md` | 실제 DynamoDB 접근 패턴 조사 기반 초안 |

**결정 경위(왜 이렇게 정했는가)는 이 폴더가 아니라 worklog에 있다** —
`docs/worklog/2026-09/2026-09-08-postgres-schema-단계별-설계.md`. 이 폴더는
결과(지금 설계가 어떤 모습인가)만, worklog는 과정(왜 이 모습이 됐는가)만 담는다.

## 논리 설계에서 해결한 이슈 (2026-09-08)

- **회원 탈퇴 = 소프트 삭제**로 확정. `users.deleted_at` 추가, `status='withdrawn'`
  시점엔 CASCADE가 발동하지 않는다. 법정 보존기간 경과 후 별도 하드 삭제
  배치가 돌 때만 실제 CASCADE가 일어난다. → `06-users.mmd`
- **`ai_usage_logs`의 배타적 FK(rendition_id/message_id/candidate_id 중 하나만)를
  폐기**하고 `subject_type + subject_id`(비FK, 앱이 참조무결성 보장)로 변경.
  배타 FK + CHECK 조합이 대상 테이블의 CASCADE/SET NULL 삭제 정책과 구조적으로
  충돌하기 때문(회원 하드 삭제 시 비용 원장이 같이 지워지거나 CHECK를
  위반하는 문제). → `11-pipeline.mmd`
