# 웹툰 독자 지표 계측 (GA4)

갱신: 2026-10-03. 목적: 웹툰 표시 방식을 바꾼 효과(기존 v1 vs 웹툰식 v2)를 "느낌"이 아니라 숫자로 비교한다. 구현은 서비스 프론트 `shared/lib/tracking/`, 전송은 기존 GA4(`trackEvent`, 측정 ID는 `app/layout.tsx`).

## 1. 이벤트

| 이벤트 | 언제 | 파라미터 |
|---|---|---|
| `webtoon_start` | 첫 컷이 화면에 절반 이상 보인 순간(글당 1회) | article_id, variant, total_cuts |
| `webtoon_cut_view` | 각 컷이 절반 이상 보인 순간(컷당 1회) | article_id, variant, total_cuts, cut_index |
| `webtoon_complete` | 마지막 컷(핵심 정리 카드 포함)에 도달한 순간(1회) | article_id, variant, total_cuts, reached(그때까지 본 컷 수), elapsed_s(시작부터 초) |
| `webtoon_cta_click` | 웹툰 끝의 "레터로 더 자세히 읽기" 클릭 | article_id, variant, target(letter) |
| `format_switch`(기존) | 레터·웹툰·팟캐스트·영상 탭 전환 | 기존 |

variant: `v2` = 웹툰식 말풍선 + "핵심 정리" 카드가 붙은 글(이미지 캡션 "핵심 정리"로 판별, `webtoonVariant()`), `v1` = 그 이전 방식. 별도 DB 필드는 없다.

"본 것"의 기준은 IntersectionObserver threshold 0.5(절반 이상 보임)다. 스치기만 한 컷은 세지 않는다.

## 2. 지표 정의

- 시작 수 = `webtoon_start` 이벤트 수
- 컷 n 도달률 = (`webtoon_cut_view` where cut_index = n) / 시작 수 → 컷별 이탈 지점이 보인다
- 완주율 = `webtoon_complete` / 시작 수
- 평균 완주 시간 = `webtoon_complete`의 elapsed_s 평균(너무 짧으면 훑어 넘김, 너무 길면 막힘)
- 이어 읽기율 = `webtoon_cta_click` / `webtoon_complete`(웹툰을 끝까지 본 사람이 레터로 이어 가는 비율)
- 비교는 variant별로 같은 지표를 나란히 본다.

## 3. GA4에서 등록할 것 (한 번만 설정, 등록한 시점부터 집계 — 과거 데이터에는 소급 안 됨)

한도: 표준 속성은 이벤트 범위 맞춤 측정기준 50개, 맞춤 측정항목 50개, 사용자 범위 25개. 아래 목록은 합쳐도 20개 안쪽이다. 같은 의미의 기본 측정기준이 있는 값(페이지 경로 등)은 등록하지 않는다(한도만 쓴다). 값의 종류가 아주 많은 항목(글 ID, 레터 ID)은 보고서에서 "(other)"로 묶이므로 등록해도 쓸모가 적다 — 글별 분석은 기본 측정기준 "페이지 경로"로 한다.

관리 > 맞춤 정의 > 맞춤 측정기준 만들기 (범위: 이벤트)

| 측정기준 이름 | 이벤트 매개변수 | 쓰이는 이벤트 | 용도 |
|---|---|---|---|
| 웹툰 방식 | variant | webtoon_* | v1 기존 / v2 웹툰식 비교(가장 중요) |
| 웹툰 컷 번호 | cut_index | webtoon_cut_view | 컷별 도달률(이탈 지점) |
| 웹툰 총 컷 수 | total_cuts | webtoon_* | 8컷/9컷(카드 포함) 구분 |
| 카테고리 | category | webtoon_*, format_switch, source_link_click | 증시·부동산 등 주제별 반응 비교(2026-10-03부터 실림) |
| 형식 | format | media_progress, source_link_click | 레터·웹툰·팟캐스트·영상별 비교 |
| 이전 형식 | from_format | format_switch | 어떤 형식에서 넘어왔나 |
| 이동한 형식 | to_format | format_switch | 어떤 형식으로 넘어갔나(형식 전환율) |
| 미디어 진행률 | pct | media_progress | 팟캐스트·영상 25/50/75/100% |
| 유입 출처 | source | session_source | utm 출처별(직접·검색·SNS) |
| 지표 이름 | metric_name | web_vitals | LCP/INP/CLS/FCP/TTFB 구분 |
| 지표 등급 | metric_rating | web_vitals | good/needs-improvement/poor |
| 스크롤 깊이 | percent_scrolled | scroll(GA4 기본 이벤트) | 기사 읽기 깊이(기본 측정이 켜져 있을 때 자동 수집, 90% 도달 시 1회) |
| 이어 읽기 대상 | target | webtoon_cta_click | 웹툰 끝에서 어디로 이어 갔나(현재 letter) |
| 게임 | game | game_open, game_play_open | 게임별 |

맞춤 측정항목 (범위: 이벤트)

| 측정항목 이름 | 이벤트 매개변수 | 단위 | 용도 |
|---|---|---|---|
| 웹툰 완주 시간 | elapsed_s | 초(표준) | 시작부터 마지막 컷까지 걸린 시간 — 평균으로 본다 |
| 웹툰 도달 컷 수 | reached | 표준 | 완주 시점에 실제로 본 컷 수(건너뛴 컷 확인) |
| 웹 바이탈 값 | metric_value | 표준 | 반드시 "지표 이름"으로 필터해서 본다(LCP는 ms, CLS는 소수) |
| 용어 풀이 수 | terms | 표준 | 레터에서 풀어 본 용어 개수(letter_term_explain) |

등록하지 않는 것: editor(에디터 페이지를 삭제해 값이 오지 않음, 2026-10-03), article_id, letter_id(값이 너무 많음), page_path(기본 측정기준과 중복), gender·surface(compat_input, 개인 성격이 있는 입력이라 보고서에 올리지 않는다).

관리 > 이벤트에서 "주요 이벤트(key event)"로 표시: webtoon_complete, webtoon_cta_click, letter_complete, newsletter_subscribe. 완주·이어 읽기·구독이 서비스의 목표 행동이기 때문이다.

관리 > 데이터 설정 > 데이터 보관에서 이벤트 데이터 보관 기간을 2개월(기본)에서 14개월로 바꾼다 — 탐색(자유 형식) 보고서는 보관 기간을 넘은 데이터를 못 보여 주므로, 전·후 비교를 몇 달에 걸쳐 하려면 필수다.

BigQuery 내보내기(관리 > 제품 링크): 표준 속성도 일 단위 내보내기는 무료다(저장 비용은 소액). 켜 두면 GA4 화면의 한도(맞춤 정의 개수, 보관 기간, (other) 묶음)에 막히지 않고 SQL로 글별·컷별 분석을 할 수 있다. 맞춤 정의 없이도 모든 이벤트 매개변수가 들어 있다.

탐색 > 자유 형식 보고서 예: 행 = 웹툰 방식, 값 = 이벤트 수, 필터 = 이벤트 이름이 webtoon_start / webtoon_complete / webtoon_cta_click 중 하나. 컷별 도달률은 행 = 웹툰 컷 번호, 필터 = webtoon_cut_view, 열 = 웹툰 방식.

## 3-1. Microsoft Clarity 연동

- 설치 완료(2026-10-03): 프로젝트 ID `x8tf88chwu`, `service/frontend/src/app/layout.tsx`의 `<Script id="clarity-init" strategy="lazyOnload">`. 설치 전에는 사이트 HTML과 저장소에 스니펫이 없었다. 실제 사이트에서 스크립트 로드와 아래 연동(태그 `category`·`format`·`variant`, 이벤트 `format_switch`·`webtoon_complete`·`webtoon_cta_click`)을 헤드리스 브라우저로 확인했다. 태그는 값이 바뀔 때만 보낸다(호출 수 제한 대비).
- 코드 준비는 끝났다: `trackEvent`가 GA4로 보내는 이벤트 중 목표 행동(`webtoon_complete`, `webtoon_cta_click`, `newsletter_subscribe`, `letter_complete`, `format_switch`)을 Clarity 이벤트로도 보내고, `variant`·`category`·`format` 값을 세션 태그로 올린다. 스니펫이 없으면 아무 일도 안 한다.
- 설치 후 Clarity에서 하는 일: 필터에서 태그(variant=v2 등)와 이벤트(`webtoon_complete` 없음 = 중간 이탈)로 세션 녹화를 골라 본다. 웹툰 컷 어디에서 스크롤이 멈추는지, 말풍선·나레이션 띠 구간에서 반응이 있는지는 GA4 숫자로 알 수 없는 부분이라 녹화와 히트맵(스크롤 맵)이 보완한다.
- 설치 시 주의: 모바일 LCP를 지키기 위해 `next/script`의 `lazyOnload`로 늦게 불러온다. 입력창 내용은 Clarity가 기본으로 가린다(이메일 구독 입력 포함, 설정에서 마스킹 유지). 쿠키 동의 정책은 서울경제 방침을 따른다.
- GA4 연동: Clarity 설정 > Google Analytics 연동을 켜면 GA4 세션에서 Clarity 녹화로 바로 이동할 수 있다(Clarity 쪽 설정, 사용자가 수행).

## 4. 해석 시 주의

- v1 글과 v2 글은 기사 내용도 다르다. 주제·길이 차이가 섞이므로 처음 일주일은 방향만 보고, 같은 카테고리끼리 비교한다.
- v2는 컷 수가 9개(카드 포함)다. 완주율 비교는 total_cuts 차이를 감안해 "마지막 본문 컷(8번)까지 도달률"도 같이 본다(컷 8 도달률).
- 표본이 적으면(웹툰 시작 수 글당 수십 건 이하) 비율이 흔들린다. 글 여러 개를 합쳐서 본다.
- 이미 발행된 v1 글을 새 방식으로 다시 만들면(재생성) 그 글의 전·후를 같은 글에서 비교할 수 있다. 3개 글(더휴식·삼성전자·코스피)은 2026-10-02 밤에 재생성했다.

## 5. 검증 방법

- 배포 후 GA4 실시간 보고서 또는 DebugView에서 `webtoon_start`, `webtoon_cut_view`, `webtoon_complete`, `webtoon_cta_click`이 variant 값과 함께 들어오는지 확인한다.
- 개발 환경(`NODE_ENV !== production`)에서는 브라우저 콘솔에 `[trackEvent]`가 출력된다.
- 2026-10-03 클라이언트 쪽 검증 완료: 헤드리스 브라우저로 실제 사이트(웹툰 탭 → 9컷 스크롤 → 이어 읽기 클릭)를 돌려 `window.dataLayer`의 이벤트를 읽었다. `webtoon_start` 1, `webtoon_cut_view` 9(컷 번호 1~9), `webtoon_complete` 1(reached 9, elapsed_s 6), `webtoon_cta_click` 1, `format_switch` 2가 variant=v2, total_cuts=9, category=증시와 함께 정상 발생했다. 즉 코드는 의도대로 이벤트를 만든다.
- 남은 확인: GA4 서버가 받는지는 별도. 같은 날 사용자 본인 브라우저의 테스트 방문은 실시간 보고서에 반영되지 않았다(광고 차단 확장·내부 트래픽 필터·반영 지연 중 하나로 추정, 미확인). 확인법: 크롬 개발자도구 > 네트워크에서 `collect`로 필터 후 웹툰을 스크롤해 요청이 나가는지(빨갛게 막히면 확장 프로그램), GA4 데이터 필터의 내부 트래픽 상태.
- 주의: 2026-10-03 오전 검증용 헤드리스 방문 몇 건이 실제 GA4로 전송됐을 수 있다(이벤트 전송을 가로채려 했으나 요청 주소가 달라 막히지 않았을 가능성). 이 날의 웹툰 이벤트에 소량의 합성 세션(HeadlessChrome)이 섞일 수 있으니, 수치가 작은 초기 비교에서는 10/3분을 제외하거나 감안할 것.
