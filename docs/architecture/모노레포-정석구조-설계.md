# 모노레포 정석 구조 설계 — 네이티브 앱 + 웹 + 백엔드

작성: 2026-10-13. 전제: 네이티브 앱 100만 다운로드 규모. 판단 기준은 효율·마이그레이션 비용이 아니라 **운영 안정성과 확장성**. 효율을 위해 정석을 깎지 않는다.

## 결론 먼저

- 레이아웃 정석: 최상위를 `apps/`(배포 단위) + `packages/`(공유 코드) + `services/`(백엔드) + `infra/`(IaC) + `docs/` 5개 네임스페이스로 재편한다.
- 지금 평면 나열(`service/`, `mobile/`, `mobile-capacitor/`, `admin/`, `pipelines/`)은 앱·서비스가 늘면 깨진다 — 정석 2계층(`apps/`·`packages/`)으로 모은다.
- 공유 코드(API 클라이언트·도메인 타입·인증)는 프론트 소스에 묶여 있어 앱이 못 쓴다 — `packages/`로 승격해 웹·앱이 한 소스를 쓰게 한다.
- 네이티브 산출물(APK·AAB·keystore)은 git에서 제외한다. 서명키는 저장소가 아니라 비밀 관리 채널·CI 시크릿에 둔다.

## 현재 상태 (2026-10-13 실측)

| 항목 | 사실 |
|---|---|
| 웹 | `service/frontend` Next.js 16 + React 19, CloudFront→ECS Fargate |
| 공개 API | `service/lens-cms-api` EC2(PM2), `service/backend` 레거시 Lambda. 경로 `/api/v2/*` |
| 인증 | AWS Cognito 사용 중(`shared/lib/auth`) |
| 앱(기존) | `mobile/` 네이티브 Android(TWA 추정) + `mobile-capacitor/` Capacitor iOS/Android. 서명 AAB까지 빌드됨 |
| 공유 후보 | `service/frontend/src/shared/lib/api`(9) · `shared/types`(2) · `shared/lib/{auth,content,date,...}` |
| 바이너리/시크릿 git 추적 | 없음. mobile-capacitor는 keystore를 .gitignore 처리 중. mobile/의 APK·keystore는 워킹트리에만 존재(미추적) |
| 모노레포 도구 | 없음(pnpm-workspace/turbo/nx 부재) |

## 정석 레이아웃

```
2_ai_lens/dev/
├─ apps/                         # 배포 단위(각자 독립 배포). "무엇을 출시하는가"
│  ├─ web/                       # ← service/frontend (Next.js)
│  ├─ mobile/                    # ← 네이티브 앱 (프레임워크는 아래 '미결' 참조)
│  │  ├─ android/
│  │  ├─ ios/
│  │  └─ src/                    # 앱 전용 코드(네비게이션, 네이티브 브릿지, 푸시 등록)
│  └─ admin/                     # ← admin/frontend (CMS)
│
├─ packages/                     # 공유 라이브러리(배포 안 함, 앱이 import). "무엇을 재사용하는가"
│  ├─ api-client/                # ← shared/lib/api + shared/config/apiClient
│  │  └─ src/                    #   REST 호출, 재시도, 토큰 주입. 웹·앱 공용
│  ├─ domain/                    # ← shared/types + shared/lib/{content,date,poll,...}
│  │  └─ src/                    #   도메인 타입·순수 로직(플랫폼 비의존)
│  ├─ auth/                      # ← shared/lib/auth (Cognito 토큰 수명주기)
│  ├─ ui-web/                    # 웹 전용 React 컴포넌트(RN이 아닌 것)
│  └─ config/                    # 공유 eslint/tsconfig/상수
│
├─ services/                     # 서버 사이드. "무엇이 돌고 있는가"
│  ├─ lens-cms-api/              # ← service/lens-cms-api (EC2)
│  ├─ legacy-lambda/             # ← service/backend (레거시 Lambda, 축소 중)
│  ├─ push/                      # ★ 신규: 푸시 토큰 등록 API + 팬아웃 워커
│  └─ pipelines/                 # ← pipelines/ (발행 자동화)
│
├─ infra/                        # IaC. 지금 CLI로 흩어진 설정을 코드로 수렴
│  ├─ ecs/  cloudfront/  cognito/  sns-push/  terraform|cdk/
│
├─ docs/                         # 현행 유지
├─ config/                       # 현행 resources.env 등(또는 infra/로 흡수)
└─ pnpm-workspace.yaml           # ★ 워크스페이스 정의(apps/* packages/* services/*)
```

### 왜 이 3분할인가 (apps / packages / services)

- `apps/` = 독립 배포 단위. 각자 자기 CI·배포 스크립트·버전을 가진다. "출시물".
- `packages/` = 배포되지 않고 `apps`가 가져다 쓰는 코드. 100만 DL에서 웹·앱이 **같은 API 계약·같은 도메인 타입**을 쓰게 하는 것이 안정성의 핵심 — 계약 불일치로 인한 런타임 깨짐을 컴파일 타임에 잡는다.
- `services/` = 서버. 앱/웹과 생명주기가 다르다(배포 리듬·스케일링 단위가 다름).
- 이 경계가 "확장성"의 실체다. 앱 하나(관리자앱 등)·서비스 하나(알림 서비스) 추가가 기존 구조를 안 흔든다.

## 공유 코드 승격 원칙

| 지금 위치 | 정석 위치 | 플랫폼 의존성 |
|---|---|---|
| `shared/lib/api/*` | `packages/api-client` | 없음(fetch 추상화) → 그대로 공유 |
| `shared/types` | `packages/domain` | 없음 → 그대로 공유 |
| `shared/lib/{content,date,poll,rss}` | `packages/domain` | 순수 로직 → 공유 |
| `shared/lib/auth` | `packages/auth` | Cognito SDK → 공유(플랫폼별 저장소만 주입) |
| `shared/ui/*` | `packages/ui-web` | React DOM → **웹 전용**, 앱은 재사용 불가 |

핵심: UI는 공유하지 않는다. 네이티브 앱 UI는 별도 구현한다(웹뷰 래핑이 아니라면). 공유하는 것은 **UI 아래의 모든 것**(계약·타입·로직·인증).

## 푸시 — services/push 신설

```
앱(푸시 토큰) ──register──▶ services/push: POST /push/register
                                   │  push_tokens(user_id, token, platform, updated_at)
발행 트리거 ──▶ 팬아웃 워커 ──배치──▶ AWS SNS Platform Application ──▶ FCM / APNs
   (pipelines 재사용)        (레이트리밋·무효토큰 정리)
```

- 100만 대상 발송은 토큰 관리(만료·교체·무효 정리)와 배치 팬아웃이 본체다. 뉴스레터 발송 로직 재사용, 채널만 푸시 추가.
- 발송 경로 결정(SNS Mobile Push vs FCM 직결)은 별도 설계 문서로 분리한다.

## 미결 — 앱 프레임워크 (이 설계와 독립)

폴더 정석은 프레임워크와 무관하게 위 구조로 간다. `apps/mobile/` 내부만 프레임워크 선택에 따라 달라진다.

- Expo(React Native): 네이티브 렌더·OTA·EAS. 100만 DL 성능 유리. 기존 Capacitor 투자 버림.
- Capacitor 유지: 웹뷰 래핑. 기존 서명·빌드 재사용. 리스트·스크롤·푸시 UX가 웹뷰 한계.

운영 안정성·확장성 우선이라면 Expo가 정석에 더 가깝다(네이티브 성능·OTA 핫픽스). 단 전환 비용이 크므로 별도 결정 문서로 다룬다.

## 전환 순서 (정석 유지, 무중단)

1. `pnpm-workspace.yaml` 추가 + `packages/` 뼈대 생성.
2. 공유 코드를 `packages/{api-client,domain,auth}`로 이동, 웹은 import 경로만 교체(동작 불변 — 특성화 테스트로 보증).
3. `service/frontend`→`apps/web`, `admin/frontend`→`apps/admin`, 백엔드→`services/*` 이동. 배포 스크립트 경로 갱신.
4. `apps/mobile` 신설(프레임워크 결정 후). `packages/*` 재사용.
5. `services/push` 신설 + `infra/sns-push`.
6. `mobile/`(구 TWA)·`mobile-capacitor/`는 결정에 따라 `apps/mobile`로 흡수 또는 `docs/archive`로 보존.

각 단계는 독립 PR. 2단계는 "이동+경로교체"만이라 동작 변화 0을 테스트로 증명한 뒤 머지한다.

## 안 하는 것

- UI 코드 웹·앱 공유(플랫폼 특성 무시한 공유는 양쪽을 다 망친다).
- 효율을 이유로 `apps/`·`packages/` 경계 생략.
- 서명키·바이너리의 git 커밋.
