### 1.2 구조에서 알아둘 점
- 사이트의 글 데이터는 CloudFront `/api/v2/posts*` 경로로 콘텐츠 API(EC2)를 거친다. 옛 Lambda 중 검색·피드·타임라인 등은 아직 호출되므로 `service/backend/deploy.sh`도 현역이다 (`docs/architecture/배포_스크립트_지도.md`).
- 프론트 태스크 1개, API 서버 1대, DB 단일 AZ다. 오토스케일링이 없다 (`docs/architecture/aws-infra-spec-2026-10-06.html`).
- IaC가 없다. `provision*.sh`는 최초 구축 기록이라 다시 돌리지 않는다 (`docs/architecture/배포_스크립트_지도.md`).
- CLI로만 바꾸고 코드에는 없는 설정: ALB 헬스체크 10초×2회, ECS 서킷 브레이커 롤백, EC2 nginx gzip·스왑 2GB·CloudWatch 에이전트 (`docs/architecture/배포_스크립트_지도.md`, `docs/worklog/2026-10/2026-10-01-seo-rss-보강-배포속도-백엔드-안정화.md`).
- 관리자 API·파이프라인·옛 Lambda는 콘텐츠 API를 코드에 적힌 서버 주소로 부른다(환경변수 `LENS_CMS_API_URL`로 덮어쓰기 가능). 고정 주소 적용은 선행 과제로 남아 있다 (`pipelines/common/lens_cms_client.py`, `admin/backend/shared/lens_cms_client.py`, `service/backend/config/constants.py`, `docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 이름에 `dev`가 붙은 운영 자원(미디어 버킷·DB 클러스터·Lambda 다수)을 정리 대상으로 오인하지 않는다 (`docs/worklog/2026-10/2026-10-04-검색노출-SEO점검과-개선.md`, `docs/architecture/aws-infra-spec-2026-10-06.html`).
- 한 기능이 DDL·콘텐츠 API·nginx·파이프라인 이미지·관리자 Lambda 다섯 곳에 걸친 사례가 있다. 여러 곳을 같이 바꿀 때는 빠진 곳이 없는지 목록으로 확인한다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 범위 밖: 사주 앱, 소스가 이 저장소에 없는 정적 사이트 2개, 모바일 앱 셸(사이트를 원격 URL로 띄움) (`docs/architecture/배포_스크립트_지도.md`, `docs/architecture/소스-없는-배포본.md`, `mobile-capacitor/README.md`).

### 1.3 저장소 문서끼리 어긋나는 곳 (현행 스크립트를 따른다)
- `service/frontend/README.md`·`service/backend/README.md`는 사이트 배포를 EC2+PM2로 적었다. 현행 `service/frontend/deploy.sh`는 ECS Fargate다(2026-09-04 전환) (`service/frontend/deploy.sh`, `docs/worklog/2026-09/2026-09-04-frontend-ecs-fargate-migration.md`).
- `service/backend/infrastructure/README.md`는 2026-07-30에 폐기된 Step Functions 파이프라인 기준이다 (`service/backend/deploy.sh`).
- `service/lens-cms-api/README.md`의 "재배포"(손으로 복사 후 재시작)는 2026-09-18 신설된 `deploy.sh`로 대체됐다. 같은 README가 가리키는 Lambda 쪽 쌍둥이 파일은 지금 `service/backend/clients/pg/cms_posts.py`다 (`service/lens-cms-api/deploy.sh`, `service/lens-cms-api/README.md`).
- `CLAUDE.md`의 `dev`/`dev2` 폴더 이름은 현재 로컬 폴더와 다를 수 있다. 체크아웃은 원격 주소로 판단한다 (`docs/worklog/2026-10/2026-10-07-개선계획/06-오류개선-QA-리팩토링.md`).
- 태그 규칙은 2026-09-30에 `Service`를 `atlas4`에서 `lens`로 원복한다고 정했지만, `tags-ecs.json`(프론트·파이프라인)과 `provision*.sh`는 아직 `atlas4`다. 원복 완료 기록은 찾지 못했다 (`CLAUDE.md`, `service/frontend/tags-ecs.json`, `pipelines/frontpage_auto/tags-ecs.json`).

## 3. 배포 절차

### 3.0 모든 배포 공통 사전 확인
1. **체크아웃** — `git remote -v`가 `sedaily-ai/AILENS`(하이픈 없음)인지 본다. `AI-LENS`(하이픈)는 낡은 저장소인데 같은 AWS 자원을 가리킨다. 거기서 배포하면 운영의 최신 코드를 덮어쓴다(2026-08-06 실제 장애) (`CLAUDE.md`, `docs/worklog/2026-08/2026-08-06-dev-dev2-checkout-incident.md`).
2. **다른 곳의 최근 배포** — worklog·git log·원격 브랜치를 확인한다. 다른 작업자의 배포 시각이 그 사람의 마지막 푸시보다 늦으면 운영에 원격에 없는 커밋이 있다는 신호다. 푸시·병합 전에는 배포하지 않는다 (`CLAUDE.md`, `docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`).
3. **검증** — 화면은 `tsc`·`eslint`·`build`(+ 순수 함수 테스트 `npm test`), 백엔드·파이프라인은 `pyflakes`. pre-commit 훅은 설치한 사람에게만 돌고 CI는 없다 (`CLAUDE.md`, `service/frontend/CLAUDE.md`, `.pre-commit-config.yaml`).
   - 관리자 백엔드 테스트는 운영 감사 테이블에 쓴다는 보고가 있다. 로컬에서 함부로 돌리지 않는다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`).
4. **AWS 자격 증명** — `aws sts get-caller-identity`로 유효한지 본다 (`admin/frontend/deploy-admin.sh`).
5. **Bedrock 호출을 추가·변경하는 배포**
   - `modelId`에 베어 모델 ID(`us.anthropic.*`·`global.anthropic.*`·`anthropic.claude-*`·`amazon.nova-*`)를 넣지 않는다. 비용 태그가 붙은 application inference profile ARN을 쓴다 (`docs/architecture/비용태깅_규칙.md`).
   - 새 프로파일 순서: ① 태그를 붙여 생성 ② 호출 주체 IAM에 프로파일·시스템 프로파일·파운데이션 모델 ARN 3종 권한 ③ 호출부 교체. 2026-10-01 이후 신규는 `Service=lens`. 생성 뒤 태그를 재조회한다 (`docs/architecture/비용태깅_규칙.md`, `AGENTS.md`).
   - 아직 베어 값이 남은 곳: `service/backend/config/constants.py`의 Haiku·Sonnet·Nova·챗봇 상수 (`docs/architecture/비용태깅_규칙.md`).
6. **태그 덮어쓰기** — 태스크 정의는 불변이라 배포마다 `tags-ecs.json`으로 태그를 다시 붙인다. 값을 바꿀 때는 `tags-ecs.json`과 `provision*.sh`의 `SERVICE_TAG`를 함께 바꾼다 (`service/frontend/deploy.sh`, `service/frontend/provision-fargate.sh`, `docs/architecture/비용태깅_규칙.md`).
7. **커밋과 순서** — 배포는 커밋·PR 머지를 기다리지 않는다(2026-09-18 규칙). 단, 서비스 사이트는 2026-10-11 결정으로 main 기준으로만 배포한다(§3.1). 팀이 알아야 할 변경은 브랜치 → PR → main으로 남긴다 (`CLAUDE.md`, `docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`).

### 3.1 서비스 사이트 (ECS Fargate)
**사전 확인**
- main에서만 배포한다. 개인 작업 폴더·미병합 브랜치에서는 배포하지 않는다 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`).
- 드리프트 비교 — 운영과 main의 차이를 배포 전에 확인한다 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`, `docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`).
  1. main을 로컬에서 빌드하고 standalone 서버를 로컬 포트로 띄운다.
  2. 비교할 경로를 운영에서 모은다: 운영 사이트맵 색인(`/sitemap.xml` → core·월별 파일 표본), 홈 내비게이션, 특수 경로(`/letter`·`/api/health`·위젯·카드 등). 고정 목록은 쓰지 않는다 — 10/09에는 고정 목록이 새 경로를 놓쳐 `/letter`가 약 20분 404였다.
  3. 운영과 로컬의 상태 코드와 주요 화면 본문을 비교해 차이가 이번 변경분뿐인지 확인한다.
  - 비교 스크립트는 저장소에 없다(절차만 worklog에 있다).
- 되돌릴 지점 기록 — 지금 운영 중인 태스크 정의 리비전과 이미지 digest를 worklog에 적는다 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`).
- Docker가 실행 중이고 `linux/arm64` 빌드가 돼야 한다 (`service/frontend/deploy.sh`).

**명령** (`service/frontend/deploy.sh`)
```bash
cd service/frontend
./deploy.sh            # 빌드 → ECR push → 태스크 정의 새 리비전(태그 포함) → 롤링 → 안정화 대기
                       # → CloudFront /* 무효화 → ALB 헬스체크 → 스모크 테스트
./deploy.sh --no-wait  # 롤링 시작 직후 반환(새 코드는 보통 약 40초 뒤 서비스)
```
- 실측 총 소요 258~345초 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`, `docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`).

**배포 후 확인**
- 스모크 테스트(`service/frontend/scripts/smoke.sh`): 주요 페이지, 308 이동, 위젯, 날짜 라우트, `/sitemap.xml`·`/robots.txt`·`/llms.txt`·`/rss.xml`, 사이트맵에서 뽑은 실제 기사. 실패하면 배포 스크립트가 종료 코드 1로 끝난다 (`service/frontend/scripts/smoke.sh`, `service/frontend/deploy.sh`).
- 경로를 개편했으면 `smoke.sh` 기대값도 같이 고친다. 낡은 기대값 때문에 의도된 308이 실패로 나온 적이 있다 (`docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`).
- `--no-wait`였다면 롤아웃 상태를 본다: `aws ecs describe-services --cluster sedaily-lens-frontend --services sedaily-lens-frontend --query 'services[0].deployments[0].rolloutState'` (`service/frontend/deploy.sh`).
- 운영 주소에서 `/api/health`·`/sitemap.xml`·이번에 바뀐 경로가 200인지 직접 본다 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`).
- ALB 직접 헬스체크는 사무실에서 시간 초과가 날 수 있다. 그때는 운영 주소로 확인한다 (`service/frontend/deploy.sh`).
- CloudFront 무효화 실패 경고가 나오면 수동으로 무효화하거나 최대 5분(TTL) 기다린다 (`service/frontend/deploy.sh`).

### 3.2 콘텐츠 API (EC2)
**사전 확인**
- 새 경로 접두사를 추가했으면 서버 nginx에 location을 손으로 넣는다. `deploy.sh`는 nginx 설정을 배포하지 않는다. 저장소 `nginx.conf`와 서버를 항상 맞춘다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`, `service/lens-cms-api/nginx.conf`).
- DB 스키마 변경(DDL)은 배포와 별개다. 버전별 SQL을 멱등(`IF NOT EXISTS`)으로 써서 마스터 계정으로 실행하고 `db-changelog`에 남긴다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 공개 조회 쿼리·스키마를 바꾸면 Lambda 쪽 쌍둥이 코드도 같이 고친다 (`service/lens-cms-api/README.md`, `docs/worklog/2026-09/2026-09-29-발행일-kst-버그-수정-및-배포스크립트-최적화.md`).
- 서버의 PM2 설정에는 비밀값이 서버에서만 들어간다. `deploy.sh`는 그 파일을 저장소 템플릿(비밀값 없음)으로 덮어쓴다. `pm2 restart`는 저장된 환경을 써서 괜찮지만, 재부팅 뒤 `pm2 start ecosystem.config.js`로 새로 띄우면 DB 비밀번호·내부 토큰이 빌 수 있다 (`docs/architecture/배포_스크립트_지도.md`, `service/lens-cms-api/ecosystem.config.js`).

**명령** (`service/lens-cms-api/deploy.sh`)
```bash
cd service/lens-cms-api
./deploy.sh   # tar 묶음 → S3 → SSM 원격 실행(압축 풀기, requirements가 바뀐 경우만 pip, pm2 restart) → 헬스체크
```

**배포 후 확인**
- SSM 상태 `Success`, 원격 `local health: 200`, 외부 `/health` 200 (`service/lens-cms-api/deploy.sh`).
- SSM 대기는 약 60초(2초×30회)다. 넘기면 실패로 끝나도 원격 명령은 계속 돌 수 있으니 명령 상태를 다시 본다 (`service/lens-cms-api/deploy.sh`).
- `/health`는 프로세스가 살아 있는지만 본다(DB 미확인). 공개 목록 API(`https://ailens.sedaily.ai/api/v2/posts?channel=lens`)로 DB 경로까지 확인한다 (`service/lens-cms-api/main.py`, `docs/worklog/2026-10/2026-10-01-레터-파싱-버그-백필-및-lens-cms-api-502-장애.md`).
- 로그 `/lens-cms-api/app-error`에서 `connection pool exhausted` 같은 오류가 다시 나는지 본다 (`docs/worklog/2026-10/2026-10-01-seo-rss-보강-배포속도-백엔드-안정화.md`).

### 3.3 관리자 콘솔 화면 (S3 + CloudFront)
- 사전: `.env.local`(또는 `.env.production`)에 관리자 API 주소(`NEXT_PUBLIC_ADMIN_API_BASE_URL`)가 있어야 한다 (`admin/frontend/deploy-admin.sh`).
- 명령: `cd admin/frontend && ./deploy-admin.sh` 또는 `./admin/deploy-all.sh frontend` (`admin/frontend/deploy-admin.sh`, `admin/deploy-all.sh`).
- 동작: 빌드 → 해시 자산은 1년 캐시, 페이지는 no-cache로 업로드 → RSC `.txt`는 `text/x-component`로 업로드 → 옛 파일 정리(`_next/static`은 열린 탭 보호로 남김) → CloudFront `/*` 무효화 후 전파 완료까지 대기 (`admin/frontend/deploy-admin.sh`).
- 배포 후: 스크립트가 콘솔 주소 `/`의 200을 확인한다. 로그인과 글 목록을 직접 열어 본다 (`admin/frontend/deploy-admin.sh`).

### 3.4 관리자 API (Lambda)
- 사전:
  - 스크립트는 코드만 바꾼다. 함수·역할·라우트·환경변수는 만들지 않는다 (`admin/backend/deploy-admin-api.sh`).
  - `handler.py`에 라우트를 추가했으면 API Gateway에도 `aws apigatewayv2 create-route`로 따로 등록한다. 빠뜨리면 404다(세 번 반복된 실수) (`admin/backend/handler.py`, `docs/worklog/2026-09/2026-09-26-api-gateway-라우트-누락-버그.md`).
  - 환경변수 변경(`update-function-configuration --environment`)은 전체 교체다. 기존 값을 읽어 합친 뒤 넣는다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 명령: `./admin/backend/deploy-admin-api.sh` 또는 `./admin/deploy-all.sh backend` (`admin/backend/deploy-admin-api.sh`, `admin/deploy-all.sh`).
- 동작: 소스·공유 모듈 복사 → 의존성 설치(requirements 해시가 같으면 캐시 재사용) → 네이티브 모듈 ABI 검사(실패하면 중단) → zip → S3 → `update-function-code` (`admin/backend/deploy-admin-api.sh`).
- 배포 후: 무인증 `GET /admin/posts`가 401이면 정상, 5xx면 배포가 깨진 것(콜드스타트 import 오류 등)이니 CloudWatch 로그를 본다. 새 라우트는 `get-routes` 결과와 `handler.py`를 대조한다 (`admin/backend/deploy-admin-api.sh`, `docs/worklog/2026-09/2026-09-26-api-gateway-라우트-누락-버그.md`).

### 3.5 옛 공개 API (Lambda 묶음)
- 명령: `cd service/backend && ./deploy.sh [all|api|time-machine]` — zip 하나를 목록의 함수 전부에 올린다 (`service/backend/deploy.sh`).
- 함수 하나만 고쳤으면 그 함수에만 올려 영향 범위를 좁힌다 (`service/backend/README.md`).
- 런타임이 python3.11·3.12가 아니거나 Durable 설정이 있으면 건너뛴다. 코드를 올린 뒤 Handler 경로를 `lambda_handlers.txt`에 맞춘다 (`service/backend/deploy.sh`). Handler 경로 불일치는 2026-08-06 500 장애의 원인이었다 (`docs/worklog/2026-08/2026-08-06-dev-dev2-checkout-incident.md`).
- 배포 후: 대표 함수 헬스체크(`GET /api/v2/posts?channel=letters&limit=1`)가 200이 아니면 경고가 나온다. CloudWatch 로그를 본다 (`service/backend/deploy.sh`).
- 호출이 없는 함수를 지우기 전에는 호출 지표부터 본다 (`docs/architecture/배포_스크립트_지도.md`).

### 3.6 자동 발행 파이프라인 (공유 이미지)
- 명령: `cd pipelines && ./frontpage_auto/deploy.sh` — 이미지 빌드(arm64) → ECR push(`:latest`) → `frontpage_auto` 태스크 정의 새 리비전 등록 (`pipelines/frontpage_auto/deploy.sh`).
- `mustknow_auto`와 영상 랩 태스크도 같은 이미지를 `:latest`로 쓴다. 한 번 배포하면 셋 다 다음 실행부터 바뀐다 (`pipelines/README.md`, `pipelines/video/video-lab-taskdef.json`).
- 바로 확인해야 하면 `aws ecs run-task`로 수동 실행한다(네트워크 설정은 `pipelines/README.md`). 실제 발행과 생성 비용이 생긴다 (`pipelines/README.md`, `pipelines/frontpage_auto/run.py`).
- 배포 후: CloudWatch 로그의 회차 요약(`[frontpage-auto] 완료 — {...}`, `[mustknow-auto] 완료 — {...}`)과 공개 API의 새 글을 본다 (`pipelines/frontpage_auto/run.py`, `pipelines/mustknow_auto/run.py`, `docs/worklog/2026-09/2026-09-03-자동발행-검증.md`).
- 실행 태스크 비용 태그: EventBridge 타깃의 `PropagateTags=TASK_DEFINITION`과 EventBridge 역할의 `ecs:TagResource`가 함께 있어야 한다. `put-targets` 성공만 보지 말고 실행된 태스크의 태그를 확인한다 (`pipelines/mustknow_auto/provision.sh`, `docs/architecture/비용태깅_규칙.md`).
- 모델·프롬프트 변경은 카나리(하루 7회 중 1회) → 전체 순서로 한다(10/07 개선 계획의 진행 규칙). 롤백 기준: 숫자 오류 1건 이상, 분량 위반율 30% 초과, JSON 파싱 실패 (`docs/worklog/2026-10/2026-10-07-개선계획/00-README.md`, `docs/worklog/2026-10/2026-10-07-개선계획/01-비용절감.md`).
- 프롬프트는 버전 저장과 '프로덕션에 적용'이 따로일 수 있다. 적용 뒤 활성 버전을 확인한다 (`docs/worklog/2026-09/2026-09-28-자동발행-웹툰영상버그-수정-백필.md`, `admin/backend/routes/prompts.py`).
- Remotion Lambda(영상 랩): 저장소에 배포 스크립트가 없다. `npx remotion lambda functions deploy`·`npx remotion lambda sites create`로 한 번 배포했다. Remotion 버전을 올리면 다시 배포하고 코드 상수를 고친다 (`pipelines/video/scripts/render-lambda.ts`).

## 4. 롤백 절차
- 저장소에 롤백 전용 스크립트는 없다. 실제로 쓴 복구는 모두 "정상 코드로 다시 배포"였다 — 2026-08-06 정본의 마지막 커밋으로 4개 구성 요소 재배포, 2026-10-09 누락분을 가진 작업자의 재배포(rev 91) (`docs/worklog/2026-08/2026-08-06-dev-dev2-checkout-incident.md`, `docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`).
- 배포 스크립트는 현재 작업 폴더 내용을 그대로 올린다. 그래서 되돌릴 코드는 정상 커밋 상태의 작업 폴더에서 같은 스크립트로 올린다 (`CLAUDE.md`).

### 4.1 서비스 사이트 (ECS)
- 자동: 서킷 브레이커 롤백이 켜져 있다(배포가 안정화에 실패할 때). CLI로 설정했고 코드에는 없다 (`docs/worklog/2026-10/2026-10-01-seo-rss-보강-배포속도-백엔드-안정화.md`).
- 수동(직전 이미지 고정) — 저장소에 실행 기록은 없고, 되돌릴 지점(digest)을 기록하는 관행만 있다 (`docs/worklog/2026-10/2026-10-11-main-배포-rev95-운영확인.md`):
  1. 배포 전에 적어 둔 직전 리비전의 이미지 digest를 찾는다.
  2. `taskdef.json` 사본의 `image`를 `<ECR 리포지토리>@sha256:<digest>`로 바꿔 등록한다: `aws ecs register-task-definition --cli-input-json file://<사본> --tags file://tags-ecs.json` (태그 필수).
  3. `deploy.sh` 4단계 명령(`aws ecs update-service ... --task-definition sedaily-lens-frontend --force-new-deployment`)을 실행한다. 방금 등록한 리비전이 최신이라 그대로 적용된다. 이어서 `aws ecs wait services-stable`.
  4. CloudFront `/*` 무효화 → `service/frontend/scripts/smoke.sh` (2~4는 `service/frontend/deploy.sh`의 명령을 그대로 쓴다).
- 주의: `taskdef.json`이 이미지를 `:latest`로 참조한다. 리비전 번호만 되돌리면 이전 코드가 보장되지 않는다. 그래서 digest를 기록한다 (`service/frontend/taskdef.json`).
- ECR에 수명 주기 정책이 없어 이전 이미지가 남아 있다(2026-10-06). 수명 주기를 넣을 때는 되돌릴 이미지 보존 개수를 정한다 (`docs/architecture/aws-infra-spec-2026-10-06.html`).

### 4.2 콘텐츠 API (EC2)
- **저장소에 정해진 롤백 절차 없음.**
- `deploy.sh`는 매번 같은 S3 키에 묶음을 올리고 서버 폴더에 풀어 덮어쓴다. 이전 묶음은 보관하지 않는다. 정상 커밋으로 `deploy.sh`를 다시 실행하는 것 말고는 저장소가 주는 수단이 없다 (`service/lens-cms-api/deploy.sh`).
- nginx 설정은 바꾸기 전에 서버에 백업 파일을 남겼다. 되돌릴 때는 백업으로 바꾸고 nginx를 재시작한다 (`docs/worklog/2026-10/2026-10-01-seo-rss-보강-배포속도-백엔드-안정화.md`, `docs/architecture/백엔드-정리-계획서_인수인계.md`, `service/lens-cms-api/provision.sh`).
- 저장소 전환 스위치(`SEEN_BACKEND`·`JOBS_BACKEND`)의 기본값은 롤백용 `ddb`다 (`docs/architecture/백엔드-정리-계획서_인수인계.md`).

### 4.3 Lambda (관리자 API, 옛 공개 API)
- **저장소에 정해진 롤백 절차 없음.**
- 두 스크립트 모두 같은 S3 키에 zip을 덮어쓰고 `update-function-code`만 한다. 버전·별칭을 발행하지 않는다 (`admin/backend/deploy-admin-api.sh`, `service/backend/deploy.sh`).
- 기록된 복구: 정상 커밋으로 같은 스크립트를 다시 실행(2026-08-06) (`docs/worklog/2026-08/2026-08-06-dev-dev2-checkout-incident.md`).
- 404가 라우트 누락 때문이면 코드가 아니라 API Gateway 라우트를 등록한다 (`docs/worklog/2026-09/2026-09-26-api-gateway-라우트-누락-버그.md`).

### 4.4 관리자 콘솔 화면 (S3)
- **저장소에 정해진 롤백 절차 없음.** 기록된 복구는 정상 커밋으로 `deploy-admin.sh`를 다시 실행한 것이다 (`docs/worklog/2026-08/2026-08-06-dev-dev2-checkout-incident.md`, `admin/frontend/deploy-admin.sh`).

### 4.5 자동 발행 파이프라인
- 코드: 원복 → `frontpage_auto/deploy.sh`로 이미지 재배포 → 다음 실행부터 적용 (`docs/worklog/2026-10/2026-10-07-개선계획/01-비용절감.md`).
- 설정(환경변수): EventBridge는 family의 최신 리비전을 쓴다. 이전 설정으로 새 리비전을 등록한다(예: `SEEN_BACKEND` 제거). 이미지가 `:latest`라 리비전만 바꿔서는 코드가 돌아가지 않는다 (`pipelines/frontpage_auto/deploy.sh`, `pipelines/frontpage_auto/taskdef.json`, `docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 프롬프트: 관리자 콘솔에서 이전 버전을 '프로덕션에 적용'한다(`POST /admin/prompts/{category}/{name}/activate`). 다음 실행부터 반영된다 (`admin/backend/routes/prompts.py`, `pipelines/README.md`).
- 긴급 중지: `aws events disable-rule --name <규칙 이름>`, 다시 켤 때 `enable-rule`. 관리자 콘솔 `/drivers`는 `sedaily-mbti-`로 시작하는 규칙만 다뤄서 발행 규칙(`sedaily-lens-*`)은 끌 수 없다 (`pipelines/mustknow_auto/provision.sh`, `admin/backend/routes/drivers.py`).

### 4.6 데이터·설정
- 글 하나: 관리자 콘솔 '내리기'(비공개, 다시 '발행' 가능)가 먼저다. 콘솔 '삭제'는 DB에 `deleted_at`만 찍는 소프트 삭제지만 화면에서는 되돌릴 수 없다. DB에서 `deleted_at`을 NULL로 바꾸면 복구된다 (`admin/frontend/src/app/(authenticated)/lens/edit/page.tsx`, `service/lens-cms-api/admin_posts_repo.py`, `docs/worklog/2026-10/2026-10-09-웹툰영상-canonical-검색엔진점검.md`).
- 복구 스크립트(`pipelines/scripts/repair_*.py`·`regen_letters.py`)는 쓰기 전에 글 전체를 `pipelines/scripts/repair_backup/`에 JSON으로 남긴다(커밋하지 않음) (`pipelines/scripts/repair_missing_formats.py`, `.gitignore`).
- 미디어: 미디어 버킷은 버저닝이 켜져 있고(이전 버전 90일 보관), 버킷 삭제 거부 정책이 있다(2026-10-04) (`docs/worklog/2026-10/2026-10-04-검색노출-SEO점검과-개선.md`).
- 스키마: SQL 파일 맨 아래에 롤백 주석을 두는 사례가 있다(데이터 입력 전에만 유효) (`docs/architecture/db-changelog/postgres/v1.37-이슈레터-신설.md`).
- DB 전체: Aurora 백업 보존 기간은 1일이다. 복원 절차는 저장소에 없다 (`docs/architecture/db-changelog/postgres/v1.2-인프라-프로비저닝.md`, `docs/architecture/aws-infra-spec-2026-10-06.html`).
- 인프라 설정: 바꾸기 전 현재 설정을 JSON으로 백업한다(CloudFront·Cognito 사례). CloudFront 캐시 정책이 문제를 일으켰을 때 동작의 정책을 `CachingDisabled`로 되돌린 사례가 있다 (`docs/worklog/2026-10/2026-10-09-cloudfront-변경전-설정백업.json`, `docs/ops/cognito/`, `docs/worklog/2026-09/2026-09-30-cloudfront-캐시-재도입-generateStaticParams-누락.md`).

### 5.4 비용 확인
- 청구를 가르는 태그는 `Service` 하나다(2026-09-30까지 `atlas4`, 2026-10-01 이후 신규 `lens`) (`docs/architecture/비용태깅_규칙.md`).
- 조회: 이테크시스템 DSA 포탈 비용 탐색기에서 태그 `user:Service`로 일별 조회하고 `docs/cost/`에 스냅샷을 남긴다 (`docs/cost/README.md`, `docs/cost/2026-09-28-atlas4-일별-비용-스냅샷.md`).
- 청구 반영은 T+3~4일이다. Cost Explorer는 조직 SCP로 막혀 있다 (`docs/architecture/비용태깅_규칙.md`).
- Bedrock 배치 추론은 CloudWatch 호출 지표·로그에 남지 않는다. 실청구로만 확인한다 (`docs/architecture/비용태깅_규칙.md`).
- 태그 확인: `aws resourcegroupstaggingapi get-resources --tag-filters Key=Service,Values=<값>`, 실행 중 ECS 태스크는 `aws ecs list-tags-for-resource` (`docs/architecture/비용태깅_규칙.md`).
- 관리자 콘솔 비용 화면(`/cost`)과 CloudWatch 대시보드 정의(`service/backend/observability/dashboards/`)는 폐기된 지표 기준이라 지금 비용 확인에 쓰지 않는다 (`admin/backend/routes/cost.py`, `service/backend/observability/README.md`).

## 7. 비밀정보 관리

**저장 위치(종류)**
- SSM Parameter Store SecureString: 내부 API 토큰, 관리자 로그인 비밀값(비밀번호 해시·JWT 서명 키), 사이트 캐시 무효화 웹훅 시크릿. 코드는 복호화 옵션으로 읽는다 (`docs/architecture/admin-stack.md`, `admin/backend/shared/ssm_client.py`, `pipelines/common/lens_cms_client.py`, `pipelines/common/publish_utils.py`).
- Secrets Manager: 외부 API 키(ElevenLabs·OpenAI), DB 마스터 비밀번호(AWS 관리형) (`pipelines/common/elevenlabs_tts.py`, `pipelines/common/openai_client.py`, `docs/architecture/백엔드-정리-계획서_인수인계.md`).
- ECS 태스크 정의 `secrets`: 사이트 컨테이너는 시작할 때 SSM 값을 주입받는다. 실행 역할에는 그 파라미터 하나의 읽기와 SSM 경유 복호화만 준다 (`service/frontend/taskdef.json`, `service/frontend/execution-role-secrets-policy.json`).
- EC2 콘텐츠 API: DB 앱 비밀번호와 내부 토큰은 서버의 PM2 설정에만 넣는다. 저장소의 `ecosystem.config.js`는 비밀값 없는 템플릿이다(재부팅 주의는 §3.2) (`service/lens-cms-api/ecosystem.config.js`).

**원칙**
- 저장소에 비밀값을 넣지 않는다. `.env`·`.env.*`는 git에서 빠져 있다 (`.gitignore`).
- 비밀값을 못 읽으면 기본값으로 넘어가지 않고 오류로 멈춘다(fail-closed) (`docs/architecture/admin-stack.md`, `service/frontend/src/app/api/revalidate/route.ts`).
- 새 비밀값을 쓰는 주체에는 그 파라미터 읽기와 KMS 복호화(SSM 경유 조건)를 함께 준다 (`docs/architecture/admin-stack.md`, `service/frontend/execution-role-secrets-policy.json`).
- 값을 채팅·문서·로그에 남기지 않는다. 평문으로 노출되면 바로 교체·무효화하고 문서에서 지운다(2026-09-25 기록 속 DB 비밀번호를 교체한 사례) (`docs/architecture/백엔드-정리-계획서_인수인계.md`).
- 공개 저장소: 계정 ID·개인 IAM 사용자 이름이 든 루트 증적 문서는 PR #52로 내렸다. 배포 스크립트·일부 문서에는 계정 ID·리소스 ID·서버 주소가 아직 하드코딩돼 있어 정리 대상이다 (`docs/worklog/2026-10/2026-10-09-비교카드-본지위젯-사이트문구정정.md`, `service/frontend/deploy.sh`, `service/lens-cms-api/deploy.sh`).
- 비밀값 교체 주기는 저장소에 정해져 있지 않다.
