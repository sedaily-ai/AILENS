# backoffice — CMS 프롬프트 실험공간을 전문성 있게 구축하기

갱신: 2026-09-25.

## 이 폴더가 담는 것

기존 `docs/`는 "어떤 질문에 답하는 문서인가"(architecture/product/evaluation/...)
기준으로 나뉜 구조다. `backoffice/`는 그 축과 다르게 **"어드민 콘솔(CMS) 자체를
기능 단위로 깊게 판다"**는 목적으로 따로 뗀 폴더다 — 어드민의 프롬프트 실험
공간(4포맷 탭)에 관한 문서를 성격(기술/제품/평가)별로 흩어놓지 않고 한곳에
모아, 이 기능만 보고 싶을 때 여러 폴더를 오가지 않아도 되게 하는 것이 목적.

날짜가 붙는 작업 기록(무엇을 언제 왜 고쳤는지)은 지금처럼 계속
`worklog/YYYY-MM/`에 남긴다. 이 폴더는 날짜와 무관하게 **지금 유효한 정본**만
담는다 — worklog가 쌓여 방향이 바뀌면 이 폴더의 문서를 그때그때 갱신한다.

## 시작 전 상태 (2026-09-25 기준)

`content-quality-audit.md`(2026-09-23 조사)가 확인한 현재 CMS 프롬프트
실험공간의 실제 상태:

- 품질 검증이 코드로 실체화된 건 영상 포맷(`validate_script()`) 하나뿐 —
  레터·팟캐스트·웹툰은 프롬프트 문구의 자기규율에 의존
- 공통 원칙(3항목)이 4개 프롬프트에 손으로 복붙돼 있어 하나 고치면
  나머지가 어긋날 위험
- 발행물과 프롬프트 버전을 잇는 필드가 없어 **버전 간 성능 비교가 불가능**
- 저장이 곧 발행이라 실험(초안)과 실전(라이브)이 분리되지 않음

즉 지금은 "실험공간"이라기보다 실시간 편집기에 가깝다.

## 목표

"바꿨더니 뭐가 어떻게 좋아졌는가"를 답할 수 있는 최소 인프라를 갖춘
진짜 실험공간으로 만든다.

## 폴더 뼈대 — 4축 (2026-09-26)

AI-GLOBE `docs/translation/`의 성격 분류(기계 자체 / 지켜보는 활동 /
평가하는 활동 / 데이터 거버넌스)를 그대로 대입해 나눈다. 처음엔 3축(평가/
아키텍처/워크플로우)으로 잡았다가, 9/24~25 실제 작업(Bedrock reasoning
비활성화·프롬프트 캐싱·재시도·로깅 커버리지)이 그 세 축 어디에도 안
들어맞아 재검토 — "잘 기록되는가"(관측성)와 "잘 판단하는가"(평가)는
AI-GLOBE에서도 별개 폴더였다.

| 폴더 | 성격 | 담는 것 |
|---|---|---|
| `워크플로우/` | 기계 자체 | 실험 콘솔이 실제로 어떻게 동작하는가의 변화 — 저장=즉시발행 구조, 4탭 상태 유지, 생성물 저장, 미디어 생성(TTS/렌더) |
| `관측성/` | 지켜보는 활동 | Bedrock 호출이 빠짐없이·신뢰성 있게 로깅되는가 — reasoning/캐싱/재시도/타임아웃 |
| `평가/` | 평가하는 활동 | 산출물이 실제로 좋아졌는가 — 버전별 채점, `content-quality-audit.md`가 제기한 "70점 통과 기준"의 후속. MBTI `evaluation/harness/` 선례 참고 |
| `아키텍처/` | 데이터 거버넌스 | 4포맷 공용 원칙의 복붙 구조를 스키마·모듈로 관리 |

**아직 4축 다 착수 전 — 어느 것부터 팔지는 별도로 정한다.** vault
`축기록/00_안내.md`의 "축은 열려있다" 원칙과 같이, 이 4개가 고정
개수는 아니다 — 나중에 다섯 번째 성격이 필요해지면 늘어난다.

## genaiops/ — 이 분야 자체에 대한 지식 (2026-09-26)

위 4축이 "우리가 실제로 한 일"을 담는 반면, [genaiops/](genaiops/README.md)는
그 일을 하는 데 참고할 **바깥 지식**(학술 벤치마크·롤모델 기업·오픈소스
프레임워크)을 계속 쌓는 곳이다. backoffice가 다루는 분야 자체가
"LLMOps + 생성형 미디어 파이프라인을 아우르는 GenAIOps"라는 게 이름의
근거. 내부는 `reference/`(살아있는 지도)·`research/`(조사 세션 기록)로
나뉜다 — 상세 규칙은 그 폴더의 README.

## 문서 성격 안내

같은 폴더 안에도 성격이 다른 문서가 섞일 수 있다 — 헷갈리지 않게 구분한다
(AI-GLOBE `docs/translation/` 프레임워크에서 가져온 구분, 2026-09-25):

| 성격 | 예 | 특징 |
|---|---|---|
| **의사결정 기록** (번호+날짜 파일) | `평가/01-2026-10-01-...md`(예시, 아직 없음) | 그때 왜 그렇게 결정했는지 — append-only. 뒤집히면 지우지 않고 새 파일 추가 + 옛 파일 맨 위에 대체 배너만 붙임 |
| **살아있는 참고 문서** (번호 없음) | 이 `README.md` 자체 | "지금 뭐가 맞나" — 계속 갱신됨. 이 문서 자체가 정본 |
| **원본 데이터** (번호 없음) | — | 참고 문서가 인용하는 원자료. 아직 없음 |

의사결정 기록은 `_TEMPLATE.md` 뼈대(**문제 발견 → 문제 정의 → Why(목적) →
목표 → 가설 → 문제→솔루션 → Before/After**, 7단)를 따른다. 이건 새로
만든 틀이 아니라 두 곳에서 이미 검증된 것을 그대로 가져온 것이다 —
AI-GLOBE `docs/translation/`의 의사결정 기록 형식(문제발견~어떻게달라졌는지)에,
개인 Obsidian Vault `축기록/00_안내.md`가 같은 형식을 채택하며 추가한
"목표"·"가설" 두 단계([[feedback_hypothesis_before_recording]] 규칙)를
얹은 버전. 문체는 개조식·단문·수치 구체적으로
([[문체정본_보이스·톤매트릭스]]와 동일 원칙). 뒤집는 파일이 생기면
`_TEMPLATE.md`의 대체 배너 형식(`[YYYY-MM-DD 이 기록으로 대체됨 →
새 파일 링크]`)을 옛 파일 맨 위에 붙인다.

## 새 항목 추가 규칙

1. 위 "폴더 뼈대" 네 축(워크플로우/관측성/평가/아키텍처) 중 하나에
   착수하면, 그 축 이름의 하위 폴더를 그때 만든다 — 착수 전에 미리
   만들지 않는다.
2. 하위 폴더 안 파일명은 `NN-YYYY-MM-DD-주제.md`(번호는 그 폴더 안에서
   날짜순으로 이어붙임). 폴더 안에 또 하위 폴더를 만들지 않는다.
3. 여러 축에 걸치는 사건이면 핵심이 바뀐 축 하나에 파일로 귀속시키고
   나머지 축에서는 링크만 건다.
4. 이미 있는 문서의 서술이 나중에 틀린 것으로 밝혀지면 지우지 말고,
   그 문서 맨 위에 `_TEMPLATE.md` 형식의 대체 배너를 붙이고 새 파일을
   추가한다(작은 갱신이면 해당 문장에 취소선 + 정정 각주로 충분).
5. 날짜가 명확한 단발 작업 기록은 지금처럼 `worklog/YYYY-MM/`에 남기고,
   그중 이 폴더의 네 축과 직접 관련된 것만 이 폴더에도 의사결정
   기록으로 남긴다(중복이 아니라 worklog=전체 세션 기록, 여기=이
   기능 전용 요약).

## 기존 폴더와의 관계

- `evaluation/`, `product/`, `architecture/`에 이미 있던 관련 문서(예:
  `architecture/admin-stack.md`, `evaluation/4format-evaluation-system.md`)는
  아직 옮기지 않았다 — 전체 `docs/` 폴더 아키텍처 재설계를 별도로 할
  예정이라, 그 전까지는 중복 이동 대신 이 폴더에서 필요할 때 링크로 참조한다.
- 재설계 시점엔 이 폴더의 구조(기능별 묶음)가 다른 기능(예: `service/`,
  `pipelines/`)에도 같은 방식으로 적용될지 판단 기준이 될 수 있다.
