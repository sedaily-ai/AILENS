# genaiops — 이 분야의 지식을 계속 쌓는 곳

[← backoffice](../README.md)

갱신: 2026-09-26.

## 이 폴더가 담는 것

`워크플로우/`·`관측성/`·`평가/`·`아키텍처/`(backoffice 4축)가 **우리가
실제로 한 일**(의사결정 기록)을 담는 곳이라면, 여기는 **그 일을 하는 데
참고할 바깥 지식**을 담는 곳이다 — 학술 벤치마크·논문, 이 분야를 이미
제품으로 만든 회사, 오픈소스 프레임워크. backoffice가 다루는 분야 자체가
**LLMOps(프롬프트 워크플로우·평가·관측성·거버넌스) + 생성형 미디어
파이프라인(TTS·영상)을 아우르는 GenAIOps**라는 게 이 폴더 이름의 근거
(2026-09-25 대화에서 확정).

## 폴더 구조

| 폴더 | 성격 | 담는 것 |
|---|---|---|
| `reference/` | 살아있는 참고 문서 (번호 없음) | 지금 이 분야의 지도 — 학술 벤치마크·롤모델 기업·오픈소스 프레임워크 목록. 새로 알게 되면 그 자리에서 갱신, 이 문서 자체가 정본 |
| `research/` | 조사 기록 (번호+날짜) | 특정 질문을 파고든 세션의 기록 — 예: "HELM 논문 정독", "Humanloop 실제 써보고 UX 비교". `NN-YYYY-MM-DD-주제.md`, append-only |

## research/ 작성 틀

engineering 의사결정 기록(`../_TEMPLATE.md`, 7단)과는 성격이 달라 —
"무엇을 결정했나"가 아니라 "무엇을 알아냈나"이므로 더 가벼운 3단을 쓴다:

```
## 조사 배경 — 왜 이걸 찾아봤나
## 찾은 것 — 핵심 내용 요약 (출처 포함, 팩트만)
## 시사점 — backoffice 4축 중 어디에 어떻게 쓸 수 있나
```

문체는 동일하게 개조식·단문·수치 구체적으로. "찾은 것"(팩트)과
"시사점"(평가)을 한 문단에 섞지 않는다([[문체정본_보이스·톤매트릭스]]
"숫자로 말한다, FAE 안 섞는다" 원칙).

## 새 항목 추가 규칙

1. 이미 알고 있는 걸 `reference/README.md`에 추가할 땐 새 파일을 만들지
   않고 그 문서를 갱신한다 — 목록이 길어져 성격별로 쪼갤 만큼 커지면
   그때 `reference/` 아래 하위 파일(예: `reference/논문.md`,
   `reference/제품.md`)로 나눈다.
2. 특정 세션에서 뭔가를 깊게 조사했으면 `research/`에 새 번호 파일을
   추가하고, 그 결과로 `reference/README.md`에 새 항목이 생기면
   거기도 같이 갱신한다(중복이 아니라 research=조사 과정 기록,
   reference=결론만 남은 지도).
3. backoffice 4축(워크플로우/관측성/평가/아키텍처) 중 특정 축 착수에
   바로 쓸 자료면 그 축 폴더에서 링크로 참조한다 — 자료 자체는
   여기 하나에만 둔다.
