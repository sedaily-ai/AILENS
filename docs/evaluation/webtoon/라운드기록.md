# 웹툰 파이프라인 — 화풍·구조 개선

계기: 사용자가 "육하원칙 기반 웹툰 프롬프트"(다른 GPT 이미지 툴에 통째로
붙여넣는 독립형 프롬프트) 문서와, 그 프롬프트로 뽑은 참고 샘플(카카오톡
공유, 8~9장)을 전달. 실제 프로덕션 파이프라인(`pipelines/webtoon/`,
Bedrock 기반) 출력과 톤앤매너가 전혀 다르다는 지적으로 시작해서,
근본 원인 진단→모델 전환→구조 정리→후속 결함 수정까지 이어진 작업.

관련 코드: `pipelines/webtoon/pipeline.py`, `pipelines/webtoon/compose_text.py`,
`pipelines/webtoon/prompts.py`, `pipelines/common/webtoon_image.py`,
`pipelines/common/rekognition_client.py`(신설), `pipelines/common/assets/webtoon_style_reference.png`(신설),
admin DDB `PROMPT#webtoon/published`·`PROMPT#webtoon-image/published`.

관련 worklog: `docs/worklog/2026-09/2026-09-08-webtoon-style-guide-migration.md`
(R1~R2 요약), 이 파일은 그보다 더 세밀한 라운드별 실험 기록.

## 목표·베이스라인

**솔직히 기록**: 이 작업은 시작 시점에 정량적 목표·베이스라인을 먼저
정의하지 않고, 사용자의 정성적 판단("참고 샘플이랑 톤앤매너가 다르다" /
"이상해요, 전혀 달라" / "이거예요")을 신호로 라운드를 반복하며 원인을
좁혀가는 방식으로 진행됐다. 아래는 라운드가 진행되며 사후적으로 굳어진
평가 기준이다 — **다음 라운드부터는 착수 전에 이 체크리스트로 베이스라인을
잡을 것**.

**정성 기준(사용자 판정)**
- [ ] 화풍이 참고 샘플과 같은 "플랫 셀 채색 웹툰"으로 보이는가(반실사
      디지털 페인팅이 아닌가)
- [ ] 인물(헤어스타일·색상·복장 실루엣)이 8컷 내내 일관되는가
- [ ] 인포그래픽·소품이 장면에 자연스럽게 통합되는가

**정량 기준(실측 가능)**
- [ ] 8컷 중 몇 컷이 성공(생성+QA 통과)하는가 — 컷 성공률
- [ ] 주요 화자로 판정된 얼굴의 Rekognition 신뢰도(%) — 95%+ 목표
- [ ] 말풍선이 얼굴/다른 말풍선과 겹치는 컷 수(육안 검수) — 0 목표

이번 라운드 묶음 전체에서 실측한 정량 수치는 아래 이슈 트래커·라운드별
기록에 그대로 남긴다.

## 라운드 3 (2026-09-08) — Stable Image Style Guide 발견·전환

**문제**: #4가 안 풀리는 근본 원인을 좁히다가, Bedrock 이미지 모델
목록에서 `stability.stable-image-style-guide-v1:0`(참고 이미지를 화풍
기준으로 받는 모델)을 발견. 단발 테스트(참고 이미지 1장 고정, 서로
다른 장면 2개) — 화풍·인물 톤이 크게 근접함을 확인하고 프로덕션 전환
결정.

**솔루션**: `lens-webtoon-image-style-guide` application inference
profile 신설(비용태깅_규칙.md 준수), 참고 이미지를
`pipelines/common/assets/webtoon_style_reference.png`로 자산화,
`webtoon_image.py`에 `build_style_guide_prompt()`/
`generate_bedrock_style_guide_image_bytes()` 신설, `IMAGE_PROVIDER`
기본값을 `"bedrock"`→`"bedrock-style-guide"`로 승격.

**검증(1차 통합, 실패)**: 테스트_뤼미에르파트너십_v4_styleguide 8/8컷
생성됐으나 화풍이 반실사로 회귀(단발 테스트와 다른 결과) + aspect_ratio
파라미터 누락으로 1:1 정사각형 생성(#6) + 그 여파로 말풍선이 얼굴을
가림(#7). 원인 분석: 파이프라인에 옮기며 "flat cel-shaded webtoon"
텍스트 힌트를 "참고 이미지가 대신 전달하겠지"라며 빼고 대신 장문의
인물 묘사·재강조 텍스트를 붙인 게 원인으로 추정(#5). fidelity를
0.5→0.75로 올려도 개선 안 됨(오히려 참고 이미지의 스튜디오 사진
요소가 더 강하게 전이됨).

**솔루션(수정)**: `build_style_guide_prompt()`를 의도적으로 짧게
재작성 — 스타일 힌트 한 줄("flat cel-shaded... NOT photorealistic")
+ 카메라 + [SCENE] + 짧은 내용 규칙만, 장문 인물 묘사(characters_block/
CHARACTER_REINFORCEMENT)는 제외(#5). `generate_bedrock_style_guide_image_bytes()`에
`aspect_ratio: BEDROCK_ASPECT_RATIO` 명시(#6).

**검증(2차, 성공)**: 테스트_뤼미에르파트너십_v5 — **8컷 중 7컷 성공**

## 라운드 5 (2026-09-08) — 말풍선 얼굴 회피(Rekognition)

**문제**: 사용자가 "말풍선이 인물들을 가리는데 왜 어려운가" 질문 —
기존 구조 설명(Claude 비전 모델에게 얼굴 x좌표만 추정시키던 방식, 세로

**리서치**: AWS Rekognition `DetectFaces`를 우리 웹툰 컷 8장(v5 산출물)에
실측 — **주요 인물은 신뢰도 98~100%로 정확한 바운딩 박스 반환**(만화
일러스트인데도 잘 동작), 배경 엑스트라가 섞인 컷에서는 주요 인물(신뢰도
99~100%, 상대적으로 큰 크기)과 배경 엑스트라(신뢰도 60~90%대, 훨씬
작은 크기)가 뚜렷이 구분됨 — 필터링 가능. 비용은 이미지당 약 $0.001.
기존 Claude 비전 방식(x좌표 하나만 추정) 대비 명백히 우월하다고 판단.

**목표 설정**: (1) 신뢰도 95%+·폭 5%+ 필터로 주요 화자만 추리기,
(2) 말풍선을 얼굴 바운딩 박스 상단 바로 위(150px 여백)에 배치,
(3) 좌우는 기존 "첫 화자=오른쪽" 규칙 유지·감지 순서와 매핑,
(4) 감지 실패/개수 불일치 시 균등분할 폴백 유지.

손 안 대고 다음 라운드로 이월.

**근본 원인 조사(#10 재현·재수정)**: "화면 폭 50% 미만이면 벌린다"는
R5의 고정 비율 로직이 왜 안 먹혔는지 재현 테스트를 여러 번 시도했으나
번번이 재현 실패 — 로직 자체는 정상 동작함을 확인. `_draw_bubble()`의
화면 경계 clamp 코드(`max(10, min(img.width-bw-10, anchor_x-bw/2))`)를
다시 읽고서야 원인을 특정: **긴 대사로 말풍선이 넓어지면, 앵커 간격은
충분해도 그 넓은 말풍선이 화면 경계에 걸려 clamp가 안쪽으로 밀어
넣으면서 두 말풍선이 다시 가까워질 수 있다** — 앵커 위치만 보는
고정 비율 검사로는 이 경우(경계 근처 + 긴 텍스트)를 못 잡는 구조적
허점이었다. "화면 폭의 50%"라는 가정 자체가 실제 텍스트 폭과 무관한
추측이었던 것이 근본 원인.

**#13(제목-말풍선 충돌) 원인**: `draw_title()`/`draw_cover_header()`가
알약을 그리고도 실제 하단 y좌표를 버리고 있었다 — `draw_dialogue()`는
"제목 아래 16% 지점"이라는 고정 비율로 안전거리를 추측했는데, 제목
글자 수가 길어(예: "영진위·MPA도 한팀") 알약이 예상보다 커지는 컷에서
그 추측이 실제 알약 하단보다 위쪽(=더 좁은 여유)이라 말풍선이 제목과
겹쳤다.

**솔루션**:
- `draw_dialogue()`: 화면 폭 비율 추측 대신 실제 텍스트를 `_wrap_text`/
  `_measure_block`으로 미리 측정해 진짜 말풍선 폭(half-width)을 구하고,
  (1) 그 폭 기준 최소 간격(두 반폭 합+40px)으로 앵커를 벌린 뒤 (2) 벌린
  쌍 전체가 화면 안에 들어가도록 함께 이동시킨다 — 각자 따로 clamp하면
  간격이 도로 좁아지는 문제를 이 순서로 피한다.
- `draw_title()`/`draw_cover_header()`가 `_draw_pill()`의 반환값(알약
  하단 y좌표)을 그대로 돌려주도록 수정. `compose()`가 그 실제값을
  `draw_dialogue()`의 새 `min_top_y` 파라미터로 전달 — 고정 16% 비율은
  제목이 없는 컷에서만 쓰는 폴백으로 격하.

## 라운드 9 (2026-09-08) — 배경 엑스트라(#14) 근본 원인 조사

대본은 분명 카페에서 둘이 대화하는 장면인데, 그림엔 스튜디오 카메라

어디 있는 거지? 저 사람은 누구지?" 하는 혼란을 겪는다.

**실측 1 — 재현 확인**: 실제 v8 파이프라인 코드로 컷4 장면("카페 창가

카메라 조명 장비 + 행인 무리**로, 대본의 "카페"와는 완전히 다른 장소가
나왔다. #4(장면 이행력)와 #14(엑스트라)가 사실 같은 뿌리 문제일 가능성을

**시도 1 — 프롬프트에 "하지 말라" 문장 추가**: `_STYLE_GUIDE_CONTENT_RULES`
수준의 텍스트 지시를 더 강하게(STRICT LOCATION RULE 블록) 추가해도

본문 프롬프트의 부정문보다 강함을 재확인(R3에서 이미 알려진 한계와 같은
성격).

**시도 2 — fidelity 낮추기(0.5→0.3)**: 참고 이미지 영향을 줄이면 프롬프트
(카페 장면)가 더 잘 먹힐 거라 예상했으나, 실제로는 모델의 기본값("도심
거리의 젊은 직장인들" 클리셰)으로 흘러가며 오히려 행인이 더 늘어남 —
낮은 fidelity가 [SCENE] 텍스트를 더 잘 따르게 하는 게 아니라 그냥
참고 이미지도 프롬프트도 아닌 모델 자체의 디폴트 화면으로 흘러감을 확인.

**시도 3 — Bedrock `negative_prompt` 파라미터**: 문서화는 안 돼 있지만
Style Guide 요청 바디에 별도 `negative_prompt` 필드가 실제로 동작함을

원본)이었는데, 이걸 **모든 기사의 범용 화풍 앵커로 계속 재사용**하고
있었다 — Style Guide는 "화풍"만이 아니라 참고 이미지의 장면 구성·소품

**결론**: #14와 #4는 사실 하나의 근본 원인 — **주제 특화 참고 이미지를

소스(원래 사용자가 GPT-image 등으로 만든 방식) 확보가 먼저 필요**해

## 라운드 11 (2026-09-08) — #4(장면 이행력) 리서치·돌파구: 2단계 구도-화풍 분리 파이프라인

**계기**: 사용자 요청("다른 방법들은 없으려나... 라이브러리나... 다른 서비스를... 에이전트를 쓴다거나")으로
Bedrock 밖의 대안까지 리서치. AWS Bedrock의 Stability AI Image Services가
2025년 9월 정식 출시돼 13개 도구를 제공하는데, 지금까지 Style Guide 1개만
쓰고 있었다는 걸 발견 — Control Structure(진짜 ControlNet), Style
Transfer가 우리 문제에 정확히 맞아 보였다.

**시도 1 — Control Structure**: PIL로 그린 단순 레이아웃 스케치(두 사람
실루엣+테이블+창문+조명)를 구조 참조로 넣고 텍스트로 화풍 지정,
control_strength 0.4/0.45/0.55/0.7 비교. 결과: 인원수 통제는 됐다갔다
(4번 중 2번만 깔끔), 장소(카페)는 여전히 안 나옴(거리·회색 벽 등),
strength 0.7에서는 내 조잡한 스케치가 그대로 색깔까지 새어나오는 부작용.
**결론: 이 문제엔 뚜렷한 개선 없음.**

**시도 2 — Style Transfer로 발상 전환**: Style Transfer는 "구도를
보존하며 화풍만 입힌다"(init_image+style_image+prompt). 핵심 통찰:
**"카페에서 대화하는 두 사람" 같은 평범한 사진 프롬프트는 Stable
Image Core가 놀랍도록 정확히 따른다** — 지금까지의 문제는 "플랫 셀
웹툰체 캐릭터"라는 화풍 지정이 붙을 때만 특정 배경(거리+군중)으로
쏠리는 현상이었지, 모델이 장소 지시 자체를 못 따르는 게 아니었다.
즉 **화풍과 장면 구성을 한 번에 요구하는 게 문제의 근원**이었다.

**해결 구조**: (1) Stable Image Core로 포토리얼 사진 프롬프트("정확히
두 사람만, 카페 창가 테이블, 코스터·화분·펜던트 조명")를 만들면 장소·
인원수가 정확히 나옴(negative_prompt로 "제3의 인물" 배제까지 포함).
(2) 이 결과를 init_image로, 기존 webtoon_style_reference.png를
style_image로 Style Transfer 호출 → 구도(장소+인원수)는 그대로 두고
화풍만 지금 확립한 플랫 셀 웹툰체로 덧입힌다.

**검증**: 카페 장면 2회(다른 composition_fidelity/style_strength 조합)
+ 사무실 장면 1회, 총 3회 모두 성공 — 대본이 요구한 장소(카페 내부/
사무실 뉴스룸)가 실제로 재현됐고, 전경 인물은 정확히 2명(성별도 정상),
화풍도 참고 이미지와 일치. 사무실 장면엔 배경 동료들이 자연스럽게
등장했는데(뉴스룸이라 원래 있어야 할 인물), 이건 R9~R10에서 문제
삼았던 "카페인데 갑자기 스태프가 낀다"는 종류의 위화감이 아니라 맥락에
맞는 배경이라 성격이 다름 — 기존 Rekognition QA 게이트(신뢰도·크기
필터)로 여전히 걸러질 수준.

**의의**: R9에서 "이 캐릭터 아키타입 자체에 대한 모델의 강한 편향"이라고
결론 내렸던 게 정확히는 아니었다 — 편향은 "화풍+장면"을 한 프롬프트에
동시에 요구할 때만 나타났다. 화풍(Style Transfer)과 장면 구성(포토리얼
프롬프트)을 분리하니 양쪽 다 모델이 원래 갖고 있던 지시 순응력을
