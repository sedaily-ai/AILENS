# 나의 LENS — 프론트엔드 연결 현황과 백엔드 요청

작성일: 2026-10-14. 프론트엔드 진입 경로: `/my-lens`.

> 백엔드 개발 인계 정본(같은 날 최신 코드 조사): [개발 인수인계](백엔드_개발_인수인계.md) → [API 계약](../../architecture/나의LENS_백엔드_API계약.md) → [데이터·구현 설계](../../architecture/나의LENS_백엔드_데이터·구현설계.md). 이 문서는 프론트 구현 단계의 연결/요청 이력을 보존한다. 아래 예전 응답 제안·개발 비로그인 유지 문구와 충돌하면 새 문서와 현재 0절을 우선한다. 신규 서버 API는 아직 구현하지 않았다.

> 선행 보완: 기존 개인 서랍 GET은 무인증일 때 query user_id가 저장소 조회에 전달될 수 있는 코드 경로가 확인됐다. 프론트 로그인 gate는 이를 해결하지 않는다. 개인 목록 JWT 필수·sub 소유권 검사를 P0로 구현해야 한다. 현재 CMS 뉴스의 응답 id는 slug이며 기존 읽기 저장의 article_no와 같다고 가정할 수 없다. 새 인수 문서 3절을 먼저 확인한다. 운영 영향은 이번 조사에서 검증하지 않았다.

기준은 [개인화 대시보드 통합 기획안](../../worklog/2026-10/2026-10-14-개인화-대시보드-통합기획-design.md)의 15~18절이다. 이번 구현은 프론트엔드에 한정한다. 아래 신규 API·DB·분석·푸시 발송·리워드 판정은 제안이며 서버에 구현하지 않았다. 리워드 미리보기와 개인화 푸시 설정 초안은 프론트엔드에 추가했다.

## 0. 확정 접근 정책과 프론트엔드 활성화

| 구분 | 정책 | 적용 시점 |
|---|---|---|
| 정식 서비스 | ‘나의 LENS’(`/my-lens`)는 로그인한 사용자만 접근 | 프론트엔드 제한은 2026-10-14 사용자 전환 요청으로 적용. 서버 인수·운영 배포는 별도 |
| 현재 개발 단계 | 비로그인 접근 예외 종료. 직접 URL·내부 탭·딥링크에도 로그인 필요 | 인증 확인 중에는 대시보드 훅·본문을 마운트하지 않음. 비로그인은 `/login`으로 이동 |

기존 `AuthContext`로 로그인 상태를 확인하고, 기존 내부 경로 복귀 기능으로 로그인 뒤 탭·검색 파라미터·해시를 복원한다. 로그아웃하면 대시보드를 내리고 계정 변경 시 화면 상태를 다시 만든다. 이전 절의 비로그인 유지 문구는 당시 구현 기록이며 현재는 이 0절을 우선한다. 백엔드 인증 동작은 변경하지 않았다. 대시보드 로그인 필수는 계정 동기화 완료를 뜻하지 않는다. 공용 홈·공개 콘텐츠의 열람 정책도 별개다.

정식 서비스에서 백엔드·프론트엔드가 함께 충족할 요구사항(프론트엔드 제한 활성화와 서버 인수 완료는 별개):

1. 메뉴뿐 아니라 직접 URL·북마크·알림 링크에서도 대시보드 로그인 여부를 확인한다. 비로그인 사용자는 로그인 화면으로 이동하고, 로그인 성공 후 `/my-lens`로 복귀한다. 복귀 주소를 받는 경우 허용된 내부 경로만 사용한다.
2. 개인 대시보드 집계 및 계정 기록 조회·변경 API는 요청마다 서버가 인증 토큰을 검증한다. `X-Voter-Id`, 클라이언트의 로그인 표시, 요청의 `user_id`만으로 인증을 대신하지 않는다.
3. 인증 정보가 없거나 만료·무효이면 개인 데이터를 반환하지 않고 `401`을 반환한다. 인증 후에도 다른 계정 소유 데이터에 대한 접근은 거부한다. 이 실패를 빈 목록이나 공통 추천의 정상 응답으로 감추지 않는다.
4. 세션 만료·로그아웃 시 프론트엔드는 계정에 속한 화면 상태·클라이언트 캐시의 개인 데이터를 비우고 로그인을 안내한다. 사용자 집계 응답은 `Cache-Control: private, no-store`로 제공한다. 기존 익명 브라우저 기록을 계정에 자동 귀속하거나 임의로 삭제하는 정책을 뜻하지 않는다.
5. 운영 개인 API에 익명 우회 경로·공용 사용자 ID를 추가하지 않는다. 이번 변경은 프론트엔드 화면 진입 제한이며 서버 인증·계정 이관·배포를 대신하지 않는다.

## 1. 이번에 실제 연결한 것

아래 표는 현재 개발 단계의 데이터 연결 현황이다. 화면은 로그인 후 접근하며 브라우저·기기 기반 저장과 미연동 기능의 범위는 그대로다.

| 화면 | 사용한 데이터/기능 | 범위와 제약 |
|---|---|---|
| 나를 위한 레터 | 기존 발행 목록 + 기존 관심 피드 + 명시적 관심 카테고리 + 작성 에디터 팔로우 | 관심 근거가 없으면 ‘최근 발행된 레터’. 후속 기사·이해도·취향 확률이라고 표현하지 않음 |
| 읽을 시간 | 실제 `read_minutes` 합계가 5/10분 이하인 최대 3편 | ‘여유롭게’는 시간 상한 없음. 시간에 맞는 편이 없으면 조건 변경 안내. 설정은 이 브라우저에 저장 |
| 저장한 레터 | 기존 `lens-letter-saved`, `useLetterShelf` | 기존 레터 목록·상세와 같은 slug·저장 키. 최대 200개, 로그인해도 계정 동기화는 아직 없음 |
| 아직 안 읽은 레터 | 저장 slug와 기존 `lens-letter-read`의 차집합 | 기존 상세에서 70% 진행 시 읽음으로 기록. 정확한 중단 위치·청취 진행·완독 시각은 없음 |
| 이전 레터 복원 | 최신 50편 밖의 저장/읽음 slug를 기존 상세 API로 조회 | 동시 요청 4개. 실패/비공개/삭제를 현재 상세 API만으로 구분할 수 없어 기록을 지우지 않고 재조회 안내 |
| 관심사 설정 | 기존 기기별 관심 GET/PUT, 주제 목록 | 카테고리는 공용 `ECON_CATEGORIES`, 주제는 기존 API. 선택하지 않은 기존 topic도 보존. 실패하면 선택 유지·오류 안내 |
| 관심의 흐름 | 읽음 slug와 불러온 레터의 카테고리 교집합 | 확인된 카테고리별 레터 수만 집계. 날짜 없는 이력으로 주간 통계·연속일·학습 성취를 만들지 않음 |
| 팔로우한 에디터 | 기존 `lens-letter-editors`, 에디터 사전 | 브라우저 범위. 실제 에디터 소개/기존 레터 화면으로 연결. 대시보드에서 기존 관심을 덮어쓰는 팔로우 변경은 하지 않음 |
| 내 서랍에서 다시 발견 | 로그인 상태의 기존 저장 문장 조회 API | 로그인 사용자 ID가 바뀌면 이전 계정의 문장을 표시하지 않음. 홈 최대 3개 요약·통합 서랍과 원문 연결. 기존 `/?tab=archive` 및 저장·삭제 유지(11절) |
| 읽기 리워드 | 주간 스탬프·배지 조건·달성 화면 예시 | 실제 기록은 미연동 상태. 예시를 명시적으로 켠 경우에만 가상 스탬프·배지를 표시하며 저장·지급하지 않음 |
| 개인화 푸시 설정 | 유형 3종, 빈도·시간·시간대·주간 요일·일시 중지, 로컬 초안 | 기본 전체 꺼짐. 브라우저 저장만 가능. 동의·구독·푸시 권한 요청·토큰 등록·발송 없음 |
| 이메일 알림 | 기존 `SubscribeDialog`, 구독/확인/수신거부 API | 기존 동의 및 확인 메일 절차 재사용. 전송 성공이나 이미 구독한 상태를 대시보드가 추정하지 않음. 푸시 권한 요청 없음 |

### 기존 API (새 API가 아님)

- `GET /api/v2/issue-letters?limit=50`
- `GET /api/v2/issue-letters/{slug}`
- `GET /api/v2/issue-letters/topics`
- `GET /api/v2/issue-letters/me/interests`
- `PUT /api/v2/issue-letters/me/interests` — `{"interests":[{"type":"category","key":"industry"},{"type":"topic","key":"semiconductor"}]}`
- `GET /api/v2/issue-letters/me/feed?limit=30`
- 관심 관련 요청은 기존 `X-Voter-Id` 기기 식별 방식. 계정 인증·동기화를 뜻하지 않음.
- `GET /api/archive?user_id=…&limit=200` — 대시보드는 기존 로그인 인증 클라이언트 `authFetch` 사용. 이전 서랍의 기본 50개 조회는 유지.
- 기존 `POST /api/archive`, `DELETE /api/archive/{id}?user_id=…` — 통합 서랍에도 기존 문장 저장·삭제 재사용(11절).
- `POST /api/v2/issue-letters/subscriptions` 및 기존 `/subscriptions/confirm`, `/subscriptions/unsubscribe`, `/subscriptions/preview`, `/subscriptions/test`.

API origin은 기존 프론트엔드 설정을 따른다. API 응답 실패 시 화면 전체를 중단하지 않고 영역별 안내를 보여준다. 관심 설정의 PUT은 전체 교체 방식이다. 새로운 부분 수정 API가 생기기 전에는 기존 topic을 빠뜨리지 않아야 한다.

## 2. 우선 요청: 계정 기준 저장과 목록 일괄 조회

**북마크·팔로우·열람 이력의 계정 동기화와 오래된 저장 레터 일괄 조회**가 가장 먼저 필요하다. 기존 [북마크 동기화 연동 요구사항](../모아쓰기레터/북마크_동기화_연동요구사항.md)과 API/충돌 정책을 먼저 맞춘다. 같은 목적의 API를 별도로 중복 구현하지 않는다.

요청 사항:

1. 계정은 서버가 검증한 인증 토큰에서 결정한다. 기기 ID나 클라이언트 `user_id`만으로 다른 계정의 기록을 조회·수정할 수 없어야 한다. 기존 아카이브 API도 토큰 소유자 검사를 확인한다.
2. 로그인 전 로컬 기록은 안내와 동의를 거쳐 계정 기록에 병합한다. 실패하면 원본 로컬 기록을 유지한다. 계정 변경·로그아웃 시 다른 계정에 로컬 기록을 자동 귀속하지 않는다.
3. 저장/해제는 멱등이어야 한다. 재시도·중복 클릭·네트워크 지연으로 저장이 반전되지 않도록 `PUT`(저장), `DELETE`(해제) 또는 명시적 상태 요청을 사용한다.
4. 응답에 `saved_at`, `updated_at`, stable slug, 표시용 메타데이터, `next_cursor`를 포함한다. 삭제·비공개·조회 실패를 구별하고 표시 불가능한 콘텐츠 본문을 반환하지 않는다.
5. 이미 발행 목록 밖으로 밀려난 저장 slug를 일괄 복원할 읽기 API가 필요하다. 현재 프론트엔드는 상세 요청을 4개씩 나누어 처리한다. 저장 수가 많으면 초기 지연과 요청량이 늘 수 있다.
6. 에디터 팔로우와 직접 선택한 관심사를 구분해 저장한다. 기존 레터의 팔로우 변경이 관심 전체를 대체하는 동작과 충돌하지 않도록 한다.

## 3. 대시보드 집계 응답 제안

아래는 프론트엔드가 원하는 **응답 형태 제안**이다. 경로는 서버 팀과 기존 북마크 설계에 맞춰 확정한다. 현재 프론트엔드에서 이 경로를 호출하지 않는다.

`GET /api/v2/me/dashboard?minutes=5&format=letter&cursor=…`

```json
{
  "generated_at": "2026-10-14T02:00:00Z",
  "scope": "account",
  "preferences": {
    "interests": [{"type": "category", "key": "industry", "label": "산업"}],
    "followed_editor_ids": ["mincheol"],
    "minutes": 5,
    "format": "letter"
  },
  "recommendations": [{
    "slug": "existing-published-slug",
    "title": "실제 발행 콘텐츠의 제목",
    "read_minutes": 4,
    "formats": ["letter"],
    "reason": {"type": "selected_category", "key": "industry", "text": "관심 카테고리 ‘산업’의 레터예요"},
    "saved": true,
    "read": false
  }],
  "saved": {"items": [], "total": 0, "next_cursor": null},
  "continue": [],
  "followups": [],
  "review_highlights": [],
  "activity": {"available": false, "timezone": "Asia/Seoul"},
  "notifications": {"email_status": "unknown", "push_supported": false}
}
```

- 공개 콘텐츠만 공유 캐시한다. 사용자 집계 응답은 `Cache-Control: private, no-store`를 사용하고 CDN에서 타 계정에 재사용하지 않는다.
- 영역별 `available`, `error_code`, `retryable`을 구분한다. 데이터 없음은 빈 배열, 조회 실패는 명시적 상태로 전달한다.
- 추천의 근거는 enum과 표시 문구를 함께 전달한다. 단순 주제 겹침과 편집자가 검증한 후속 관계는 다른 근거다.
- 개별 콘텐츠의 제공 포맷과 실제 길이를 내려준다. 재생 가능한 미디어가 없는 레터에 듣기·보기 버튼을 만들지 않는다.
- 읽기 예산은 선택 콘텐츠의 실제 합계를 상한으로 삼는다. 추천 후보가 부족하면 공통 최신 콘텐츠로 보완하되 그 이유를 표시한다.

## 4. 이용 이력·이어보기·리워드

기존 레터 읽음 기록에는 slug만 있다. 후속 뉴스 개인화에서 추가한 브라우저 열람 신호에는 시각·분류·키워드가 있지만 화면 체류에 따른 약한 관심 신호이며 유효 완료/보상 기록이 아니다. 주간 보상, 연속 이용, 재생 위치, 완료 시각, 포인트 잔액을 계산할 근거로 사용하지 않는다. 프론트엔드에는 미연동 상태의 스탬프·배지와 명시적인 달성 예시를 추가했다. 다음 데이터가 준비된 뒤 실제 기록을 표시한다. 데이터가 없다는 이유로 0일·미획득으로 단정하지 않는다.

| 필요 기능 | 필요한 서버 데이터/정책 |
|---|---|
| 주간 기록 | 유효 이용 이벤트 시각, KST 일자, 콘텐츠·포맷별 완료 기준. 중복 방문을 하루 여러 번으로 세지 않음 |
| 이어 읽기 | 계정/콘텐츠/포맷 키, 마지막 위치, 마지막 이용 시각, 완료 여부. 열린 것과 완료한 것을 구분 |
| 이어 듣기 | 실제 미디어 ID·길이·재생 초, 여러 기기 갱신 충돌 정책 |
| 리워드 | 적립 조건·상한·유효기간·중복 방지 키·정정 가능한 원장. 클라이언트 클릭만으로 지급하지 않음 |
| 내 기록 재발견 | 저장 시각과 마지막 노출 시각, 숨김/빈도 설정. 민감한 문장은 푸시 본문에 기본 노출하지 않음 |

기존 `letter_complete` 계측과 상세의 70% 읽음 기준이 서비스에서 의도한 유효 이용에 해당하는지 먼저 합의한다. 기존 읽음 slug를 과거 주간 기록으로 소급 변환하지 않는다. 리워드는 선택 참여이며 끊긴 연속일 때문에 기존 기록을 지우지 않는다.

## 5. 관심 이슈의 후속 소식

키워드 검색 결과를 ‘다음 소식’이라고 부르지 않는다. 콘텐츠 간 관계를 내려줄 서버 기능이 필요하다.

- `seed_content_id`, `related_content_id`, `relation_type`(`followup`, `background`, `different_perspective`), `relation_reason`, 관계 확인 시각.
- 실제 새 변화가 발생한 후속과 단순 배경 해설을 구별한다.
- 이미 읽은 내용, 중복 이슈, 품질/다양성 제어와 관심 없음 피드백을 반영한다.
- 추천 실패·관계 없음이면 해당 섹션을 생략한다. 정해진 개수를 채우려고 임의의 기사를 후속으로 표시하지 않는다.

## 6. 개인화 알림

기존 이메일 구독 신청·동의·확인 흐름과 신규 개인화 푸시 설정을 분리한다. 이메일 구독 폼은 기존 정책대로 `frequency=daily`, `send_hour=8`을 보내며 신규 설정으로 변경되지 않는다. 개인화 푸시는 유형·빈도·시간·시간대·주간 요일·일시 중지를 조작하는 프론트엔드 초안이며 실제 수신 설정이 아니다. 서버 연결 전까지 제목 옆에 ‘푸시 발송 미연동’, 본문과 저장 결과에 ‘브라우저 초안·수신 시작 안 됨’을 표시한다.

- 채널별 동의 상태, 이메일 확인 상태, 주제/에디터 선택, 시간대, 발송 시간, 빈도, 조용한 시간, 일시 중단, 최근 발송 상태를 조회·수정하는 API.
- 브라우저/앱 push token 등록·해제, 권한 거부/만료 처리와 로그아웃 시 토큰 귀속 해제. Web Push 지원 범위를 명시한다.
- 알림의 도착 경로는 실제 존재하는 콘텐츠/이슈 또는 `/my-lens`로 연결한다.
- 기본은 하루 한 번 요약, 중복 발송 방지, 이미 읽은 콘텐츠 제외, 연속 미반응 시 빈도 축소를 기획 기본안으로 검토한다.
- 테스트 발송과 정식 구독은 별도이며, 신청 응답만으로 확인된 구독 상태를 반환하지 않는다. 주소 존재 여부를 노출하지 않는 기존 정책을 유지한다.

## 7. 백엔드 인수 조건


1. `/my-lens`의 직접 진입·메뉴·알림 진입 모두 비로그인 시 로그인으로 연결되고 성공 후 대시보드로 복귀한다. 개인 API의 무인증·만료 토큰 요청은 `401`로 거부되며, 로그아웃·계정 변경 후 이전 계정 데이터가 화면이나 캐시에 남지 않는다.
2. 두 계정 A/B의 저장·관심·아카이브가 섞이지 않는다. 인증 만료·권한 없음과 빈 목록이 구분된다.
3. 로그인 전 기록 병합·실패 복구·여러 기기 해제 충돌·재시도 멱등성이 검증된다.
4. 오래된/삭제된/비공개 콘텐츠와 페이지네이션에서 중복·누락·불필요한 상세 요청이 없다.
5. 추천 이유·제공 포맷·예상 길이가 실제 데이터와 일치한다. 타임스탬프 없는 기존 이력으로 주간 기록을 만들지 않는다.
6. 구독 동의/확인/해제·알림 토큰 귀속·중복 억제·조용한 시간·수신거부가 실제 발송 경로에서 검증된다.
7. 서버 문서가 준비되면 프론트엔드의 로컬 저장 어댑터와 영역별 조회를 교체한다. 기존 내 서랍 및 레터 저장 경로는 회귀 검증한다.


## 8. 리워드·개인화 푸시 프론트엔드 확장 계약 (2026-10-14)

### 8.1 현재 프론트엔드 경계

- 별도 새 API를 호출하지 않는다. `ReadingRewards`는 실제 상태를 ‘기록 연동 준비 중’, 주간 기록을 `— / 3일`로 표시한다. ‘달성 화면 예시 보기’의 월·수·금 스탬프와 주간 배지는 가상 예시다. 기본 꺼짐이며 새로고침 시 닫힌다. 클라이언트 수동 지급·실제 잔액·교환 버튼은 없다.
- `NotificationSettings`는 `lens-dashboard-notification-draft-v1` 키에 버전 1 JSON을 명시적 저장 버튼으로 기록한다. 동의 필드·push token·user ID가 없다. 타입/버전/시간대/요일/시각 검증에 실패한 저장값은 복원하지 않고 재설정을 안내한다. 저장 실패 시 선택을 유지하고 성공으로 표시하지 않는다.
- 초안은 브라우저 단위로 공유되며 계정 설정이 아니다. 로그인·계정 전환으로 자동 업로드하거나 수신 동의로 승격하지 않는다. 서버 연결 이후에도 사용자 검토와 별도 동의 없이 이 초안을 적용하지 않는다.
- 푸시 유형: `briefing`, `followups`, `weekly`, 기본 모두 `false`. 빈도: `daily` 또는 `threeDays`(월·수·금), `time=08:00`, `timezone=Asia/Seoul`, `weeklyDay=1`(0=일요일), `paused=false`. 주간 기록 요일은 다른 두 유형의 빈도와 별개다.
- 현재 선택 가능 시간대: `Asia/Seoul`, `America/New_York`, `Europe/London`, `UTC`. 선택 시간대의 21:00~08:00을 방해 금지로 취급하며 허용 시각은 08:00~20:59다. 프론트엔드 초안은 실제 예약 시각·DST 전환을 계산하지 않는다.
- 알림 미리보기는 선택 유형·빈도·시각을 설명한다. 브리핑 문구에는 기존 추천 레터 제목이 있으면 재사용한다. 후속 소식·주간 기록은 일반 예시 문구이며 검증된 후속 기사나 실제 집계가 있다고 주장하지 않는다.
- 기존 북마크·내 서랍·이메일 구독·로그인 정책을 변경하지 않는다. 정식 로그인 필수와 개발 중 비로그인 진입 예외는 0절 그대로 유지한다.

### 8.2 제안 API와 응답 상태

경로와 필드명은 서버 팀과 확정할 계약 초안이다. 현재 화면은 호출하지 않는다.

| 제안 API | 요청/응답과 책임 |
|---|---|
| `GET /api/v2/me/rewards?week=YYYY-MM-DD` | 계정, 시간대, 월요일 기준 `week_start`, `week_end`, `rules_version`, 실제 일별 스탬프와 배지/진척을 반환. 주간 데이터 없음과 일별 미완료와 조회 실패를 구별 |
| `GET /api/v2/me/notification-preferences` | 설정 `revision`, 유형·빈도·시각·IANA 시간대·주간 요일·중지 여부, 별도의 채널 동의/기기 등록/전송 가능 상태 반환 |
| `PUT /api/v2/me/notification-preferences` | 검증된 설정 + 동시 수정 방지 revision. 성공 응답은 저장된 정규화 값 반환. 충돌은 409, 검증 실패는 422. 수신 동의와 기기 권한이 없으면 설정을 저장해도 발송하지 않음 |
| `POST /api/v2/me/push-subscriptions` | 별도 동의와 사용자 액션에 따른 권한 허용 후 기기 구독 등록. 인증 토큰으로 소유자 결정 |
| `DELETE /api/v2/me/push-subscriptions/{id}` | 해당 계정 소유 구독만 해제. 로그아웃·계정 변경 시 이전 계정에 연결된 기기 토큰 해제 정책 마련 |

- 완료는 열람 slug와 다르다. 기획안의 초기 완료 추정(레터·웹툰 80% + 전면 이용 시간, 미디어 유효 구간 80%)을 운영 확정하고 `rules_version`으로 관리한다. 같은 이슈·일자·계정의 중복 지급 방지와 지연 이벤트·정정 정책을 포함한다. 스탬프는 하루 최대 1개, 주간 배지는 서로 다른 3일/3개 분야/저장한 2편 재확인 등 기획의 조건을 서버가 판정한다.
- `paused=true`면 모든 개인화 푸시를 중단하되 선택값을 보관한다. 전체 유형이 꺼져 있으면 발송하지 않는다. 서버 저장 실패를 구독 성공으로 바꾸지 않는다. 이메일 구독에는 영향을 주지 않는다.
- 여러 유형이 같은 날 겹치면 계정·채널을 합쳐 하루 최대 1건으로 묶는다. 후속 이슈의 유효성, 이미 읽음/중복/삭제/오래된 콘텐츠 제외, 주간 기록 부재, 빈 후보 시 생략, 휴면 7일 빈도 축소·14일 중단을 기획 정책과 합의한다. 밀린 알림을 다음 날 몰아서 보내지 않는다.
- 실제 예약에는 IANA 시간대와 DST, 방해 금지 구간, 일자 경계를 적용한다. 지원 범위 밖 시간대와 잘못된 시각을 서버에서도 거부한다. 사용자 수정·중지·수신거부는 대기 큐에도 반영한다.
- 서버 연동 시 현재 ‘미연동’ 표시를 단순 삭제하지 않는다. `서버 설정 저장됨`, `권한 필요`, `기기 미등록`, `수신 중`, `일시 중지`, `저장 실패`를 실제 상태에 맞춰 구별한다. 브라우저 권한 요청을 페이지 진입/설정 초안 저장 시 자동 실행하지 않는다.

### 8.3 추가 인수 시나리오

1. 새 방문에서는 리워드 값이 미확정으로 표시되고 모든 푸시 유형이 꺼져 있다. 예시 스탬프·배지가 실제 획득으로 저장되지 않는다.
2. 유형·주 3회·시각·시간대·주간 요일·중지 값을 저장/복원한다. 변경 취소는 마지막 성공 저장값으로 돌아간다. 저장소 실패·손상된 저장값·21시 경계는 명확히 안내한다.
3. 초안 저장과 리워드 예시 조작만으로 푸시 권한·서버 쓰기·메일 전송·보상이 발생하지 않는다.
4. 서버 연동 후 로그인·권한·동의·기기 등록을 각각 확인한다. 사용자 A의 동의나 기기 토큰이 B 계정으로 승계되지 않고 익명 초안은 별도 검토 없이 전송되지 않는다.
5. 시간대/DST·중복 완료/발송·중지·유형 전체 꺼짐·주간 기록 없음·후속 관계 없음·발송 직전 읽음/삭제를 실제 서버 경로에서 검증한다.


## 9. 오른쪽 주간 요약과 주·월·연 읽기 기록 (2026-10-14)

### 프론트엔드 반영

- 오른쪽 첫 카드에 이번 주 스탬프 7일, 주간 목표 3일 요약, ‘주·월·연 기록 보기’를 배치했다. 실제 기록은 연동 대기이며, 본문에서 켠 예시 상태는 요약 카드에도 동기화한다. 예시 닫기/기간 변경 시 양쪽 모두 실제 기록 대기 상태로 돌아간다.
- 본문 읽기 기록의 기간 선택: 주=월~일 스탬프, 월=실제 날짜 달력, 연=12개월별 읽은 날/콘텐츠 요약. 이전/다음과 이번 주/이번 달/올해 복귀를 제공한다. 현재보다 미래인 기간으로 이동하지 않는다. 기간 단위 변경은 해당 단위의 현재 기간으로 복귀한다.
- 현재 날짜와 달력은 한국 시간(`Asia/Seoul`) 기준이다. 월의 길이·윤년·연도 경계를 계산하며, 오늘을 표시한다. 화면의 날짜·빈 달력은 실제 이용 데이터가 아니다. 날짜 없는 기존 slug로 주·월·연 집계를 만들지 않으며 ‘—’는 0이 아닌 미확정값이다.
- 기간별 집계는 읽은 날·읽은 콘텐츠·만난 분야를 보여줄 자리다. 기존 브라우저 누적 카테고리 집계는 별도 유지한다. 기간 선택으로 기존 누적 수치가 해당 기간의 기록처럼 보이면 안 된다.
- 보상 조건은 계속 주간 기준이다. 월/연 조회를 추가했다고 월간/연간 보상이나 알림을 새로 지급·발송하지 않는다. 알림의 ‘한 주의 관심 기록’은 기존 주간 유형으로 유지한다. 개발 중 비로그인 진입도 유지한다.

### 서버 조회 계약 추가 제안

`GET /api/v2/me/activity?period=week|month|year&anchor=YYYY-MM-DD&timezone=Asia/Seoul`

프론트엔드는 아직 위 경로를 호출하지 않는다. 기존 대시보드/리워드 집계와 공통 완료 이력을 사용하고 동일 목적 집계 서비스를 중복 만들지 않는다.

- 서버가 인증 토큰의 계정을 기준으로 범위를 판정한다. 응답에 `period`, `timezone`, `range_start`, `range_end`, `available`, `generated_at`, `rules_version`과 `summary`, `buckets`를 제공한다.
- 주간: 월요일~일요일 7개 일별 bucket. 월간: 해당 월의 모든 날짜. 연간: 1~12월의 월별 bucket. 각 bucket에 실제 `read_days`, `completed_content_count`, `category_count`, `stamp_count`를 정의하고 제공한다. 미래 bucket은 `future`, 집계 미준비/실패는 `unavailable`로 0과 구분한다.
- `summary.read_days`는 해당 기간에 유효 읽기/재확인 활동이 있는 고유 일자 수다. `stamp_count`는 신규 완료가 발생해 스탬프가 지급된 날짜 수다. 복습만 한 날은 읽은 날로 인정할 수 있어 두 수치를 같다고 가정하지 않는다. 세부 인정 기준은 완료 정책과 함께 확정한다.
- `completed_content_count`는 기간 내 유효 완료한 고유 콘텐츠/이슈 기준으로 제안한다. 같은 이슈의 포맷 전환/반복 열기를 중복 집계하지 않는다. 월/연 합계는 주/월 bucket 단순 합산으로 계산하지 않고 기간 전체 고유 키로 계산한다. `category_count`도 분류 키의 합집합으로 산출한다.
- 실제 일별/기간 기록에 없는 값은 만들어 채우지 않는다. 성공 응답의 실제 활동 없음은 0/빈 기록으로, 조회 실패는 오류 상태로 전달한다. 프론트엔드는 연동 대기·로딩·조회 실패·활동 없음·실제 기록을 각각 구분해 연결한다.
- 주가 월·연도를 가로질러도 요청한 주 전체를 반환한다. 한국 시간의 완료일/주 경계, 지연 이벤트 반영, 수정/취소된 완료 이벤트의 재집계, 보관 기간·가장 오래 조회 가능한 범위를 명시한다. 보관 기간 밖은 0이 아니라 조회 범위 제한으로 응답한다.
- 오른쪽은 언제나 현재 주를 조회한다. 본문에서 과거 월/연을 선택해도 오른쪽을 과거 주로 바꾸지 않는다. 실제 동일 주를 조회할 때는 같은 데이터/캐시를 사용해 수치가 불일치하지 않게 한다.

### 필요한 서버 기능 — 기존 계약을 확장할 것

1. **콘텐츠 식별/메타데이터:** raw news ID, CMS lens ID, 레터 slug, 원문 URL, 이슈 ID, 포맷을 매핑한다. 과거 읽음·저장 문장의 기사 ID를 일괄 해석하고 실제 분류·표준 키워드·발행/수정/공개 상태·canonical URL을 제공한다. 제목 유사성만으로 같은 글/후속 관계를 단정하지 않는다.
2. **동의·개인화 제어:** 계정별 수집/추천 활성화, 제외 분야·키워드, 관심 없음, 추천 이유, 프로필 수정/초기화, 열람/저장 원문 데이터의 목적과 보존/삭제 범위를 마련한다. 게스트 기록은 별도 사용자 검토 없이 계정에 합치지 않는다. 민감한 성향을 추론하거나 단순 클릭을 확정 선호로 저장하지 않는다.
3. **이벤트 수집:** 인증 계정, 콘텐츠/이슈/포맷, event ID, 발생 시각·수신 시각, 가시 체류 시간, 진행률/유효 재생 구간, 완료 기준 버전과 처리 상태를 받는다. 클라이언트 재시도·포맷 이동·동일 글 반복 노출을 구분하고 중복 방지한다. 새 프론트엔드의 10초 신호를 `complete`나 보상 요청으로 승격하지 않는다.
4. **관심 프로필:** 직접 선택, 열람, 저장 문장, 북마크를 서로 다른 출처로 계산한다. 기사별 고유 집계, 최근성 감쇠, 장기/단기 관심, 반복 기사 노출 편향·분류 다양성·사용자 수정/거부를 반영한다. 응답에 `evidence_type`, 근거 콘텐츠 수, 분석 기간, 신뢰/가용 상태를 포함한다.
5. **연관 키워드/문장 추천:** 별칭·동의어·관련 주제, 문장 임베딩/의미 검색과 재정렬을 서버에 구현한다. 예: 실제 엔터티 사전으로 ‘반도체 ↔ 메모리·HBM’ 관계가 확인된 경우만 확장한다. 직접 단어 일치와 확장 관계의 이유를 구별하고 관계/모델 버전·검증 근거를 제공한다. 현재 화면의 ‘연관 키워드 분석 준비 중’ 표시는 이 계약 인수 후 변경한다. 이번 작업에서 추론 모델 호출/인프라 생성은 하지 않는다.
6. **‘좋은 글’ 후보:** 공개·발행 상태, 신뢰 가능한 근거/출처, 정정·취소 여부, 최신성, 편집자 검수·추천 여부, 독창적인 새 사실·내용 충실도 등 운영 기준을 합의한다. 편집 검수/품질 필터를 통과한 후보 안에서 관심 연관성과 다양성을 정렬한다. 클릭률/인기만으로 품질을 정의하거나 빈칸을 임의 점수로 채우지 않는다. 아직 존재하지 않는 품질 기준을 화면에서 충족했다고 표시하지 않는다.
7. **새 글 알림:** 발행/정정 이벤트에서 품질·관심·사용자의 활성 기준을 모두 확인한다. 자주 본 분야의 새 글, 등록/연관 키워드의 새 글, 저장 문장과 연관된 새 글을 하나의 브리핑 후보로 묶는다. 단순 연관 추천과 검증된 이슈 후속을 구별한다. 이미 읽었거나 저장 원문 자체인 글, 오래된 글, 중복 이슈는 제외한다. 후보 없으면 생략하고 계정·채널 통합 하루 최대 1건·조용한 시간·중지·휴면·철회 정책을 적용한다.
8. **비공개 문장 보호:** 저장 문장 기반 추천 참여와 푸시 사용을 분리한다. `sentenceSource=false`이면 문장 근거만 있는 글을 발송 후보에서 제외하고, 활성화해도 문장 원문은 잠금 화면/알림 로그/공개 검색 URL에 포함하지 않는다. 계정/기기 토큰 변경과 문장 삭제/수신 철회 시 대기 큐와 프로필/캐시를 갱신한다.

집계 응답에는 `signals.categories[]`, `signals.keywords[]`, `signals.sentence_topics[]`, 출처/범위/미해석 수와 `recommendations[].reasons[]`를 제안한다. 알림 설정 계약에는 `sources: {categories, keywords, saved_sentences}`를 추가하고 현재 로컬 flat 필드와 명시적으로 매핑한다. 브리핑이 켜져 있는데 기준이 모두 꺼진 상태는 저장 검증에서 거부한다. 기존 이메일 구독으로 이 설정을 전달하지 않는다.

### 인수 조건과 현재 검증 경계

- 현재 확인: 게스트의 실제 기사 10초 열람 → 브라우저 기록 → 대시보드 분야·용어 노출·읽은 글 제외. 별도 fixture로 분야/키워드 필터, 소스 선택·저장·복원·근거 없는 문장 예시 방지, 공개 조회 실패·재시도를 검사한다. 문장 단어 일치·ID 제외·중복/구 카테고리와 저장 초안 마이그레이션은 순수 함수 검사 대상이다.
- 서버 연동 때 실제 로그인 A/B 변경·세션 만료, 과거 기사 메타데이터 일괄 해석, 실제 저장/삭제 문장 반영, 의미 확장 정확도·다양성·품질 기준, 새 글 발행 후 동의/비동의·중지·중복·미열람 조건별 실제 발송을 검증한다. 기존 read POST는 배지 부수효과가 있어 이번 약한 신호 연결에는 사용하지 않았다.
- 새 이벤트·통합 프로필·의미 검색·품질 선별·예약/푸시는 이번에 백엔드에 구현하지 않았다. 로그인 API 응답은 코드 계약을 확인해 클라이언트만 연결했으며 실제 인증 계정 데이터 인수는 미완료다.

## 11. 내 서랍을 나의 LENS에 편입 (2026-10-14)

### 화면·진입 계약

- 개인 메뉴의 진입점을 ‘나의 LENS’로 통합한다. 내부 메뉴는 홈(`/my-lens`), 내 서랍(`?tab=archive`), 읽기 기록·리워드(`?tab=records`), 관심사·알림(`?tab=settings`)이다. 기존 `/?tab=archive`와 그 화면의 문장 저장·삭제 기능은 유지한다. 기존 주소를 다른 화면으로 리다이렉트하거나 삭제하지 않는다.
- 홈은 현재 계정의 최근 저장 문장을 최대 3개 표시한다. 문장마다 원문 보기와 관련 글 보기를 제공한다. 서랍은 담은 문장/저장한 레터 구분, 제목·내용 검색, 문장 복사·삭제, 문장별 관련 뉴스를 제공한다. `?tab=archive&sentence={id}#ml-sentence-related`로 선택한 문장을 공유 없이 개인 화면 안에서 다시 찾을 수 있다. 저장 레터 바로가기는 `?tab=archive&kind=letters`다.
- 개발 중 게스트의 화면 접근을 유지한다. 게스트에게 계정 문장을 예시로 채우거나 인증 API를 우회하지 않는다. 정식 서비스에서 나의 LENS 및 내부 메뉴·딥링크는 모두 로그인 필수다. 인증 주체 확인은 서버에서도 적용하며 URL의 문장 ID나 `user_id`를 권한 근거로 믿지 않는다.

### 이번 프론트엔드에서 재사용한 연결

| 기능 | 연결 | 범위 |
|---|---|---|
| 뉴스 본문 문장 저장 | 기존 `POST /api/archive` 그대로 사용. 성공 안내에 통합 서랍 바로가기 추가 | 기존 로그인 조건·원문/저장 payload 유지. 실제 알림 수신 동의나 보상 지급 요청 없음 |
| 통합 서랍·홈·관심 프로필 | 기존 `GET /api/archive?user_id=…&limit=200` 한 조회 결과 공유 | 이전 50개에서 최대 200개로 확대. 이전 서랍 자체의 기존 조회 계약은 유지. 개인 서버 문장과 브라우저 저장 레터의 범위를 구분해 표시 |
| 삭제 | 기존 `DELETE /api/archive/{id}?user_id=…` | 사용자가 확인한 뒤 요청. 실패 시 문장 유지, 성공 시 서랍/홈/관심 근거에서 제외 |
| 화면 갱신 | 성공한 문장 저장·삭제 뒤 계정 ID만 담은 브라우저 이벤트로 재조회, focus/pageshow 시 재조회 | 이벤트에 문장 원문을 담지 않는다. 다른 탭 변경은 다시 포커스할 때 조회. 서버 실시간 스트림 아님 |
| 문장별 관련 글 | 선택한 문장 1개에서 단어 추출, 최신 공개 lens 후보 100개와 일치 비교 | 읽은 뉴스 및 모든 저장 문장의 원문을 제외. 일치 결과만 최대 3개. 일치 없으면 빈 결과, 최신 뉴스로 대체하지 않음. 의미 검색·품질 검증은 아직 미연동 |
| 원문 | 공개 기사 메타데이터의 정식 분류/날짜 URL 우선, 확인된 레터 slug면 레터 상세, 미확인 ID는 기존 `/lens/{id}` 유지 | URL 조회 범위 밖 원문의 전체 매핑은 서버 확장 필요 |
| 저장 레터 | 기존 `lens-letter-saved`와 동일한 북마크 상태·해제 동작 | 기기 저장만 제공. 문장처럼 계정 동기화가 끝났다고 표시하지 않음 |
| 관련 글→알림 | `?tab=settings#ml-notifications`로 연결 | 문장 활용 기본 꺼짐, 알림 유형별 수신 모두 기본 꺼짐. 로컬 초안만 저장, 실제 동의/발송은 미연동 |

### 서버에 필요한 후속 작업

1. **서랍 페이지 조회**: 최대 200개는 전체 보관함을 보장하지 않는다. 인증된 계정의 cursor 페이지 조회, 검색/필터, `next_cursor`·총수 또는 조회 범위·보관 정책을 제공한다. 문장 ID, 원문 콘텐츠 종류/ID, 정식 URL, 발행/저장 시각을 반환해 범위 밖 원문도 정확히 연결한다. 현재 프론트엔드는 새 페이지 조회 API를 호출하지 않는다.
2. **문장별 추천**: 제안 계약은 `GET /api/v2/me/archive/{sentence_id}/recommendations?limit=3`이다. 서버가 해당 문장의 계정 소유권을 확인하고 원문 제외·이미 읽은 글 제외·발행 상태·편집 품질 조건을 적용한다. 의미 확장은 실제 분석 근거와 갱신 시각을 반환하며 현재 단어 일치 결과와 구분한다. 문장 원문을 공개 URL 검색 문자열로 전달하지 않는다. 결과 없음/권한 없음/삭제됨/분석 대기/조회 실패를 구별한다.
3. **추천·알림 데이터 갱신**: 문장 삭제 시 추출 주제 및 추천·발송 대기 항목을 재계산/무효화한다. 삭제한 원문/문장이 추천 근거로 남지 않게 한다. 대기 중 삭제와 계정 전환/세션 만료를 인수 조건에 포함한다.
4. **별도 동의**: 저장은 보관·서비스 내 추천 흐름의 입력이며 푸시 수신 동의가 아니다. 실제 발송 전에 로그인, 알림 유형과 활용 신호에 대한 별도 동의, 기기 권한·토큰, 서버 동의 버전/철회 상태를 확인한다. 문장 활용이 꺼져 있으면 그 신호를 알림 후보 선정에서 제외한다. 계정별 동의 저장/동기화 후에만 실제 수신 상태로 표시한다.
5. **좋은 새 글 알림**: 기존 10절의 새 글 이벤트·분야/키워드 매칭과 품질 조건을 사용한다. 중복 원문/동일 이슈 정리, 의미 있는 새 변화, 발행 상태, 하루 최대 1건 및 쉬는 시간/일시 중지/내용 없음 미발송을 적용한다. 알림 payload에는 저장 문장 원문을 넣지 않고 접근 시 다시 계정 권한을 확인한다.
6. **리워드**: 문장 저장·복사·삭제·북마크·알림 설정만으로 스탬프를 지급하지 않는다. 기존 읽기 완료 계약과 주·월·연 집계를 그대로 사용한다.

### 인수 범위

실제 인증 계정으로 저장→재조회→삭제→홈/추천 제외, 오래된 문장 페이지 조회, 서버 소유권 검증, 동의 철회와 삭제 후 대기 알림 취소를 백엔드 연동 인수에서 확인한다.

## 12. 관심 설정의 역할과 화면 정리 (2026-10-14)

- 관심 설정은 사용자가 직접 고른 분야/등록 주제를 추천 입력으로 추가하는 기능이다. 행동으로 관찰한 분야·키워드와 구분한다. 뉴스는 공개 후보에서 분야·주제 단어가 일치하는 글을 우선하고 근거를 표시한다. 레터는 기존 `/me/feed`의 주제·분야 매칭 결과와 이유, 로컬 분야·팔로우 정렬을 함께 사용한다. 선택 자체를 의미 이해·완독·보상 획득으로 해석하지 않는다.
- 현재 저장 계약은 `X-Voter-Id` 기기 식별자 기반의 기존 `GET/PUT /api/v2/issue-letters/me/interests`다. 서버의 `reader_interests` 저장·조회 및 `/me/feed` 추천 구현이 코드에 있다. 계정 인증·기기 간 동기화 완료를 뜻하지 않으며 정식 로그인 필수 정책과 별개다. 로그인 전환 시 서버 권한/계정 이관 조건은 기존 0절을 따른다.
- 뉴스 주제 일치는 주제 사전의 이름을 사용하며 의미 확장은 미연동이다. 레터 서버 피드는 등록 주제/분류의 실제 겹침과 최신성을 사용한다. 겹치는 발행 글이 없으면 추천 결과가 없을 수 있다. 관심 저장으로 푸시·이메일 수신 동의를 변경하지 않는다.
- 기존 서버 `MAX_INTERESTS=40` 계약에 맞춰 분야·주제 합계 40개에서 추가 선택을 차단하고 선택 해제를 허용한다. 변경하지 않은 경우 재저장을 요청하지 않는다. 검색/분야 필터로 안 보이는 기존 선택도 보존한다.
- UI는 선택한 관심 요약/해제, 9개 분야, 선택 사항인 주제 검색·분야별 탐색으로 정리했다. 주제의 실제 `category_slug`로 묶으며 미분류는 기타 주제로 표시한다. 검색은 모든 분야를 대상으로 한다. 주제 목록이 비어 있어도 기존 선택과 분야 설정은 보존한다. 저장 실패 시 선택과 기존 저장값을 유지한다.

- 관심 설정 운영 인수는 후속 범위다. 이번 작업은 프론트 구현과 서버 개발 인계에 한정하며 운영 자료 저장·초기화·발송을 수행하지 않는다.

- 개발 메뉴 노출(2026-10-14): 비로그인 헤더/모바일 메뉴에서 ‘나의 LENS’ 링크는 제거하고 로그인 버튼만 표시한다. 로그인 후 사용자 메뉴에는 ‘나의 LENS’를 유지한다. 후속 전환 요청으로 `/my-lens` 직접 접근에도 0절의 프론트엔드 로그인 제한을 활성화했다.
