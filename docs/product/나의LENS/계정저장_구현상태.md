# 나의 LENS 계정 저장 — 첫 개발 묶음

> 2026-10-14 추가 구현: 계정별 형식 선호·추천/알림 연결, 에디터 팔로우, 서버 완료 읽음 필터, 사용자 선택 북마크 가져오기를 로컬 구현했다. 현재 계약은 [형식 선호·계정 연결](형식선호·계정연결_구현상태.md)의 v1.53·API를 따른다. 아래 이전 단계의 미구현 표시는 해당 구현으로 대체하며 운영은 미반영이다.

> 이후 [백엔드 리뷰 보완](백엔드_리뷰_보완.md)을 적용했다. 콘텐츠 조건·서랍 검사·알림 metadata/lease·worker 회전은 해당 계약을 우선한다. 운영은 미반영이다.

기준: 2026-10-14, 로컬 구현. 운영 DB 마이그레이션·API Gateway 연결·배포는 미실행.

## 구현한 흐름

- 개인 서랍 GET도 Cognito ID token 필수. owner는 검증한 sub로 덮어쓰며 공개 인기 문장은 별도 유지.
- JWT의 exp/sub/iss/aud 필수 및 ID token 검사. 개인 목록·신규 개인 API는 no-store.
- 콘텐츠 resolver는 publication/issue_letter와 id/slug를 명시적으로 구분한다. publication 구slug를 현재 공개 원문으로 해석하고 숫자 slug를 ID로 추정하지 않는다.
- 문장 저장은 현재 공개 publication slug 또는 `publication:ID`를 받으며 기존 article_id 응답은 현재 slug로 유지한다. 조회·저장 응답에 content_key와 href를 추가한다.
- 직접 고른 관심과 읽을 시간은 user_lens_preferences에 계정별 저장한다. 첫 revision은 0→1, 변경은 서버 revision 비교 후 갱신하며 충돌은 409다.
- 레터 북마크는 user_letter_bookmarks에 stable issue_letter ID로 저장한다. 반복 PUT은 saved_at을 바꾸지 않으며 DELETE는 이미 해제된 경우에도 성공한다.
- 저장 목록은 cursor/total을 반환하고 필요한 카드 정보를 일괄 조회한다. 비공개/soft delete 레터는 제목·본문 대신 unavailable을 반환하고 해제를 허용한다. hard delete는 FK CASCADE로 북마크도 제거한다.
- 로그인 프론트는 기존 authFetch로 계정 API를 호출한다. 레터 북마크의 저장·해제는 로그인 필수다. 비로그인 클릭은 로그인 안내만 열고 기존 `lens-letter-saved`는 조회용으로 보존하며 추가·삭제·자동 계정 병합하지 않는다. 기기 관심은 별도 유지한다.
- 저장 결과는 서버 확정 후 표시한다. 개인 API의 401 또는 세션 없음은 대시보드 개인 화면을 내리고 로그인을 다시 요구한다. 실패·설정 충돌을 안내하고 계정 변경/로그아웃 때 늦은 응답을 취소하고 이전 계정 화면 자료를 숨긴다.
- 목록·상세·대시보드의 북마크 상태는 같은 계정 API를 사용하며, 같은 화면 이벤트/탭 저장 이벤트/포커스 복귀에서 재조회한다. 홈의 다시 펼쳐볼 레터와 내 서랍의 저장한 레터는 서버 최근 저장순을 유지한다. 로그인 안내는 복귀 주소를 보존하며 로그인 후 저장 버튼을 다시 눌러야 한다. [레터 북마크 상세 정책](../모아쓰기레터/북마크_동기화_연동요구사항.md)을 함께 따른다.
- 직접 관심을 에디터 팔로우로 덮어쓰지 않는다. 계정 팔로우 저장 자체는 후속이다.

## 공개 API 소스와 내부 경로

공개 handler: `service/backend/handlers/user/dashboard.py`.
내부 router/repo: `service/lens-cms-api/routes_dashboard.py`, `dashboard_repo.py`.
공개 `/api/v2/me` → 내부 `/internal/personal/lens` → PostgreSQL.

| 공개 경로 | 이번 지원 |
|---|---|
| GET/PUT `/api/v2/me/preferences` | 관심·읽을 시간·revision |
| GET `/api/v2/me/letter-bookmarks` | limit 1~200, cursor, 제목 검색 q, read=all만 지원 |
| PUT/DELETE `/api/v2/me/letter-bookmarks/{letter_id}` | stable issue_letter ID, 상태 지정 |
| GET `/api/v2/me/content/resolve?kind=issue_letter&key_type=slug&key=…` | slug를 stable ID와 정식 주소로 해석. publication도 지원 |

`content/resolve`는 slug만 가진 기존 레터 UI의 연결용 추가 계약이다. 개인 GET이며 로그인이 필요하다. 요청 user_id로 owner를 지정할 수 없다. 내부 라우트는 X-Internal-Token 필수다.

## 로컬 실행

기존 `service/backend/main.py`는 여러 AWS 클라이언트를 초기화하므로 개인 기능용 `local_account_api.py`를 추가했다. .env를 자동 로드하지 않으며 LENS_CMS_API_URL에 loopback 주소가 없으면 시작하지 않는다. 이 shim도 제품의 토큰 검증을 그대로 사용한다. 인증 우회/테스트 계정은 제품 코드에 포함하지 않는다.

1. 격리 PostgreSQL에 기존 테이블 구조를 준비하고 `docs/architecture/lens-erd-src/lens_schema_v1.48_2026-10-14.sql`을 적용한다. 운영 접속 정보 사용 금지.
2. 내부 CMS에 `LENS_PG_HOST`, `LENS_PG_DATABASE`, `LENS_PG_USER`, `LENS_PG_PASSWORD`를 로컬 값으로 명시하고 `ADMIN_INTERNAL_TOKEN`을 로컬 전용 값으로 설정한다. 환경변수의 실제 이름은 기존 db.py 정본을 따른다.
3. 공개 shim은 `LENS_CMS_API_URL=http://127.0.0.1:8000`, 같은 로컬 `LENS_CMS_API_TOKEN`을 설정한 뒤 `uvicorn local_account_api:app --host 127.0.0.1 --port 8001`로 실행한다.
4. 프론트는 `NEXT_PUBLIC_API_URL=http://127.0.0.1:8001`, `NEXT_PUBLIC_CMS_API_URL=http://127.0.0.1:8000`을 명시해 실행한다. 기존 개발 서버와 병렬 실행할 때 Next 산출물도 분리한다.

운영 계정의 실제 Cognito/JWKS 호출은 별도 운영 인수 범위다. 로컬 기능 검증에는 외부 통신을 차단하고 별도 로컬 서명키/JWKS stub와 합성 계정만 사용한다. 로컬 DB 테스트는 `LENS_ACCOUNT_TEST_DB=loopback` 명시가 필요하다. 기존 스키마 일부를 재현한 테스트 fixture이며 전체 운영 DDL·서비스 역할 권한을 인수한 것은 아니다.

## 운영 반영 전 남은 작업

- 실제 적용된 DB 스키마·서비스 역할 권한과 v1.48 충돌 여부 확인 후 SQL을 별도 적용. 기존 users·topics·issue_letters·categories 조회/사용자 생성 권한도 필요하다.
- 공개 API_URL origin의 신규 경로를 dashboard handler에 연결하는 API Gateway integration과 함수 등록. 이번에는 lambda_handlers.txt/deploy.sh 및 AWS 리소스를 변경하지 않았다.
- 내부 CMS 라우터 코드를 먼저 반영하고 공개 API를 연결한 후 프론트를 전환한다. 내부 호출은 HTTPS 또는 신뢰 네트워크로 보호한다.
- 현재 프론트는 새 계정 API가 없는 환경에서 연결 실패를 표시하며 기기 설정이나 북마크로 몰래 대체하지 않는다.
- 기존 브라우저 북마크·기기 관심 가져오기, 계정 에디터 팔로우, 서버 열람 필터/추천/리워드/알림은 후속이다. 로컬 레터 읽음은 계정별 브라우저 키이며 서버 완료 기록이 아니다.
- issue_letter 문장을 현재 publication slug FK에 넣지 않는다. 문장 source FK 확장/기존 문장 backfill·보존 정책은 후속 마이그레이션으로 분리한다.
- 기존 user_readings의 article_no/publication_id 계약은 유지했다. 새 resolver를 이용 이벤트에 적용하는 것은 다음 개발 묶음이다.
