# 나의 LENS — 백엔드 개발 인수인계

기준일: 2026-10-14. 조사 기준: HEAD `fc8c46e4` 및 현재 작업 트리의 미커밋 프론트엔드 변경. **이 문서는 구현 요청 명세이며, 새 백엔드를 구현하거나 배포한 결과가 아니다.** 기존 서버 경로는 소스로 확인했고 운영 DB·실제 로그인·발송은 이번 문서 작업에서 호출하지 않았다.

## 1. 처음 읽는 개발자를 위한 제품 설명

‘나의 LENS’는 로그인 사용자의 개인 뉴스 공간이다. 레터만 추천하는 공간이 아니다. 사용자가 읽은 뉴스의 분야·등록 키워드, 직접 고른 관심사, 저장한 문장, 저장한 레터와 팔로우한 에디터를 연결한다.

대표 흐름은 **뉴스 이용 → 관심 신호 축적 또는 문장 저장 → 내 서랍에서 확인 → 관련 뉴스·레터 추천 → 사용자가 별도로 동의한 경우 새 글 알림**이다. 유효하게 콘텐츠를 완료한 기록은 주·월·연 기록과 스탬프·배지의 근거가 된다. 단순 열람, 완료, 추천 관심, 알림 동의는 각각 다른 상태다.

화면의 리워드는 현금성 포인트가 아니다. 하루 스탬프와 주간 배지이며 교환·쿠폰·금전 잔액을 만들지 않는다. 푸시 설정을 저장했다고 자동으로 발송하지 않는다.

읽는 순서:

1. 이 문서: 화면, 범위, 선행 문제, 구현 순서와 완료 기준.
2. [API 계약](../../architecture/나의LENS_백엔드_API계약.md): 신규 계약 제안, 요청·응답·오류·동시성.
3. [데이터·구현 설계](../../architecture/나의LENS_백엔드_데이터·구현설계.md): 기존 서버 책임, 파일 배치, 저장 모델·트랜잭션·검증.
4. [기존 연결 요구사항](백엔드_연동요구사항.md), [프론트 작업 기록](../../worklog/2026-10/2026-10-14-나의LENS-프론트엔드-구현.md): 이전 작업의 상세 맥락. 계약이 충돌하면 이 인수 문서와 연결된 새 계약을 우선한다. 사업 수치의 제안과 확정 사항은 아래 9절을 따른다.

## 2. 현재 화면과 실제 연결 상태

진입점: [MyLensRoute](../../../service/frontend/src/widgets/MyLensPage/MyLensRoute.tsx) → [MyLensPage / MyLensDashboard](../../../service/frontend/src/widgets/MyLensPage/MyLensPage.tsx). 상단 사용자 메뉴의 ‘나의 LENS’로 진입한다. 이전 서랍 주소 `/?tab=archive`는 유지한다.

| 화면·URL | 지금 하는 일 | 백엔드가 완성해야 할 일 |
|---|---|---|
| `/my-lens` 홈 | 뉴스 추천 최대 4개, 레터 최대 3개, 읽을 시간 0/5/10분, 저장 레터 요약, 문장 최대 3개, 에디터·주간 스탬프 요약 | 계정 프로필·추천·저장 목록의 집계 응답. 최신 100개 뉴스 밖의 과거 기록까지 분석 |
| `?tab=archive` 내 서랍 | 기존 로그인 문장 API 조회·삭제, 검색·복사·원문·문장별 관련 글. 저장 레터 필터 | 서랍 인증 보완, 페이지네이션·서버 검색·원문 정식 주소, 계정 레터 북마크·과거 자료 일괄 조회 |
| `?tab=records` 읽기 기록·리워드 | 로컬 레터 카테고리 집계. 주·월·연 전환과 가상 달성 예시 | 서버의 실제 완료 일자·기간 집계·배지 원장. 예시와 운영 응답의 분리 |
| `?tab=settings` 관심사·알림 | 관심 dialog는 기존 기기별 API. 알림 유형·시간·요일·중지·추천 근거는 브라우저 초안 | 직접 선택 관심의 계정 저장, 푸시 별도 동의·기기 구독·스케줄·발송 결과 |

딥링크도 보호 대상이다: `?tab=archive&sentence=ID#ml-sentence-related`, `?tab=archive&kind=letters`, `?tab=records#ml-rewards`, `?tab=settings#ml-notifications`.

### 현재 인증 정책

**개발 중 비로그인 접근 예외는 종료됐다.** 프론트는 AuthContext 확인 전 개인 화면의 훅을 마운트하지 않고, 비로그인이면 내부 복귀 주소를 저장한 뒤 `/login`으로 이동한다. 기존 이메일 로그인·소셜 콜백은 탭·쿼리·해시를 복원한다. 로그아웃하면 대시보드를 내리고 계정 ID가 바뀌면 화면 상태를 다시 만든다.

이것은 프론트 진입 제한이다. 브라우저에 남아 있는 북마크·알림 초안이 계정 저장으로 변한 것은 아니다. 개인 API는 서버의 Cognito ID 토큰 검증과 소유권 검사로 별도 보호해야 한다. 공용 홈·공개 기사에는 이 제한을 확대하지 않는다.

### 저장 범위의 차이

| 자료 | 현재 정본·범위 | 이관 시 주의 |
|---|---|---|
| 문장 | 기존 서버 `user_archives`, 계정 범위. 대시보드 최근 200개 | 새 문장 테이블을 중복 생성하지 않는다. 200개가 전체 건수라고 표시하지 않는다 |
| 직접 관심 | `reader_interests`, `X-Voter-Id`로 찾는 기기 해시 | 계정 관심과 별개. 로그인만으로 계정에 자동 귀속 금지 |
| 레터 북마크 | `lens-letter-saved`, 브라우저 공용 slug 배열, 저장 최대 200개 | A 계정 캐시와 B 계정 캐시로 재사용 금지. 별도 가져오기 흐름 |
| 레터 열람 | `lens-letter-read`, slug 배열. 상세 스크롤 70% 기준 | 날짜·실제 완료·포맷 없음. 과거 보상으로 소급 금지 |
| 에디터 팔로우 | `lens-letter-editors`, 브라우저 공용 ID 배열 | 직접 관심과 분리 저장. 팔로우가 관심 전체를 덮어쓰면 안 됨 |
| 뉴스·레터 약한 관심 | `lens-reading-signals-v1:account:SUB` / `...:browser` | 화면 visible 10초, 콘텐츠별 최근 한 건, 최근 90일·최대 200개. 완료/보상 아님 |
| 알림 | `lens-dashboard-notification-draft-v1`, 브라우저 공용 초안 | 수신 동의·push 구독·실제 발송 상태 아님. 가져와도 다시 검토·동의 필요 |
| 읽을 시간 | `lens-dashboard-budget`, 브라우저 0/5/10 | 초기 계정 기본값 제안으로만 가져오기. 알림 동의와 무관 |

## 3. 기존 서버에서 재사용할 것과 선행 보완

### 기존 요청 경로

```text
프론트 authFetch: Authorization Bearer Cognito ID token
  → service/backend/handlers/user/{archive,user}.py (공개 Lambda 진입)
  → services/user/{archive,profile}.py (업무 규칙)
  → repositories/personal_repository.py
  → clients/pg/personal.py (서버 전용 내부 토큰)
  → service/lens-cms-api/routes_users.py (/internal/personal/*)
  → personal_repo.py → db.get_cursor() → PostgreSQL
```

공개 CMS 뉴스·이슈 레터는 `lens-cms-api/main.py`에 등록된 기존 라우터를 쓴다. `service/backend/main.py`는 로컬용 shim이며 거기에만 코드를 추가해서 운영 구현이 끝났다고 판단하지 않는다. 내부 토큰을 프론트로 전달하지 않는다.

### P0-1: 개인 서랍 GET의 인증을 반드시 보완

현재 [archive handler](../../../service/backend/handlers/user/archive.py)의 GET 분기는 `try_get_authenticated_user_id`를 사용한다. 토큰이 없거나 무효면 쿼리의 `user_id`를 지우지 않는다. [handle_list](../../../service/backend/services/user/archive.py)가 그 값을 받아 [저장소](../../../service/backend/repositories/personal_repository.py)로 전달한다. **무인증 요청이 클라이언트 지정 계정의 조회 경로에 진입할 수 있는 정적 코드 결함**이다. 운영 악용·노출 여부는 조사하지 않았다.

수정 요구: `/api/archive` 개인 목록은 유효 ID 토큰 필수, owner는 검증한 `sub`만 사용. 없음·만료·잘못된 서명은 `401`. 클라이언트 `user_id`는 무시하거나 검증된 owner와 불일치 시 거부한다. `/api/archive/popular` 공개 집계는 별도 분기 유지. 타인 삭제·문장별 추천은 존재 여부를 노출하지 않는 `404`.

### P0-2: 콘텐츠 ID 정규화

- 현재 공개 CMS repo는 내부 `publication_id`와 `slug`를 가진다. [cms_posts_shaping.shape_lens](../../../service/lens-cms-api/cms_posts_shaping.py)는 프론트 뉴스 응답의 `id`에 **slug**를 넣는다. 프론트의 뉴스 id를 publications.id 숫자로 바로 저장하지 말고 slug→stable ID로 resolve한다.
- 기존 문장 `article_id`는 CMS slug로 저장되는 경로가 있다. `personal_repo._ARCHIVE_SELECT`는 `publications.slug`와 JOIN한다. [v1.34 기록](../../architecture/db-changelog/postgres/v1.34-user_archives-article_no-fk-수정.md)이 이를 설명한다.
- 기존 읽기 클라이언트는 `article_id`를 `article_no`로 보낸다. 읽기 저장소는 `articles.article_no` 또는 `publications.id`를 받는다. 문장과 같은 의미라고 가정해 복사하면 FK 오류나 분석 누락이 생길 수 있다.
- 이슈 레터는 `issue_letters` 별도 엔터티다. `publications` 레터 형식과 혼동하면 안 된다.

새 API는 `publication:ID` 또는 `issue_letter:ID`의 안정적인 키를 정본으로 사용한다. slug·구주소·기사 코드 해석은 서버 resolver 한 곳에서 처리하고 프론트에 `href`를 제공한다. 모호한 ID는 임의 추정하지 않는다. 상세 규칙은 데이터 설계 3절.

### P0-3: 기존 통계·배지를 새 리워드로 직접 연결하지 않음

[profile service](../../../service/backend/services/user/profile.py)는 현재 읽은 횟수, 제한된 목록에서 계산한 streak·주간 기사 수와 `reader_10`, `weekly_5` 등 기존 배지를 다룬다. [personal repo](../../../service/lens-cms-api/personal_repo.py)는 재방문 시 콘텐츠별 `read_at`을 최신값으로 갱신한다. 과거 모든 읽은 날을 보존하는 완료 원장이 아니다. 대시보드의 주간 3일·분야 3개·다시 읽기 배지와 규칙도 다르다.

기존 API 계약·기존 배지를 보존하고 새 완료 이벤트·일별 스탬프·주간 배지는 별도로 구현한다. 예전 읽음 slug 또는 최신 `read_at`으로 스탬프를 소급 지급하지 않는다.

## 4. 기능별 구현 요구사항

### LENS-01 직접 고른 관심·에디터 팔로우

목적: 사용자 선택을 계정에 저장하고 추천 근거로 사용한다. actor는 로그인 사용자다. 사전 조건은 활성 계정·유효 토큰이며 입력은 category/topic 키와 에디터 ID다.

정상 흐름: 계정 설정 조회 → dialog에서 추가·해제 → revision을 포함한 전체 관심 목록 저장 → 저장 응답으로 태그 갱신 → 추천 재조회. 카테고리 9개와 주제 합계 최대 40개는 기존 제약을 유지한다. ‘관심 없음’과 추천 실패는 별개다.

예외: 알 수 없는 신규 키 거부, 비활성화된 기존 선택은 조회에 `inactive`로 표시하고 변경하지 않은 항목은 보존. A/B 기기 동시 전체 교체는 `409 REVISION_CONFLICT` 후 다시 조회·선택 검토. 실패 시 선택 유지. 팔로우는 멱등 PUT/DELETE이며 관심 전체 교체를 호출하지 않는다.

출력: 계정 관심, 팔로우, revision, 갱신 시각. 완료 조건: 다른 브라우저의 같은 계정에서 재조회 가능하고 다른 계정에는 보이지 않음. [기기별 기존 검증·점수](../../../service/lens-cms-api/interests_repo.py)의 순수 검증·사전 조회를 재사용하되 reader_hash를 계정 owner로 간주하지 않는다.

### LENS-02 계정 레터 북마크와 내 서랍

문장은 기존 저장·삭제·주소를 보존한다. 홈에는 최근 3개만 요약한다. 전체 서랍은 cursor로 더 읽고 검색은 서버의 본인 문장·원문 제목 범위에서 처리한다. 클립보드 복사는 프론트 기능이므로 새 복사 API는 필요 없다.

레터 저장: 안정적인 issue_letter ID의 PUT 저장·DELETE 해제 → 서버 확정 응답 → 목록·상세·대시보드에 같은 상태. 최신 50개 밖의 레터도 저장 목록에서 메타데이터를 일괄 반환한다. 발행 취소·삭제 항목은 본문 없이 `unavailable` 상태와 해제 수단을 제공한다.

문장별 관련 글: 본인 문장 ID로 요청 → 서버에서 문장 조회 → 단어/등록 용어 추출 → 공개 뉴스 후보 추천 → 이미 열람한 뉴스와 저장 문장의 원문 제외 → 최대 3개. 일치 없음은 빈 결과이며 일반 추천으로 채우지 않는다. 문장 텍스트를 공개 검색 URL·외부 서비스에 보내지 않는다. 삭제된 문장 딥링크는 본인 기준 `404` 후 서랍 안내.

완료 조건: 저장/해제 반복 요청이 같은 결과이고 오래된 항목·페이지 경계 중복이 없음. 문장 삭제 성공 후 홈 요약·문장 추천 근거·알림 후보 캐시도 무효화한다. 기존 서랍도 회귀 확인한다. [북마크 상세 요구](../모아쓰기레터/북마크_동기화_연동요구사항.md)를 함께 적용한다.

### LENS-03 이용 기록과 자동 관심

약한 관심 신호와 완료 신호를 분리한다. 서버는 계정·콘텐츠·실제 제공 포맷·세션·이벤트 ID·서버 수신 시각을 기록한다. 카테고리·키워드·제목은 서버 콘텐츠에서 결정하며 클라이언트 제공 점수·날짜·분류를 보상 근거로 믿지 않는다.

같은 콘텐츠를 반복 열어 카테고리 선호가 부풀지 않게 최근 90일의 서로 다른 콘텐츠를 기본 집계 단위로 한다. 10초 visible 신호는 현재 프론트와 호환되는 추천용 초기 기준이다. 백그라운드·숨겨진 포맷·탭 열기만으로 완료를 만들지 않는다. 상세의 기존 70% 열람 표시는 유지하되 서버 완료 판정과 구분한다.

주·월·연은 KST 날짜 기준이고 주는 월~일이다. 서버 UTC 시각을 `Asia/Seoul`로 변환해 일자를 판정한다. 비어 있는 정상 기간은 실제 0건, 연동 미준비·조회 실패는 `unavailable/error`로 구분한다.

### LENS-04 뉴스·레터 추천과 이유

현재 목록 계약의 한계: `GET /api/v2/posts?channel=lens`는 [shape_lens_summary](../../../service/lens-cms-api/cms_posts_shaping.py)에서 lenses를 label/question/bullets만으로 축약해 등록 keywords를 반환하지 않는다. 상세에서 얻은 이 브라우저의 열람 신호에는 등록 용어가 있지만 새 후보의 단어 일치는 현재 제목·요약으로 제한된다. 기존 계정 history를 축약 목록과 JOIN해도 키워드는 채울 수 없다. 제목/요약에 없고 본문 등록 용어에만 있는 관련 글까지 추천하려면 서버가 경량 키워드 metadata를 일괄 제공해야 한다. 프론트 UI에도 이 미연동 범위를 표시하며 100개 상세를 추가 조회하는 방식으로 우회하지 않는다.

현재 프론트 기준을 서버의 초기 버전으로 옮긴다. 근거는 직접 선택, 관찰된 카테고리, 등록 키워드, 저장 문장 단어, 팔로우 에디터로 구분한다. 뉴스의 분야/키워드/문장 필터는 이유 타입 기준이며 ‘관심 키워드’는 자유 입력 태그가 아니라 읽은 콘텐츠의 등록 용어다.

현재 뉴스는 문장 이유 4점·키워드 3점·분야 2점으로 정렬하고 동점은 발행일 순이다. 레터는 서버 피드 이유/직접 카테고리/팔로우/최신성 및 미열람 가산 후 최대 3개를 고른다. 레터 5/10분 설정은 **선택 묶음 전체의 실제 read_minutes 합계** 상한이다. 이 점수는 초기 호환 기준이며 확률·품질 점수가 아니다. [뉴스 모델](../../../service/frontend/src/widgets/MyLensPage/lib/news/newsModel.ts), [레터 모델](../../../service/frontend/src/widgets/MyLensPage/lib/dashboardModel.ts), [문장별 추천](../../../service/frontend/src/widgets/MyLensPage/lib/drawerModel.ts)을 근거로 한다.

서버 확장: 최신 100개 목록 안에서만 이력과 JOIN하는 현재 한계를 없앤다. 공개/삭제 여부 확인·동일 콘텐츠 제거·읽은 뉴스와 저장 원문 제외·부족한 개인화 이유 구분을 적용한다. 전체 추천은 근거가 없을 때 최신 공개 뉴스로 보완할 수 있지만 필터별 추천·문장별 관련 글은 임의 보완하지 않는다.

‘좋은 글’은 단어 일치가 아니다. 초기에는 편집 검증·공개 상태·명시적인 알림 대상 가능 여부로 제한하는 방안을 권장한다. 현재 전용 품질 필드가 확인되지 않았으므로 필드·편집 운영 기준 확정 전 알림 발송을 활성화하지 않는다.

완료 조건: 추천 이유가 저장값/콘텐츠 메타데이터로 재현 가능, 소스가 없으면 ‘최근 발행’으로 표시, 실패를 근거 없는 정상 추천으로 숨기지 않음. 의미가 비슷한 키워드 추천은 후속 범위로 별도 구현·평가한다.

### LENS-05 읽기 기록·스탬프·주간 배지

화면 기준은 [ReadingRewards](../../../service/frontend/src/widgets/MyLensPage/components/ReadingRewards.tsx)와 [WeeklyStamps](../../../service/frontend/src/widgets/MyLensPage/components/WeeklyStamps.tsx)다.

| 표시 | 구현할 규칙 | 경계 |
|---|---|---|
| 하루 스탬프 | 새 콘텐츠를 최초 유효 완료한 KST 날짜, 하루 최대 1개 | 같은 이슈의 다른 포맷·재열람 중복 없음. 단순 저장·알림 설정은 지급 안 함 |
| 꾸준한 시선 | 한 주 서로 다른 3일 읽기 | 초기안: 스탬프를 얻은 3일을 기준. 재열람만 한 날 포함 여부는 9절에서 확정 |
| 새로운 발견 | 한 주 서로 다른 3개 분야의 유효 완료 | 콘텐츠의 정식 카테고리 사용. 주/보조 카테고리 집계 규칙 확정 필요 |
| 다시 보는 깊이 | 한 주 이미 읽고 저장한 서로 다른 2편 다시 유효 완료 | 최초 완료·저장이 재열람보다 앞선 경우만. 같은 요청 재시도·동일 세션 제외 |

쉬어간다고 기록·배지를 지우지 않는다. 월·연 화면은 조회 범위만 바꾸며 월간·연간 보상이나 새 알림을 생성하지 않는다. 완료 원장 → 일별 스탬프 → 주간 배지 평가를 서버에서 멱등하게 처리하고, 동시 기기 요청에서도 한 번만 부여한다. 실제 연동 후 예시 버튼·‘연동 대기’는 프론트에서 실제 상태와 분리한다.

### LENS-06 개인화 푸시

현재 유형은 `briefing`(관심 뉴스), `followups`(관심 이슈의 확인된 다음 소식), `weekly`(지난주 기록)다. 모든 유형 기본 꺼짐. 알림 근거는 category/keyword 기본 켜짐, sentence 기본 꺼짐이다. 근거 선택은 브리핑 후보 필터이고 수신 동의 자체가 아니다.

정상 흐름: 계정 알림 설정 저장 → 별도 수신 동의 → 사용자 행동으로 브라우저 권한 요청 → 구독 등록 → 실제 발송 가능 상태 표시. 브라우저 초안을 서버로 저장해도 동의·구독은 자동 생성하지 않는다. 지원되지 않는 환경·권한 거부·구독 만료·서비스 미준비를 구분한다.

followup의 초기 seed는 본인이 북마크한 레터와 서랍 문장의 원문 중 source가 확인되는 콘텐츠로 제안한다. 자동 열람 분야만으로 특정 이슈를 팔로우했다고 간주하지 않는다. 삭제/해제한 seed는 다음 알림 대상에서 제외한다. 별도 이슈 팔로우 버튼·테이블은 현재 UI에 없으며 필요한 경우 후속으로 설계한다.

빈도는 매일 또는 월·수·금, 시간은 선택 시간대 08:00~20:59, 주간 요일 0=일~6=토. 시간대는 현재 UI의 4개 IANA zone을 지원한다. 하루 최대 **계정당 개인화 푸시 묶음 1회**로 합친다. 여러 기기로 보내는 전달 수와 사용자 알림 묶음 수는 별도로 센다. 내용이 없거나 이미 읽었으면 보내지 않는다. 일시 중지·동의 철회·로그아웃 기기 해제는 전송 직전에 재확인한다.

서랍 문장 원문은 푸시 본문·일반 로그에 넣지 않는다. followup은 편집/서버에서 확인된 관계가 필요하며 단순 키워드 일치를 ‘새 변화’라고 알리지 않는다. 기존 레터 이메일 구독·동의·확인·수신거부는 별도이며 이 설정으로 덮어쓰지 않는다.

완료 조건: 설정 저장·동의·권한·활성 구독 상태가 구분되고, 중복 잡/DST/철회/전송 실패/만료 endpoint에서 중복 또는 원치 않는 발송이 없음. 실제 수신 테스트가 끝나기 전 ‘발송 완료’로 표시하지 않는다.

### LENS-07 4가지 시선 선호 — 후속 확장

계정별 형식 선호를 계산하는 대시보드 기능은 현재 없다. `format_switch` 분석 이벤트와 온보딩 선택은 누적 이용 선호가 아니다. 신규 activity에는 실제 사용한 `letter/webtoon/podcast/video`를 받되 기본 선택 탭·전환 클릭·자동 재생만으로 선호를 계산하지 않는다.

추천안: 최근 30일 계정별 유효 이용 세션을 집계하고 최소 5세션 미만이면 `insufficient_data`. 서로 다른 콘텐츠/세션의 이용 횟수와 형식 내 길이 대비 진행률을 사용한다. 단순 초 합계로 긴 팟캐스트를 우대하지 않는다. 숫자와 알고리즘은 9절의 미확정 항목이며 최초 대시보드 MVP의 필수 UI가 아니다.

## 5. 프론트엔드와 백엔드 작업 경계

| 서버가 담당 | 프론트가 후속으로 연결 | 새 API 불필요 |
|---|---|---|
| 인증·계정 저장·owner·페이지네이션·추천 근거·완료 판정·리워드·동의·발송 | 계정 API 어댑터, 실패/401 처리, 가져오기 안내, 실제 기록 UI, 동의·브라우저 구독, 늦은 응답 차단 | 서랍 복사, 탭 전환, dialog 레이아웃, 검색 입력 UI, 기존 기능 아이콘 |

지금 프론트에 백엔드 계약을 구현했다고 가정하지 않는다. `useLetterShelf`의 `toggleSaved`는 동기 boolean 반환이므로 서버 저장 성공을 그 반환값으로 즉시 표현할 수 없다. 비동기 저장·진행 상태·실패 시 복구로 호출부를 함께 수정해야 한다. 소유자별 요청 취소/캐시, 서버 반환 `href`, 알림 상태, 기록 상태도 교체한다.

새 호출은 기존 `authFetch`와 API 설정을 사용한다. FSD의 feature 공개 index를 경유하며 브라우저에 내부 토큰·DB 주소를 넣지 않는다. 기존 관심 client의 `X-Voter-Id` 경로를 그대로 계정 API라고 부르지 않는다.

## 6. 개발 순서와 단계별 산출물

| 단계 | 개발 내용 | 완료 증거 |
|---|---|---|
| P0 | 서랍 GET 인증, 콘텐츠 resolver, 실제 schema/권한 확인 | 무인증·무효·타인 조회 실패, ID별 resolve와 공개 상태 검사 |
| P1 | 계정 관심·팔로우·레터 북마크·가져오기, 서랍 페이지 조회 | A/B 계정 분리, 두 기기 재조회, 충돌·재시도·해제 부활 방지 |
| P2 | activity 약한 신호, 추천·프로필 집계, 문장별 관련 뉴스, dashboard 응답 | 실제 콘텐츠로 이유 재현, 과거 읽은 글 제외, 빈 결과·실패 분리 |
| P3 | 서버 완료 판정·KST 기간 집계·스탬프·배지 원장 | 동시·중복·재열람·날짜 경계 테스트, UI 예시 제거 후 실제 기록 표시 |
| P4 | 계정 알림·동의·Web Push 구독·품질/후속 관계·발송 작업 | 동의 철회·구독 만료·하루 제한·DST·실제 수신 검증 |
| 후속 | 의미 추천·계정 형식 선호·다양성/관심 없음 피드백 | 평가 데이터·정확한 설명 문구·최소 표본 정책 |

각 단계에서 API 스키마·DB 변경·단위/통합 테스트·프론트 연결·문서 갱신을 함께 제출한다. 기존 서비스 API 응답을 전부 새 envelope로 바꾸지 않는다. 신규 경로에만 새 계약을 적용하고 기존 API는 호환성을 지킨다.

## 7. 인수 시나리오

아래는 **실행해야 할 테스트 명세**다. 이번 문서 작업에서 통과한 서버 테스트가 아니다.

| ID | 조건 → 행동 | 기대 결과 |
|---|---|---|
| AUTH-01 | 토큰 없이 개인 API에 다른 `user_id` 지정 | 401, 저장소 조회 없음 |
| AUTH-02 | 계정 A 토큰으로 B 문장 ID 조회/삭제/추천 | 404 또는 계약의 접근 거부, B 데이터 없음 |
| AUTH-03 | 만료·서명/iss/aud/token_use 불일치 | 401, 빈 배열 정상 응답으로 감추지 않음 |
| SYNC-01 | 같은 레터 PUT/DELETE 반복·동시 요청 | 한 행/한 상태, 요청 재시도로 토글 반전 없음 |
| SYNC-02 | 가져오기 성공 뒤 다른 기기 해제, 같은 가져오기 재시도 | 해제 북마크가 되살아나지 않음 |
| SYNC-03 | A 로그아웃·B 로그인 중 A의 늦은 응답 도착 | B 화면/계정에 A 자료 반영 없음 |
| PREF-01 | 두 기기가 같은 revision의 전체 관심을 변경 | 한 요청 성공, 다른 요청 409, 원본 보존 |
| DRAWER-01 | 200개보다 많은 문장·동일 saved_at | cursor로 중복·누락 없이 조회, 정확한 total/반환 count 구분 |
| DRAWER-02 | 내 문장 삭제 후 홈·문장 추천 재조회 | 삭제 문장과 단어 근거 제거, 알림 동의에는 영향 없음 |
| REC-01 | 이미 읽은/원문/삭제/비공개 후보 혼합 | 공개 미열람 후보만, 이유와 실제 메타데이터 일치 |
| REC-02 | 문장 일치가 없는 상태로 관련 뉴스 조회 | 빈 배열, 무관한 최신 글 보완 없음 |
| REC-03 | 5분 예산·4분 레터 여러 개 | 묶음 총합 5분 이하, 무조건 3개 채우지 않음 |
| ACT-01 | 숨김 탭·빠른 스크롤·자동 재생·임의 완료 요청 | 약한 신호/보상 완료 구분, 부정·불충분 완료는 미지급 |
| REWARD-01 | 같은 이슈를 4포맷·두 기기로 동시 완료 | 최초 완료 1회, 당일 스탬프 1개 |
| REWARD-02 | KST 23:59/00:00, 월/연/주 경계 | 정확한 일자·월요일 주 시작, 이전 배지 유지 |
| REWARD-03 | 저장·완료 후 두 편을 다른 세션에서 다시 읽기 | 재열람 배지만 평가, 최초 완료 스탬프 중복 없음 |
| PUSH-01 | 로컬 초안/서버 설정만 저장, 동의 또는 구독 없음 | 전송 없음, blocked 상태와 이유 표시 |
| PUSH-02 | 중복 스케줄·재시도·여러 유형·DST | 계정당 해당 local day 1묶음, 타입 합치기, 발송 원장으로 중복 억제 |
| PUSH-03 | 예약 후 pause/철회/로그아웃·권한 해제 | 발송 전 재확인으로 중단·해당 구독 비활성화 |
| FAIL-01 | 관심/서랍/추천/기록 한 영역만 실패 | 인증 실패는 전체 401, 일반 장애는 영역 error, 데이터 없음과 구분 |

## 8. 현재 인계 상태와 실행 범위

- 현재 프론트 구성·기존 호출 경로·저장 범위를 서버 handler/repo/라우터와 대조한 인계 문서다. 기존 프론트 구성과 운영 서버 인수 완료는 구분한다.
- 이 문서의 신규 API·테이블·파일은 **구현 제안**이다. 현재 대시보드가 호출하는 API로 표시하지 않는다.
- 운영 DB DDL·행 건수·권한, API Gateway/CloudFront 연결, Cognito 실제 로그인, 실제 푸시 수신·메일 발송은 이번 작업에서 미검증이다.
- 제품 코드, DB, AWS 리소스, 배포, 커밋·push는 변경하지 않는다. 문서와 작업 기록만 갱신한다.

## 9. 착수 기본안과 출시 전 확정할 항목

API 문서의 숫자 중 기존 40개 관심·홈 4/3개·읽을 시간 0/5/10·UI 시간대/알림 시간·주간 목표 3일은 현행 코드 기준이다. 다음 값은 구현 가능한 **권장 초기안**이며 제품 담당자와 확정하고 `rule_version/algorithm_version`으로 관리한다.

| 항목 | 권장 초기안 또는 결정 필요 사항 | 막히는 범위 |

| 유효 완료 | 읽기 80% + visible 최소 30초, 웹툰 실제 컷 80% + 10초, 듣기/영상 실제 소비 구간 80%. 길이/짧은 콘텐츠 예외는 서버 규칙화 | 미확정 시 activity 약한 신호만 출시, 리워드 미연동 유지 |

## 10. 개발 AI에 전달할 작업 지시

> 이 저장소의 CLAUDE.md와 적용 범위 AGENTS.md를 먼저 읽고, 이 문서와 연결된 API·데이터 설계를 기준으로 나의 LENS 백엔드를 구현한다. 기존 개인 Lambda 인증 → 내부 CMS API → PostgreSQL 책임을 유지한다. 현재 운영 라우팅·DDL 적용 상태는 먼저 확인하고, 문서에만 있는 신규 API를 기존 구현으로 오인하지 않는다. P0 인증/ID 문제 → P1 계정 저장 → P2 추천 → P3 리워드 → P4 푸시 순서로 분리한다. 미확정 완료/보상/알림 정책은 출시 전에 확정하며 그 전에는 미연동 상태를 유지한다. 원본 서랍·기존 주소·레터 이메일 구독·공개 콘텐츠를 보존한다. 계정은 JWT sub에서 결정하고 X-Voter-Id를 계정 인증으로 사용하지 않는다. 신규 파일은 데이터 설계 2절의 기존 레이어에 배치한다. 개인 문장·토큰을 로그/공개 검색/외부 모델로 보내지 않는다. 로컬 가져오기와 알림 동의는 분리한다. 이번 문서 전달 자체는 운영 DDL·AWS 비용 발생·배포·커밋·push 승인으로 해석하지 않는다. 변경 단계마다 계약·소유권·중복·실패 테스트와 문서를 함께 갱신한다.
