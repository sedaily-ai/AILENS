템플릿의 빈 값은 실제 입력이 아니다. 누락된 환경변수·스키마·권한·리소스는 preflight에서 실패하며 임의 성공 처리하지 않는다. AWS 계정은 config/resources.env의 계정과 일치해야 한다. 신규 dashboard 함수는 `Service=lens`로 생성하고 실제 태그를 재조회한다.

## 1. DB 선행 적용

운영 DB의 기존 적용 버전(v1.47까지의 선행 테이블), PostgreSQL 버전, 실제 컬럼·인덱스·제약, 기존 역할, 예상 자료량의 실행계획·락 시간을 확인한다. `IF NOT EXISTS`는 잘못된 기존 정의를 고쳐주지 않는다. 백업/PITR과 복구 담당자, **별도 복구 DB에서 백업 복원 성공**을 먼저 확인한다. SQL은 앱 역할로 적용하지 않는다.

```bash
bash
set -euo pipefail
cd /Users/ldy/Desktop/Code/Sedaily/AILENS
chmod 600 /tmp/lens-release.env /tmp/lens-acceptance-id-token
python3 -m venv /tmp/lens-release-venv
source /tmp/lens-release-venv/bin/activate
python3 -m pip install -r service/lens-cms-api/requirements.txt
set -a
source /tmp/lens-release.env
set +a
: "${PGHOST:?}" "${PGDATABASE:?}" "${PGUSER:?}" "${PGPASSWORD:?}"
test "$PGHOST" = "$LENS_PG_HOST"
test "$PGDATABASE" = "$LENS_PG_DATABASE"
test "$PGUSER" != "$LENS_PG_USER"
pg_dump --format=custom --file=/tmp/lens-account-before.dump
chmod 600 /tmp/lens-account-before.dump
pg_restore --list /tmp/lens-account-before.dump >/dev/null
cd service/lens-cms-api
python3 scripts/account_schema.py --baseline
python3 scripts/account_schema.py --apply --backup /tmp/lens-account-before.dump
python3 scripts/account_schema.py
```

실행 호스트에 Python 3.11 이상과 CMS requirements의 psycopg2, 호환되는 `pg_dump/pg_restore`가 필요하다. 격리 venv를 만들어 `python3 -m pip install -r requirements.txt`로 설치하고 사용한다. SQL 순서는 **v1.48 →49 →50 →51 →52 →53 →54 →55**다. SQL 파일은 CMS tar의 migrations에도 포함되지만 CMS deploy가 실행하지는 않는다.

한 파일에서 실패하면 그 파일 transaction만 rollback하고 이후 파일은 실행하지 않는다. 앞서 완료된 버전은 보존한다. 원인을 수정한 뒤 같은 명령을 재실행할 수 있다. 로컬 재실행은 확인했으나 운영의 다른 정의·자료량까지 자동 교정하는 도구는 아니다.

```bash

```

SSM은 DB 선행 검사와 dry_run 환경 검사를 **코드 교체 전에** 수행한다. 기존 ecosystem.config.js를 보존하고 서버 `/tmp/lens-cms-before-*.tar.gz`에 코드 백업을 남긴다. 새 의존성 설치·PM2 환경 갱신·로컬/외부 health 중 하나라도 실패하면 중단한다. worker 소스와 systemd 정의는 공급만 하며 정기 실행은 자동 활성화하지 않는다.

Python 3.11/x86_64 일반 Lambda만 허용하고 현재 runtime을 임의 변경하지 않는다. 코드/handler 갱신 완료 후 `/api/v2/me/{proxy+}`, `/api/archive`, `/api/archive/{proxy+}`를 연결한다. 이미 존재하는 개인 경로의 더 구체적인 메서드 경로도 동일 함수로 맞춘다. 전체 API의 기존 CORS origins는 보존하고 실제 사이트 origin·PUT/DELETE/POST·Authorization을 추가한다.

Cognito **ID token 검증은 기존 handler**가 수행하므로 Gateway AuthorizationType은 NONE이다. 내부 CMS 라우트를 공개 통합하지 않는다. 개인 응답의 401·성공·쓰기·오류는 private/no-store이며, 공개 `/api/archive/popular`는 그대로 공개 집계다. HTTP API는 AutoDeploy stage가 아니면 preflight에서 멈춘다.

스모크는 무인증 401, 실제 ID token 200, private/no-store, 실제 origin의 OPTIONS/PUT/Authorization을 검사한다. 실제 A/B 계정 분리·계정 전환/만료·Cognito 설정·운영 자료량은 이 간단한 스모크와 별도로 인수한다. 실패하면 프론트를 배포하지 않는다.

## 5. 콘텐츠 메타데이터 공급

CMS의 별도 관리 CLI를 사용한다. 직접 DB 쓰기가 가능한 편집/마이그레이션 역할을 명시하며 앱 역할의 편집 테이블 쓰기 권한을 확대하지 않는다. 입력 JSON과 실행 결과는 `/tmp`에만 보관한다. 주제·원문 유사성으로 작성자·동일 이슈·편집 승인을 추정하지 않는다.

```bash
set -euo pipefail
cd /Users/ldy/Desktop/Code/Sedaily/AILENS/service/lens-cms-api
python3 scripts/content_metadata_supply.py --manifest /tmp/lens-content-metadata.json
python3 scripts/content_metadata_supply.py --manifest /tmp/lens-content-metadata.json --apply
```

첫 명령은 검증·변경 결과를 조회한 뒤 전체 transaction을 rollback한다. `--apply`만 commit한다. 대상의 stable ID는 기존 관리자 콘텐츠에서 확인한다. 입력은 아래 필드 중 변경할 것만 포함한다. 아래 모양은 설명용이며 실제 ID와 승인 내용을 입력해야 한다.

- `content_key`: `publication:<ID>` 또는 `issue_letter:<ID>`.
- `reward_group_key`: 편집 확인한 `issue:<승인한식별자>` 또는 명시적 null(보상 대기).
- `editor_slugs`: 이슈 레터의 실제 작성자 slug 배열. 명시한 배열로 교체하며 빈 배열은 관계 해제다.
- `followups`: `{target_content_key, editor_approved}` 배열. 승인은 반드시 boolean으로 명시한다. 기존 관계의 승인 철회는 false로 갱신한다. 생략한 관계는 유지한다.
- `media`: 뉴스의 `{asset_id, file_url, duration_seconds}` 배열. 뉴스 소유 asset만 허용하며 직접 재생 HTTPS 파일과 실측 길이만 입력한다. iframe 주소는 거부한다. 관리자 원본과 media_assets projection을 함께 갱신한다.

신규 파이프라인 산출물은 `pipelines/common/publishing.py`가 완성된 MP3/MP4 파일을 ffprobe로 측정해 길이를 공급하도록 수정했다. 파이프라인 이미지 갱신은 별도 적용 단위이며 여기서 실행하지 않았다. 기존 운영 콘텐츠는 위 CLI로 승인한 메타데이터를 공급할 수 있다. 측정 실패는 null로 남겨 완료 판정 대기를 유지한다. 미입력 레터 보상 그룹·후속 관계·작성자는 그대로 대기/추천 빈 상태다.

## 6. worker 정기 모의 처리 (CMS 서버에서만)

> **2026-10-20 알림 워커 제거 — 이 절은 실행하지 않는다.** 새 CMS에는 워커 경로가 없다. 옛 타이머가 남아 있으면 정리 명령은 [기능 다이어트 2차 작업 기록](../../worklog/2026-10/2026-10-20-기능-다이어트-2차.md) '다음'을 따른다.

아래는 CMS 배포와 공개/프론트 인수 이후 실행할 **서버 셸 명령**이다. 새 AWS 리소스를 만들지 않고 기존 EC2 systemd timer를 사용한다. 기존 worker는 중지한 상태에서 교체한다. 서버 파일 `/etc/lens-notification-worker.env`에는 `LENS_CMS_API_URL=http://127.0.0.1:8000`, CMS의 ADMIN_INTERNAL_TOKEN과 같은 `LENS_CMS_API_TOKEN`을 안전하게 공급한다. 권한은 root:lens-notification 640으로 둔다. LENS_PUSH_MODE=dry_run, LENS_PUSH_LIVE_ENABLED=false는 service 정의가 강제한다. `--live`를 사용하지 않는다.

```bash
set -euo pipefail
cd /opt/lens-cms-api
if ! id lens-notification >/dev/null 2>&1; then
  sudo useradd --system --no-create-home --shell /usr/sbin/nologin lens-notification
fi
sudo chown root:lens-notification /etc/lens-notification-worker.env
sudo chmod 640 /etc/lens-notification-worker.env
sudo install -m 644 notification-worker.service /etc/systemd/system/lens-notification-worker.service
sudo install -m 644 notification-worker.timer /etc/systemd/system/lens-notification-worker.timer
sudo systemctl daemon-reload
sudo systemctl start lens-notification-worker.service
test "$(sudo systemctl show --property=Result --value lens-notification-worker.service)" = success
sudo systemctl enable --now lens-notification-worker.timer
sudo systemctl list-timers lens-notification-worker.timer --no-pager
sudo journalctl -u lens-notification-worker.service -n 50 --no-pager
```

서비스 계정이 `/opt/lens-cms-api/venv`와 notification-worker 소스를 읽고 실행할 수 있어야 한다. oneshot 종료 후 1분에 다시 실행하며 동시 실행하지 않는다. API 내부에 timer를 만들지 않는다. CMS가 live로 바뀌면 기본 worker는 계획/claim 전에 실패한다. owner 처리 실패는 종료 코드 1을 남긴다. 실제 provider 발송·기기 수신·운영 알람/unknown 관제는 미검증이며 별도 운영 인수/활성화가 필요하다.

## 실패 시 중단·롤백

- **DB**: SQL 실패 후 새 CMS를 적용하지 않는다. 자료가 생긴 이후 신규 테이블을 DROP해 되돌리지 않는다. 기존 코드를 먼저 복구하고 필요할 때 담당자가 승인한 백업/PITR로 별도 DB에 복구·검증 후 전환한다. `pg_restore --list`만으로 복구 성공이나 백업 대상 일치를 증명하지 않는다.
- **공개 API**: 같은 `/tmp` 백업 디렉터리를 유지하고 다음 명령을 실행한다. 기존 코드 ZIP·handler·환경·개인 경로·CORS를 복구한다. 신규 미연결 함수/통합은 자동 삭제하지 않으며 별도 정리 대상이다. 백업에는 환경 비밀이 있으므로 외부 공유하지 않는다.

```bash
set -euo pipefail
cd /Users/ldy/Desktop/Code/Sedaily/AILENS/service/backend
```

## 실제 운영에서 남는 인수

실제 Cognito A/B 계정·다른 기기/탭·만료/로그아웃, 운영 스키마/권한/자료량·쿼리 성능, CMS/Lambda 네트워크·IAM·토큰 일치, 기기 권한 거부/만료·네이티브 구독·provider 접수/수신, worker 장애/unknown 관제는 실제 환경에서 확인해야 한다. 로컬 빌드는 외부 fetch를 차단하고 글꼴 fixture를 사용한 격리 빌드이며 실제 운영 콘텐츠나 최종 Docker ARM64 이미지 인수를 대신하지 않는다. 일반 화면의 모의 검증 조작은 development 빌드에만 남겼다.


## 배포 후 확인 순서

1. CMS health와 PM2 오류 로그, 공개 계정 API의 `account_smoke.py`를 다시 확인한다. 실패하면 worker를 시작하지 않는다.
2. 실제 A/B 계정으로 홈·관심 변경·레터 저장/해제·문장 서랍·팔로우·명시적 가져오기·완료/리워드·만료 후 재로그인을 확인한다. 새 화면의 데이터가 이전 계정에서 남지 않아야 한다.
3. worker oneshot의 Result=success와 timer 상태를 확인하고 원장의 dry_run/simulated 처리 및 unknown을 관찰한다. 운영 화면에 모의 기기·후보·발송 시각이 없어야 한다.
4. live 활성화는 이번 적용에 포함하지 않는다. 실제 기기 권한·provider·수신과 운영 관제를 별도 인수한다.

Gateway preflight는 두 함수의 환경·태그·기존 invoke 정책·라우트/통합 조회를 변경 전에 검사한다. DB `--baseline`은 첫 DDL 전에 실제 앱 연결·기존 테이블·읽기 권한·Cognito ID 컬럼 타입·public CREATE 금지를 확인한다. 모든 IAM 쓰기 권한·운영 성능을 읽기 전용 preflight만으로 증명할 수는 없으며, 쓰기 실패 시 중단하고 위 백업으로 복구한다.
