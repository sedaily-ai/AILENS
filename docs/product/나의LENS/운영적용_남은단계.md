새 Fastify/Nest 서버나 별도 사용자 DB를 추가하지 않는다. 기존 개인 API의 Lambda→CMS 경계를 확장한다. 콘텐츠 공개 API는 기존 CMS에서 공급한다. [배포 실행 명령](배포실행_명령.md)에 DB → CMS → 공개 계정 Lambda/Gateway → 실제 인증 스모크 → 프론트 → worker 모의 정기 실행과 복구 경로를 준비했다. dashboard는 lambda_handlers 대응표와 config/resources.env에 등록했으며 `deploy.sh account`가 기존 archive 계약을 확인한 뒤 신규 함수를 생성·연결한다. worker는 CMS 릴리스의 별도 소스 묶음과 systemd 정의로 공급한다. 실제 운영 실행은 하지 않았다.

## 1. 변경 묶음을 확정한다

- v1.48~55 SQL·CMS·공개 handler/service/repository·프론트·필요 의존성과 문서를 하나의 릴리스 범위로 확정한다. 이번 변경의 기준은 [형식 선호·계정 연결](형식선호·계정연결_구현상태.md)과 [전체 리뷰 보완](백엔드_리뷰_보완.md)다.
- 코드 리뷰·커밋·PR·병합은 팀 절차로 진행한다. 현재 미커밋 작업을 운영에 적용한 상태로 간주하지 않는다.
- 로컬 합성 DB·JWT·콘텐츠 fixture, 검증 로그·스크린샷은 제품 배포물이나 운영 데이터로 복사하지 않는다.
- 이후 신규 AWS 리소스가 필요하면 먼저 [비용태깅 규칙](../../architecture/비용태깅_규칙.md)을 따른다. 2026-10-01 이후 신규는 Service=lens이고 리소스 이름은 config/resources.env가 정본이다. 이번 기능은 Bedrock 추론을 필요로 하지 않는다.

다음 단계 조건: 배포 대상 코드와 SQL 순서가 확정되고 책임자가 정해져 있어야 한다.

## 2. 스테이징 DB에서 전체 스키마·권한을 리허설한다

로컬 최소 합성 테이블과 실제 서비스 DB는 구분한다. 운영과 같은 기존 스키마·제약·역할을 가진 스테이징에서 실행한다.

현재는 별도 스테이징이 없어 전용 로컬 DB의 리허설로 진행한다. 로컬 기준 스키마는 저장소의 원본 DDL과 기존 변경 기록으로 재구성하며 운영 스키마를 직접 조회하거나 운영 데이터를 복사하지 않는다. 로컬에 없는 vector·pg_bigm·pg_partman과 실제 운영 역할 설정·자료량은 별도 환경에서 확인해야 한다. 이 리허설만으로 실제 스테이징·운영 성능과 권한 확인이 완료된 것으로 처리하지 않는다.

1. 기존 적용 버전, 백업/PITR·복구 책임자, 테이블 수/행 수와 락·적용 시간을 확인한다.
2. v1.48 →49 →50 →51 →52 →53 →54 →55 순서로 적용한다. 스크립트의 IF NOT EXISTS는 기존 칼럼/제약의 다른 정의를 자동 교정하지 않으므로 결과를 직접 조회한다.
3. lens_service_app으로 users 생성/조회, 기존 서랍·메타데이터 조회, 새 계정 테이블의 실제 CRUD와 시퀀스 권한을 확인한다. DDL은 별도 마이그레이션 역할로만 실행한다.
4. 기본 스키마의 users.id=Cognito sub VARCHAR(64), issue_letters/publications stable ID, letter_editors 관계와 기존 rendition/article_no 서랍 연결을 유지한다.
5. v1.54의 UUID별 PK·snapshot 조회 인덱스, 가져오기 재생·거부 재검사·동시 호출을 확인한다. 기존 영수증과 북마크는 보존한다.
6. v1.55 함수의 소유자·고정 search_path·PUBLIC 실행 권한 회수·앱 역할 EXECUTE를 확인한다. 앱 역할은 후속 관계에 직접 쓰거나 함수 정의를 바꿀 수 없어야 한다. 기존 자료와 새 원장·제약·인덱스·권한은 SQL 재실행과 백업 복원 후에도 유지돼야 한다.
7. 실제 예상 데이터량으로 추천/형식 집계/읽음 필터/알림 fingerprint 쿼리의 실행 계획·DB 풀·지연을 확인한다. 현재 로컬 검증을 성능/실제 운영 역할 권한 확인으로 확대하지 않는다.

다음 단계 조건: 실제 서비스 역할로 처리 가능하고, 기존 자료를 유지하며 복구 절차가 준비돼 있어야 한다.

## 3. 운영 콘텐츠에 필요한 메타데이터를 공급한다

| 자료 | 없을 때 현재 동작 | 필요한 작업 |
|---|---|---|
| media_assets.duration_seconds와 직접 재생 URL | 듣기·영상 완료/보상은 대기. iframe 매체의 완료를 추정하지 않음 | 생성/업로드 파이프라인에서 실제 길이를 저장하고 기존 자료를 확인 후 보강. iframe은 SDK 설계가 별도 필요 |
| 실제 준비된 본문·웹툰 컷 | 비어 있거나 미래/비공개 자료는 유효 추천·완료 대상에서 제외 | 공개 카드와 준비 상태가 실제 읽기/재생 자료를 가리키는지 확인 |
| content_reward_groups의 이슈 레터 그룹 | 완료·서버 읽음은 기록하되 스탬프/배지는 그룹 확인 대기 | 편집 담당자가 같은 이슈의 관계를 확정. 자동 텍스트 유사성으로 묶지 않음 |
| content_followup_links와 editor_approved | 승인 후속 알림 후보가 없음 | 편집 승인 관계 등록 절차/관리 도구를 마련. 저장 이후 등록된 관계만 후보가 됨 |
| issue_letter_editors의 실제 작성자 | 담당 주제로 작성자를 추정하지 않음. 해당 팔로우 추천도 없음 | 실제 작성자 관계를 사전에 등록·점검 |

리워드 그룹·후속 관계·실제 레터 작성자의 편집 확인 입력은 `scripts/content_metadata_supply.py`로 준비했다. 기본은 rollback이며 명시한 --apply만 commit한다. 관리자 웹 입력 UI는 별도이며 파이프라인 실측 재생 길이 공급은 로컬 수정 상태다. 추천은 분야·등록 키워드·문장 단어 정확 일치와 실제 형식 가중치다. 의미 유사도 추천·품질 평가 모델은 미구현이며 이번 운영 적용의 필수 선행조건으로 추가하지 않는다. 직접 선택 관심과 관찰 관심은 계속 구분한다.

## 4. 계정 API·CMS를 연결한다

- v1.55까지 DB·잠금 함수 준비 후 CMS 내부 router/의존성을 적용한다. 내부 /internal/personal/lens 경로는 X-Internal-Token이 필요하고 공개 프록시를 통해 무인증으로 노출하지 않는다.
- 공개 API의 /api/v2/me/*를 dashboard handler에 연결하고 기존 /api/archive를 갱신한다. 신규 Lambda/권한/Gateway 등록은 기존 배포 목록과 충돌 없이 구성한다.
- 기존 환경 설정 LENS_CMS_API_URL/LENS_CMS_API_TOKEN 및 Cognito issuer/client 설정을 맞춘다. CMS 측 ADMIN_INTERNAL_TOKEN도 같은 내부 인증 계약을 사용한다. 운영 비밀값을 문서·프론트 번들에 넣지 않는다.
- 실제 프론트 origin의 CORS·OPTIONS·PUT/DELETE/POST와 Authorization 전달을 확인한다. 개인 응답 Cache-Control: private, no-store가 Gateway/CDN에서 유지돼야 한다.
- 로그인 제한을 유지한다. 서버 장애를 익명 브라우저 저장 성공으로 대체하지 않는다.

다음 단계 조건: 해당 환경에서 계정 API와 인증·오류 응답을 확인할 수 있어야 한다.

## 5. 검증용 UI·문구를 정리하고 프론트를 배포한다

- 알림 설정의 ‘로컬 검증 기기 연결’, ‘서버 후보 미리보기’와 모의 구독 목록·모의 발송 시각 등 개발 검증용 조작·정보를 일반 사용자 화면에서 제외한다. 검증 수단은 개발 환경이나 별도 테스트 도구에서 유지한다.
- ‘로컬 검증 · 실제 발송 없음’, ‘로컬 검증 준비 완료’ 등 기술적인 문구를 정리한다. 실발송이 비활성인 환경에서는 ‘알림 발송은 아직 활성화되지 않았어요.’처럼 실제 상태를 간단히 안내하고, 모의 연결을 실제 기기 연결로 표시하지 않는다.
- 서랍과 대시보드의 고정 ‘운영 푸시 발송 준비 중’ 안내는 서버 발송 상태에 맞춰 교체한다. 실제 발송 활성화·인수 완료 후에는 준비 중 안내를 제거한다.
- 이미 없어진 브라우저 저장·동기화 준비 중 문구가 재등장하지 않는지 확인한다. 계정 저장 안내, 수신 동의, 실제 기기 권한·연결, 오류·빈 상태 등 사용에 필요한 안내는 유지한다.
- API가 정상화되고 위 정리가 끝난 뒤 NEXT_PUBLIC_API_URL/NEXT_PUBLIC_CMS_API_URL을 해당 환경에 맞춘 프론트를 빌드·배포한다. 뉴스 정본 주소의 ?format=...가 실제 형식 탭을 여는지 확인한다.

다음 단계 조건: 출시 화면에 검증용 조작·문구가 노출되지 않고 실제 발송 상태가 정확해야 한다. 새 API의 401/403/409/503과 프론트 재시도·빈 상태도 실제 환경에서 구분되어야 한다. 현재 출시 빌드에서 모의 기기·서버 후보·모의 처리 시각은 제외하고 development 빌드에만 남겼다. 서버 mode/support와 실제 구독에 따른 상태 표시를 로컬 검증했다. 실제 운영 화면 인수는 배포 후 수행한다.

## 6. 실제 Cognito 계정·두 기기로 인수한다

- A/B 계정의 관심·읽을 시간·문장·레터 저장·팔로우·읽음·완료·리워드·알림 설정이 서로 분리되는지 확인한다. body/query의 user_id를 바꿔도 JWT의 sub만 owner가 되어야 한다.
- 같은 계정의 다른 기기에서 계정 저장이 다시 조회되는지 확인한다. 직접 관심과 새 유효 이용/저장 문장에 맞춰 추천 이유가 갱신되어야 한다.
- 실제 읽기·웹툰 컷·직접 듣기/영상 재생의 신호를 확인한다. 동일 뉴스의 여러 형식 이용은 선호 분석에 각각 반영하되 중복 보상은 하지 않는다.
- 표본 부족/형식 동률/지원하지 않는 형식, 비공개·삭제·본문 없음, 관심 없는 계정의 최신 뉴스 대체와 정확 일치 레터의 정상 빈 결과를 확인한다.
- 세션 만료·로그아웃·빠른 계정 전환·느린 응답·다른 탭 설정 충돌에서 이전 계정 화면과 쓰기가 남지 않아야 한다.
- 기존 브라우저 북마크는 명시적 선택만 가져온다. 응답 손실·부분 거부·공개 전환·가져오기 후 해제를 확인한다. 브라우저 원본·팔로우·읽음·동의는 자동 병합하지 않는다.

다음 단계 조건: 실제 JWT/JWKS와 브라우저의 계정 동작이 통과하고 운영 콘텐츠의 품질·공급 상태가 확인돼야 한다.

## 7. 알림을 dry_run으로 먼저 정기 실행한다

- [알림 구성 예제](../../../service/lens-cms-api/.env.example)에 있는 암호화 키/버전·정책 버전을 안전하게 공급한다. 저장 구독을 읽는 암호화 키를 유지하고 교체 시 이전 키 복호화 경로를 준비한다.
- 기존 worker가 실행 중이라면 먼저 중지하고 mode 필수 계약의 CMS/worker를 같은 버전으로 갱신한다. batch에서 고른 모드가 계획·claim·send에 전달돼야 하며 모드 변경 요청은 차단한다.
- 알림 API 프로세스 안에 타이머를 추가하지 않고 별도 oneshot worker를 정기 실행한다. 기존 상시 실행 환경의 작업 스케줄러를 우선 검토하고, 배치 회전·중복 실행·최대 처리 시간·실패 격리를 관찰한다.
- 후보 없음, 관심 source별 선택, 저장 문장 사용 미동의, 승인 후속 글, 형식 선호, 주간 기록, 수신 철회·일시 중지·기기 해제에서 계획/취소가 맞아야 한다.
- 전달 원장·최근24시간 중복 제한·lease 만료/unknown·재시도 제한·provider 실패를 확인한다. last_simulated_at을 실제 발송 시각으로 표시하지 않는다.
- 필요하면 원시 이용 이벤트/전달/동의 원장 보관 기간·정리 작업을 확정한다. 가져오기 영수증을 임의 삭제하면 해제 보존이 깨질 수 있어 별도 정책이 필요하다.

다음 단계 조건: 정기 모의 처리와 장애/복구 모니터링이 안정적이어야 한다. dry_run을 live로 변경하는 것은 별도 운영 승인 대상이다.

## 8. 동의한 실제 기기로 푸시를 점진 활성화한다

- VAPID 공개/비공개 키·subject, HTTPS·브라우저 권한·service worker scope, 정책 버전/동의 문구를 준비한다. 레터 이메일 구독은 별도 기능으로 유지한다.
- 테스트 계정과 명시적으로 동의한 기기에 먼저 실제 발송·수신·알림 클릭을 확인한다. 클릭은 /my-lens#ml-news로 이동하며 로그인/선호 형식 링크와 이어져야 한다.
- CMS의 LENS_PUSH_MODE=live/LENS_PUSH_LIVE_ENABLED 및 worker의 --live 활성화는 승인한 환경에만 적용한다. dry_run의 합성 구독은 실제 발송 대상이 아니다.
- 제공자 accepted는 실제 기기 수신/열람과 다르다. Safari·모바일 등 지원 브라우저/설치 조건을 실제 기기에서 확인한 범위로 표시한다.
- 제공자410의 기기 비활성화,429/5xx 제한 재시도, 전송 결과 불명확 unknown의 자동 재발송 금지, 키 교체·로그아웃 해제 실패를 인수한다.
- 이후 대상 계정을 단계적으로 넓히며 DB/API 지연·에러·구독 실패·중복·발송 실패를 모니터링한다. 처리량이 늘면 큐/분리 worker/쿼리 최적화는 측정 후 결정한다.

## 되돌리기와 출시 판단

푸시 문제가 생기면 우선 정기 worker와 live 발송을 중지한다. API/CMS/프론트는 호환되는 이전 코드 조합으로 되돌리되 계정 기록과 영수증을 지우지 않는다. v1.54 이후 같은 snapshot의 여러 UUID가 있을 수 있으므로 이전 UNIQUE 제약을 단순 재생성하면 안 된다. DB 되돌리기는 실제 데이터 영향과 백업을 확인한 별도 계획으로 수행한다.

출시 시점에는 필수 기능(로그인·소유권·관심·서랍·추천·기록)의 스테이징 인수가 선행돼야 한다. 메타데이터나 편집 관계가 준비되지 않은 기능은 대기/빈 결과로 표시하고, 푸시는 dry_run 또는 중지 상태로 먼저 출시할 수 있다. 실제 푸시 인수까지 완료되기 전에는 ‘운영 알림 전체 완료’로 표시하지 않는다.
