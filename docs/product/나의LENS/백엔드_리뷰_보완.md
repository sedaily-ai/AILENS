# 나의 LENS 백엔드 리뷰 보완

> 최신 보완: 형식 선호·팔로우·서버 읽음·브라우저 가져오기와 실제 스키마 타입·앱 역할의 알림 잠금 권한까지 포함한다. SQL 적용 순서는 v1.48~v1.55이며 운영 미반영이다. 운영 단계는 [운영 적용 전 남은 단계](운영적용_남은단계.md)를 따른다.

## 실제 스키마 타입·앱 역할 호환 보완

- v1.38의 `issue_letter_categories.category_slug`는 VARCHAR(32)다. 레터 카테고리 배열과 요청의 TEXT[]를 비교하기 전에 양쪽을 TEXT[]로 맞춘다. 추천 후보의 분야·키워드 조건과 순서는 유지한다.
- `content_followup_links`는 앱 역할에 SELECT만 허용한다. PostgreSQL의 `FOR SHARE`는 UPDATE 권한도 필요하므로 기존 발송 직전 쿼리는 이 역할에서 실패할 수 있다.
- [v1.55 잠금 함수](../../architecture/lens-erd-src/lens_schema_v1.55_2026-10-15.sql)를 v1.54 다음에 마이그레이션 역할로 적용한다. `public.lock_notification_followup_sources(TEXT[])`는 해당 source의 관계 행을 정렬해 잠그기만 한다. 같은 트랜잭션의 발송 조건 재검사까지 잠금을 유지한다.
- 함수는 SECURITY DEFINER로 실행하며 search_path를 고정하고 관계 테이블을 `public`으로 명시한다. PUBLIC 실행 권한을 회수하고 `lens_service_app`에 EXECUTE만 부여한다. 앱 역할에는 관계의 INSERT/UPDATE/DELETE나 함수 소유권·public 스키마 CREATE를 부여하지 않는다. 함수 소유자는 기존 마이그레이션 역할로 유지한다.
- **v1.55 적용과 함수 권한 확인 후 CMS 알림 코드를 갱신한다.** 함수 없이 신규 `send_claim`을 배포하면 안 된다. 기존 v1.48~54 SQL과 API 요청/응답은 변경하지 않는다.

## 형식 선호와 계정 연결 추가 리뷰

현재 프론트의 홈·서랍·읽기 기록·알림 설정은 로그인 계정 API를 사용한다. 계정의 직접 관심, 유효 뉴스/레터 이용, 저장 문장, 북마크, 실제 작성자 팔로우를 처리한다. 4형식 선호는 뉴스 publication의 읽기·웹툰·듣기·영상 세션/완료 원장에서 조회한다. 이슈 레터는 형식 비교에서 제외하되 관심·완료·추천에는 포함한다.

### 수정한 동작

- 알림은 미열람·최근72시간·미통지 필터를 **순위/개수 제한 전에** 적용한다. 상위 후보가 이미 통지되었다는 이유로 다음 새 글을 놓치지 않는다.
- 브리핑과 승인 후속 글을 함께 선택했고 후속 글이 있다면 최대4개 중 최소1개를 후속 글로 확보한다. 나머지 후보의 관심 점수·제공 형식 선호 순서는 유지한다. 같은 글은 한 번만 넣고 더 높은 추천 근거를 보존한다.
- worker가 조회한 mode를 계획·claim·send-claim 요청에 고정한다. 내부 operation은 mode를 필수로 검사하고, 계정 잠금 이후와 발송 직전에도 모드를 재확인한다. dry_run 요청은 provider를 호출하지 않는다. CMS가 도중 live로 전환되어도 기본 검증 worker가 실제 발송으로 넘어가지 않는다.
- 전달 계획과 전송 직전 재조회는 선택한 content_keys 순서를 유지한다. 콘텐츠 종류별 조회/발행일 정렬 때문에 선호·관심 순서가 바뀌지 않는다. 이용 형식 근거가 바뀌면 source_fingerprint 변경으로 기존 계획을 취소한다.
- 가져오기는 UUID별 요청 입력을 영수증에 기록한다. 새 UUID로 같은 선택을 재생한 경우도 해당 UUID의 다른 목록은409다. 응답 손실 후 화면 재시도는 같은 UUID를 유지한다.
- 같은 목록을 **새 UUID로 명시적으로 다시 요청**하면 이전에 수락한 slug를 다시 저장하지 않고, 거부된 slug만 현재 공개 상태로 재검사한다. 공개 전환된 거부 항목은 새로 가져올 수 있다. 같은 UUID의 재전송은 최초 결과를 그대로 반환한다.
- 실제 제공 형식이 일부만 있는 기사도 format 키로 탭·본문·분량·설명·이동·계측을 일관되게 처리한다. 읽기/영상 두 형식의 두 번째 항목을 웹툰으로 해석하지 않고, 제공하지 않는 다음 형식 버튼을 만들지 않는다.
- 기존 읽기 이력 SQL은 articles의 a 별칭을 유지한다. 문장 source의 ap 별칭 변경이 기존 프로필/읽기 조회와 저장 SELECT에 전파되지 않게 한다.
- 레터 목록/상세/추천에서 작성자가 지정되지 않았을 때 담당 주제로 작성자를 추정하던 코드를 제거했다. 서버의 실제 작성자 관계만 표시한다. 작성자 없는 에디터 페이지의 목록이 줄어들 수 있으며, 담당 분야 추천과 작성자 표시는 구분한다.
- 저장 목록 API가 실패하면 정상 빈 결과/모두 완료 결과로 표시하지 않고 재시도 안내를 제공한다. 알림 설명은 계정 연결과 운영 발송 준비를 구분한다.

### v1.54와 가져오기 계약

[lens_schema_v1.54_2026-10-14.sql](../../architecture/lens-erd-src/lens_schema_v1.54_2026-10-14.sql)은 user_lens_imports의 계정/snapshot_hash UNIQUE를 제거하고 계정/hash/처리시각/UUID 조회 인덱스로 바꾼다. 계정/import_id PK는 그대로다. 별도 새 테이블은 필요하지 않으며 기존 영수증·북마크를 지우지 않는다. **v1.54 없이 새 가져오기 코드를 배포하면 안 된다.**

새 UUID 요청은 재생 요청을 포함해 계정당 최근24시간20회까지 처리한다. 같은 UUID의 정상 재시도는 새 영수증/제한 횟수를 만들지 않는다. accepted는 해당 선택 목록에서 처리한 누적 수락 결과이며 실제 현재 북마크 목록과 다를 수 있다. 현재 저장 상태는 letter-bookmarks로 조회한다. 해당 목록과 다른 부분 목록을 사용자가 명시적으로 선택하면 별도 가져오기다. 브라우저 원본은 모든 경우 보존한다.

## 수정한 동작

| 항목 | 수정 후 동작 |
|---|---|
| 실제 본문 확인 | publication의 `rendition_blocks.content`는 스키마 정본의 TEXT로 검사한다. 공백 본문/이미지 URL은 준비된 형식으로 보지 않는다. issue_letter의 JSONB 문단은 실제 문자열·text/label/title/value 등 화면 내용만 검사한다. 빈 배열·공백·href/block 메타데이터만으로 추천·완료를 인정하지 않는다 |
| 게시 시각 | 미래 또는 발행 시각이 없는 자료는 개인 resolver·추천에서 제외한다. 저장한 레터는 unavailable로 표시하고 해제는 허용한다 |
| 기존 저장 문장 | article_no 외에 기존 rendition_id도 같은 publication의 stable key/href로 연결한다. 홈 문장·후속 관계·알림 원천 확인에 같은 join을 사용한다 |
| 서랍 계정/입력/실패 | 기존 서랍 조회·저장·삭제도 계정 active 상태를 검사한다. 쓰기는 사용자 row lock으로 직렬화한다. JSON 객체·문자열·ID·개수·날짜 오류는400, 차단 계정은403, 저장 서버 장애는503으로 처리한다. 삭제 장애를404로 감추지 않는다. 응답마다 CORS 헤더를 복사해 개인 캐시 설정이 공유 상수를 바꾸지 않게 한다 |
| 대시보드 요청 | POST/PUT의 비객체 JSON은 내부 저장 API 호출 전에400으로 거부한다 |
| 활성 기기 집계 | 최신50개 기기 목록과 전체 활성 기기 수를 별도 계산한다. 오래된 활성 기기가 최근 비활성 기기에 가려져 blocked/0개로 표시되지 않는다 |
| 기기 해제/계정 이동 | target 취소 후 부모 delivery의 done/canceled/failed/unknown도 정리한다. live에서 이미 lease를 받은 sending은 실제 전송 여부를 단정할 수 없어 unknown으로 남긴다. 철회 이후 재전송은 막고 미확정 흔적을 삭제하지 않는다 |
| 시각/lease | lock 대기 전 transaction 시작 시각 대신 실제 `clock_timestamp()`로 일정·만료·lease를 검사한다 |
| 알림 메타데이터 | 직접 관심/저장/이용 원천뿐 아니라 관찰한 공개 분야·키워드 변경도 hash에 반영한다. 후보 메타데이터 signature를 계획에 저장하고 전송 직전 부모를 잠근 뒤 다시 읽어 비교한다. 변경된 추천을 그대로 보내지 않는다. hash만 저장하며 문장 원문/후보 본문은 발송 원장에 추가하지 않는다 |
| worker 회전 | 검사 시각이 오래된 계정부터 batch를 확보한다. 빈 후보·실패·이미 계획된 계정이 앞100개를 계속 점유하지 않는다. 계정별 오류는 다른 계정 처리와 분리하고 예외 내용/endpoint를 로그에 넣지 않는다 |

새로운 계정 팔로우·의미 추천·기존 기기 자료 가져오기·iframe 공급자 SDK를 구현한 것은 아니다. 빈 레터는 새 이용 세션에서도400으로 거부하며, 이전에 시작한 세션의 본문이 바뀌면 기존 CONTENT_CHANGED 검사를 유지한다.

## SQL과 내부 worker 계약

**v1.48 → v1.49 → v1.50 → v1.51 → v1.52** 순서로 준비한다. 새 `lens_schema_v1.52_2026-10-14.sql`은 `user_notification_preferences.scan_checked_at`과 회전 인덱스만 추가한다. 기존 설정 revision/updated_at·동의·보상 기록을 바꾸지 않는다. 운영 적용은 별도다.

- GET `/internal/personal/lens/notifications/due`: 조회 전용으로 mode와 다음 후보를 확인한다.
- POST 같은 경로: 내부 토큰 필수. body `{mode:'dry_run'|'live',limit:1..100}`. 서버 mode 불일치는409이며 DB 회전 시각을 바꾸지 않는다.
- POST는 단일 advisory lock에서 오래된 검사 시각 순으로 선택하고 scan_checked_at을 갱신한다. 응답 `{mode,server_now,owners}`는 유지한다. 잠금은 batch 확보 후 종료하고 개인 후보 계산·전송 동안 유지하지 않는다.
- worker는 먼저 GET으로 모드를 확인한다. dry_run worker는 live이면 POST batch/plan/claim 전에 중단한다. 이후 POST로 최대 limit개를 확보하고 각각 계획/target 처리를 수행한다.
- 한 계정 처리 오류는 `{planned,processed,error:'DEPENDENCY_UNAVAILABLE'}`로 남기고 다음 계정으로 진행한다. stdout/로그에 owner·구독 endpoint·키·예외 원문을 추가하지 않는다.
- 기존 pending delivery에 후보 signature가 없으면 보수적으로 취소한다. 운영에 이미 원장이 있는 환경에서 이 변경을 적용할 때 대기 작업 인수를 별도로 검토한다.

## 운영 인수 경계

현재의 batch 회전은 영구 누락 방지용 초기 구현이다. 계정/기기 규모에 맞는 실행 주기·처리량·중복 worker 관제·리트라이 대기 지연·unknown 처리·보관/정리 작업은 운영 인수에서 확정한다. 전송의 단일 DB lock은 유지하므로 부하 검증과 규모 확대 설계가 필요하다.

미디어 길이 공급·보상 그룹·편집 후속 관계·알림 품질 정책, 실제 운영 스키마/권한·Gateway·Cognito·키 공급·스케줄러·실제 푸시 수신·롤백은 여전히 운영 인수 대상이다. 이번 보완을 운영 적용 완료로 해석하지 않는다.
