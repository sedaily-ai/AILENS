# 콘텐츠 완료·기간 기록·리워드 실행 계획

목표: 계정 상세 이용 → 서버 완료 판정 → KST 기간 기록·일별 스탬프·주간 배지 → 실제 대시보드.
구조: 기존 Python Lambda → 내부 FastAPI → PostgreSQL. 운영 DB·AWS·배포·커밋·push는 제외한다.
정본: 백엔드_개발_인수인계.md 5/9절과 API 계약 9/10절의 권장 초기안. 로컬 개발 규칙 completion-v1이며 출시 전 제품 정책 확정이 필요하다.

## 설계와 경계

- 읽기: 본문 도달 비율80%, visible30초. 짧은 본문도30초. 웹툰: 실제 컷80%, visible10초, 컷별 프론트 노출1초. 미디어: 등록 길이의 소비 구간80%, 사용자 재생 조작 이후의 시간 구간만 계측. 서버 길이가 없으면 미완료/메타데이터 대기.
- visible/active/소비 누적은 서버 경과·증가 한도를 검사한다. 클라이언트 보고가 사람의 독해를 증명하지 않으며 현금성 보상은 없다. 과거 visible-v1 세션·로컬70% 표시를 완료로 소급하지 않는다.
- 동일 publication 4형식은 동일 보상 그룹. 별도 이슈 레터는 content_reward_groups의 명시적 편집 매핑이 있어야 보상한다. 매핑이 없으면 완료 기록은 남기되 보상 대기. 재게시 publication의 그룹 병합도 편집 매핑으로 처리한다.
- 완료 원장/최초 그룹 완료/스탬프/배지는 같은 트랜잭션. 하루 스탬프1개, 주간3일, 최초 완료의 주 분야3개, 이미 완료·저장한 서로 다른2그룹 재완료. 재완료는 별도 세션이며 이전 완료와 최소30분 간격으로 구분한다.
- 저장 이전 시각은 현재 북마크 saved_at 또는 현재 서랍 문장 saved_at으로 확인. 삭제 자료의 저장 이력은 인정하지 않는다. 날짜는 서버 수신 시각 KST, 주는월요일 시작. 월/년은 조회만 확장한다.
- 기간 조회는 전체 원장 SQL, 수집 시작 이전/미래/빈값/오류를 구분. 개인 API no-store와 JWT owner 유지.
