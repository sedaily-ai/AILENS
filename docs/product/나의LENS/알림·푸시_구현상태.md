2026-10-14 로컬 구현. 기존 **공개 Python Lambda → service/repository → 내부 FastAPI → psycopg2/PostgreSQL** 구조를 유지했다. 프론트 계정 설정·수신 동의·기기 연결·서버 후보 미리보기를 연결했다. 운영 DB 적용·Gateway 연결·배포·실제 푸시 등록/발송은 하지 않았다.

기존 인수인계의 제안 계약과 차이가 있으면 이 문서와 현재 코드가 우선한다. 실제 브라우저 수신은 별도 운영 인수 대상이다.

## 사용자 흐름과 상태

1. 로그인 계정으로 유형·시간·빈도·시간대·활용할 관심 기록을 저장한다. 저장은 동의나 구독을 생성하지 않는다.
2. 사용자가 동의 문구를 확인하고 체크한 뒤 **수신 동의 저장**을 누른다. 정책 버전을 저장한다. 정책이 바뀌면 다시 동의해야 한다.
3. 별도의 기기 연결 버튼으로 구독을 등록한다. `dry_run`은 합성 기기를 연결하고 브라우저 권한·외부 PushManager를 호출하지 않는다. `live`일 때만 명시적 클릭으로 Notification 권한과 service worker/PushManager를 연결한다.
4. **서버 후보 미리보기**는 저장된 계정 설정으로 후보를 조회한다. 발송·전달 작업·브라우저 알림을 생성하지 않는다.
5. 별도 worker가 시간이 된 계정을 계획하고 DB 대상 lease를 확보한 뒤 전송 직전 조건을 재검사한다. 서버 `mode`가 실제 전달과 로컬 검증을 구분한다.
6. 동의 철회는 모든 해당 계정 기기와 대기 작업을 비활성화한다. 기기 해제는 본인 기기만 가능하다. 로그아웃은 서버 기기 해제 요청을 최대5초 대기한 뒤 기존 signOut을 진행한다. 서버 해제 실패가 로그아웃을 막지는 않으며, 전용 native 구독도 종료를 시도한다. 이 실패 경로는 서버에 활성 행이 잠시 남을 수 있다.

초기 유형은 모두 꺼짐이다. categorySource/keywordSource는 켜짐, **sentenceSource는 꺼짐**이다. 브라우저 공용 알림 초안을 계정에 자동 가져오지 않는다. 계정 변경·만료·취소된 요청·늦은 미리보기 응답은 다른 계정 상태에 반영하지 않는다.409 revision 충돌은 선택을 유지하고 최신 설정을 다시 확인하게 한다. JSONB 필드 순서는 변경 여부 비교에 영향을 주지 않는다.

화면은 `blocked/ready/paused`, 필요한 조건, 활성 기기 수, 최근 **로컬 검증 시각**과 **제공자 접수 시각**을 분리한다. `ready`는 발송 조건 충족이며 실제 수신 증거가 아니다. provider의 accepted 역시 기기 도착/열람 확인이 아니다. 기존 레터 이메일 구독·확인·수신거부는 별도다.

## 후보·일정 규칙

| 유형 | 입력과 필터 |
|---|---|
| briefing | categorySource: 직접 선택 분야·최근 이용 분야. keywordSource: 직접 선택 주제·등록 키워드 이용 신호. sentenceSource: 본인 저장 문장 단어, 별도 선택했을 때만 조회·활용. 기존 정확 일치 추천 규칙을 사용하고 무관한 최신 글로 채우지 않음 |
| followups | 현재 본인 레터 북마크 또는 서랍 문장의 확인된 publication 원문 + `content_followup_links.editor_approved=true`. 관계 등록 시각이 저장 시각 이후인 글만 사용. 일반 열람/유사 키워드를 편집 확인된 후속 사건으로 간주하지 않음 |
| weekly | KST 지난주 월~일의 완료가 있었던 날·현재 남아 있는 해당 기간 저장 문장/레터 수. 과거 삭제된 저장의 이력 집계가 아님.0건이면 생략 |

- 뉴스와 이슈 레터를 함께 사용한다. 공개·삭제되지 않음·실제 준비된 콘텐츠·72시간 이내 게시·아직 열람하지 않음 조건을 적용한다. 관심 단어는 서버 등록 메타데이터와 정확히 일치해야 한다. 의미 유사도/품질 점수 모델은 추가하지 않았다.
- 미열람·최근72시간·미통지 필터를 순위/개수 제한 전에 적용한다. 후보는 중복 제거 후 최대4개다. 브리핑·승인 후속 글을 함께 선택하고 후속 후보가 있으면 최소1개를 후속 글로 확보한다. 전달 원장과 전송 직전 재검사도 이 순서를 유지한다. 실제 전달 원장에 이미 제시한 콘텐츠는 다시 넣지 않는다. 같은 주간 집계 기간도 반복 전달하지 않는다. 여러 기기에는 같은 묶음을 전달할 수 있다.
- briefing의 source 필터는 기존 대시보드 관심/추천 설정을 바꾸지 않는다. 동의를 철회하거나 일시 중지해도 개인 대시보드 자체의 추천을 중지하지 않는다.
- 일정은 선택한 IANA 시간대 `Asia/Seoul`, `America/New_York`, `Europe/London`, `UTC` 중 하나다.08:00~20:59에 설정 시각 이후 처리한다. 매일 또는 월·수·금, weeklyDay는0=일~6=토다.21:00~08:00에는 처리하지 않는다. worker가 지연되어 조용한 시간에 들어갔으면 보내지 않는다.
- 계정/선택 시간대 날짜/mode unique로 **하루 최대1묶음 계획**을 만든다. 완료·결과 미확정 작업 이후24시간 제한을 추가한다. DST와 시간대 변경에도 연속 전달을 제한한다. 취소된 날짜의 계획을 재생성하지 않으므로 그날 설정 변경 후 새 묶음은 다음 가능한 날짜에 계획된다.
- 전송 직전 현재 동의/정책·설정 revision·시간·계정·기기 소유/활성/만료·공개/미열람·원천 fingerprint를 재검사한다. 관심 설정·저장/열람/완료·저장 원문의 편집 후속 관계가 계획 후 바뀌면 보수적으로 취소한다. 이슈 레터 기간 집계는 KST이고 알림 도착 시각만 선택 시간대다.
- 푸시 본문은 ‘관심에 맞는 새 글 N편’ 또는 ‘지난주의 관심 기록’처럼 일반 문구다. 저장 문장 원문·관심 단어·endpoint·구독 키를 일반 응답/본문/로그에 노출하지 않는다. 클릭은 `/my-lens`로 이동한다.

## 공개 API

모두 `Authorization: Bearer <Cognito ID token>` 필수, owner=검증된 sub, `Cache-Control: private, no-store`. 클라이언트 user_id로 다른 계정을 선택할 수 없다.

| 경로 | 요청/반환 |
|---|---|
| GET `/api/v2/me/notifications/preferences` | `{revision,preferences,consent,config,subscriptions,delivery}` |
| PUT 동일 경로 | 정확히 `{revision,preferences}`. 성공200·새 revision.400 입력,409 stale |
| GET `/api/v2/me/notifications/consent` | 설정 조회와 동일한 계정 상태 |
| PUT 동일 경로 | 정확히 `{channel:'web_push',granted:boolean,policy_version:string}`.200 상태,409 정책 변경 |
| POST `/api/v2/me/push-subscriptions` | `{permission:'simulated'\|'granted',subscription:{endpoint,keys:{p256dh,auth},expirationTime:null\|milliseconds}}`. 신규201·갱신200 `{id,active,simulated,created_at,created}` |
| DELETE `/api/v2/me/push-subscriptions/{UUID}` | 본인 기기만200 `{id,active:false}`, 다른 계정/없는 기기404 |
| GET `/api/v2/me/notifications/preview` | `{mode,content_count,items:[{title,href}],weekly,empty,delivery,actual_sent:false}`. 후보가 없어도200 빈 상태 |
| GET `/api/v2/me/dashboard` | notifications 영역에 실제 설정 상태를 집계. 다른 영역 실패와 구분 |

저장 preferences의 실제 필드:

```json
{"version":1,"briefing":false,"followups":false,"weekly":false,"frequency":"daily","time":"08:00","timezone":"Asia/Seoul","weeklyDay":1,"paused":false,"categorySource":true,"keywordSource":true,"sentenceSource":false}
```

내부 prefix는 `/internal/personal/lens`, `X-Internal-Token` 필수다. 공개 라우팅이 아니다. preferences/consent/subscriptions에 더해 GET `/notifications/context`, `/inputs`, `/candidates`, `/due`, POST `/notifications/due`(batch 확보), POST `/notifications/plans`, `/claim`, `/send-claim`을 제공한다. due 외에는 검증된 owner를 user_id로 전달한다. 발송 worker 원장을 public API로 노출하지 않는다.

## 암호화·기기 소유권

HTTPS 제공자 host는 FCM·Mozilla Push·Apple Push 허용 목록을 사용한다. localhost/사설 주소/임의 host·userinfo·fragment·비표준 port·공백은 거부하며 redirect를 따라가지 않는다. endpoint는 정규화 후 hash한다. `push.invalid` 합성 endpoint는 dry_run만 허용한다. keys는 유효한65바이트 P-256 공개키와16바이트 auth다. 만료 구독은 연결/전송에서 제외한다.

구독 전체(endpoint·keys)를 Fernet로 암호화한다. 응답에는 기기 ID·상태·시각만 반환한다. 암호화 키를 repo/로그에 남기지 않는다. 같은 endpoint의 다른 계정 연결은 기존 키 쌍 소유를 비교한 뒤 이전 계정 대기 target을 취소하고 owner를 이동한다. 신규 연결은 계정당24시간50건으로 제한한다.

이 장치의 `{id,mode}`만 계정별 localStorage에 남는다. 다른 기기 해제는 현재 브라우저 native 구독을 건드리지 않는다. localStorage를 막으면 서버 저장은 성공할 수 있으나 현재 기기 식별/자동 해제 보장이 낮아진다. 계정 만료/비정상 종료 시 서버 행 정리는 별도다.

## 발송·실패 처리

- 기본 `dry_run`은 HTTP provider 호출이 없고 `simulated_at`만 기록한다. 실제 구독과 합성 구독을 mode별로 구분한다.
- 계획/철회/계정 전환/전송은 초기 구현의 **단일 PostgreSQL advisory transaction lock**으로 직렬화한다. 전송은 이 lock을 잡은 채 provider 연결/읽기 timeout 각각10초를 사용하며 worker의 send-claim 내부 HTTP 대기는30초다. 조건 변경과 전송의 순서를 명확히 하는 소규모 초기안이며, 많은 기기의 병렬 처리에는 account/subscription lock 순서를 재설계해야 한다. 철회 완료 후 새 전송은 막지만 이미 제공자에 접수된 알림은 회수할 수 없다.
- claim은 전송 전에 `sending`/UUID lease/2분 만료/시도 수를 commit한다. 중복 호출은 동일 lease를 다시 처리하지 않는다. 미완료 lease 만료는 unknown이며 자동 재획득하지 않는다.
- 제공자200/201/202는 accepted,404/410은 gone+기기 비활성,429/5xx는 최대3시도/2·4분 재시도다. 기타4xx는 failed, network timeout·결과 없는 실패는 unknown이다. 코드만 보관하며 endpoint가 포함될 수 있는 예외 문자열은 저장/출력하지 않는다.
- 여러 기기 중 queued/retry가 남으면 processing, 불명확한 결과가 있으면 unknown, 성공이 있으면 done을 기록한다. unknown은 운영자가 별도로 확인해야 하며 임의 자동 재발송하지 않는다.
- 유효 후보가 없으면 계획하지 않는다. 편집 승인 관계·실제 준비된 콘텐츠 공급이 없으면 기능은 빈 상태다.

live adapter는 고정 버전 [pywebpush2.5.0](https://pypi.org/project/pywebpush/2.5.0/)을 사용한다. 라이브러리 호출 계약은 [공식 저장소](https://github.com/web-push-libs/pywebpush)를 따른다. redirect 차단, 프록시 환경 무시, TTL1시간, Topic=전달 ID, 새 VAPID claims를 사용한다. 라이브러리 설치와 경로 구현은 실제 기기 수신 검증과 별개다.

## 환경 설정·worker 인수

신규 이름은 `service/lens-cms-api/.env.example`에 값 없이 기록했다. 비밀은 운영 비밀 저장소로 공급하며 `.env.example`을 그대로 실행 환경으로 쓰지 않는다.

| CMS 환경 변수 | 의미 |
|---|---|
| LENS_PUSH_MODE | 미설정은dry_run. live는 별도 명시 |
| LENS_PUSH_POLICY_VERSION | 동의 정책 버전. 기본lens-personal-push-v1, 바꾸면 재동의 필요 |
| LENS_PUSH_KEY_VERSION | 현재 암호화 키 버전, 기본v1 |
| LENS_PUSH_ENCRYPTION_KEY | 현재 버전 Fernet 키. 유효 키 없으면 기기 등록/전송 준비 차단 |
| LENS_PUSH_ENCRYPTION_KEYS | 선택 JSON keyring `{version:FernetKey}`. 이전 버전도 읽을 때 사용. 값은 비밀 |
| LENS_PUSH_LIVE_ENABLED | 정확히true와 live mode가 함께 있어야 외부 경로 활성화 |
| LENS_PUSH_VAPID_PUBLIC_KEY / PRIVATE_KEY / SUBJECT | live 제공자 구성. subject는 승인한 연락용 mailto/HTTPS. 공개 키만 frontend config로 반환 |

worker client는 기존 `LENS_CMS_API_URL`, `LENS_CMS_API_TOKEN`을 사용한다. CMS과 별도 프로세스/실행 환경이다. 기본 CLI는 loopback만 허용하며 서버가 live라고 응답하면 계획/claim 전에 중단한다. `--live`는 client의 `LENS_PUSH_LIVE_ENABLED=true`도 필요하다. 실제 활성화 승인/비밀 공급 전에는 이 옵션을 사용하지 않는다.

```bash
cd /Users/ldy/Desktop/Code/Sedaily/AILENS/service/backend
python notification_worker.py --limit 100
```

이 명령은 사전에 **격리 로컬 API/DB와 loopback URL·내부 토큰을 준비한 환경**에서만 실행한다. repo의 운영 .env를 자동 로드하지 않는다. worker는 due 계정 최대100개, 계정당 target 최대50개를 처리하고 끝난다. 실행 주기·프로세스 관리·공정한 분할/대규모 큐·알림/unknown 관제·보관 기간/폐기 작업은 운영 인수 사항이며 이번에 스케줄러나 AWS 리소스를 만들지 않았다.

## 남은 운영 작업

SQL 적용과 실제 role 권한, API Gateway/CORS/private-cache 연결, 공개/내부 API와 SW/프론트 배포, 암호화/VAPID 키 비밀 공급·회전, 승인된 동의 문구·정책, 뉴스 알림 품질 기준·편집 관계 공급, worker 실행/관제·원장 보관 기간, 승인된 기기의 실제 provider 접수/수신·권한 거부/만료 등을 확인해야 한다. 공개·준비 상태와 관심 일치는 구현됐으나 별도 ‘좋은 글’ 품질 점수/자동 편집 승인 모델은 없다. 운영 활성화 전에 편집 품질 기준을 확정해야 한다.

기존 다른 service worker와 scope 충돌, VAPID 키 교체 시 기존 native 구독 재연결, Cognito 실사용 로그인, iOS 설치/PWA 제약도 실제 환경 인수 대상이다. 이번 로컬 검증은 이러한 운영 조건을 통과했다고 의미하지 않는다. 검증 전용 토큰·DB fixture·스크린샷·실행 로그는 작업 기록/문서에 포함하지 않는다.

## 내부 worker 모드 계약 보완

POST /internal/personal/lens/notifications/plans 및 send-claim의 body에 mode=dry_run|live가 필수다. claim은 {"mode":"dry_run"} 형태의 JSON 객체만 받는다. mode는 UUID 필드와 분리하며, 현재 CMS 모드와 다르면 MODE_CHANGED로 거부한다. worker가 batch 조회에서 고른 mode를 모든 쓰기에 동일하게 전달한다. 공개 미리보기 API는 그대로이며 발송 요청을 생성하지 않는다.

계정 잠금 이후·계획 저장 직전·발송 직전에도 모드를 재검사하고 dry_run은 provider.send를 호출하지 않는다. 배포 중 모드가 변경되면 기본 검증 worker의 실제 발송을 차단한다. 새 CMS와 worker는 같은 계약으로 적용한다. 기존 worker가 이미 동작 중이면 중지한 뒤 CMS/worker를 함께 갱신하고 재시작한다.
