# 레터 북마크 — 브라우저 저장과 계정 동기화 연동 요구사항

확인일: 2026-10-13. **브라우저 저장은 구현됨. 레터 북마크의 계정 저장·기기 간 동기화는 미구현이다.** 아래 API·DB·로그인 병합 절차는 후속 구현안이며, 현재 호출할 수 있는 기능으로 설명하지 않는다.

## 현재 구현과 이번 반영 범위

| 항목 | 확인한 상태·근거 |
|---|---|
| 비로그인 저장 | `service/frontend/src/features/letter/lib/useLetterShelf.ts`에서 localStorage 사용. 로그인 필수 조건 없음 |
| 북마크 저장값 | `lens-letter-saved`: 레터 slug 문자열 배열. 저장 시 최근 200개를 기록하며 계정 ID로 분리하지 않음 |
| 읽음 저장값 | `lens-letter-read`: 별도 문자열 배열. 이번 북마크 동기화 범위에 포함하지 않음 |
| 목록·상세 | `LetterListView.tsx`, `LetterRow.tsx`, `ReadingTools.tsx`가 같은 훅 사용. 페이지 이동·새로고침 시 같은 origin의 저장값을 읽음 |
| 저장 범위 | 브라우저·origin별. 브라우저 데이터 삭제 시 사라짐. localStorage 쓰기가 실패하면 이번 방문의 메모리 상태만 유지 |
| 로그인 | 현재 로그인해도 북마크 서버 요청·계정 병합·다른 기기 조회는 실행하지 않음. 같은 브라우저에서 다른 계정으로 로그인해도 현재 로컬 저장값은 공용 |
| 기존 서버 보관함 | `service/backend/handlers/user/archive.py`, `service/lens-cms-api/routes_users.py`, `personal_repo.py`의 내 서랍은 **문장 보관**. 레터 전체 북마크 저장소가 아님 |
| 기존 관심·투표 | `routes_letters.py`의 관심 API는 `X-Voter-Id`를 해시한 기기 식별자 기반. 로그인 계정 북마크 인증으로 사용하면 안 됨 |
| 레터 식별자 | 프론트 `IssueLetter`는 slug 사용. 서버 `issue_letters`의 안정적인 PK와 slug 변환을 후속 연동에서 결정해야 함 |

이번 변경은 저장 안내만 추가한다. 서버·DB·인증·메일 구독·북마크 저장 로직은 바꾸지 않는다. 운영 배포도 하지 않는다.

## 사용자에게 표시하는 문구

현재 목록과 상세의 저장 도구 근처에 아래 문구를 함께 표시한다. 저장 버튼은 `aria-describedby`로 이 설명과 연결한다. 문구 정본은 `useLetterShelf.ts`의 `LETTER_SHELF_NOTICE`다.

> 이 브라우저에 저장돼요. 로그인 후 기기 간 동기화는 준비 중이에요.

후속 연동 검증을 마친 뒤 사용할 문구:

| 상태 | 문구·표시 조건 |
|---|---|
| 비로그인 | `이 브라우저에 저장돼요. 로그인하면 다른 기기에서도 볼 수 있어요.` — 계정 동기화가 실제 활성화된 뒤에만 사용 |
| 로그인·서버 반영 완료 | `계정에 저장돼요. 다른 기기에서도 볼 수 있어요.` — 로그인 여부만이 아니라 서버 저장·조회 성공을 확인한 상태 |
| 서버 동기화 중 | `저장한 레터를 동기화하고 있어요.` |
| 서버 반영 실패 | `계정에 저장하지 못했어요. 다시 시도해주세요.` — 재시도 행동과 미반영 상태 표시 |
| 브라우저 저장 실패 | `이 브라우저에 저장할 수 없어요. 이번 방문 동안만 유지돼요.` — 저장 실패 감지 UI는 후속 보완 항목 |

API가 없거나 연동하지 않은 상태에서 `로그인하면 동기화돼요`, `동기화 완료`를 표시하지 않는다. 계정 동기화가 일부 계정에만 열렸다면 실제 사용 가능 여부를 기준으로 문구를 선택한다.

## 백엔드 구현안 — 아직 없는 API

공개 경로는 기존 인증 API의 배치 방식과 대조해 프론트 담당자와 확정한다. 아래 `/api/letter-bookmarks`는 **제안 경로**다. 기존 내 서랍에 레터 제목을 문장처럼 넣거나, 공개 관심 API에 북마크를 섞지 않는다.

| 제안 API | 역할·요구사항 |
|---|---|
| `GET /api/letter-bookmarks` | 로그인한 본인의 북마크만 조회. cursor 페이지네이션, 예시 기본 50개·최대 100개. `items`, `next_cursor` 반환 |
| `PUT /api/letter-bookmarks/{encoded-slug}` | 저장 상태를 명시적으로 설정. 같은 요청 재시도 시 중복 생성 없이 저장된 상태 반환 |
| `DELETE /api/letter-bookmarks/{encoded-slug}` | 본인의 저장 해제. 이미 해제된 항목도 성공 처리. 다른 계정 행에 영향 없음 |
| `POST /api/letter-bookmarks/import` | 비로그인 저장 목록의 로그인 계정 병합. `slugs` 배열 최대 200개, 중복 제거·존재/공개 여부 검증. `accepted_slugs`, `rejected`와 병합 결과를 반환 |

필수 계약:

- 로그인 주체는 검증된 토큰에서 서버가 결정한다. 본문·쿼리의 `user_id`나 `X-Voter-Id`를 계정 소유권 증명으로 신뢰하지 않는다. 기존 `core/auth.py`·문장 보관 API의 인증 경계를 참고한다.
- 사용자별 데이터의 응답은 `Cache-Control: private, no-store`. 로그에 인증 토큰·원본 전체 요청을 남기지 않는다. 쿠키 인증을 선택하면 기존 CSRF 보호도 적용한다.
- slug는 URI 인코딩/디코딩 경계를 확인하고 문자열 길이·배열 크기를 서버에서 제한한다. 숫자 PK로 변환한 뒤 권한과 발행 상태를 검증한다.
- 비로그인 요청은 401. 존재하지 않거나 접근할 수 없는 레터는 북마크로 추가하지 않는다. 가져오기는 각 항목의 성공/실패를 구분해 전체 목록을 무조건 버리지 않게 한다.
- 저장/해제는 원하는 상태를 명시하는 멱등 API로 만든다. `toggle` 서버 API는 네트워크 재시도로 저장 상태가 뒤집힐 수 있어 사용하지 않는다.
- 오류 코드·사용자 메시지·재시도 가능 여부를 구분한다. 실패 시 서버 반영 완료로 응답하거나 표시하지 않는다. 기존 인증 API 기준의 요청 제한도 적용한다.

### 저장 모델 제안

별도 계정 북마크 테이블(가칭 `user_letter_bookmarks`)에 `user_id`, 안정적인 `issue_letter_id`, `saved_at`, 필요 시 갱신 버전을 둔다. `(user_id, issue_letter_id)`는 유일해야 한다. 컬럼 타입·FK·조회 인덱스·운영 권한은 실제 `users`·`issue_letters` 스키마를 기준으로 마이그레이션에서 확정한다.

slug는 사용자 주소에 쓰되 서버 저장의 정본은 안정적인 레터 ID로 한다. slug 변경, 발행 취소, 레터 삭제 시 이전 링크·목록·해제 API가 어떻게 동작할지 함께 정한다. 발행 취소 콘텐츠는 본문을 노출하지 않고, 삭제된 항목을 목록에서 제외하거나 이용 불가 상태로 반환한다.

이 문서는 마이그레이션을 실행하지 않는다. AWS 리소스·운영 DB 변경 전에 저장소 비용태깅/배포 규칙과 적용 권한을 확인한다.

## 프론트 연동과 로그인 병합

1. `useLetterShelf`의 호출부 계약(`ready`, `saved`, `isSaved`, `toggleSaved`)은 가급적 유지한다. 계정 서버 조회가 완료되기 전 빈 배열로 기존 브라우저 저장값을 덮어쓰지 않는다. 읽음 기록과 글자 크기 설정은 별도 유지한다.
2. 비로그인 상태는 브라우저 저장을 계속 허용한다. 로그인 뒤 비로그인 저장 목록을 서버에 가져오고, 서버 북마크와 합집합을 만든다. 빈 로컬 목록을 서버 전체 삭제로 해석하지 않는다.
3. 가져오기 요청에는 같은 원본 목록의 재전송을 식별할 키를 사용한다. 서버는 계정별로 완료된 가져오기의 결과를 재반환해야 한다. 과거 목록의 재전송 때문에 다른 기기에서 해제한 북마크가 살아나면 안 된다. 키·보존 기간·동시 요청 처리 방식은 API 확정 시 결정한다.
4. 서버가 수락한 항목만 가져오기 완료로 처리한다. 실패/거부된 항목을 조용히 삭제하지 않는다. 서버 오류·로그인 만료 시 원본 브라우저 목록을 보존한다.
5. 완료 후 로그인 화면은 서버 조회값을 기준으로 표시한다. 서버 반영 전에는 동기화 중/실패 상태를 분리한다. 첫 버전에서 오프라인 쓰기를 지원하지 않는다면 실패 상태와 명시적 재시도만 제공하고 자동으로 동기화 완료 처리하지 않는다.
6. 계정 캐시·가져오기 완료 기록은 사용자별로 분리한다. 비로그인 저장 목록과 계정에서 내려온 캐시는 별도 보관한다. 현재 공용 `lens-letter-saved` 값을 사용자의 A 계정 캐시로 재사용해 B 계정에 자동 업로드하면 안 된다.
7. 로그아웃·계정 전환 때 진행 중 요청을 취소하거나 이전 계정의 늦은 응답을 무시한다. A 계정 북마크가 B 계정 화면에 보이거나 B 계정에 병합되지 않아야 한다.
8. 다른 기기에서 동일 계정 로그인/새로고침/화면 복귀 시 서버 최신 상태를 조회한다. 첫 버전에 실시간 푸시가 없다면 ‘실시간’이라고 안내하지 않는다. 여러 탭의 저장 상태 갱신도 점검한다.
9. 현재 문자열 배열에는 각 항목의 저장 시각이 없다. 이전 항목의 과거 저장 시각을 지어내지 말고 가져오기 시각 또는 별도 이관 규칙을 사용한다.

## ‘로그인하면 동기화’ 안내를 켜기 전 완료 조건

- [ ] 백엔드 저장/조회/해제/가져오기 API와 마이그레이션·권한을 구현한다.
- [ ] 인증되지 않은 요청 및 다른 계정 데이터 접근·수정을 차단한다.
- [ ] 실제 프론트 저장 훅을 연결하고 서버 성공/실패/동기화 중 상태를 구분한다.
- [ ] 비로그인 저장 후 새로고침, 목록↔상세 이동에서 기존 동작을 유지한다.
- [ ] 브라우저 A의 비로그인 저장을 계정에 가져오고, 브라우저 B의 동일 계정에서 확인한다.
- [ ] 서버 목록이 있는 상태에서 빈 로컬 목록을 병합해도 서버 저장이 사라지지 않는다.
- [ ] 같은 가져오기 재시도와 동시 요청에 중복이 없고, 해제 항목이 과거 가져오기로 되살아나지 않는다.
- [ ] 저장/해제 후 다른 기기에서 다시 조회하면 같은 상태를 확인한다.
- [ ] 로그아웃·A→B 계정 전환·로그인 만료·늦은 응답에서 계정 간 데이터가 섞이지 않는다.
- [ ] 네트워크/서버/localStorage 실패 시 원본 데이터와 실패 안내를 확인한다.
- [ ] 320px~1440px 축소·확대 및 키보드·스크린리더 설명 연결을 확인한다.
- [ ] 실제 연동 결과를 검증한 뒤 준비 중 문구를 상태별 완료 문구로 교체한다.
