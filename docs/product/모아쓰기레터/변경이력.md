## 23. 라네즈 레터 발행, 그리고 사이트가 이전 버전으로 되돌려진 사고 (2026-10-09 밤)
- **문제**: ① 라네즈 레터가 서울경제 원문과 어긋나 있었고(변경 이력 대조표 참조) 근거 기사가 우리 DB에 없어 발행하지 못했다. ② 라네즈를 발행한 직후 서비스 `/letter`가 404였다. 운영 사이트(ECS 개정 90)가 20:15에 다른 곳에서 다시 배포되어, 로컬에서 배포했던 개정 89(레터 탭·헬스 라우트·사이트맵 인덱스 등)가 이전 코드로 덮였다.
- **기존**: 사이트 배포가 개인 로컬 작업 폴더 기준이라, 로컬 커밋 34개가 원격에 없는 상태에서 팀원이 main(PR #51이 19:35에 병합된 시점의 스냅샷)을 기준으로 배포하면 그 이후의 작업이 사라진다. 이 저장소에 이미 기록된 "로컬 체크아웃과 배포가 서로 덮어쓰는 사고"(2026-08-06)와 같은 유형이다.
- **개선**: ① 서버에서 수정 스크립트로 라네즈를 교체·발행했다(기사 4건 보관, 점검 통과, 제 2호). API로 라네즈(제 2호)와 부캉이(제 1호)가 모두 공개 확인됨. ② 사이트를 로컬 기준으로 다시 배포(개정 91, 20:36): `/letter` 200에 두 레터, 라네즈 상세 200, `/api/health` 200, `/sitemap.xml`이 사이트맵 인덱스로 복구됨. 팀원 쪽 변경(PR #52)은 루트 문서 삭제뿐이라 사이트에 영향 없음.
- **근거·영향**: **재발 가능성이 남아 있다.** 로컬 커밋 34개가 아직 원격에 올라가지 않았으므로, 누구든 main을 기준으로 다시 배포하면 레터 탭이 또 사라진다. 해소하려면 로컬 브랜치를 푸시해 PR로 main에 병합해야 한다(푸시·PR은 사용자 승인 필요). 그 전까지는 사이트 배포를 이 폴더에서 한 사람에게 맞추는 것이 안전하다.

## 22. 빅카인즈 출처 전환 운영 반영 + 관련도 정렬 고정 문제 발견 (2026-10-09 밤)
- **문제**: 21번의 코드가 로컬에만 있어 운영 관리자 화면은 여전히 우리 DB 검색이었다. 반영 중 사이트 타임머신(빅카인즈) 검색이 일시적으로 502를 돌려준 뒤, 관련도순 정렬이 꺼져 계속 최신순으로만 나왔고 결과 품질이 눈에 띄게 떨어졌다(같은 검색이 몇 분 전에는 라네즈 핵심 기사를 1~3위로 냈음).
- **기존**: 타임머신 Lambda가 "빅카인즈가 관련도 정렬을 한 번 거부하면 그 사실을 컨테이너가 사라질 때까지 영구히 기억해 최신순만 쓴다". 일시적인 거부(호출 한도·순간 장애)도 몇 시간씩 검색 품질을 떨어뜨린다.
- **개선**: ① 운영 반영(사용자가 v1.40 DDL을 마스터 계정으로 적용 → 서버 배포 → 관리자 Lambda 배포 → API Gateway `GET …/candidates` 삭제·`POST …/archives` 추가 → 관리자 프런트 배포). 확인: 서버 목록·부캉이 상세 정상(기존 출처 4건 유지), 새 라우트 무인증 401, 삭제한 경로는 더 이상 후보 검색으로 가지 않음, 관리자 화면 200. ② 정렬 고정 수정: 거부를 5분만 기억하고 다시 관련도순을 시도하도록 고쳤고 테스트로 확인했다(거부 → 최신순 대체 → 5분 뒤 관련도 복구). **이 수정은 코드만 있고 배포하지 않았다** — `service/backend/deploy.sh`가 구형 Lambda 여러 개를 한 묶음으로 올리는 구조라 범위가 커서 별도 확인 후 진행한다. 그때까지는 컨테이너가 교체되면(수 시간) 저절로 복구되고, 관리자 화면은 최신순으로 대체됐을 때 그 사실을 표시한다.
- **근거·영향**: 사용자 승인("그 설계로 구현"). 남은 일: 부캉이 출처 4건을 빅카인즈 검색으로 후보에 담아 재연결, 라네즈 레터를 핵심 기사(`20099230`, `20099214`)로 재구성. 빅카인즈 호출 한도는 아직 모른다.

## 21. 레터 출처를 빅카인즈 보관 기사로 전환 (2026-10-09 밤, 코드 완료·미배포)
- **문제**: 레터를 발행하려면 서울경제 기사 3개 이상을 근거로 연결해야 하는데, 후보를 찾는 곳이 우리 기사 DB뿐이었다. 이 DB는 2026-02-02부터 19,932건뿐이고, 수집기가 하루 원본 450건 안팎 중 50건만 저장하며 3월이 통째로 비어 있다. 그 결과 라네즈 레터의 핵심 근거 기사(`20099230`)가 DB에 없어 발행하지 못했고, 몇 년 전 기사를 배경으로 걸고 싶어도 찾을 수 없었다.
- **기존**: 후보 검색 = 우리 DB 키워드 검색(최신순, 최근 일부). 출처 = `articles` 참조(또는 승인된 외부 URL). 레터가 `articles`에 의존해 이 테이블을 폐기할 수 없는 구조.
- **개선**: ① 후보 검색을 빅카인즈 하나로 정했다(서울경제만, 1990~, 관련도순, 한 번에 최대 6년 — 사이트 타임머신과 같은 공개 API). ② 편집자가 고른 기사를 `external_archives`에 "후보로 담고"(제목·날짜·원문 링크·미리보기), 클립보드에 `제목 | 주소`로 복사한다. ③ 레터 JSON의 출처는 `url`만 받고(기사 번호·외부 매체 지정 불가), 저장 때 서버가 그 주소를 보관 기사와 대조해 연결한다. 담지 않은 주소는 "후보로 담은 서울경제 기사가 아니다"로 거부 — AI가 지어낸 주소가 저장될 수 없다. ④ 공개 상세·목록의 출처 제목·주소는 항상 보관 기사에서 읽는다. ⑤ DB v1.40(추가만): `external_archives.url_key`, 레터 출처의 보관 기사 참조 칸, 앱 권한. 기존 `articles` 참조는 전환기 한정으로 유지(부캉이), v1.41에서 정리.
- **근거·영향**: 사용자 결정("빅카인즈 하나로, 서울경제 provider는 파라미터로 이미 설정됨"). 검증: 서버 테스트 60개 통과, 실제 Postgres로 보관 → 저장 → 발행 → 공개 상세 전 과정과 거부 경로(담지 않은 주소, 같은 기사 중복) 확인, 관리자 화면은 가짜 API로 검색·선택·담기 확인. 한계: 빅카인즈 장애·호출 한도(미확인)에 의존, 서버는 빅카인즈를 직접 호출하지 않고 관리자가 보낸 검색 결과를 신뢰, 과거 기사의 원문 링크는 `NewsView/<ID>` 형식(최근은 `article/<번호>`)이라 주소에서 번호를 뽑는 코드가 두 형식을 처리해야 함(도메인은 모두 서울경제 — 처음에 "이데일리 주소"라 한 것은 출력을 잘라 보고 오독한 것으로 정정). 운영 반영 순서: ① v1.40 DDL(사용자) → ② 서버 배포 → ③ 관리자 Lambda 배포 + API Gateway 라우트 교체(`GET …/candidates` 삭제, `POST …/archives` 추가) → ④ 관리자 프런트 배포 → ⑤ 부캉이 출처 4건·라네즈 재구성.

## 20. 라네즈 레터 제목을 열린 질문으로 (2026-10-09 밤)
- **문제**: 제목 "라네즈가 필리핀에서 문을 닫았는데, 이게 오히려 전략이라고요?"가 "전략"이라는 해석을 정답처럼 단정하고, 질문 형식으로 독자를 그 해석으로 유도했다. 전 레터 중립 원칙(해석은 출처 있는 인용으로만)과 맞지 않는 문구였다.
- **기존**: 원본 샘플 제목을 그대로 사용(운영 DB 초안과 시드 파일 모두).
- **개선**: "같은 달 인도에서는 사업부를 새로 만들고, 필리핀에서는 라네즈 직영몰을 닫았어요. 무슨 일이 있었나요?" — 기사에 나온 사실(인도 프리미엄 사업부 신설, 필리핀 공식 온라인몰 운영 중단)만 담고 해석을 빼며 열린 질문으로 마무리. 시드 파일은 수정 완료(저장 검증 통과). 운영 DB의 초안은 관리자 화면에서 "JSON 수정"으로 바꾼다(이 레터는 아직 초안이라 사이트에 노출되지 않음).
- **근거·영향**: 사용자 결정. 템플릿 v2의 "나쁜 예"에 이 제목 유형이 이미 들어 있다.

## 19. 운영 반영 — 레터 탭 정식 연결 (2026-10-09 밤)
- **문제**: 서버·관리자·사이트 코드가 로컬에만 있어서 편집자가 레터를 입력할 수 없었고, 운영 사이트의 `/letter`는 여전히 코드에 박힌 목업 화면이었다.
- **기존**: 운영 `/letter`는 목업 5편(예시 데이터), 관리자에 이슈 레터 메뉴 없음, 서버는 이전 규칙(외부 출처 허용 설계, 후보 검색 라우트 없음).
- **개선**: 5단계를 순서대로 반영했다. ① 서버 `lens-cms-api` 재배포(헬스 200, 테스트 50개 통과 후) ② 관리자 Lambda 배포 ③ API Gateway(`chzwwtjtgk`)에 `/admin/issue-letters*` 라우트 8개 생성(기존 관리자 라우트와 같은 연결·인증 없음 설정, 토큰 검사는 Lambda 안에서) ④ 관리자 프런트 배포(`lensdb.sedaily.ai`) ⑤ 사이트 프런트 배포(ECS 개정 89). 확인: 새 관리자 경로 4개는 로그인 없이 호출하면 401(Lambda까지 연결 확인), 없는 경로는 404; 관리자 `/issue-letters`·`/issue-letters/edit` 200; 사이트 `/letter` 200에 부캉이(호수 1)가 실제 데이터로 나오고 `noindex` 유지, 부캉이 상세 200, 초안인 라네즈 상세 404, 홈·사이트맵 200.
- **근거·영향**: 사용자 승인("5개 모두 진행"). 사이트 `/letter`는 지금 발행된 부캉이 1편만 보인다(검색엔진에는 아직 `noindex`). 관리자 화면에서의 실제 입력·발행은 로그인이 필요해 편집자가 직접 확인한다. 투표는 화면에서의 첫 투표를 아직 해보지 않았다(운영 집계에 남기 때문).

## 18. 출처 후보 기사 키워드 검색 칸 + 서버리스 방침 정리 (2026-10-09 밤, 미배포)
- **문제**: 출처 주소를 누가 어떻게 찾는지가 불명확했다. 서버에 후보 검색 기능이 있었지만 관리자 화면에는 없어서, 편집자가 서울경제 기사를 찾으려면 AI에게 맡기거나 사이트에서 직접 뒤져야 했고, AI가 목록에 없는 기사를 만들어 낼 여지도 있었다.
- **기존**: 키워드 검색은 서버 API만 존재. 관리자 라우트와 화면 없음. 템플릿 v2의 "후보 기사 목록" 입력은 있었지만 만들 도구가 없었다.
- **개선**: 관리자 백엔드에 `GET /admin/issue-letters/candidates`(8번째 라우트), 새 레터 화면 맨 위에 "출처 후보 기사 검색" 칸을 추가했다. 단어로 검색하면 서울경제 기사 DB에서 제목·본문에 단어가 들어간 최신 기사(제목·날짜·주소)가 나오고, 고른 기사를 `제목 | 주소` 줄로 복사해 템플릿의 후보 기사 목록에 붙여 넣는다. 단순 키워드 일치이며 AI·유사도 검색은 쓰지 않는다(의미 검색용 벡터는 DB에 준비돼 있으나 사용 안 함).
- **근거·영향**: 사용자 지시("심플한 방향, 키워드 검색 칸 추가"). 기사 선정은 사람이, 레터와의 연결(기사 번호)은 서버가 저장 때 주소로 찾아서 한다. 서버리스 정리: 관리자 CMS 백엔드는 아직 Lambda + API Gateway(라우트 약 90개)이고 공개 API(`lens-cms-api`)와 기사 수집만 일부 EC2/Lambda로 나뉘어 있다. 레터 관리자 라우트는 기존 관리자 구조에 맞춰 같은 방식으로 붙이기로 했다(옵션 A) — 서버리스를 늘리는 일이지만, 관리자 전체를 EC2로 옮길 때(계획서 5b) 레터는 서버 코드가 이미 EC2에 있어 거의 그대로 옮겨진다. 옵션 B(레터 관리자 API만 EC2 직결)는 관리자 백엔드가 두 군데로 갈라져 채택하지 않았다.

## 17. 관리자 입력 화면 — 템플릿 JSON 붙여넣기 → 초안 → 검수 → 발행 (2026-10-09 밤, 미배포) + 출처는 서울경제 원문만
- **문제**: 레터를 만들려면 서버 안에서 스크립트를 돌려야 했다(임시 방편). 편집자가 쓸 수 있는 정식 입력 경로가 없었다. 또 템플릿이 만드는 JSON은 출처가 기사 주소(URL)뿐인데 서버는 기사 번호를 요구해서 그대로 넣을 수 없었다. 출처로 외부 매체도 허용하는 설계였는데 사용자 결정은 "서울경제 원문 기사만 인정"이었다.
- **기존**: 입력은 샘플 입력 스크립트뿐. 출처는 `article_no` 또는 승인된 외부 URL 중 하나. 관리자 화면 없음.
- **개선**: ① 서버: 출처를 `url`(서울경제 기사 주소)로 지정하면 기사 DB에서 번호를 찾아 연결하고(꼬리표 `?ref=` 무시), 찾지 못하면 "서울경제 기사 DB에 없다"고 거부한다. 외부 매체 출처는 모두 거부한다(DB 컬럼은 남겨 둠). ② 관리자 백엔드: `/admin/issue-letters*` 라우트 7개(후속 18번에서 후보 검색이 추가되어 8개)가 서버 API를 호출하며, 서버의 거부 사유 문장(입력 오류 400, 상태 충돌 409, 발행 규칙 422)을 그대로 화면에 전달한다. 감사 로그를 남긴다. ③ 관리자 화면 `/issue-letters`(상태 필터 목록), `/issue-letters/edit`(새 레터: JSON 붙여넣기 → 초안 저장 / 기존 레터: 발행 전 점검 목록, 검수 요청·발행·내리기, JSON 수정, 본문·출처·투표 미리보기). 발행 규칙을 통과하지 못하면 발행 버튼이 비활성이다.
- **근거·영향**: 사용자 결정("서울경제 원문 기사만 인정하고 B 진행"). 검증: 서버는 실제 Postgres로 URL 입력·외부 거부·전 과정 통과(테스트 50개), 관리자 백엔드는 응답 전달·오류 매핑·감사 로그를 스텁으로 확인, 관리자 화면은 가짜 API로 목록·검수 화면을 직접 확인(tsc·eslint·정적 빌드 통과). 아직 배포하지 않았다 — 배포에는 서버 재배포, 관리자 Lambda 배포, API Gateway 라우트 7개 생성, 관리자 프런트 배포가 필요하다. 한계: 관리자가 공유 계정이라 사람 단위 승인은 불가(v1.39).

## 16. 프론트를 목업에서 실제 API로 교체 (2026-10-09 밤, 미배포)
- **문제**: 화면이 코드에 박힌 목업 데이터를 그리고 있어서, 서버에 발행된 레터가 화면에 나오지 않았다. 투표는 이 기기에만 저장되는 가짜 집계였다.
- **기존**: `/letter`와 `/letter/{slug}`가 `mockLetters.ts`(5편)를 읽고, 투표 집계는 슬러그에서 만든 고정값 + 내 1표(localStorage), 상세 경로는 목업 슬러그만 열림(`dynamicParams=false`).
- **개선**: 두 페이지가 서버(`/api/v2/issue-letters`)에서 발행된 레터를 60초 단위로 읽는다(ISR). API 응답을 기존 화면 타입으로 바꾸는 계층(`letterApi.ts`)을 추가해 화면 컴포넌트는 거의 그대로 썼다. 자사 기사는 매체명을 "서울경제"로 표기, 시각은 한국 날짜로 변환. 투표는 이 기기의 익명 식별자(UUID)를 서버로 보내 레터당 한 표를 저장하고, 투표한 사람에게만 실제 집계를 보여 준다(이미 투표했으면 기존 선택·집계 표시, 저장 실패 시 안내 문구). 목업 데이터 파일은 삭제(샘플 내용은 시드 JSON에 보존).
- **근거·영향**: 검증은 운영 데이터를 읽는 로컬 화면으로 했다 — 부캉이 목록·상세 정상, 초안(라네즈)은 404, 한마디·투표·출처·인라인 링크 표시, 하이드레이션 오류 0, tsc·eslint·vitest 59개·빌드 통과. 운영 DB에 시험 투표는 넣지 않았다(삭제 수단이 없어 실제 집계에 남기 때문). 투표 저장 동작은 서버 쪽을 로컬 DB로 검증했고, 화면에서의 첫 투표는 배포 후 확인한다. 아직 `noindex`이며 푸시·배포는 하지 않았다.

## 15. 샘플 3편을 운영 DB에 입력 (2026-10-09 저녁)
- **문제**: 서버 API가 배포됐지만 DB가 비어 있어 화면으로 확인할 레터가 없었다. 샘플을 넣으려면 기사 DB와 연결해야 했고, 내용은 목업 코드에만 있었다.
- **기존**: 목록 API가 빈 배열. 샘플 3편은 프론트 코드(`mockLetters.ts`)에만 존재.
- **개선**: 입력 스크립트가 서울경제 기사 DB에서 제목으로 기사를 찾아 `article_no`로 연결해 관리 API로 저장하고, 서버의 발행 규칙을 통과한 레터만 발행했다. 결과: 부캉이 발행(호수 1, 출처 4건, 본문 링크 3개), 라네즈·종로3가는 규칙에 걸려 초안으로 남음(라네즈: 출처가 AI LENS 기사 페이지라 기사 DB에 없어 0건, 본문 링크 불일치 2건 / 종로3가: 자사 기사 링크 1개로 3개 미만). 외부 확인: 목록·상세 정상, 초안은 공개 상세 404.
- **근거·영향**: 규칙이 의도대로 걸러냈다는 증거이기도 하다(원본 샘플이 기사 연결 기준에 못 미침). 해소하려면 서울경제 기사로 근거를 더 찾거나 AI LENS 기사 페이지를 출처 종류로 인정하는 결정(v1.40 후보)이 필요하다.

## 14. 편집자 FK 제거 — 관리자에 개인 식별이 없다는 사실 반영 (v1.39)
- **문제**: 샘플을 발행하려고 편집장 사번을 조회했더니 `editors` 테이블이 비어 있었다. 확인해 보니 관리자 서비스는 개인 계정 없이 공유 비밀번호 하나로 로그인하고(토큰 사용자는 항상 `admin`), `editors`는 어디에서도 쓰이지 않았다. 내가 `author_no`·`reviewer_no`·`approved_by`를 `editors` FK로 걸어 두어, 어떤 승인자 값을 넣어도 발행이 제약 위반으로 막혔다. 설계 단계에서 "편집자 테이블이 실제로 쓰이는가"를 확인하지 않은 내 오류다.
- **기존**: 작성→검수→발행을 "편집장(admin 역할)만 승인, 작성자 본인 승인 불가"로 설계(Q7). 승인자 칸은 `editors` FK.
- **개선**: v1.39에서 세 FK를 제거하고 칸을 문자열 식별자로 정의했다(지금은 `admin`). 사람 단위 규칙("본인 승인 불가")은 코드에 남겨 두어 개인 로그인이 생기면 같은 칸에 개인 식별자를 넣는 것만으로 작동한다. 지금도 작성 → 검수 요청 → 발행의 단계는 상태로 강제된다.
- **근거·영향**: 현실에 맞춘 정정(사용자 방향: 처음 기획을 고수하지 않고 fit을 맞춘다). 한계: 공유 계정 구조에서는 누가 승인했는지 사람 단위로는 남지 않는다. 개인 로그인 도입은 별도 과제. 이 한계는 Q7 결정 기록에도 반영한다.

## 13. 샘플 입력용 파일을 서버 배포 묶음에 포함 (+ 배포 권한 사고 수정)
- **문제**: 샘플 입력에 필요한 파일(시드 JSON, 입력 스크립트, v1.38 DDL)을 서버로 옮기려고 사용자가 S3에 따로 올려야 했다. 콘텐츠의 최종 저장소는 RDB인데 임시 이동 절차가 번거로웠다.
- **기존**: 사용자가 로컬에서 S3로 올리고, 서버에서 다시 받는 두 단계. 배포 묶음에는 코드(`*.py`)만 있었다.
- **개선**: 배포 스크립트가 스크립트·시드·DDL을 같은 묶음에 넣어 서버 `/opt/lens-cms-api/{scripts,seed}/`에 놓는다. 콘텐츠는 서버에 남지 않고 스크립트가 관리 API로 RDB에 저장한다. 이 과정에서 임시 폴더 권한(700)이 서버의 `/opt/lens-cms-api` 폴더 권한을 덮어써 접속 계정이 들어가지 못하는 문제가 생겼고(서비스 영향 없음, root로 동작), 서버에서 `chmod 755`로 복구하고 배포 스크립트에 `chmod 755` 한 줄을 추가해 재발을 막았다.
- **근거·영향**: 사용자 질문("레터 콘텐츠도 RDB에 쌓는데 S3가 아니라 RDB로 옮기는 게 맞지 않나") — 이동 통로만 단순화하고 저장은 RDB라는 원칙 확인. 정식 경로는 관리자 JSON 입력 화면(다음 단계)이며 이 스크립트는 그때 폐기한다.

## 12. 레터 생성 프롬프트 템플릿 v1 → v2
- **문제**: 템플릿이 중립 원칙 이전 기준이라, AI가 원칙에 어긋나는 레터를 처음부터 만들 수 있었다. 외부 웹 검색으로 외부 매체를 인용하게 했고, 투표에 찬반형을 허용했고, 문체가 "반말체"로 적혀 있어 실제 샘플(해요체)과 달랐다.
- **기존**: 설계 원칙 3가지(지어내기 금지·인라인 링크·3축). 에디터 한마디는 "관찰 1~2문장", 투표는 "금융은 감정형, 일반 소재는 찬반 2지선다 가능". 조사는 웹 검색. 출력은 HTML 위젯 하나. 체크리스트 8개.
- **개선**: 원칙 4가지로 확장(중립·무편향 신설). 프롬프트 맨 앞에 "최우선 원칙: 중립"과 금지 표현 목록을 넣었다. 조사는 서울경제 기사 안에서만, 후보 기사 목록이 주어지면 그 안에서만 고르게 했다. 다른 시각 섹션은 AI의 비판이 아니라 출처 있는 다른 해석으로, 제목은 해석을 단정하지 않게, 한마디는 사실 연결 정리로, 투표는 감정 반응형 + "잘 모르겠어요" 필수로 바꿨다. 출력은 서버 입력과 같은 저장용 JSON이 1순위, 미리보기 HTML은 선택. 문체는 해요체. 체크리스트 11개, 자주 나오는 문제 5가지.
- **근거·영향**: 사용자 지시("논란이 터지면 안 된다"). 템플릿과 서버 검사가 같은 기준이라 템플릿으로 만든 레터는 서버 발행 검사를 그대로 통과한다. v1은 원안으로 보존. 파일 `마스터DB/06_콘텐츠/레터/ailens_레터생성_프롬프트템플릿_v2_261009.html`.

## 11. 에디터 한마디 — 의견에서 사실 연결 정리로
- **문제**: 한마디가 의견 성격이라 전 레터 중립 원칙과 충돌했다. 샘플에 "재밌는 건…", "아이러니예요", "탁월하지만" 같은 평가·감탄이 있었고, 라네즈 샘플은 "브랜드가 밀려서가 아니에요"처럼 본문에 없는 원인을 단정했다.
- **기존**: 기획 원안은 "이슈 맥락을 한 발 더 짚는 관찰 1~2문장"이었고 금지는 자기반영 고백뿐이었다.
- **개선**: 코너를 없애지 않고 역할을 재정의했다. 본문에 이미 나온 사실만 엮는 2문장·200자 이내 칸으로 바꾸고, 평가어·감탄·새 주장·예측 단정·판단 요구를 금지했다. 샘플 4편을 다시 썼고, 서버가 금지 표현과 길이를 발행 때 검사한다. 기준 문서는 `에디터한마디_작성기준.md`.
- **근거·영향**: 사용자 방향("원칙에 맞게 fit을 찾는다, 좋은 기획이면 틀지 말고 전달 방법을 고민"). 새 문장은 모두 본문 사실만 썼지만 AI가 쓴 샘플이라 작성자 확인이 필요하다.

## 10. 투표 — 전 레터 감정 반응형만
- **문제**: 금융 분류에만 걸던 제한으로는 부족했다. 샘플 투표 중 "지금 보내는 게 맞을까요?"(결정 요구), "합리적인 선택"(평가), "지켜봐야 한다"(행동 방향 시사), 선택지 부가 설명("가볼 이유가 생겼어요")이 유도 소지가 있었다.
- **기존**: 투표 종류 두 가지(이분형·감정형), 금융 분류만 감정형 강제. 중립 선택지 없음.
- **개선**: 모든 레터에서 감정 반응형만 허용(이분형 폐지). 질문·선택지의 평가·권유·결정 표현을 서버가 저장·발행 때 거부. 모든 투표에 "잘 모르겠어요"(`unsure`) 필수, 선택지 부가 설명 제거. 샘플 5개를 모두 고쳤다.
- **근거·영향**: 사용자 지시("주관·유도·권유·결정 뉘앙스 금지, 편향 없는 질문"). 문구 목록 방식이라 우회 표현은 놓칠 수 있어 편집장 검수가 최종 방어선이다. 다중 분류는 이미 지원하며 부캉이를 시그널·사회·경제로 넓혔다.

## 9. DB 분류 설계 오류 정정 (v1.37 → v1.38)
- **문제**: v1.37이 레터 분류를 `categories` 테이블(옛 7분류)에 FK로 걸었는데, 사이트가 쓰는 9분류(시그널·사회 등)와 달라 '사회'·'시그널'을 저장할 수 없었다. 샘플 입력을 준비하며 발견했다.
- **기존**: `issue_letter_categories(letter_id, category_id → categories.id)`.
- **개선**: v1.38에서 `category_slug`(문자열)로 교체하고, 허용 목록은 앱이 검증한다(분류의 정본은 사이트 코드). 테이블이 비어 있을 때만 적용되고 데이터가 있으면 중단된다. 로컬 Postgres에서 v1.37→v1.38 적용·재적용·중단 동작을 확인했다.
- **근거·영향**: 데이터 입력 전에 발견해 이관 비용이 없었다. 운영 DB 적용은 대기 중.

## 8. 운영 배포 — 이슈 레터 API
- **문제**: 설계만 있고 서버·네트워크 경로가 없어 프론트가 연결할 수 없었다.

- **근거·영향**: 상세는 `db-changelog/postgres/v1.37-이슈레터-신설.md`. 인스턴스 메모리 사용률 92%대라 데이터가 늘기 전 확인 필요.

## 7. lens-cms-api 이슈 레터 저장소·라우트
