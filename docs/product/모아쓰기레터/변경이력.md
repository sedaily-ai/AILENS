## 38. 자동 발행 Sonnet 전환·문서 분량 기준·투표 카드 디자인 (2026-10-11, 로컬 커밋·이미지 반영, 사이트 미배포)
- **문제**: 자동 발행이 Opus로 돌아 비용이 크고, 템플릿 v2의 분량 규칙(본문 2,500~3,500자)이 코드로 강제되지 않았다. 삼성전자 실적처럼 증권사 전망 인용이 많은 묶음이 매번 1순위로 뽑혀 권유 표현 검사에 3회 연속 걸리며 비용만 쓰였다. 투표 보기는 단순 목록이라 홍예린 님 시안 같은 시각 효과가 없었다.
- **기존**: 모델 lens-letters-opus-5, 분량 검사 없음, 한 묶음에서 3회 시도 후 중단, 투표는 보기 목록.
- **개선**: ① 모델을 lens-letters-sonnet-46(같은 letters 비용 태그 체계)으로 교체하고 작업 역할 IAM에 해당 프로파일을 추가. ② 본문 2,500~3,500자 검사를 초안 단계에 추가(미달·초과 사유를 모델에 돌려 재생성). ③ 묶음 본문의 투자 권유 표현 수가 적은 묶음부터 시도하고, 한 묶음에서 2회 실패하면 다음 묶음으로(최대 2묶음×2회로 비용 상한 고정). ④ 투표 보기를 카드형으로 각색: 보기별 색 점(파랑, 우려류 앰버, 모름 회색), 투표 후 퍼센트와 얇은 막대, "내 선택" 표시. 이모지·그라데이션 없이 사이트 톤 유지, 데이터 구조 변경 없음.
- **근거·영향**: 드라이런(Sonnet, 태스크 정의 rev 5): 묶음 2개 선정, 삼성전자 대신 금융권 보안 묶음이 선택되어 1회 시도에 초안 저장. 결과물 본문 2,553자, 3축 모두 존재, 요약 3줄, 한마디 2문장, 투표 보기 4개, 서버 발행 규칙 위반 0건. 테스트 22개 통과. 미확인: 사실 대조 누락률, 같은 방식의 반복 통과율, 투표 카드의 실제 화면. 위험: 권유 표현이 적은 묶음을 우선하면 시장·증시 소재가 계속 밀려 소재 편향이 생길 수 있다. 며칠 관찰 후 판단한다.
- **초안 id 34, 35**: 드라이런이 저장한 초안으로 발행 상태가 아니며 노출되지 않는다. 정리는 DB 직접 삭제가 필요해 보류.

## 37. 기획서 대조 점검 후 발행 검증 보강과 "핵심:" 라벨 (2026-10-11, 로컬 커밋, 미배포)
- **문제**: 기획서 8건 대조 결과, 템플릿 v2의 필수 규칙 일부가 코드로 강제되지 않았다. 사이트 섹션 상단에 "핵심:" 라벨이 없었고(메일에는 있음), 서버 발행 검증이 3축 존재·평가어·한마디 문장 수·투표 보기 수·요약 줄 수를 보지 않았다. 자동 발행은 편집장 검수 없이 나가므로 코드 강제가 필요하다.
- **기존**: 발행 검증은 섹션 3개 이상, 인라인 링크 3개 이상, 투표 중립, 한마디 200자·금지어, 권유·지시어만 확인.
- **개선**: ① 사이트 섹션에 "핵심:" 라벨 표시. ② 발행 검증 추가: 3축(소식·실체·다른 시각) 모두 존재, 1분 요약 2~3줄, 에디터 한마디 2문장 이내, 투표 선택지 3~4개, 제목·부제·요약·섹션 제목·핵심 한 줄의 평가·감탄 표현 차단(아이러니, 놀라운, 흥미로운, 충격, 느낌표 등), 본문은 인용문 오차단을 피하려고 분명한 평가 부사(놀랍게도, 흥미롭게도, 안타깝게도, 다행히, 아이러니)만 차단. 저장(초안) 단계 규칙은 그대로 두고 발행 때만 적용.
- **근거·영향**: 테스트 110개 통과(신규 2개), 프론트 `tsc` 통과. 운영 배포 전. 이미 발행된 3편은 영향 없음(발행 시점 검사). 운영 3편은 3축, 요약 3줄, 투표 보기 3개로 새 규칙을 충족하는 것으로 확인.
- **기록으로 남기는 미결·불일치**: ① 본문 분량이 문서 기준(2,500~3,500자) 대비 운영 3편 889~1,088자. 기준을 지킬지 새 기준으로 삼을지 결정 대기, 검증 미적용. ② 서버 저장 단계의 한마디 상한 1000자, 요약 상한 6줄은 초안 편의를 위한 완화이며 발행 때 조인다. ③ 자동 발행 재생성은 설계서 2회, 구현 3회(구현이 기준, 설계서 갱신 필요). ④ 부캉이 레터는 샘플 대비 타임라인·양측 카드·접기 박스가 빠졌고 변경 기록이 없음, 복원 여부 결정 대기. ⑤ 라네즈 수치 시각 카드가 본문 텍스트로 바뀐 이유 기록 없음. ⑥ 기사 상세에서 레터로 가는 역연결, 성공지표 측정 판정, 에디터 4명 이미지·음성·MBTI는 남은 일.

## 36. 모아쓰기 레터 자동 발행 파이프라인 (2026-10-11, 인프라 생성·코드 완료, 서버 연동·가동은 배포 후)
- **문제**: 모아쓰기 레터는 기사 선정(빅카인즈 검색), 본문 생성(외부 AI에 프롬프트 복사), 저장·검수·발행을 사람이 이어 가는 반자동이라 하루 한 편 발행이 담당자 시간에 묶여 있다. 레터가 3편뿐이라 에디터·구독 구조가 제 효과를 내지 못한다.
- **기존**: 1기사형 레터(지면 1면·필수뉴스)는 `pipelines/`의 EventBridge+Fargate가 매일 자동 발행하나 모아쓰기는 그 경로에 없다.
- **개선**: `pipelines/issueletter_auto/` 신설. ① 최근 3일 서울경제 기사(344건)에서 모델이 같은 사안을 묶고, 코드가 걸러냄(없는 기사 번호, 3건 미만, 이미 쓴 기사와 겹침, 정치·젠더·세대·지역 갈등 소재 제외). ② 기존 비용 태그 프로파일(lens-letters-opus-5)로 템플릿 v2 기반 초안 생성. ③ 서버에 저장하기 전에 검증: 묶음 밖 링크 차단, 기사에 없는 수치 차단, 투자·행동 권유 표현 차단(귀속된 인용 포함, 순매도 같은 시장 보도어는 허용), 별도 모델 호출의 사실 대조(고유명사·직함·인용·인과), "핵심:" 접두어 중복 제거. 실패하면 사유를 모델에 돌려 최대 3회 재생성, 모두 실패하면 중단. ④ 담당 분야가 겹치는 에디터 1~2명 자동 지정(겹침 없으면 보류). ⑤ 서버 규칙을 통과하면 검수 요청 → 발행(서버가 구독한 에디터의 구독자에게 발송). 안전장치: ISSUELETTER_AUTO=1일 때만 발행(기본 0은 초안 저장까지), 하루 1편 상한, 발행 시각 창 KST 06~18시. AWS: IAM 역할 2개, 로그그룹, 태스크 정의, EventBridge 규칙(DISABLED, 매일 08시), 이미지 전용 태그 issueletter-1(실가동 중인 기존 파이프라인의 latest와 분리). 모든 리소스에 비용 태그.
- **근거·영향**: 사용자 지시("완전 자동화가 목표"). 검증: 테스트 20개(순수 검증 7, 흐름 13), 실제 기사·실제 모델 드라이런 — 5개 묶음 중 4개 통과, 삼성전자 실적 이슈 선정, 1~2회는 투자 권유 인용("분할 매수로 대응해야")을 잡아 거부, 3회째 모든 관문 통과, 작성 에디터 준서·지훈 지정, 3축·귀속 인용·감정형 투표 확인. 미확인: Fargate 실제 실행(서버 에디터 API 배포 전), 서버 저장·발행·발송 연동, 호출 비용, 사실 대조의 누락률. 위험: 사실 대조는 모델 판단이라 완벽하지 않아 가동 초기에는 드라이런을 며칠 관찰하고 발행 후 점검이 필요하다. 설계: `자동발행_설계.md`.

## 35. 에디터 DB·구독한 에디터 기준 발송·레터 생성 프롬프트 자동 조립 (2026-10-11, 로컬 완료, DDL v1.45는 사용자 실행 대기)
- **문제**: 에디터가 프론트 상수라 레터와는 주제 겹침으로만 연결되고, 구독은 주제 목록을 저장해 "구독한 에디터가 쓴 글이 올라오면 보낸다"를 정확히 구현할 수 없었다. 임의로 둔 하루 1통·시각 선택 제한이 "올라올 때마다 받는다"는 요구와 충돌했다. 레터 생성 프롬프트는 사람이 주제·기사·에디터를 손으로 채워 복사했다.
- **기존**: 에디터 소개·담당 분야는 코드 안, 구독은 주제 기준, 발송은 수동 실행(시각·하루 1통 제한).
- **개선**: ① DB v1.45: 에디터(letter_editors, 담당 분야 포함), 레터↔작성 에디터, 구독↔구독한 에디터. ② 서버: 에디터 사전 저장·공개 목록(내부 id 제외), 레터 JSON의 editors 필드, 구독 신청이 에디터 저장(에디터나 주제 중 하나는 필수), 발행 직후 그 레터를 쓴 에디터를 구독한 활성 구독자에게 한 통씩 자동 발송(중복 방지, 수신 제외, 야간 보류, LETTER_AUTO_SEND 스위치). 하루 1통·시각 선택·"받는 방식" 제한 삭제. ③ 관리자: 후보 기사를 담으면 주제·기사·에디터 목록이 채워진 프롬프트 전체를 복사, 레터 상세에 작성 에디터 표시(없으면 경고), JSON 수정에 editors 포함. ④ 레터 상세와 목록은 서버가 지정한 에디터를 우선 표시.
- **근거·영향**: 사용자 지시. 검증: 서버 테스트 108개, 실제 Postgres로 에디터 저장·지정·구독·발송 시나리오(겹치는 구독자만, 재실행 중복 없음, 같은 날 두 번째 레터도 발송, 야간 보류) 확인. 배포 순서: ① v1.45 DDL(마스터 계정) ② 서버 배포 ③ 에디터 시드(`seed_topics.py editors`) ④ 레터 에디터 지정(`assign`, 드라이런 먼저) ⑤ 관리자·사이트 배포 ⑥ LETTER_AUTO_SEND 결정. 기존 테스트 구독자는 구독한 에디터가 없어 새로 신청해야 한다.

## 34. 상세 읽기 도구·링크 미리보기·용어 설명·저장·관련 레터·모바일 최적화 (프론트, 2026-10-11, 로컬 완료·미배포)
- **문제**: 독자가 긴 레터를 읽을 때 위치·글자 크기·공유·출처 확인·어려운 용어 설명·저장 같은 기본 기능이 없었고, 모바일은 소개 카드와 안내가 목록 위에 쌓여 레터가 화면 아래로 밀렸다.
- **개선**: 읽기 진행 막대, 섹션 목차(넓은 화면), 글자 크기(4단계, 기억), 링크 복사 공유, 본문 링크에 마우스를 올리면 기사 제목·매체 카드, 용어 해설(기존 1기사형 레터와 같은 형광펜 마커·카드 컴포넌트 재사용, 레터 한 편에서 처음 한 번만), 나중에 읽기 저장과 읽은 표시(브라우저 저장, 70% 이상 읽으면 읽음), 같은 주제의 관련 레터, 작성 시각(시·분), 에디터 알약(프로필+이름), 모바일에서 레터 목록을 먼저·구독은 아래에서 올라오는 시트. 팔로우는 로그인 필요, 로그인 후 원래 화면으로 복귀(같은 사이트 경로만 허용). 헤더 레터 메뉴에 편지→우체통 애니메이션 아이콘(모션 줄이기 설정 존중).
- **근거·영향**: 사용자 지시. 알려진 한계: 용어 사전은 12개 목업, 저장·읽음은 브라우저 기록, 터치 기기 동작은 미확인.

## 33. 구독 대화상자 개편 — 이렇게 와요 미리보기·테스트 메일·받는 시각 삭제 (2026-10-11, 서버 배포 완료, 화면 미배포)
- **문제**: 구독 신청 폼이 길고 선택지가 많았으며, 메일이 실제로 어떤 모양으로 오는지·정말 오는지 확인할 방법이 없었다.
- **개선**: 이메일 하나가 핵심인 중앙 대화상자(모바일은 아래에서 올라오는 시트), 약속 3줄, 동의 미체크, "이렇게 와요" 메일 미리보기(서버가 만든 실제 메일 본문), "테스트로 한 통 먼저 받아보기"(주소당 10분 1회·하루 3회, 구독과 별개, 수신거부 링크 없음), 받는 시각·받는 방식 선택 삭제(새 레터가 올라오면 바로), 신청 후 3단계 안내와 선택형 온보딩(상황·필요한 것 → 맞는 에디터 추천). 사용자 행동 정의: `구독_UX_행동정의.md`.
- **근거·영향**: 서버(미리보기·테스트 메일 엔드포인트)는 운영 배포, 테스트 메일 실제 수신 확인. 화면은 배포 전.

## 31. 레터 화면 다듬기 — 에디터 8명, 초상형 선택줄, 소개 카드, 구독 대화상자, 파랑 톤 통일, 헤더 더보기 삭제 (프론트 목업, 2026-10-11, 로컬 완료·미배포)

## 30. 에디터 중심 레터 탭 — 에디터 선택줄(카테고리처럼), 자기소개, 그 에디터의 레터 목록 (프론트 목업, 2026-10-10, 로컬 완료·미배포)
- **문제**: 분류 칩(시그널·경제·산업…)은 1차원적이라 "누구의 관심 영역인지"가 없다. 기획서의 독자 페르소나 8개와 이전 에디터 탭(카드 → 자기소개 → 쓴 글 → 구독)의 흐름이 레터에 반영되지 않았고, 1차 목업의 에디터 5명도 분류에 이름만 씌운 것이었다.
- **기존**: 분류 칩 + 관심 묶음·분야·주제 선택 바, 에디터 개념 없음.
- **개선**: ① 목록 상단을 카테고리처럼 쓰는 에디터 선택줄(전체 + 8명, 아바타·이름·역할)로 교체. ② 에디터를 고르면 아래에 자기소개(이미지, 역할·대상, 소개 문구, 세부 분야, 소개 듣기, 팔로우, 메일 구독)가 나오고 그 아래에 그 에디터의 세부 분야와 겹치는 레터 목록이 나옴(주소 `?editor=` 또는 `/letter/editors/{id}`로 직접 진입 가능). ③ 에디터는 이전 서비스(MBTI 에디터)의 12명을 이름·MBTI 그룹·담당 분야 그대로 이어 씀(출처 legacy/dev_v1/.../editorsData.ts): NT 민철·지훈·서연, NF 하은·수빈·예린, ST 준서·도윤·시우, SF 소율·유나·다은. 이미지가 있는 4명(민철 INTJ·하은 INFP·준서 ISTJ·소율 ESFP, public/editors)을 앞에 두고 나머지 8명은 이니셜 아바타(이미지 생성 전). 담당 분야는 옛 signature를 주제 사전 slug로 옮겼고, 자기소개는 옛 소개 문구(대표 4명)와 옛 bio를 사용. 소개 음성은 옛 기록의 voiceId·설정(ElevenLabs eleven_multilingual_v2: 민철 TeddyNote, 하은 JiYoung, 준서 Deck, 소율 Hana Lee)으로 대표 4명분 mp3를 미리 생성해 정적 파일로 배포(service/frontend/scripts/generate_editor_voices.py, 키는 Secrets Manager ai-labs/elevenlabs에서 읽고 출력하지 않음, 결과 public/editors/voice/*.mp3, 길이 6~12초). 소개 듣기 버튼은 음성 파일이 있는 에디터에만 표시. 소개 머리에 AI 에디터와 MBTI(대표 4명) 또는 그룹(NT 등)을 표시. ④ 한 레터는 주제가 겹치는 여러 에디터에 속함. ⑤ 팔로우(복수, 브라우저 저장)한 에디터의 세부 분야 합집합을 기존 관심 API로 보내 "전체" 목록에서 겹치는 레터에 이유를 표시, "내 에디터" 한 줄 바(겹치는 레터만 N, 메일로 받기). ⑥ 에디터는 말투·입장이 아니라 관심 영역만 다르며 중립 원칙 동일(화면에 명시), 모두 "AI 에디터" 표시.
- **근거·영향**: 사용자 지시(카테고리처럼 페르소나를 고르면 자기소개와 그 에디터의 글 목록, 이전 에디터 이미지 재사용, 이름 지정). 검증: tsc·eslint·vitest 통과, 데스크톱·모바일 스크린샷(`docs/worklog/2026-10/2026-10-09-레터탭-목업/editors/ed3_*`), 선택·팔로우·주소 진입 확인. 한계: 에디터 정의는 프론트 상수, 팔로우는 브라우저 저장, 소개 음성은 대표 4명만 있고 나머지 8명은 이미지·음성 생성 전(옛 구조는 브라우저에서 ElevenLabs 키를 쓰던 방식이라 채택하지 않고 미리 생성한 파일을 씀), 사전에 없는 세부 분야(대기업 채용·경제 용어·의료비)는 점선 칩으로 표시만 하고 관심 저장에서 제외. 메일 구독 신청 자체는 운영 API로 실제 메일이 나가므로 이번 확인에서는 누르지 않음. 옛 에디터의 MBTI별 문체 차별(단정형·친구 톡 등)은 자기소개 말투에만 남기고 레터 본문은 중립 원칙을 유지(본문까지 문체를 살릴지는 결정 필요).

## 29. 레터 목록 화면 재구성 — 첫 레터가 먼저 보이게 (2026-10-09 밤, 로컬 완료·미배포)
- **문제**: 레터 탭에 들어가면 소개·분류·검색·관심사 안내가 레터보다 먼저 쌓였고, 관심사를 고르면 같은 카드가 "내 관심사 레터"와 아래 목록에 두 번 나왔으며, 메일 신청 폼이 목록 중간을 크게 차지했다.
- **기존**: 소개 3줄 + 분류 칩 + 검색 + 큰 관심사 카드 → (선택 후) 추천 구역 + 신청 폼 → 최신 레터 → 지난 레터.
- **개선**: 소개를 두 줄로 줄이고 분류 칩과 검색을 한 줄로 합침. 관심사는 얇은 한 줄 바(내 관심사 칩 4개 + 나머지 개수, "관심사 레터만 N", 수정, 메일로 받기)로 바꾸고 편집·메일 신청은 눌렀을 때만 바 아래로 펼침. 별도 추천 구역을 없애고 같은 목록의 해당 카드에 이유 한 줄만 덧붙임(순서는 늘 최신순이라 추천이 편향으로 읽히지 않음). 관심사 상태를 훅(`useInterests`)으로 올려 목록과 바가 공유.
- **근거·영향**: 사용자 지시(레터 탭 진입 후 화면을 다시 그려 보기). 검증: tsc·eslint·vitest 통과, 데스크톱 1280·모바일 390에서 기본·편집·관심사 선택·관심사 레터만·메일 신청 상태 스크린샷(`docs/worklog/2026-10/2026-10-09-레터탭-목업/list-redesign/`). 서버 변경 없음. 배포 전.

## 28. 이메일 구독 — 신청·확인·수신거부·다이제스트 발송 (Phase 2, 2026-10-09 밤, 운영 반영 완료)
- **문제**: 독자가 관심사를 골라도 새 레터가 나왔을 때 다시 올 장치가 없다. 메일은 광고성 정보라 동의 기록, 이중 확인, 수신거부, 야간 발송 금지를 지켜야 하고, 한 통이 두 번 나가거나 모르는 주소로 나가면 도메인 평판이 깨진다.
- **기존**: 이메일 시설(SES 도메인, 지면용 구독자 5명)은 있으나 레터와 무관. 레터 구독 테이블·API·화면 없음. 목록의 주제 칩은 눌러도 동작하지 않았고 검색이 없었다(이 항목에서 함께 개선: 주제 칩 클릭 필터, 제목·주제 검색).

## 27. 독자 관심 설정과 "내 관심사 레터" — Phase 1 (2026-10-09 밤, 운영 반영 완료)

## 26. 레터 주제 태그와 주제 사전 — 독자 관심·구독의 1단계(Phase 0) (2026-10-09 밤, 운영 반영 완료)
- **문제**: 레터가 앞으로 수백 편 쌓이면 독자가 "내게 맞는 레터"를 찾고, 관심 분야를 구독하고, 비슷한 레터를 이어 읽는 기능이 필요하다. 그런데 레터에는 분류 9개뿐이라 너무 거칠고, 페르소나 기획서가 말한 삼성전자·금리·환율·임대료 같은 구체적 관심을 담을 방법이 없다. 이 메타데이터는 레터가 쌓인 뒤에 소급해 붙이면 비용이 가장 크다. 목록 카드는 모든 카드에 똑같은 "소식·실체·다른 시각" 배지만 있어 정보가 없었다.
- **기존**: 레터의 의미 정보 = 분류(주 1 + 보조 N)뿐. 카드 배지는 레터와 무관하게 동일. 모아쓰기 배지도 모든 카드에 동일.
- **개선**: ① 통제된 **주제 사전**(75개: 증시·금융·경제·부동산·산업·국제·정치·사회·문화, 기업·장소 포함)과 별칭("기준금리"→금리, "삼전"→삼성전자, "원/달러"→환율)을 DB에 두고, 레터의 `topics`를 사전의 이름·별칭·slug 어느 것으로 적어도 정규화해 저장한다(앞의 두 개가 주 주제). 사전에 없는 태그는 목록과 함께 거부, 이름·별칭이 서로 겹치는 사전 변경은 전체 거부(공백·대소문자 무시). ② 발행 규칙에 "주제 태그 1~8개" 추가. ③ 이미 발행된 레터에도 본문을 바꾸지 않고 태그만 소급 적용하는 경로. ④ 공개 목록·상세 응답에 주제를 포함. ⑤ 사이트 카드·상세 머리에 레터별 주제 칩, 정보가 없던 "모아쓰기" 배지 제거, 레터가 적을 때 카드가 한 줄을 채우도록 격자 조정. ⑥ 관리자 미리보기·JSON 수정에 태그 반영, 사전 입력·소급 스크립트(`seed_topics.py`). ⑦ 템플릿 v2에 주제 사전 목록과 태그 규칙·점검 항목 추가(사전 파일에서 생성해 어긋나지 않게 함). 기존 레터 3편에 태그 부여안 작성. DB: v1.42(주제 사전·태그). 독자 관심(v1.43)·구독·발송(v1.44) 초안은 단계별 파일로 분리.
- **근거·영향**: 사용자 지시("Phase 0부터"). 검증: 서버 테스트 79개 통과, 사이트 vitest 59개·tsc·eslint·빌드(사이트·관리자) 통과, 실제 Postgres로 사전 75개 입력·재입력, 별칭 정규화, 사전에 없는 태그 거부, 발행, 공개 목록·상세 태그, 발행된 레터 소급 태깅, 본문 수정 거부 유지 확인. 화면은 운영 응답에 태그만 얹은 임시 서버로 확인. 운영 반영 순서: ① v1.42 DDL(사용자) → ② 서버 배포(nginx `/admin/topics` 추가 포함) → ③ 서버에서 사전 입력·레터 3편 태그 소급 → ④ 관리자·사이트 프런트 배포. 한계: 사전은 초안(75개)이라 편집팀 검토·보강 필요, 사전 변경 화면은 아직 없음(스크립트·API로 관리). **운영 반영 결과(2026-10-09 21시경)**: v1.42 적용(사용자), 서버 배포, 사전 75개 입력, 레터 3편 태그 소급(부캉이·라네즈·종로3가 모두 발행 상태에서 태그만 적용), 관리자 프런트 배포, 사이트 프런트 개정 92 — 운영 `/letter`에 주제 칩이 보이고 홈·헬스·상세 정상. 후속: 같은 주 주제 사이의 표시 순서가 입력 순서가 아니라 가나다순이다(입력 순서 보존에는 컬럼 추가 필요). nginx `/admin/topics` 위치는 관리자 화면에서 사전을 편집할 때 추가한다.

## 25. 빅카인즈 관련도 정렬이 일시 오류 뒤에도 고정되던 문제 수정·배포 (2026-10-09 밤)
- **문제**: 출처 후보 검색은 관련도순에 의존하는데, 빅카인즈가 한 번 정렬 요청을 거부하면 검색 품질이 계속 떨어졌다. 같은 검색이 몇 분 전에는 라네즈 핵심 기사를 1~3위로 냈는데 이후 구글 전력 기사 같은 엉뚱한 결과가 1위로 나왔다. 원인이 두 겹이었다. ① 타임머신 Lambda가 "관련도 정렬을 거부당하면 컨테이너가 사라질 때까지 영구히 최신순만 쓴다". ② 기간 검색 결과를 30일 캐시하는데, 관련도순을 요청했다가 최신순으로 대체된 결과까지 저장해서 같은 조건의 검색이 한 달간 최신순으로 굳는다.
- **기존**: 일시적인 거부(호출 한도·순간 장애) 한 번이면 몇 시간 동안 모든 검색이 최신순, 그중 해당 조건은 30일 동안 최신순.
- **개선**: ① 거부를 5분만 기억하고 그 뒤 다시 관련도순을 시도한다. ② 관련도순 요청이 최신순으로 대체된 결과는 캐시하지 않는다. 이 동작을 검증하던 기존 테스트 3개는 옛 동작("영구 기억", "대체 결과도 캐시")을 단언하고 있어서 새 동작에 맞게 고쳤고, 거부 후 대기 시각 변수가 테스트 사이에 새지 않도록 초기화도 추가했다. 단위 테스트 188개 통과. 배포: 구형 Lambda 21개를 한 번에 올리는 `deploy.sh`는 함수별 핸들러 설정 함정이 있어, 타임머신 하나만 올리는 `./deploy.sh time-machine` 대상을 추가해 사용했다. 확인: "라네즈 필리핀"·"라네즈"·"아모레 인도" 모두 `relevance`, 관련 기사가 위에 나옴, 타임라인(하루 모드) 200.
- **근거·영향**: 사용자 지시(2번 정렬 수정 배포). 이전에 일시 오류 시점에 캐시된 몇몇 검색 조건은 최대 30일간 최신순 결과가 남을 수 있다(관리자 화면은 기간 끝을 오늘로 보내 날마다 다른 조건이라 영향이 거의 없음). 빅카인즈 호출 한도는 여전히 미확인.

## 24. 종로3가 레터 재작성·발행, 빅카인즈 주소 형식 정정 (2026-10-09 밤)

- **문제**: 출처 주소를 누가 어떻게 찾는지가 불명확했다. 서버에 후보 검색 기능이 있었지만 관리자 화면에는 없어서, 편집자가 서울경제 기사를 찾으려면 AI에게 맡기거나 사이트에서 직접 뒤져야 했고, AI가 목록에 없는 기사를 만들어 낼 여지도 있었다.
- **기존**: 키워드 검색은 서버 API만 존재. 관리자 라우트와 화면 없음. 템플릿 v2의 "후보 기사 목록" 입력은 있었지만 만들 도구가 없었다.
- **개선**: 관리자 백엔드에 `GET /admin/issue-letters/candidates`(8번째 라우트), 새 레터 화면 맨 위에 "출처 후보 기사 검색" 칸을 추가했다. 단어로 검색하면 서울경제 기사 DB에서 제목·본문에 단어가 들어간 최신 기사(제목·날짜·주소)가 나오고, 고른 기사를 `제목 | 주소` 줄로 복사해 템플릿의 후보 기사 목록에 붙여 넣는다. 단순 키워드 일치이며 AI·유사도 검색은 쓰지 않는다(의미 검색용 벡터는 DB에 준비돼 있으나 사용 안 함).
- **근거·영향**: 사용자 지시("심플한 방향, 키워드 검색 칸 추가"). 기사 선정은 사람이, 레터와의 연결(기사 번호)은 서버가 저장 때 주소로 찾아서 한다. 서버리스 정리: 관리자 CMS 백엔드는 아직 Lambda + API Gateway(라우트 약 90개)이고 공개 API(`lens-cms-api`)와 기사 수집만 일부 EC2/Lambda로 나뉘어 있다. 레터 관리자 라우트는 기존 관리자 구조에 맞춰 같은 방식으로 붙이기로 했다(옵션 A) — 서버리스를 늘리는 일이지만, 관리자 전체를 EC2로 옮길 때(계획서 5b) 레터는 서버 코드가 이미 EC2에 있어 거의 그대로 옮겨진다. 옵션 B(레터 관리자 API만 EC2 직결)는 관리자 백엔드가 두 군데로 갈라져 채택하지 않았다.

## 17. 관리자 입력 화면 — 템플릿 JSON 붙여넣기 → 초안 → 검수 → 발행 (2026-10-09 밤, 미배포) + 출처는 서울경제 원문만
- **문제**: 레터를 만들려면 서버 안에서 스크립트를 돌려야 했다(임시 방편). 편집자가 쓸 수 있는 정식 입력 경로가 없었다. 또 템플릿이 만드는 JSON은 출처가 기사 주소(URL)뿐인데 서버는 기사 번호를 요구해서 그대로 넣을 수 없었다. 출처로 외부 매체도 허용하는 설계였는데 사용자 결정은 "서울경제 원문 기사만 인정"이었다.
- **기존**: 입력은 샘플 입력 스크립트뿐. 출처는 `article_no` 또는 승인된 외부 URL 중 하나. 관리자 화면 없음.
- **개선**: ① 서버: 출처를 `url`(서울경제 기사 주소)로 지정하면 기사 DB에서 번호를 찾아 연결하고(꼬리표 `?ref=` 무시), 찾지 못하면 "서울경제 기사 DB에 없다"고 거부한다. 외부 매체 출처는 모두 거부한다(DB 컬럼은 남겨 둠). ② 관리자 백엔드: `/admin/issue-letters*` 라우트 7개(후속 18번에서 후보 검색이 추가되어 8개)가 서버 API를 호출하며, 서버의 거부 사유 문장(입력 오류 400, 상태 충돌 409, 발행 규칙 422)을 그대로 화면에 전달한다. 감사 로그를 남긴다. ③ 관리자 화면 `/issue-letters`(상태 필터 목록), `/issue-letters/edit`(새 레터: JSON 붙여넣기 → 초안 저장 / 기존 레터: 발행 전 점검 목록, 검수 요청·발행·내리기, JSON 수정, 본문·출처·투표 미리보기). 발행 규칙을 통과하지 못하면 발행 버튼이 비활성이다.
- **근거·영향**: 사용자 결정("서울경제 원문 기사만 인정하고 B 진행"). 검증: 서버는 실제 Postgres로 URL 입력·외부 거부·전 과정 통과(테스트 50개), 관리자 백엔드는 응답 전달·오류 매핑·감사 로그를 스텁으로 확인, 관리자 화면은 가짜 API로 목록·검수 화면을 직접 확인(tsc·eslint·정적 빌드 통과). 아직 배포하지 않았다 — 배포에는 서버 재배포, 관리자 Lambda 배포, API Gateway 라우트 7개 생성, 관리자 프런트 배포가 필요하다. 한계: 관리자가 공유 계정이라 사람 단위 승인은 불가(v1.39).

## 16. 프론트를 목업에서 실제 API로 교체 (2026-10-09 밤, 미배포)
- **문제**: 화면이 코드에 박힌 목업 데이터를 그리고 있어서, 서버에 발행된 레터가 화면에 나오지 않았다. 투표는 이 기기에만 저장되는 가짜 집계였다.
- **기존**: `/letter`와 `/letter/{slug}`가 `mockLetters.ts`(5편)를 읽고, 투표 집계는 슬러그에서 만든 고정값 + 내 1표(localStorage), 상세 경로는 목업 슬러그만 열림(`dynamicParams=false`).
- **개선**: 두 페이지가 서버(`/api/v2/issue-letters`)에서 발행된 레터를 60초 단위로 읽는다(ISR). API 응답을 기존 화면 타입으로 바꾸는 계층(`letterApi.ts`)을 추가해 화면 컴포넌트는 거의 그대로 썼다. 자사 기사는 매체명을 "서울경제"로 표기, 시각은 한국 날짜로 변환. 투표는 이 기기의 익명 식별자(UUID)를 서버로 보내 레터당 한 표를 저장하고, 투표한 사람에게만 실제 집계를 보여 준다(이미 투표했으면 기존 선택·집계 표시, 저장 실패 시 안내 문구). 목업 데이터 파일은 삭제(샘플 내용은 시드 JSON에 보존).
- **근거·영향**: 검증은 운영 데이터를 읽는 로컬 화면으로 했다 — 부캉이 목록·상세 정상, 초안(라네즈)은 404, 한마디·투표·출처·인라인 링크 표시, 하이드레이션 오류 0, tsc·eslint·vitest 59개·빌드 통과. 운영 DB에 시험 투표는 넣지 않았다(삭제 수단이 없어 실제 집계에 남기 때문). 투표 저장 동작은 서버 쪽을 로컬 DB로 검증했고, 화면에서의 첫 투표는 배포 후 확인한다. 아직 `noindex`이며 푸시·배포는 하지 않았다.

## 15. 샘플 3편을 운영 DB에 입력 (2026-10-09 저녁)
- **문제**: 서버 API가 배포됐지만 DB가 비어 있어 화면으로 확인할 레터가 없었다. 샘플을 넣으려면 기사 DB와 연결해야 했고, 내용은 목업 코드에만 있었다.
- **기존**: 목록 API가 빈 배열. 샘플 3편은 프론트 코드(`mockLetters.ts`)에만 존재.
- **개선**: 입력 스크립트가 서울경제 기사 DB에서 제목으로 기사를 찾아 `article_no`로 연결해 관리 API로 저장하고, 서버의 발행 규칙을 통과한 레터만 발행했다. 결과: 부캉이 발행(호수 1, 출처 4건, 본문 링크 3개), 라네즈·종로3가는 규칙에 걸려 초안으로 남음(라네즈: 출처가 AI LENS 기사 페이지라 기사 DB에 없어 0건, 본문 링크 불일치 2건 / 종로3가: 자사 기사 링크 1개로 3개 미만). 외부 확인: 목록·상세 정상, 초안은 공개 상세 404.
- **근거·영향**: 규칙이 의도대로 걸러냈다는 증거이기도 하다(원본 샘플이 기사 연결 기준에 못 미침). 해소하려면 서울경제 기사로 근거를 더 찾거나 AI LENS 기사 페이지를 출처 종류로 인정하는 결정(v1.40 후보)이 필요하다.

## 14. 편집자 FK 제거 — 관리자에 개인 식별이 없다는 사실 반영 (v1.39)
- **문제**: 샘플을 발행하려고 편집장 사번을 조회했더니 `editors` 테이블이 비어 있었다. 확인해 보니 관리자 서비스는 개인 계정 없이 공유 비밀번호 하나로 로그인하고(토큰 사용자는 항상 `admin`), `editors`는 어디에서도 쓰이지 않았다. 내가 `author_no`·`reviewer_no`·`approved_by`를 `editors` FK로 걸어 두어, 어떤 승인자 값을 넣어도 발행이 제약 위반으로 막혔다. 설계 단계에서 "편집자 테이블이 실제로 쓰이는가"를 확인하지 않은 내 오류다.
- **기존**: 작성→검수→발행을 "편집장(admin 역할)만 승인, 작성자 본인 승인 불가"로 설계(Q7). 승인자 칸은 `editors` FK.
- **개선**: v1.39에서 세 FK를 제거하고 칸을 문자열 식별자로 정의했다(지금은 `admin`). 사람 단위 규칙("본인 승인 불가")은 코드에 남겨 두어 개인 로그인이 생기면 같은 칸에 개인 식별자를 넣는 것만으로 작동한다. 지금도 작성 → 검수 요청 → 발행의 단계는 상태로 강제된다.
- **근거·영향**: 현실에 맞춘 정정(사용자 방향: 처음 기획을 고수하지 않고 fit을 맞춘다). 한계: 공유 계정 구조에서는 누가 승인했는지 사람 단위로는 남지 않는다. 개인 로그인 도입은 별도 과제. 이 한계는 Q7 결정 기록에도 반영한다.

## 13. 샘플 입력용 파일을 서버 배포 묶음에 포함 (+ 배포 권한 사고 수정)
- **문제**: 샘플 입력에 필요한 파일(시드 JSON, 입력 스크립트, v1.38 DDL)을 서버로 옮기려고 사용자가 S3에 따로 올려야 했다. 콘텐츠의 최종 저장소는 RDB인데 임시 이동 절차가 번거로웠다.
- **기존**: 사용자가 로컬에서 S3로 올리고, 서버에서 다시 받는 두 단계. 배포 묶음에는 코드(`*.py`)만 있었다.
- **개선**: 배포 스크립트가 스크립트·시드·DDL을 같은 묶음에 넣어 서버 `/opt/lens-cms-api/{scripts,seed}/`에 놓는다. 콘텐츠는 서버에 남지 않고 스크립트가 관리 API로 RDB에 저장한다. 이 과정에서 임시 폴더 권한(700)이 서버의 `/opt/lens-cms-api` 폴더 권한을 덮어써 접속 계정이 들어가지 못하는 문제가 생겼고(서비스 영향 없음, root로 동작), 서버에서 `chmod 755`로 복구하고 배포 스크립트에 `chmod 755` 한 줄을 추가해 재발을 막았다.
- **근거·영향**: 사용자 질문("레터 콘텐츠도 RDB에 쌓는데 S3가 아니라 RDB로 옮기는 게 맞지 않나") — 이동 통로만 단순화하고 저장은 RDB라는 원칙 확인. 정식 경로는 관리자 JSON 입력 화면(다음 단계)이며 이 스크립트는 그때 폐기한다.

## 12. 레터 생성 프롬프트 템플릿 v1 → v2
- **문제**: 템플릿이 중립 원칙 이전 기준이라, AI가 원칙에 어긋나는 레터를 처음부터 만들 수 있었다. 외부 웹 검색으로 외부 매체를 인용하게 했고, 투표에 찬반형을 허용했고, 문체가 "반말체"로 적혀 있어 실제 샘플(해요체)과 달랐다.
- **기존**: 설계 원칙 3가지(지어내기 금지·인라인 링크·3축). 에디터 한마디는 "관찰 1~2문장", 투표는 "금융은 감정형, 일반 소재는 찬반 2지선다 가능". 조사는 웹 검색. 출력은 HTML 위젯 하나. 체크리스트 8개.
- **개선**: 원칙 4가지로 확장(중립·무편향 신설). 프롬프트 맨 앞에 "최우선 원칙: 중립"과 금지 표현 목록을 넣었다. 조사는 서울경제 기사 안에서만, 후보 기사 목록이 주어지면 그 안에서만 고르게 했다. 다른 시각 섹션은 AI의 비판이 아니라 출처 있는 다른 해석으로, 제목은 해석을 단정하지 않게, 한마디는 사실 연결 정리로, 투표는 감정 반응형 + "잘 모르겠어요" 필수로 바꿨다. 출력은 서버 입력과 같은 저장용 JSON이 1순위, 미리보기 HTML은 선택. 문체는 해요체. 체크리스트 11개, 자주 나오는 문제 5가지.
- **근거·영향**: 사용자 지시("논란이 터지면 안 된다"). 템플릿과 서버 검사가 같은 기준이라 템플릿으로 만든 레터는 서버 발행 검사를 그대로 통과한다. v1은 원안으로 보존. 파일 `마스터DB/06_콘텐츠/레터/ailens_레터생성_프롬프트템플릿_v2_261009.html`.

## 11. 에디터 한마디 — 의견에서 사실 연결 정리로
- **문제**: 한마디가 의견 성격이라 전 레터 중립 원칙과 충돌했다. 샘플에 "재밌는 건…", "아이러니예요", "탁월하지만" 같은 평가·감탄이 있었고, 라네즈 샘플은 "브랜드가 밀려서가 아니에요"처럼 본문에 없는 원인을 단정했다.
- **기존**: 기획 원안은 "이슈 맥락을 한 발 더 짚는 관찰 1~2문장"이었고 금지는 자기반영 고백뿐이었다.
- **개선**: 코너를 없애지 않고 역할을 재정의했다. 본문에 이미 나온 사실만 엮는 2문장·200자 이내 칸으로 바꾸고, 평가어·감탄·새 주장·예측 단정·판단 요구를 금지했다. 샘플 4편을 다시 썼고, 서버가 금지 표현과 길이를 발행 때 검사한다. 기준 문서는 `에디터한마디_작성기준.md`.
- **근거·영향**: 사용자 방향("원칙에 맞게 fit을 찾는다, 좋은 기획이면 틀지 말고 전달 방법을 고민"). 새 문장은 모두 본문 사실만 썼지만 AI가 쓴 샘플이라 작성자 확인이 필요하다.

## 10. 투표 — 전 레터 감정 반응형만
- **문제**: 금융 분류에만 걸던 제한으로는 부족했다. 샘플 투표 중 "지금 보내는 게 맞을까요?"(결정 요구), "합리적인 선택"(평가), "지켜봐야 한다"(행동 방향 시사), 선택지 부가 설명("가볼 이유가 생겼어요")이 유도 소지가 있었다.
- **기존**: 투표 종류 두 가지(이분형·감정형), 금융 분류만 감정형 강제. 중립 선택지 없음.
- **개선**: 모든 레터에서 감정 반응형만 허용(이분형 폐지). 질문·선택지의 평가·권유·결정 표현을 서버가 저장·발행 때 거부. 모든 투표에 "잘 모르겠어요"(`unsure`) 필수, 선택지 부가 설명 제거. 샘플 5개를 모두 고쳤다.
- **근거·영향**: 사용자 지시("주관·유도·권유·결정 뉘앙스 금지, 편향 없는 질문"). 문구 목록 방식이라 우회 표현은 놓칠 수 있어 편집장 검수가 최종 방어선이다. 다중 분류는 이미 지원하며 부캉이를 시그널·사회·경제로 넓혔다.

## 9. DB 분류 설계 오류 정정 (v1.37 → v1.38)
- **문제**: v1.37이 레터 분류를 `categories` 테이블(옛 7분류)에 FK로 걸었는데, 사이트가 쓰는 9분류(시그널·사회 등)와 달라 '사회'·'시그널'을 저장할 수 없었다. 샘플 입력을 준비하며 발견했다.
- **기존**: `issue_letter_categories(letter_id, category_id → categories.id)`.
- **개선**: v1.38에서 `category_slug`(문자열)로 교체하고, 허용 목록은 앱이 검증한다(분류의 정본은 사이트 코드). 테이블이 비어 있을 때만 적용되고 데이터가 있으면 중단된다. 로컬 Postgres에서 v1.37→v1.38 적용·재적용·중단 동작을 확인했다.
- **근거·영향**: 데이터 입력 전에 발견해 이관 비용이 없었다. 운영 DB 적용은 대기 중.

## 8. 운영 배포 — 이슈 레터 API
- **문제**: 설계만 있고 서버·네트워크 경로가 없어 프론트가 연결할 수 없었다.
- **기존**: 서버에 레터 라우트·nginx·CloudFront 경로·솔트 모두 없음.
- **개선**: 서버 코드 배포, 투표 식별자 해시용 솔트 설정(서버에서 생성, 기록 없음), nginx location 2개, CloudFront `/api/v2/issue-letters*` 추가. 관리 API는 외부에 열지 않았다. 외부 확인: 목록 200(빈 배열), 없는 상세 404, 기존 글 API·홈 정상, 외부 관리 경로 404.
- **근거·영향**: 상세는 `db-changelog/postgres/v1.37-이슈레터-신설.md`. 인스턴스 메모리 사용률 92%대라 데이터가 늘기 전 확인 필요.

## 7. lens-cms-api 이슈 레터 저장소·라우트
- **문제**: 레터를 저장·검수·발행·투표할 서버 기능이 없었다.
- **기존**: 목업 데이터(프론트 코드)만 있었다.
- **개선**: 저장소와 라우트 11개(공개 4·관리 7). 발행은 편집장만, 작성자 본인 승인 불가. 발행 검사: 섹션 3개 이상, 자사 기사 인라인 링크 3개 이상, 본문 링크는 출처 목록에 있어야 함, 자리표시 출처 금지 등. 단위 테스트 46개, 실제 DB로 전 과정 통과.
- **근거·영향**: 제목·링크가 기사 DB에서 읽히므로 지어낸 출처가 구조적으로 불가능하다.

## 6. v1.37 DB 설계 — 테이블 7개
