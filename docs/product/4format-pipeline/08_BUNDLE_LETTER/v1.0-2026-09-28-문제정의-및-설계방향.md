# v1.0 (2026-09-28) — 묶음 레터 문제 정의 및 설계 방향

작성: 문영광 + Claude Code

`03_LETTER/README.md`(기존 단일기사 레터, 그대로 유지)

## 문제 발견

지면특별코너(전체/증권/산업/시그널) 각 탭은 그날 선정된 최대 4건의 기사를
**각각 독립적으로** 4포맷(레터/웹툰/팟캐스트/영상) 콘텐츠로 발행한다 —
`pipelines/mustknow_auto/run.py`가 탭당 최대 4건을 골라 `_try_publish()`를
기사마다 한 번씩 호출하고, 그 안에서 `publish_utils.publish_article()`이
기사 1건을 받아 레터·웹툰·팟캐스트·영상 1세트를 만든다.

이 구조에서 "증권" 탭에 4건이 뽑히면 서로 무관한 4개의 증권 뉴스가
따로따로 4개의 레터로 나간다. 사용자 피드백(2026-09-28): "기사 하나로는
뭔가 안 보인다 — 마치 흩어진 퍼즐처럼. 퍼즐이 결합되고 스토리텔링이
되어야 가치가 높다."

## 문제 정의

지면특별코너 탭에서 선정된 여러 건(최대 4건)의 기사를, **레터 1건이
그 여러 건을 종합해 연결성 있는 하나의 이야기로 전달**하도록 바꾼다.
목적은 "독자 스타일에 맞는 뉴스를 친근한 형태로 전달"이며, 기사 1건
단위 발행 자체가 지켜야 할 원칙은 아니었다는 게 사용자 확인 사항이다
(브랜드명 "같은 뉴스, 네 가지 시선"의 "네 가지"는 스토리별 4관점이
아니라 4개 생성 포맷을 가리키는 것으로 확인됨 — 묶음 레터와 브랜드
충돌 없음).

## 왜 지면특별코너부터인가

지면특별코너 4탭은 애초에 카테고리로 묶여 있다(증권 탭=증권 기사만,
산업 탭=산업 기사만 등, `pipelines/mustknow_auto/run.py::_tab_of()`
참고). 같은 카테고리 안의 기사 4건을 "오늘의 증권 브리핑"처럼 묶는 건
억지 연결 없이도 자연스러울 가능성이 높다.

반면 "일반" 카테고리(정치·사회·국제·경제 등 뒤섞임, 하루 최대 20건
목표)는 서로 무관한 주제가 많아 통째로 하나의 스토리로 엮으면 억지
연결 위험이 크다 — 묶는다면 몇 개의 작은 주제 클러스터로 나눠야
한다는 방향까지만 나왔고, 클러스터링 방식은 미설계. **v1.0은
지면특별코너 4탭에만 범위를 한정한다.**

## 기존 자산 재사용 가능 여부

- `service/backend/prompts/letters/published.md`(실제 운영 레터 프롬프트,
  Postgres 경유) — "기사 원문 1건"을 입력으로 받아 "사실확인/흐름/
  구조설명/반대편사실/시각제시" 6단 구조로 재구성하는 전제. 여러 기사를
  받는 구조가 아니라 그대로 재사용 불가.
- `docs/product/4format-pipeline/03_LETTER/README.md`(문서 정본, v10) —
  같은 전제. 헤드라인 톤(반문형/발견설명형/캡션형/명사형 4종 로테이션)
  같은 세부 규칙은 재사용 가치 있음.
- `service/backend/newsletter/`(MBTI "오늘의 한 통") — 확인 결과 이건
  "페르소나 그룹별 레터 4편을 한 피드에 나열"하는 구조지, 여러 기사를
  하나의 레터로 합성하는 게 아니었다. 참고 불가.
- `1_ai_link/prism/dev/DATA/Prompt/`(AI 프리즘, 8개 독자 유형별 분류+생성
  프롬프트) — "하루 400여개 기사 중 유형별 관심 기사를 선별해 레터 1건에
  4~6건을 묶어 발행"하는, 정확히 이번 문제와 같은 구조. `core_knowledge.yaml`
  의 3단계 선별 프로세스(초기 스크리닝→심층평가→최종선별, 다양성
  메커니즘 포함)는 구조적으로 참고 가치가 크다. 다만 평가 지표 내용은
  "글로벌 투자자" 등 특정 페르소나 전용이라 AI LENS "일반 독자" 톤에는
  안 맞음 — **구조만 참고, 생성 프롬프트 문체·규칙은 AI LENS 자체 것
  (03_LETTER 스타일) 유지**가 맞는 방향.

## 영향 범위 (확인됨, 상세 설계는 미착수)

`pipelines/common/publish_utils.py::publish_article()`이 기사 1건 전제로
짠 파이프라인 전체가 영향을 받는다:

1. `extract_facts()`(0단계, 사실 추출) — 기사 1건의 facts.json을 만드는데,
   4건을 어떻게 합칠지(4건 각각 추출 후 통합 vs 통합 입력을 한 번에 추출)
   미정
2. `letters_mod.run_article()` — 새 프롬프트 필요(이 문서 범위 밖, 다음 버전)
3. `podcast_mod.run_article()` / `webtoon_mod.run_article()` / `generate_video()`
   — 전부 같은 문제. 레터만 먼저 풀고 나머지 3포맷은 후속 버전에서
   다룰지, 4포맷을 동시에 설계할지 미정
4. `lens_cms_client.create_post()`로 넘어가는 `source_url`(현재 기사 1건의
   원문 URL) — 묶음 레터는 원문 URL이 여러 개라 스키마 변경 필요할 수 있음
5. `pipelines/mustknow_auto/run.py`의 선정 로직(`_rank_tab_candidates`,
   `_try_publish`) — 지금은 기사 단위로 `_try_publish`를 호출하는데,
   묶음 레터는 "탭에서 뽑힌 N건을 한 번에 넘기는" 호출로 바뀌어야 함
