## 스펙과의 괴리 (2026-09-21 확인)

`README.md`는 이 단계 산출물을 **`facts.json`**(핵심 숫자·용어·논지가
구조화된 JSON, 각 사실에 `id`가 있어 `07_VERIFY`가 그 id로 커버리지를
대조하는 설계)이라고 서술한다. **실제 코드는 이렇게 동작하지 않는다**:

- `extract_facts()`의 반환값은 구조화 JSON이 아니라 **모델이 자유
  형식으로 쓴 프로즈 텍스트**("공통 팩트시트") 하나다. `id` 필드도,
  JSON 스키마도 없다.
- 각 포맷 파이프라인(레터·팟캐스트·웹툰·영상)은 이 팩트시트를 원문
  뒤에 이어붙인 텍스트 파일을 그대로 모델에 넘길 뿐, 별도 파싱을
  안 한다 — "facts.json을 읽는다"는 서술과 실제로는 안 맞는다.
- 각 포맷이 산출물 끝에 내보내는 `FACT_IDS: [1, 3, 4]` 트레일러는
  코드로 추출은 되지만(`text_utils.extract_fact_ids`,
  `publish_utils.py`가 각 파서에서 호출), **그 값을 무엇과 대조해
  커버리지를 검증하는 로직이 코드 어디에도 없다** — 07_VERIFY 문서가
  설명하는 "발행 게이트" 자체가 미구현이다(`07_VERIFY/
  00-2026-09-21-베이스라인.md` 참고).

즉 이 단계는 "구조화된 사실 추출 + ID 기반 커버리지 검증"이라는 설계
의도대로 동작하는 게 아니라, "한 번 더 모델에 물어봐서 요약 텍스트를
원문에 덧붙이는" 정도로 단순화된 채 운영되고 있다. 기능 자체(같은
기사에 대해 4개 포맷이 다른 숫자·표현을 쓰지 않게 한다는 목적)는
`facts_extract.py` 모듈 docstring이 밝힌 원래 동기와 여전히 일치하지만,
**구현이 스펙의 형식적 요구(JSON+id+검증게이트)까지는 못 미친다.**
