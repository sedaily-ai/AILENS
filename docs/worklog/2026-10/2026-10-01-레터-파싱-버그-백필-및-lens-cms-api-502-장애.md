# 2026-10-01 레터 파싱 버그·31건 백필, 그리고 lens-cms-api 502 간헐 장애

작성: Claude Code
관련: `pipelines/common/publish_utils.py`(리비전 89), `service/frontend`(리비전 27→29),
`service/frontend/src/shared/lib/api/cmsPostsApi.ts`, lens-cms-api EC2(`i-0e3d04bdb01584833`, t3.micro)

## 배경

레터 상세 페이지 디자인을 점검하던 중 "30초 핵심" 4번째 항목에 마크다운
`##` 기호가 섞인 본문 전체가 그대로 노출되는 걸 발견했다. 추적 결과
**오늘(2026-10-01) 발행된 레터 전량(31건)에 공통된 파이프라인 파싱
버그**였고, 이를 백필하는 과정에서 레터 상세 페이지 자체가 더 큰
구조적 문제(레터 본문이 아예 비어있음)를 안고 있었다는 게 추가로
드러났다. 두 버그를 다 고치고 31건을 백필한 뒤, 홈 "오늘의 이슈, 4가지
시선" 히어로가 간헐적으로 완전히 사라지는 별개 증상을 조사하다가 —
**이번 세션의 핵심 미해결 항목인 lens-cms-api(백엔드 EC2) 502 간헐
장애**를 발견했다. 이 문서는 그 전체 경위와, 클라우드 담당자가 판단해야
할 마지막 항목(EC2 인스턴스 증설 여부)을 정리한다.

## 한 것

### 1. 레터 파싱 버그 진단 및 수정

`pipelines/common/publish_utils.py`의 두 함수가 레터 생성 모델의 출력
섹션 순서 변경(`[핵심 요약]` 블록이 본문보다 먼저 오고, 소제목 마커가
`◾`에서 `##`로 바뀜)에 대응을 못 하고 있었다.

- `parse_letter_summary_bullets()` — `[핵심 요약]` 블록 뒤의 `##` 소제목
  을 종료 신호로 인식 못 해, 그 뒷부분 본문 전체(최대 2,650자)가
  "30초 핵심" 4번째 항목에 그대로 흘러들어감.
- `parse_letters()` — `[핵심 요약]`을 영구 종료 신호(`break`)로 오인식,
  그 뒤에 오는 실제 레터 본문(`##` 섹션 전부)이 통째로 유실돼 레터
  상세 페이지엔 리드 한 줄만 남음.

두 함수 모두 `[핵심 요약]`을 `[제목]`과 같은 "skip 구간"으로 바꾸고,
`##` 줄을 소제목 마커(기존 `◾`와 동일 역할)로 인식하도록 수정. `[용어]`
블록도 명시적 종료 마커로 추가. 합성 데이터로 두 함수 모두 재검증 완료.

프론트(`LensFormatPanel.tsx`)도 `##` 접두사를 가진 문단을 감지해 접두사는
제거하고 소제목 스타일(`lread-sub`)만 적용하도록 수정 — 안 하면 "##"
글자가 그대로 노출됨.

**배포**: 파이프라인(`frontpage_auto`/`mustknow_auto` 공용 이미지)
리비전 89, 프론트엔드 리비전 28(이후 502 조사 중 재시도 로직 추가로
리비전 29까지 진행). 둘 다 ECS 롤아웃 `COMPLETED` 확인.

### 2. 31건 백필

원본 레터 생성 시점의 마크다운은 보존되지 않아(일회성 파이프라인
산출물), 이미 손상된 상태로 저장된 "30초 핵심" 4번째 항목 텍스트에서
`##` 경계로 섹션을 재구성하는 방식으로 복원했다.

- "30초 핵심" bullets[3]을 `##` 등장 지점에서 절삭(원래 의도된 짧은
  문장만 남김) — 31건 전부 적용.
- 레터 본문(`paragraphs[]`)을 위 백업 텍스트에서 `##` 경계로 재분할해
  재구성 — 31건 전부 적용. **한계**: 버그로 인해 원래 문단 구분이 공백
  하나로 전부 합쳐진 뒤였어서, 섹션 "하나"는 복원 가능해도 그 안의
  문단 경계까지는 완전 복원이 불가능하다(근사 복원). 소제목/본문 분리는
  "## 소제목: 질문?" 패턴의 첫 물음표를 기준으로 절삭 — 32개 섹션 중
  31개 정확히 분리, 1개(물음표 없는 문장)만 섹션 전체가 소제목 스타일로
  남음(영향 낮음, 수동 확인 가능).
- 수정은 `lens-cms-api`(내부 API, `X-Internal-Token` 인증)의
  `GET/PUT /admin/posts/{admin_post_id}` 경유. 공개 API의 글 `id`(slug)와
  내부 `admin_post_id`(UUID)가 다른 값이라, `source_url`로 먼저
  `admin_post_id`를 역조회하는 단계가 필요했다(처음 이 매핑을 안 하고
  slug를 그대로 UUID 컬럼에 넣어 조회했다가 Postgres
  `invalid input syntax for type uuid`로 500을 받은 실패 경험 있음).
- 전수 검증: 공개 API 재스캔 결과 "##" 잔존 0건, 웹툰/팟캐스트/영상
  등 다른 포맷 데이터는 변경 전후 완전 일치(mismatch 0건) 확인.
- 최초 스캔(29건) 이후 추가로 발행된 2건을 별도 재스캔으로 발견해 같이
  백필 — 최종 31건.

### 3. 홈 "오늘의 이슈" 히어로 간헐적 소실 — lens-cms-api 502 발견

백필 작업 중간중간 홈 "오늘의 이슈, 4가지 시선" 섹션이 통째로 사라지는
증상이 반복 재현됐다. `fetchLensPosts()`(홈 SSR이 쓰는 함수)가 실패하면
**조용히 빈 배열을 반환**하도록 돼 있어 섹션이 아무 에러 로그 없이
사라지는 구조였다(2026-09-02에도 같은 증상 이력 있음 — 코드 주석 확인).

- 1차 조치: CloudFront 캐시 재무효화 반복 — 일시적으로는 해결되는
  것처럼 보였으나 재발.
- `fetchLensPosts()`에 재시도(2회) + 실패 로그(`console.error`) 추가
  배포(리비전 29) — 로그가 없던 게 가장 큰 문제였음.
- 로그 추가 후 CloudWatch(`/ecs/sedaily-lens-frontend`)에서 실제 원인
  확인: **`fetchLensPosts: HTTP 502 (attempt 1/2, attempt 2/2)`** —
  재시도 2회 모두 502. 즉 일회성 글리치가 아니라 요청 시점에 백엔드가
  일정 시간 지속적으로 502를 내는 패턴.
- 원인 추적: 이 요청이 가는 곳은 `https://ailens.sedaily.ai/api/v2/posts
  ?channel=lens&limit=1000` → CloudFront → **EC2 인스턴스
  `i-0e3d04bdb01584833`(t3.micro, lens-cms-api, PostgreSQL 상시 연결
  서버)**. 이 응답은 오늘 기준 **약 4.0~4.1MB**(gzip 전 기준, 발행량이
  늘면서 계속 커지는 중 — Next.js 측 로그에 "items over 2MB can not be
  cached" 경고가 계속 찍히는 것도 이 때문).
- 직접 반복 curl(5회 연속)로는 전부 200, 1.7~2.2초로 정상 — **단일
  요청으로는 재현 안 됨**. ECS 컨테이너 내부 fetch만 502를 받는
  점으로 미뤄, 동시/연속 요청(실사용 트래픽 + 세션 내 반복 테스트
  트래픽 포함)이 겹치는 상황에서만 발생하는 것으로 추정.
- CloudWatch EC2 메트릭 확인: **CPU 사용률 최대 38%, CPU 크레딧 잔량
  286~288(거의 풀)** — CPU 자원 고갈은 아님. 메모리·동시 연결·uvicorn
  워커 수 등 다른 병목일 가능성이 높으나, 이 인스턴스에 중앙화된 애플리케이션
  로그(CloudWatch Logs 연동)가 없어 **여기까지만 확인하고 더는 추적
  못 함**.

## 결정

- 백필은 원본 대신 "이미 손상된 산출물에서 역으로 재구성"하는 방식을
  택했다 — 원본 마크다운이 전혀 남아있지 않아 다른 선택지가 없었고,
  31건 중 31건이 깨끗하게 재구성 가능함을 사전에 검증한 뒤 진행했다.
- SSM 파라미터(토큰) 직접 조회는 세션 가드레일(credential
  materialization)에 막혀, 토큰이 필요한 모든 쓰기 작업은 사용자가
  직접 터미널에서 `export` 후 스크립트를 실행하는 방식으로 진행했다.
- EC2 인스턴스 증설(t3.micro → t3.small/medium 등)은 비용·운영 영향이
  있는 인프라 변경이라 **직접 실행하지 않고 클라우드 담당자 판단으로
  넘긴다.**

## 다음 — 클라우드 담당자 확인 필요

1. **`i-0e3d04bdb01584833`(lens-cms-api, t3.micro) 증설 검토.**
   `/api/v2/posts?channel=lens&limit=1000` 응답이 4MB대까지 커졌고
   앞으로도 계속 커진다(발행량 누적). CPU는 여유 있으나 간헐적 502가
   이 요청에서만 반복 확인됨 — 메모리 또는 uvicorn 동시 처리 설정이
   병목일 가능성. t3.small 이상으로 올리거나, uvicorn worker 수
   조정을 먼저 검토 요청.
2. **이 인스턴스에 애플리케이션 로그 수집(CloudWatch Logs 또는 동급)
   연동 권장** — 이번처럼 502의 서버 쪽 원인(메모리 부족/워커 큐잉/DB
   커넥션 풀 등)을 특정하려면 지금은 클라이언트 쪽 "502를 받았다"
   까지만 보이고 서버 내부는 전혀 안 보인다.
3. (낮은 우선순위) `GET /api/v2/posts?channel=lens` 응답 크기 자체를
   줄이는 근본 작업도 고려 가능 — 지금은 `limit=1000`건을 통째로
   내려받는데, 홈 히어로가 실제 쓰는 건 상위 몇 건뿐이다. 다만 이건
   프론트·백엔드 양쪽 변경이 필요해 별도 작업으로 분리.
