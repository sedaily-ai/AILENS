# 2026-10-03 홈 로딩 성능 — 계층별 점검과 변경(배포 대기 포함)

작성: Claude Code (요청: 문영광, "사이트가 느리다, 처음 들어가면 1초쯤 이전 화면이 보이다 바뀐다")

## 문제발견
- 사용자 문의: 첫 진입 시 이전 화면이 잠깐 보이다가 최신으로 바뀐다. 바로 보여야 한다.
- 실측(헤드리스 Chromium): 홈 CLS 데스크톱 0.039·모바일 0.045, 1.5~1.9초 사이 본문 전체가 한 번 아래로 밀림. 원인=공지 배너(`AnnouncementBar`)가 서버 HTML에는 없고 브라우저 로딩 후(localStorage 확인) 나타남. → 2026-10-03 배너 제거 배포(CLS 0.0001/0).

## 계층별 측정(홈, 2026-10-03)

## 변경(로컬 완료, 배포 대기)
1. `app/page.tsx`: `fetchLensPosts()`→`fetchLensPosts(100)` — 홈 HTML에서 약 1.5MB 감소 예상, 서버 호출 캐시 키가 클라이언트 조회(lens:100)와 같아짐.
2. `WebtoonPreviewSection`·`VideoPreviewSection`·`AudioPreviewSection`: 서버가 준 초기 데이터가 있으면 마운트 후 전체 목록 재요청 생략(앞 4건만 그리는 섹션).
3. `LoginButton` 로딩 자리 크기를 실제 버튼(82×32)과 같게.
4. `next.config.ts`: `expireTime: 600` — ISR 페이지의 stale-while-revalidate를 약 1년에서 300초(600−홈 revalidate 300)로. 낡은 HTML을 먼저 보여 주는 경로를 10분 이내로 제한.
5. `infrastructure/cloudfront-csp-analytics.sh`(적용 안 함): CSP에 Clarity·GA4 보조 도메인 추가.

## 결정 대기(사용자 확인 필요)
- CloudFront 가격 등급 `PriceClass_100`→`PriceClass_200`(아시아 엣지 포함). 효과가 가장 클 것으로 보이나 한국 트래픽 단가가 소폭 오른다.
- ISR 만료 후 낡은 HTML 노출 줄이기(`expireTime`/SWR 조정).
- nginx gzip(EC2), Noto Serif KR 굵기 정리.

## 가설(반증 가능)
- 가격 등급을 올리면 한국 방문자의 홈 TTFB가 0.45초대에서 0.1초대로 줄 것이다. 반증: 변경 후에도 `x-amz-cf-pop`이 ICN이 아니거나 TTFB 변화가 50ms 미만.
- 홈 HTML 축소(2.7MB→1MB 안팎)와 재요청 제거로 느린 모바일 LCP가 4.8초에서 3초대로 줄 것이다. 반증: 배포 후 같은 프로파일에서 LCP 변화가 0.5초 미만.

## 봇·검색엔진(SEO/GEO/AEO) 영향 점검 — 2026-10-03(변경 전 기준선)
- Googlebot·GPTBot·ClaudeBot·PerplexityBot·bingbot·OAI-SearchBot UA로 홈 요청: 모두 200, 같은 HTML(2.74MB 압축 전), 차단 없음.
- `robots.txt`·`llms.txt`·`sitemap.xml`(1.97MB)·`rss.xml`·`news-sitemap.xml` 모두 200. 홈에 JSON-LD 2블록·canonical·h1 1개.
- 홈의 기사 링크는 앵커 7개(`/news/YYYY/MM/DD/...` 정본 경로) — 봇의 기사 발견은 사이트맵·RSS가 주 경로. 이번 변경(최신 100건, 재요청 생략, expireTime, CDN 가격 등급)은 봇이 받는 HTML의 본문·링크·구조화 데이터를 바꾸지 않는다.
- 배포 후 같은 점검을 다시 돌려 변화 없음을 확인할 것.

가설 판정: ① 가격 등급 → TTFB 0.45→0.04~0.08초(채택, 반증 조건 미충족). ② HTML 축소·재요청 제거 → LCP 4.8→3.6초(목표 3초대 근접, 미달). 
남은 큰 항목: 브라우저가 홈 열자마자 받는 `lens limit=100`(297KB)·`letters limit=50`(270KB) 재조회, Next가 미리 받는 `/listen` RSC 508KB, GA 스크립트 535KB, Noto Serif KR CSS 466KB·폰트 1MB.

## 2차 변경(같은 날, 배포 완료) — 재요청·미리 받기·폰트
- `LensPreviewSection`: SSR이 준 최신 100건이 있으면 브라우저 재조회 생략(이 섹션은 bullets를 읽지 않음). `WordsPreviewSection`: 서버가 준 키워드가 있으면 레터 50건 재조회 생략(CMS 퀴즈만 조회). 홈의 `/listen` 링크 3곳 `prefetch={false}`(홈을 열 때 /listen 데이터 약 600KB를 미리 받던 것 제거, 링크·크롤링은 그대로).
- 폰트: Noto Serif KR 요청을 정적 5굵기(`wght@400;500;600;700;900`)에서 가변 범위(`wght@400..900`)로 — CSS 477KB→96KB, 폰트 파일 수(124)는 같고 400~900 모든 굵기가 그대로 쓰임(화면 모양 변화 없음).
- 결과(느린 모바일 1.6Mbps·CPU 4x): FCP 3.3s→1.6s, LCP 4.8s→2.7s, 스타일시트 582KB→209KB, 콘솔 오류 0, CLS 0.0001/0.
- 남은 것: `letters?limit=50` 270KB 재조회가 아직 남음(다른 소비자 확인 필요), `s3-articles` 119KB(외부 API), GA 스크립트 535KB.

## 3차 변경(같은 날, 배포 완료) — 남은 재조회 정리
- `HotLettersRail`: 서버가 준 인기 글 5건이 있으면 브라우저에서 `fetchFollowingLetters`(레터 50건 약 270KB)로 순위를 다시 계산하지 않음.
- `WordsPreviewSection`: 서버가 키워드를 계산해 줬으면(빈 배열 포함) 레터 50건 재조회 생략. 확인: 레터 목록 50건 중 `keywords`가 있는 글 0건(홈 단어 섹션은 렌더되지 않음) — 이 270KB 조회는 서버·브라우저 양쪽에서 결과 없이 받기만 하던 것이었다.
- 결과(느린 모바일): 브라우저 JSON 재조회 합 1.7MB→0.35MB(남은 것: 외부 `s3-articles` 116KB, `home_player` 33KB), FCP 1.6s·LCP 2.7s 유지, 총 전송 8.6MB→약 5.7MB(Script 2.3MB·Font 1.0MB·Document 0.5MB가 큰 항목), CLS 0.0001/0, 콘솔 오류 0, 봇 UA 200.
- 남은 후보: GA 스크립트 535KB(구글 제공, 지연 로드 시점 조정 가능), Pretendard/명조 폰트 파일 1MB(서브셋 조각 34요청), `s3-articles`(뉴스 타임머신 섹션, 화면 아래라 보일 때 로드하도록 지연 가능).
