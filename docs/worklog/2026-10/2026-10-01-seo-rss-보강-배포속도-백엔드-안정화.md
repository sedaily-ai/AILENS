## 한 것

### 1. 검색·AI 노출 보강(프론트, 배포 완료)
- 뉴스 사이트맵 `publication_date`·기사 상세 `datePublished`/`uploadDate`/OG 시각을
  `published_at`(초 단위)로, 사이트맵 `lastmod`를 실제 수정·발행 시각으로 변경.
- `robots.txt`에 `Claude-SearchBot`·`Claude-User` 명시. Bing 인증(`msvalidate.01` 메타 +
  `/BingSiteAuth.xml`). Bing Webmaster에 사이트맵 3종 제출(사용자 수행).
- 영상·웹툰 상세에 서버 렌더 텍스트 섹션 "이 이슈, 한눈에 보기"(같은 슬러그 lens 글의 요약·
  30초 핵심·용어·영상 대본·원문 링크). 초기 HTML 가시 텍스트 웹툰 1,177→1,729자,
  영상 571→1,289자. 영상 JSON-LD에 `transcript` 추가.
- RSS: `description`=30초 핵심 앞 2항목, `lastBuildDate`=최신 글 시각, 본문 하단 링크,
  `dc:source`(서울경제 원문), `<image>`·`<ttl>`, 카테고리별 피드 7종(`/{slug}/rss.xml`)과
  자동 발견 `<link>`. 구현은 `shared/lib/rss/buildRssFeed.ts` 하나로 통합.
- 공식 문서 리서치 결과: priority/changefreq는 Google이 무시, llms.txt는 공식 지원·효과
  근거 없음. 미확인 항목(Google News의 AI 생성 콘텐츠 정책, Publisher Center, 네이버
  서치어드바이저)은 사용자 확인 필요.

### 2. 레터 "30초 핵심" 오염 정리
- 원인: 10/1부터 레터 출력이 "불릿 → 도입부 문단 → ##본문" 순서로 바뀌어, 불릿 파서가 도입부를
  줄바꿈 이어쓰기로 오인해 마지막 불릿에 붙였고, `자료:` 출처 줄도 5번째 불릿으로 샜다.
  10/1 발행 36/36건 오염(이전 날짜는 정상). 파이프라인 수정(12:40 KST)은 불완전했다.
- 파서 수정(`_ends_sentence`: 직전 불릿이 문장 종결이면 이어쓰기 아님, `자료` 불릿 제외) 후
  파이프라인 배포(리비전 92). 36건 재백필(마지막 항목 첫 문장만, 출처 줄 제거) — 전부 검증
  통과(타 포맷·나머지 필드 불변), 백업은 세션 스크래치패드.
- 남은 것: 9/15·9/26·9/28에 같은 유형 각 1건(별개 사유). 도입부 문단은 `parse_letters`가
  본문에서도 버려 현재 어디에도 노출되지 않음(기획 판단 필요).

### 3. 프론트 배포 속도
- 측정: 이미지 빌드 65초, ECS 롤링 2분 37초(새 코드 서비스 시작은 ~36초). 병목은 롤링 대기.
- Dockerfile에 BuildKit 캐시 마운트(npm·`.next/cache`), 빌드 57초로 ~12% 단축(효과 작음).
- `deploy.sh`: 단계별 소요 시간 출력, `--no-wait` 옵션 추가.
- 인프라(CLI 직접 변경, 코드엔 없음): 대상 그룹 `sedaily-lens-frontend-tg` 헬스체크
  30초×5회 → 10초×2회, ECS 서비스 서킷 브레이커 `enable=true, rollback=true`.
  (`aws elbv2 modify-target-group --health-check-interval-seconds 10 --healthy-threshold-count 2`,
  `aws ecs update-service --deployment-configuration deploymentCircuitBreaker={enable=true,rollback=true},...`)

### 4. 백엔드(lens-cms-api EC2, t3.micro) 안정화 1차
진단(SSM 읽기 전용):
- 메모리 913MB 중 가용 ~40MB·스왑 0, uvicorn 워커 2개가 315/252MB. 과거 OOM 종료는
  nginx·systemd-resolve뿐(파이썬 워커 OOM 기록은 없음).
- **DB 커넥션 풀 고갈**: `db.py`의 `ThreadedConnectionPool` 최대 10(워커당). 동시 요청이 10을
  넘으면 대기하지 않고 즉시 `PoolError("connection pool exhausted")` → 500. 오늘 233회,
  03시(UTC) 174회 집중. 500 176건(상세 조회 112, admin 29)과 일치.
- 워커 프로세스가 로그 사유 없이 죽었다 재생성(`Child process died`) 9/30·10/1 각 23회.
  원인은 미확정(로그 부족).
- 502 60건은 01~03시(UTC)에 집중, 배포 재시작 시각과 무관.
- `/api/v2/posts?channel=lens&limit=1000`이 오늘 ~1,946회·응답 ~2.9MB(비압축). nginx가
  임시 파일로 버퍼링.
적용(무중단):
- nginx gzip(`/etc/nginx/conf.d/00-gzip.conf`): 같은 응답 2,953,192→826,019바이트(-72%).
  변경 전 `conf.d`는 서버 `/root/nginx_conf.d.bak.*`에 백업.
- 스왑 2GB(`/swapfile`, fstab 등록, `vm.swappiness=10`).
- CloudWatch 에이전트 설치(원래 없었음), 설정 `service/lens-cms-api/cloudwatch-agent.json`
  (SSM `/ailens/monitoring/lens-cms-api-agent`): 메모리·스왑·디스크 지표와 nginx
  access/error·앱 error/out 로그 4종(`/lens-cms-api/*`, 보존 30일, 태그 Service=lens·
  Workload=backend). 로그·지표 수신 확인.

## 결정
- 프론트를 Fargate에 둔 이유는 규모가 아니라 9/4 EC2+PM2 배포 실패 3종(배포 신뢰성). 호스팅
  재검토(Fargate+ALB 유지 vs 관리형)는 비용 실측 후 별도 결정 — Cost Explorer가 SCP로
  막혀 있어 ALB·Fargate 월비용을 직접 못 봄.
- 인스턴스 증설(t3.micro→t3.small 이상)은 중지·시작이 필요해 클라우드 담당자 판단으로 둔다.
- 교과서적 CI/CD는 "커밋 전 배포" 방침과 충돌하므로 출시 후 도입.
