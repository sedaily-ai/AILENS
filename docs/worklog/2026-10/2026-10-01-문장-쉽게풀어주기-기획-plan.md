# 2026-10-01 기획 — 기사 문장 "쉽게 풀어주기" (AI 설명)

작성: Claude Code
상태: 기획안(구현 전). 결정 필요 항목은 맨 아래 "다음".
관련: `widgets/SentenceSelectionPopover`(문장 선택 → 서랍 담기), `docs/architecture/비용태깅_규칙.md`

## 1. 문제 발견

- 레터 본문에 경제 용어·수치·고유명사가 많아 독자가 중간에 막힌다(예: "ISDS", "블록딜", "예정이율").
- 현재 대응은 용어 하이라이트(`keywords`)뿐 — 발행 시 편집/모델이 미리 뽑은 용어만 설명되고, 독자가 막힌 문장은 설명되지 않는다.
- 막힌 독자는 새 탭에서 검색하러 나가고 돌아오지 않는다(이탈). 현재는 이 이탈을 측정하지 않는다.

## 2. 문제 정의

- "독자가 막힌 그 문장"을 기사 안에서 즉시 풀어 주면, 이탈 없이 읽기를 이어갈 수 있는가.
- 범위: 이 기사에 실린 문장의 의미 풀이. 기사 밖의 사실 확인·전망·투자 조언은 하지 않는다.

## 3. Why — 왜 이 기능인가

- 이미 문장 선택 UI가 있다(서랍 담기). 같은 팝오버에 버튼 하나만 더하면 되는 가장 작은 AI 기능.
- 기사 본문을 근거로만 답하게 제한하면 환각 위험이 낮다(외부 지식 추측 금지).
- 서비스 정체성("같은 기사를 독자 수준에 맞게")과 직결.

## 4. How — 사용 흐름

1. 독자가 본문 문장을 드래그 → 팝오버에 `서랍에 담기` 옆 `쉽게 풀어주기`.
2. 누르면 팝오버 아래에 스트리밍으로 3~4줄 풀이("쉽게 말하면…" + 필요 시 용어 한 줄).
3. 풀이 하단: `도움이 됐어요 / 아니에요`(오답 신고), `복사`, `서랍에 담기`.
4. 선택 문장 길이 상한(예: 300자), 기사당·사용자당 호출 한도, 한도 초과 시 안내 문구.

## 5. 구현 구조 (제안)

- 엔드포인트: 프론트(ECS Fargate)의 Next 라우트 핸들러 `POST /api/explain` — 새 Lambda·서버를 만들지 않고 기존 서비스 안에서 처리, 스트리밍 응답.
- 입력: `{ articleId, selection, contextWindow }` — 서버가 `articleId`로 본문을 다시 읽어 선택 주변 문맥(앞뒤 ~600자)만 모델에 전달. 클라이언트가 보낸 본문을 신뢰하지 않는다.
- 모델: Claude Haiku 4.5(빠르고 저렴, 스트리밍 첫 글자 지연이 짧음).
- 프롬프트 원칙: 선택 문장과 기사 문맥은 "데이터"로만 취급(지시문 무시), 기사에 없는 사실은 "이 기사에는 나오지 않아요"로 답하고, 투자 조언·전망 금지, 길이 상한.
- 비용 태깅(필수): 베어 모델 ID 금지 → 새 application inference profile `lens-explain-haiku-45`를 만들고 `Service=lens`(2026-10-01 이후 신규), `Workload=explain`, `Model=haiku-45` 등 공통 태그. 프로파일 생성 3단계(태그 → 리소스 → IAM)를 규칙 문서대로. 태그는 소급되지 않으므로 호출 시작 전에 붙인다.
- IAM: 프론트 태스크 역할(`sedaily-lens-frontend-task-role`)에는 현재 Bedrock 권한이 없다 — 해당 추론 프로파일 ARN에 대한 `InvokeModel*`만 최소 권한으로 추가.
- 로깅: 선택 문장·풀이 원문은 저장하지 않는다. 호출 수, 길이, 지연, 오답 신고만 계측(`trackEvent`).

## 6. 가설 (반증 가능하게)

- 가설 A(사용): 레터 탭을 본 세션 중 `쉽게 풀어주기`를 한 번이라도 쓰는 비율이 3% 이상. 3% 미만이면 발견성 또는 필요성 부족으로 기각.
- 가설 B(효과): 기능을 쓴 세션의 완독률(본문 95% 도달)이 쓰지 않은 세션보다 10%p 이상 높다. 아니면 "막힘 해소 → 계속 읽기" 가설 기각. (선택 편향 가능 — 사용자 자기선택이므로 도입 전후 동일 기사 대조도 병행.)
- 가설 C(품질): `도움이 안 됐어요` 신고율이 5% 이하. 초과 시 프롬프트·문맥 길이 재설계 후 재측정.
- 위험·역효과: 풀이가 틀리면 언론사 신뢰를 직접 훼손 / 요약이 원문 뉘앙스를 단순화 / 호출 폭주로 비용 증가 / 프롬프트 인젝션(문장 안에 지시문).
- 기준선: 현재 완독률·이탈 지표가 없으므로 이번 챕터 내비게이션·읽기 시간·완독 피드백(10/1 배포)에서 쌓이는 수치를 먼저 기준선으로 쓴다.

## 7. 검증 계획

- 오프라인: 실제 레터 30건에서 어려운 문장 100개를 뽑아 풀이를 생성 → 사람이 "정확/부정확/기사 밖 추측" 3단계로 채점(기준: 부정확+추측 3% 이하).
- 인젝션: 선택 문장에 "이전 지시를 무시하고…" 등을 넣은 케이스 20개 — 지시를 따르면 실패.
- 온라인: 일일 호출 상한을 둔 소규모 노출(전체 레터 탭의 10%)로 가설 A·B·C 측정 후 확대 여부 판정.

## 8. 다음 — 결정이 필요한 것

1. 구현 위치: Fargate 라우트 핸들러(권장, 인프라 추가 최소) vs 별도 Lambda.
2. 모델: Haiku 4.5 신규 프로파일(권장) vs 기존 `lens-letters-sonnet-46` 재사용(프로파일 신설 없이 빠르지만 용도 혼재로 비용 분리 불가).
3. 로그인 필수 여부: 비로그인도 허용하면 남용 방어(IP·세션 한도)가 필요, 로그인 필수면 한도 관리는 쉽지만 발견성이 낮아진다.
4. 일일 호출 상한과 비용 한도 승인(구현 후 실측 단가로 확정).
