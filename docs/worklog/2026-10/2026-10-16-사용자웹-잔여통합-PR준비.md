# 사용자 웹 통합·반영 상태

## 배경

- 사용자 웹 잔여 구현은 [PR #120](https://github.com/sedaily-ai/AILENS/pull/120), 과거 기록 정리는 [PR #121](https://github.com/sedaily-ai/AILENS/pull/121)로 병합됐다. 이번 작업 시작 시 로컬 `main`과 `origin/main`은 `01fe75d14fe117ce03ff6bfe290240752d286ec5`이다.
- 사용자가 CMS API → 계정 API → 프론트 배포 완료를 알렸다. 초기 검증은 프론트 배포 스크립트의 검사 경로 수정과 운영 사용자 웹 재검증으로 제한했다. 이후 남은 두 항목을 마무리하라는 요청에 따라 계정 조회 복구와 관련 커밋·push·PR 생성까지 범위를 확장했다. 관리자 웹·기사 정정·설정 및 저장 항목 변경·스크린샷·병합·배포는 제외한다. 기존에 허용한 자동 이용 기록만 발생할 수 있다.

## 한 것

- PR #120에 포함됐던 과거 기록 14개를 현재 로컬 작업 트리에서 삭제했다. 별도 보관본을 새로 만들지 않았다. 기존 Git 이력은 재작성하지 않는다.
- 이 통합 기록에 현재 반영 상태와 필요한 후속 조건을 남겼다. 삭제 문서를 참조하던 배포 안내와 P01·P02 기록은 유효한 참조로 정리했다. 새 검증 보고서 파일을 추가하지 않는다.
- PR #118·#119의 원래 작업 기록은 유지한다. PR #119 배포 뒤 운영에서 내 서랍 조회·영상 29초 표시·나의 LENS 네 탭·미디어 전환을 관찰했다. 새 로그인·운영 장애 강제 주입·컨테이너 SHA 대조까지 검증한 것은 아니다.

## 배포 검사 경로 수정·운영 재검증

- `service/frontend/deploy.sh`는 시작 시 프론트 디렉터리로 이동한 뒤 상대 `$0`의 디렉터리를 다시 붙여 루트에서 실행하면 검사 경로가 중복됐다. 스모크 호출 한 줄을 기존 절대 경로 변수 `$SCRIPT_DIR/scripts/smoke.sh`로 바꿨다. 배포 절차와 실패 시 종료 동작은 유지한다.
- `bash -n service/frontend/deploy.sh` 및 `npx tsc --noEmit --project service/frontend/tsconfig.json` 통과. AWS·Docker 실행 없이 실제 경로 초기화·검사 호출 구간을 임시 스텁으로 시험해 기존 루트 실행 실패를 재현하고, 수정 후 루트·프론트·외부 디렉터리에서의 절대 경로 실행 성공 및 검사 실패 시 종료 코드 1 유지를 확인했다. 임시 시험 파일은 삭제했다.
- 운영 API URL을 지정한 `npm run build --workspace service/frontend` 종료 코드 0. 정적 생성 중 `ailens.sedaily.ai`의 DNS 조회가 `ENOTFOUND`로 실패해 기존 대체 처리가 실행됐다. 실제 운영 데이터까지 정상 수신한 빌드 검증을 뜻하지 않는다.
- 운영 검증은 `https://ailens.sedaily.ai`의 기존 로그인 세션에서 진행했다. 새 로그인·배포 컨테이너 SHA 대조·장애 강제 주입은 실행하지 않았다.

- 잔여 확인: 미디어 확인 후 나의 LENS 재진입 시 팔로우와 관심 설정에 `Failed to fetch` 표시. 관심 설정은 전용 재조회로 복구됐으나 팔로우는 두 차례 재조회 후에도 실패 문구와 `팔로우 다시 불러오기`가 남았다. 다른 기록·설정 화면은 로딩됐다. 네트워크·서비스·브라우저 중 원인은 확정하지 않았으며 관련 코드는 수정하지 않았다.
- 문구 개선 후보: 단어장은 기사 용어도 제공하지만 소개가 “레터에 나온 경제 용어”로만 되어 있다. ‘레터’가 전체 콘텐츠를 뜻하는지 판단이 필요하므로 기능 오류로 단정하거나 수정하지 않았다.
- 별도 검증 보고서·스크린샷은 만들지 않고 이 기록을 갱신했다. 관리자 웹과 기사 정정은 조회·변경하지 않았다.

## 계정 조회 복구 마무리

- `accountApi.ts`의 팔로우·관심 설정·저장 레터 조회는 `authFetch`를 직접 호출해 기존 `authReadFetch`의 제한된 복구에서 빠져 있었다. 계정 GET만 기존 복구 함수를 경유하도록 연결했다. 연결 오류·502·503·504는 한 번 재조회하고, 지속 연결 실패는 한국어 안내로 끝낸다. 인증 오류·403·429 및 PUT·DELETE·POST는 재시도하지 않는다. 계정·저장값·API 계약·인증 공급자는 변경하지 않는다.
- 관련 테스트를 추가해 수정 전 연결·게이트웨이 실패와 영문 오류 노출을 재현했다. 수정 후 전체 `npm test --workspace service/frontend` 34개 파일·172개 테스트, `npm run lint --workspace service/frontend`, `npx tsc --noEmit --project service/frontend/tsconfig.json`, `bash -n service/frontend/deploy.sh` 통과. 운영 공개 API URL을 지정한 `npm run build --workspace service/frontend`도 이번에는 DNS 오류 없이 통과했다.
- 내부 브라우저의 임시 로컬 화면에서 실제 `useFollowedEditors`·`useInterests`·계정 어댑터·조회 복구 함수를 실행했다. 인증 사용자와 전송 경계만 모의 처리해 첫 연결 실패·첫 503 후 각각 GET 2회 이내 정상 데이터 복구, 지속 실패 시 GET 2회 종료·한국어 안내, 연결 복구 후 수동 조회로 기존 팔로우·관심·5분 설정 복원을 확인했다. 임시 화면은 제품에 추가하지 않았고 검증 후 서버·탭·파일을 정리했다.
- 운영 재확인에서는 기존 로그인 세션의 홈·팔로우 조회가 정상 로딩되어 앞선 실패가 재현되지 않았다. 토큰 없는 GET은 401·private/no-store·정상 Origin 헤더, OPTIONS는 GET·Authorization 허용 응답을 확인했다. 이 결과로 과거 연결 실패의 네트워크 원인을 확정하거나 미배포 수정의 운영 적용을 선언하지 않는다.
- 기본 검증으로 전체 diff와 모든 계정 조회·저장 호출자를 자체 검토했다. 인증·저장 경로 자체를 바꾸지 않는 프론트 조회 복구 연결이므로 DB·관리자·기사 정정·독립 에이전트 검토는 범위에서 제외했다. 변경은 배포 스크립트·계정 어댑터·관련 테스트·이 작업 기록 4개 파일뿐이다.
- 사용자 요청에 따라 `fix/account-read-recovery`에서 커밋·push·PR 생성까지 진행한다. 새 과거 검증 보고서는 추가하지 않으며 보존 브랜치 6개 커밋은 그대로 둔다. 병합·배포·운영 데이터 직접 수정은 실행하지 않는다.

## 결정

- 관리자 웹과 다음 다이어트 후보는 제외한다. 기록 정리만으로 배포나 기사 정정을 실행하지 않는다.
- 기사 정정 대상은 `20101714`, `20101638`, `20101715`, `20101767`, `20099924`의 13개 필드다. 최신 운영 값 재대조, 백업 내구성·적용 영수증·조건부 복구·동시 편집 보호가 준비되지 않아 실제 적용을 보류한다. 기본 읽기 전용 도구와 수동 적용 옵션의 존재가 운영 실행 승인이나 준비 완료를 뜻하지 않는다.
- 이번 통합 변경에는 새 DB DDL·의존성·환경변수 계약이 없다. 기사 정정 도구는 CMS 배포로 자동 실행되지 않는다.

## 다음

1. 후속 PR 검토·병합 후 프론트를 배포하고 운영 팔로우·관심 설정 조회를 재확인한다. 계정 조회 코드가 추가되어 프론트 배포가 필요하며 백엔드 재배포는 필요 없다. 지속 연결 실패가 재현되면 요청 응답·네트워크 원인은 별도로 확인한다.
2. 배포 스크립트 경로 수정 자체는 다음 로컬 배포 실행부터 적용된다. 이번 요청의 완료 범위는 관련 4개 파일의 커밋·push·PR 생성까지다.
3. 단어장 소개 문구의 범위를 판단한다. 다음 다이어트 후보는 계속 보류한다.
4. 기사 5건의 운영 정정은 별도 준비·승인 대상으로 남긴다. 다음 다이어트 후보는 보류한다.
