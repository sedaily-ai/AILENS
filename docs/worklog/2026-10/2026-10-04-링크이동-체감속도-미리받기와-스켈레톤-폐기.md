## 사이클 1 — 이동 즉시성 진단과 스켈레톤 도입

### 문제 발견
- 사용자 요구: "클릭하면 실시간으로, 딜레이 없이 이동" — 출처: 사용자 요구(수치 기준 없음)
- 벤치 대상 `msp-web-ensedaily`(Spring Boot + Thymeleaf SSR) 분석: CSS 1개 약 75KB + 지연 로딩 소형 JS, 이미지 크기별 최적화·`loading="lazy"`·webp, 이동 가속 기법 없음 → 빠른 이유는 구조 단순성
- 실측(우리 사이트, 느린 모바일 가정: 지연 150ms · 1.6Mbps):
  - 홈 → 기사, 첫 3개 링크: 약 160ms(이미 미리 받음)
  - 4번째 이후 링크(미리 받기 완료 전 클릭): 새 제목 표시까지 약 2.2~2.5초, 그동안 화면 변화 0
- 기사 1건 이동 데이터: 압축 전 약 80~100KB

### 문제 정의
- 미리 받기 범위(앞 3개)를 벗어난 링크에서 2초 이상 무반응 구간 발생

### Why
- 사용자 지시 우선순위 1순위가 "즉각 반응"
- 미조치 시 손실: 홈 하단·목록에서 이동 시 무반응 체감 → 이탈

### How
- 1차 선택: 이동 즉시 뼈대 화면(`loading.tsx` + `PageSkeleton`) — 무반응 구간을 시각 피드백으로 메움
- 병행: 이웃(이전/다음) 기사 한가할 때 미리 받기(`ArticleNeighborNav`) — 스와이프·화살표 이동 지연 제거

### 가설 / 검증 (1차)
- 가설: 뼈대 화면이 체감 대기를 줄임 — 1차 측정은 뼈대 유무를 같은 조건에서 비교하지 않음(운영 vs 로컬 비교였음)
- 판정: 보류 → 사이클 2에서 재검증

## 사이클 2 — 사용자 반론 → A/B 재측정 → 스켈레톤 폐기

### 문제 발견
- 사용자 반론: "스켈레톤 자체가 로딩 속도를 저해하는 거 아님?"

### 문제 정의
- 1차 효과 주장의 비교 조건 불일치(뼈대 유무 외 변수 혼입) → 같은 코드에서 뼈대만 제거한 A/B 필요

### 검증
- 조건: 운영 빌드(webpack), 지연 150ms · 1.6Mbps, 3라운드, 변수 1개(뼈대 유무)
- 결과(미리 받지 못한 링크 클릭 → 실제 제목 표시):
  - 뼈대 있음 약 600~730ms
  - 뼈대 없음 약 400~620ms(대부분 150~250ms 빠름)
  - 미리 받은 링크(첫 3개): 두 경우 모두 약 140~180ms(차이 없음)
- 해석: 뼈대가 먼저 보이는 대신 실제 내용이 늦게 도착 — 순이익 없음
- 근거 보강(검색): Next.js 16.3 Instant Navigations는 경로 껍데기를 미리 받는 구조 — 미리 받기 없는 `loading.tsx` 단독 도입은 이득 없음

### 판정
- 폐기 — `PageSkeleton.tsx` · `(economy)/loading.tsx` · `(content)/loading.tsx` 3개 삭제
- 정정: 1차 보고("0.3초에 뼈대 표시")는 비교 조건이 달라 근거 불충분이었음을 명시
- 유지: 이웃 기사 미리 받기(측정 대상 아님)

## 사이클 3 — 링크 미리 받기 보강(LinkPrefetcher)

### 문제 정의
- 무반응 구간의 원인 = 미리 받기 범위 부족 → 범위 확대가 정공법

### How
- 구현: 손가락 닿음(`pointerdown`·`touchstart`)·마우스 80ms 호버 즉시 받기 + 로드 후 한가할 때 앞쪽 기사 링크 최대 8개를 0.25초 간격으로 받기
- 안전장치: 데이터 절약 모드·2G·3G 비활성, 동일 링크 1회 요청, 페이지 이동마다 재계산
- 버린 대안: Speculation Rules(크롬 prerender) — Next 클라이언트 이동은 라우터가 처리해 적용 범위 제한 / Next 16.3 업그레이드 — 메이저 설정 변경·위험 평가 필요(별도 과제)
- 비용: 홈 방문당 기사 8건 추가 수신, 압축 전송 기준 약 150~250KB 추정(전송량 실측 없음)

### 가설 / 검증
- 가설: 홈 체류 4.5초 이상이면 앞 8개 링크가 즉시 열림. 반증: 8개 중 다수가 500ms 이상
- 조건: 운영 빌드, 지연 150ms · 1.6Mbps, 홈에서 10개 링크 순차 클릭
- 결과(체류 4.5초): 보강 후 앞 8개 약 145~180ms(9번째만 약 550ms) / 보강 전 4~5번째 약 600~630ms
- 결과(체류 1.5초): 보강 후 약 150~260ms 개선되나 일부 370~530ms / 보강 전 약 420~590ms
- 가드레일: 어떤 경우에도 실제 내용 표시 지연 없음(스켈레톤 때와 상이)
