# 02. 인프라 정리와 캐시

결론: 인프라 비용은 월 약 23만원(7%)이라 절감 여지는 작고, 안정성 보강(월 +약 3만원)과 불필요 리소스 정리, 캐시 도입이 핵심. 캐시는 오리진 헤더·캐시 정책·무효화 연동 3개 선행이 필수.

## 1. 현황 (요약)

| 구성요소 | 스펙 | 한계 신호 [측정] |
|---|---|---|
| 프론트 | Fargate ARM64 0.5 vCPU / 1 GiB × 1, 오토스케일 없음 | CPU 일 최대 100%, 5xx 6일(합 1,121건) |
| API 서버 | EC2 t3.micro, 메모리 1 GiB | 메모리 최대 88.9%, 스왑 사용 |
| DB | Aurora Serverless v2 0.5–2 ACU, 단일 AZ | 시간별 최대 ACU 2.0 상시, CPU 100% |
| 알람 | 3개 (프론트 알람 없음) | — |

## 3. 삭제 계획 (조사 기준)

### 3.1 분류

| 분류 | 대상 | 조건 |
|---|---|---|
| A 삭제 가능(참조 없음) | Lambda `v2-article` · `external-content` · `voice-stt-url`, DynamoDB `podcast` · `engagement` · `external-content` | 백업 후 삭제 |
| B 호출 코드 제거 선행 | `question`(홈 FeedPage가 마운트마다 호출) · `voice-tts` · `voice-stt-presign` · `ws-connect` · `ws-message`(AI 검색 오버레이) · DynamoDB `ws-connections` · `quiz-questions`(admin 퀴즈 CRUD) · `cms-posts` · `daily-letters`(코드 이름 잔존) | 프론트·admin 코드 정리 → 배포 → 한 주기 관찰 → 삭제 |
| C 보존 | `v2-subscribe`(구독·법적 수신거부) · `admin-prompts`(파이프라인 읽음) · `newsletter-subscribers` · API Gateway 3개 · S3 `ailens-ssr-releases`(API 배포 사용) | 삭제 금지 |
| 후순위 | S3 `sedaily-mbti-frontend-dev` · 옛 SSR 디스크 알람 2개 | EC2 롤백 기간 종료 후 |

호출만 있고 코드 참조는 없는 `v2-quiz`(14일 1,892회)는 호출처 확인 후 삭제.

### 3.2 결정 필요 (2건)

1. 질문 기능: UI·호출 코드(`FeedPage.tsx`, `questionApi.ts`) 제거 여부
2. AI 검색 오버레이(챗봇·음성): 호출 0건이 미사용인지 연결 끊김인지 미확인 → 운영 여부 결정 후 정리

### 3.3 절차

| 단계 | 작업 |
|---|---|
| 1 | Lambda `get-function` 설정 JSON + 코드 zip 백업, DynamoDB 온디맨드 백업 (`service/backend/infrastructure/decommission-2026-07-30/` 형식 참고) |
| 2 | API Gateway 라우트·통합 삭제 |
| 3 | Lambda 삭제 |
| 4 | DynamoDB 삭제 |
| 5 | `deploy.sh` · `lambda_handlers.txt` · `config/constants.py` 정리 |

롤백: Lambda는 백업 JSON·zip으로 재생성(라우트·권한 재설정 포함), DynamoDB는 백업 복원, 프론트는 git revert 후 재배포.

주의: 호출 0건인 `v2-subscribe` · `ws-*`는 "끊어진 상태일 수 있다"는 기록이 있음. 삭제가 고장을 덮을 수 있어 운영 확인 선행.

## 4. 캐시 가이드

### 4.1 실측 현황 (운영, 2026-10-07)

| 대상 | Cache-Control | CDN | 응답 시간 | 판정 |
|---|---|---|---|---|
| 홈·기사·카테고리·지난 지면 HTML | `s-maxage=300, stale-while-revalidate` | 적중 | 30~50ms | 정상 |
| 이미지 최적화 `/_next/image` | `max-age=86400` | 적중 | 약 47ms | 정상 |
| 정적 JS | `max-age=31536000, immutable` | 적중 | 약 39ms | 정상 |
| RSS | — | 적중 | 35ms | 정상 |
| `/start` | `s-maxage=31536000` (1년) | 적중 | 40ms | 문구 변경 시 배포(전체 무효화) 필요 |
| `sitemap.xml` | `max-age=0, must-revalidate` | 미적중 | 약 396ms | 개선 필요 |
| `/api/v2/posts` (목록·단건) | `no-store` | 미적중 | 200~250ms | 항상 EC2 직행 |

API 서버 7일(nginx): `/api/v2/posts` 63,452건·응답 합 28.4GB(요청당 평균 약 448KB).

### 4.2 API 캐시 선행 조건 (3개 모두 필요)

| # | 조건 | 내용 |
|---|---|---|
| 1 | 오리진 헤더 변경 | `lens-cms-api` 공개 GET의 `Cache-Control: no-store`(`main.py:56` 등)를 `public, s-maxage=…` 로 변경 |
| 2 | 쿼리 포함 캐시 정책 신설 | 기존 RSC 정책은 쿼리스트링을 키에서 제외(`QueryStringBehavior: none`). 그대로 쓰면 `channel`·`limit`이 키에서 빠져 응답이 섞임. `channel`·`date`·`limit` 포함 별도 정책 필요 |
| 3 | 발행 시 CloudFront 무효화 | 현재 발행 후 갱신은 Next 데이터 캐시만 무효화(`revalidateTag`). CloudFront 응답은 안 지워지고 무효화 호출도 레포에 없음. 갱신 호출 끝에 `/api/v2/posts*` 무효화 추가 |

지연 누적: ISR 300초 + CDN TTL. SSR이 공개 도메인을 거쳐 API를 받으므로 낡은 응답이 다시 Next 캐시에 채워질 수 있음 → 무효화 연동 또는 SSR→API 내부 경로 분리.

### 4.3 적용 우선순위

| 순위 | 대상 | TTL(제안) | 위험 |
|---|---|---|---|
| 1 | `posts?channel=lens&limit=1000` | 30~60초 | 무효화 연동 필수. 응답 약 3MB로 Next 캐시 한도(2MB) 초과, CDN은 제한 없음 |
| 2 | `posts/{slug}` | 30~60초, 404는 짧게 | slug 변경·리다이렉트 응답 |
| 3 | 웹툰·영상·홈 플레이어 `limit=1000` | 30~60초 | 발행 즉시 반영 요구 확인 |
| 4 | `posts?date=` 과거 날짜 | 길게(시간 단위) | 당일은 짧게 |
| 5 | `sitemap.xml` | 300초 이상 | 낮음 |

호출부 `limit=1000`(lens 목록·`letters/[id]`·sitemap·카테고리 아카이브·`lensArticlePageShared`)은 필요 건수로 줄이거나 서버 페이지네이션 추가.

### 4.4 검증·롤백

| 항목 | 방법 |
|---|---|
| 적용 확인 | `curl -sI`로 `x-cache: Hit from cloudfront`, `age` 증가 확인 (같은 쿼리 2회) |
| 키 분리 확인 | `channel`·`limit`이 다른 두 요청의 응답이 다름을 확인 |
| 발행 반영 | 테스트용 draft 글 발행 후 목록 반영 시간 측정(스테이징 권장) |
| 효과 | nginx 로그 `/api/v2/posts` 요청 수·EC2 NetworkOut·Aurora CPU 비교 |
| 롤백 | 동작의 캐시 정책을 `Managed-CachingDisabled`로 되돌림 |

### 4.5 `/start` 규칙

1년 캐시이므로 온보딩 문구·레이아웃 변경은 서비스 프론트 배포(전체 무효화 포함) 필요. 배포 스크립트가 배포 후 `/*` 무효화를 자동 실행.
