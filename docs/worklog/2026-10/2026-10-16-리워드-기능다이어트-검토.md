# 2026-10-16 리워드 종류와 기능 다이어트 검토

## 배경

사용자가 나의 LENS 주간 배지 화면을 제시하고 추가 리워드 존재 여부와 기능 필요성을 검토하도록 요청했다. 로컬 코드와 제품 문서를 읽어 구현 범위와 제품 판단을 구분했다.

## 한 것

- completion_repo.py와 reading_records_repo.py에서 주간 배지 3종과 하루 최대 1개 스탬프를 확인했다. 월간·연간 추가 보상은 없으며 기간 기록 조회를 제공한다.
- profile.py의 기존 배지 규칙 7종(first_login, reader_10/50/100, streak_7/30, weekly_5)을 확인했다. first_login도 신규 기사 읽기 기록 후 배지 평가 경로에서 판정하므로 로그인 즉시 지급으로 해석하지 않는다.
- ReadingRewards.tsx와 WeeklyStamps.tsx에서 노출 방식과 현금성 포인트·교환 혜택이 없음을 확인했다. 기존 배지 7종을 현재 나의 LENS 화면에 노출하는 연결은 검색에서 확인하지 못했다.
- 운영 배포 상태와 사용자별 실제 획득 데이터는 조회하지 않았다. 코드 및 일부 문서의 구현·배포 시점이 달라 운영 제공을 단정하지 않는다.

## 결정

- 제안: 주간 배지 3종과 목표·미션 표현을 기능 다이어트 대상으로 삼고 읽은 콘텐츠·읽은 날·저장 후 재방문에 필요한 기록은 보존한다. 사용자 확정 결정이나 구현 변경은 아니다.
- 단기에는 UI를 이용 기록 중심으로 축소하고, 후속에 보상 전용 평가·스탬프·배지 쓰기를 완료 기록과 분리해 중단하는 방안을 권고한다. 기존 획득 원장과 읽기 기록은 삭제하지 않는다.
- 효과 검증 없이 리텐션 향상을 사실로 주장하지 않는다. 유지 실험 시 의미 있는 재방문·완료·저장 콘텐츠 재이용을 기준으로 비교한다.

## 다음

- 사용자 방향 확정 후 화면·API 소비·기존 클라이언트 의존성을 확인해 축소한다. 이번 요청에서는 코드 변경·배포를 수행하지 않았다.


## 후속 사용자 승인 및 구현

사용자가 권장안 적용을 승인했고, 날짜에 찍히는 시각적 표시와 주·월·연 기록은 유지한다고 명확히 했다.

- 프론트: 배지 3종·3일 목표·보상 규칙·대기 안내를 제거하고 탭을 이용 기록으로 변경했다. 주간 체크·월간 달력은 스탬프 원장이 아닌 완료 콘텐츠 유무로 표시한다. 홈 요약도 완료한 날을 사용한다. 기존 컴포넌트 이름과 딥링크는 보존했다.
- 서비스 백엔드: dashboard weekly_activity에 실제 주간 이용 기록을 제공하고 weekly_rewards는 unavailable로 보존한다. 기존 profile 배지 7종의 신규 지급을 제거했다.
- CMS: 완료·최초 완료·관심 신호·KST 집계를 유지하고 신규 스탬프/배지 INSERT, 주간 진척 집계, 30분/저장 기반 재열람 보상 판정을 제거했다. 매핑이 없는 콘텐츠도 안정 키로 기록한다.
- 기존 테이블·완료·획득 원장은 보존하며 /rewards는 과거 획득 이력 호환 조회로 남긴다. 새 DB migration·의존성·환경변수는 없다.
- 테스트: 프론트 Vitest 23개, 서비스 백엔드 pytest 57개, 임시 loopback PostgreSQL의 CMS 관련 pytest 45개 통과. CMS 첫 실행에서 기존 추천 버전 기대값이 옛 exact-format-v2여서 1개 실패했고 현재 recent-category-editor-v3로 맞춘 뒤 계정 통합 2개를 재실행해 통과했다. 단순 기대값 수정 외 추천 동작은 바꾸지 않았다.
- ESLint·TypeScript·변경 Python pyflakes·diff 공백 검사 통과. 프론트 build는 sandbox에서 뉴스 DNS 조회 경고를 동반해 완료했고, 정상 네트워크 재실행도 완료했다. 운영 로그인 화면 수동 검증은 수행하지 않았다.
- 배포 준비: 비용 규칙 전체·현재 체크아웃·최근 배포 기록·배포 스크립트를 확인했다. AWS 계정 일치와 Docker 기동을 확인했다.
- 운영 배포 시도는 자동 승인 검토에서 거부됐다. 명시적 사용자 배포 승인이 없고 서비스 장애 영향이 있다는 사유다. 계정 backend deploy 명령은 실행되지 않았으며 CMS/프론트 배포도 실행하지 않았다. 우회하지 않고 로컬 변경을 보존했다. 커밋·push·PR은 수행하지 않았다.

## 남은 단계

사용자가 운영 배포를 명시적으로 승인하면 서비스 백엔드(계정 대시보드와 기존 user 경로)·CMS·프론트를 반영하고 운영 날짜 표시·기간 조회·신규 보상 중단을 확인한다. 구현·검증과 운영 반영을 구분한다.


## PR 준비 검증

- 사용자 요청 범위는 커밋·push·PR 생성이다. 운영 배포·병합·리뷰 요청은 포함하지 않는다.
- 실제 저장소는 sedaily-ai/AILENS이며 sedaily-git-pr와 프로젝트 규칙을 적용했다. origin/main을 fetch한 뒤 최신 e5b961e0a9a2aadcba083dc43988b381faedd9dc에서 refactor/reading-records-without-rewards를 생성했다. 추가된 원격 5개 커밋은 pipelines 4개 파일뿐으로 이번 계약과 겹치지 않는다. 열린 PR #92/#42도 이 변경과 무관하며 새 DB migration은 없다.
- 영속 기록·여러 계층의 API 정책 변경이므로 강화 검증을 적용했다. 범용 독립 리뷰가 전체 raw diff·신규 파일·완료 원장·추천·저장·기존 API·진행 중 세션·계정/세션 잠금과 재전송 경로를 확인했다. 별도 실행 리뷰가 아닌 독립 정적 리뷰이며 구체적 신규 결함은 발견하지 못했다.
- 최신 main 기준으로 관련 프론트 23개, 서비스 백엔드 57개, 임시 loopback PostgreSQL CMS 45개를 다시 실행해 모두 통과했다. 이 125개는 이전 실행과 중복 합산하지 않는다. 타입·ESLint·변경 Python pyflakes·diff 공백 검사를 확인했다.
- Browser plugin이 제공되지 않아 Playwright를 사용했다. 임시 Vite 페이지에서 실제 ReadingRewards/ReadingPeriodView/WeeklyStamps, 실제 useReadingRecords와 제품 CSS를 실행했다. 인증·fetch 경계만 대역이며 운영 로그인·실제 API를 검증한 것으로 해석하지 않는다.
- 1440×1000과 390×844에서 주간 2일 체크·월간 2일 체크·연간 12개월, 배지/주간 목표 미노출, 조회 실패 한국어 안내와 복구를 확인했다. 모바일 scrollWidth=390으로 가로 넘침이 없고 최종 콘솔 error/warning과 프레임워크 오류 overlay가 없었다. 월간 범례의 색상은 실제 완료 날짜의 파란 표시와 일치하도록 보완했다. 임시 화면은 제품에 추가하지 않았다.

변경 요소 생명주기: weekly_activity는 서비스 백엔드가 /activity 주간 응답을 감싸 생성하고 프론트 타입과 홈 요약이 소비한다. 완료 원장이 저장 정본이며 주월연 일자 집계가 날짜 체크를 결정한다. reward.status=disabled/awards=[]는 응답 호환 필드로 남고 신규 지급 저장은 없다. 기존 보상 테이블은 읽기 호환으로만 보존한다. 새 제한·환경변수·운영 명령은 추가하지 않았으며 새 테스트는 기존 Vitest/pytest 탐색에 포함된다. 운영 배포는 이번 검증·Git 요청의 범위 밖이다.
