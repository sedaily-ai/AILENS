## 배경

결과 화면의 "그날의 서울경제 1면"이 처음 조회하는 날짜에서 서버 2.4~20.5초(중앙값 6.9초, 오후 15~20초) 걸렸다. 캐시가 있는 날은 0.6초다. 2026-10-21 사용자가 권장안 A·B·C·E를 한 번에 진행하기로 승인했다(D 메모리, F 장면 순서·문구, G~K CloudFront·API Gateway 캐시·정적 파일·프로비저닝 동시성은 하지 않음).

같은 날 18:33 KST 무렵부터 빅카인즈 검색 API가 응답하지 않아 A의 미리 채우기 관문 시험이 멈췄다. 사용자 결정으로 **미리 채우기는 이번에 하지 않고**, 이미 구현된 서버·프런트 개선까지만 마무리했다.

## 결정

- 미리 채우기는 빅카인즈가 회복되고 한도·약관을 확인한 뒤에 따로 한다. 지금 반영분만으로도 캐시 없는 날짜가 빨라지고, 불편이 크면 그때 미리 채우기를 진행한다(사용자 결정, 2026-10-21).
- A②는 달력 규칙(1998-01~08 공백을 `front_page_calendar.json`에 넣기) 대신 "30일 지난 날짜의 0건을 오래 보관"으로 했다. 243일을 날마다 확인하지 않고 달력에 넣으면 기사가 있는 날을 숨길 수 있고, 달력 형식·로더·수집 스크립트를 함께 고쳐야 한다.
- 미리 채우기의 `written-keys.txt`는 PutItem을 보내기 전에 키를 덧붙이고 fsync한다. 실제로 쓰지 않은 키도 들어가 목록이 실제보다 넓을 수 있지만, 대상이 캐시라 더 지워도 다음 조회 때 서버가 다시 만든다(사용자 결정).

### 3. 나중에 미리 채우기를 할 때

1. **빅카인즈 한도·약관부터 확인한다**(하루·초당 호출 수, 결과의 대량 저장). 전체는 약 2.0만 회(옛 로직이면 약 2.4만 회) 호출로 추정한다. 그날 기사 1회만 부르는 확인 호출로 응답이 돌아왔는지도 본다.
2. **관문** — 저장소 루트에서. 표본은 `.agents/tasks/AILENS-birthday-front-speed-2026-10-21/gate-dates.txt`(45일). 지난 실행의 체크포인트가 6번째 날짜에 있으니 `--restart`로 처음부터 한다(앞 파일은 `previous/<시각>/`로 옮겨진다).

   ```bash
   REPO=/Users/ldy/Desktop/Code/Sedaily/AILENS
   TASK=$REPO/.agents/tasks/AILENS-birthday-front-speed-2026-10-21
   OLD=$(mktemp -d /tmp/ailens-front-old.XXXXXX)
   git -C "$REPO" archive c041fba4 service/backend | tar -x -C "$OLD"
   cd "$REPO/service/backend"
   warm() { AWS_DEFAULT_REGION=us-east-1 uv run --no-project --with boto3==1.35.0 --with requests==2.32.3 python scripts/warm_front_page_cache.py "$@"; }
   # (1) 옛 로직 dry-run → (2) 새 로직 dry-run → (3) 비교(종료 코드 0이어야 다음으로)
   warm --dry-run --restart --workers 1 --dates "$TASK/gate-dates.txt" --code-root "$OLD/service/backend" --state-dir "$TASK/gate/old"
   warm --dry-run --restart --workers 1 --dates "$TASK/gate-dates.txt" --state-dir "$TASK/gate/new"
   warm --compare "$TASK/gate/old/results.jsonl" "$TASK/gate/new/results.jsonl"
   rm -rf "$OLD"
   # (4) 실제 채우기 300일 — 호출 수·시간·실패율을 잰다(예: 2005-01-01~2005-10-27)
   warm --from 2005-01-01 --to 2005-10-27 --workers 3 --state-dir <상태 폴더>
   ```

   dry-run은 메모리 표만 써서 DynamoDB를 읽지도 쓰지도 않는다. 지난번에는 쓰기 경로를 한 겹 더 막으려고 botocore 훅도 붙였다(`gate-report.md` 3절).
3. **전체** — 300일 결과가 괜찮으면 같은 명령에서 `--from`·`--to`를 빼고(기본 1990-01-01~오늘-7일) 밤에 `--workers 3`으로 돌린다. 끊겨도 같은 명령으로 다시 돌리면 체크포인트부터 이어 간다.

- **중지**: Ctrl-C. 스크립트도 연속 실패 5회, 최근 100건 중 실패 11건 이상, 빅카인즈 401·403·429나 한도·쿼터 응답에서 스스로 멈춘다(종료 코드 2, 이유는 `progress.log`·`summary.json`). 멈추면 진행 중인 날짜의 다음 빅카인즈 요청과 쓰기도 막는다.
- **표**: `sedaily-mbti-articles-dev`(us-east-1)는 2026-02-03부터 **PAY_PER_REQUEST**(온디맨드)다. 쓰기 속도 제한은 없고 요청 수만큼 과금된다. 캐시 항목은 GSI에 들어가지 않는다. 스크립트는 시작 전에 과금 모드를 다시 보고, PROVISIONED로 바뀌어 있으면 용량의 절반 이하로 늦춘다.
- 쓰기는 조건부 PutItem이라 살아 있는 캐시를 덮어쓰지 않는다. 보관 1년 미만 결과(순위 실패, 최근 0건)는 쓰지 않고 `retry-dates.txt`에 남긴다. `notable.jsonl`(kind=none·no_paper)은 사람이 훑어본다.

### 되돌리기 절차 — 미리 채우기로 쓴 캐시

1. 지울 목록을 만든다. 같은 날을 다시 쓰면 키가 두 번 들어가므로 중복을 뺀다. 형식이 맞는 키만 남겨 다른 항목을 건드리지 않는다.

   ```bash
   STATE=<미리 채우기 --state-dir>
   grep -E '^timemachine_frontv2_(none_)?[0-9]{4}-[0-9]{2}-[0-9]{2}$' "$STATE/written-keys.txt" | sort -u > /tmp/front-keys.txt
   wc -l /tmp/front-keys.txt
   ```

2. 목록의 키만 지운다. 표 이름 정본은 `service/backend/config/constants.py`의 `DYNAMODB_TABLE_ARTICLES_DEV`(us-east-1)다. 다른 기능도 쓰는 표라 지우기 전에 `aws dynamodb describe-table`로 과금 모드를 보고, PROVISIONED면 쓰기 용량을 넘지 않게 나눠 지운다.

   ```bash
   while read -r key; do
     aws dynamodb delete-item --region us-east-1 --table-name sedaily-mbti-articles-dev \
       --key "{\"news_id\":{\"S\":\"$key\"}}"
   done < /tmp/front-keys.txt
   rm /tmp/front-keys.txt
   ```

3. 목록이 실제 쓰기보다 넓을 수 있다(위 「결정」). 그래서 미리 채우기 전부터 있던 캐시(라이브 Lambda가 만든 항목)도 지워질 수 있다. 지워진 날짜는 다음 조회 한 번이 미리 채우기 전처럼 느리고(2~20초) 그때 서버가 같은 로직으로 다시 만들어 저장한다.
