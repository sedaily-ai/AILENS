## 2. 주제별 기록 (문제발견 → 정의 → Why → How → 가설 → 검증 → 판정 → Next)

### 2-1. 말풍선이 그림을 보지 않고 놓인다

- 문제발견: CMS 컷 생성기와 발행 웹툰에서 말풍선이 인물 얼굴을 덮고 꼬리가 허공을 가리켰다(8컷 중 대부분의 컷에서 눈·코·입이 풍선에 가려짐을 캡처로 확인).
- 문제정의: 합성기가 그림 속 인물 위치를 모르고 "위쪽 좌우 균등"에 풍선을 놓는다. 9/28에 얼굴 감지를 걷어냈기 때문이다.
- Why: 감지를 걷어낸 이유는 그림체가 아니라 실행 역할에 `rekognition:DetectFaces` 권한이 없어 호출이 매번 실패해서였다(로그 사실). 원인을 오해한 채 기능 자체를 지웠던 것이다.
- How: 생성된 그림을 Rekognition(사람 상자 + 얼굴 상자 + 성별)으로 분석 → 후보 자리(수평 11곳 × 수직 28줄)를 점수화(얼굴·머리 큰 감점, 몸통 작은 감점, 풍선끼리 겹침 사실상 금지, 화자와 가까울수록·위쪽일수록 가산, 꼬리 짧을수록 가산, 질문이 위) → 최저 비용 자리 선택. 꼬리는 머리 상자에서 풍선과 가장 가까운 변의 바깥에 닿게(얼굴 위를 지나지 않음). 감지 실패·권한 오류는 고정 배치로 조용히 폴백.
- 가설: 사람 상자는 이 그림체(반실사 일러스트)에서도 안정적이고, 얼굴 가림은 거의 사라질 것이다. 반증 조건: 머리 위 공간이 없는 구도에서는 풍선이 몸통 위로 밀리거나 두 풍선이 붙을 것이다.
- 검증: 컷 8장으로 Rekognition 시험 — 사람 상자 7/8장에서 두 인물을 모두 잡음(신뢰도 90%+), 1장은 한 명만 보여 폴백. 얼굴 상자는 큰 얼굴 위주, 작은 얼굴은 일부 놓침. 성별은 여성이 8/8장에서 잡혔고 남성은 3/8장(만화체 남성은 신뢰도가 낮음) → 남성은 위치 폴백. Before/After(같은 원본 그림, 같은 대사)에서 After는 8컷 모두 눈·코·입이 가려지지 않음. 반증 조건이 일부 확인됨(두 풍선이 가운데에 세로로 붙는 컷, 꼬리가 길게 뻗는 컷).
- 판정: 채택(CMS 토글 "말풍선 얼굴 회피", 기본 꺼짐 → 사용자가 프로덕션에 켬). 비용은 호출당 약 $0.001(컷당 2회 ≈ $0.002, 기사 하나 약 $0.016, 하루 10건 월 $5 안팎).
- 교훈: 지운 기능의 실패 원인을 권한 부재(인프라)와 모델 한계(기술)로 구분해 기록해 두지 않아 한 달 가까이 기능이 사라져 있었다. 폴백이 조용하면 사고가 보이지 않으니 로그에 이유를 남긴다.
- Next: 머리 위 공간을 비우는 구도 지시(프롬프트), 한 기사 전체 특수 톤 한도(격앙2·속삭임2·생각1)의 코드 강제.

### 2-2. 꼬리 구현에서 만난 버그들

- 꼬리가 하단 중앙 고정 → 화자 목표점 방향으로(QA 요청서 1번). 처음엔 풍선의 아래 변에서만 나가서 목표가 위·옆이면 부자연스러웠다 → 네 변 중 목표에 가장 가까운 변에서.
- 방향이 거의 수평인데 위·아래 변에서 내보내면 밑변과 방향이 나란해져 삼각형이 철사처럼 납작해진다(개정 104에서 수정: 풍선 바깥으로 더 많이 벗어난 축을 따라 변 선택). 길수록 밑변을 넓힌다.
- 삐죽 풍선(격앙)은 사각형 기준으로 꼬리를 붙였는데 실제 테두리는 안쪽이라 틈과 선이 남았다 → 실제 테두리(평균 반지름)에서 꼬리를 내고 이음새를 흰 선으로 덮는다.
- 노하우: 꼬리는 "도형의 경계 위의 점 + 목표 방향 + 이음새 지우기" 세 요소다. 타원은 `r = 1/sqrt((ux/a)^2 + (uy/b)^2)`로 경계까지 거리를 구한다.

### 2-3. 말풍선 모양과 톤

- 4종: 보통(손으로 그은 듯 살짝 흔들린 선), 격앙(삐죽 + 기울인 글자 = 가짜 이탤릭, 전단 변환), 속삭임(점선 + 회색 글자), 생각(구름 + 점점 작아지는 동그라미 꼬리).
- 톤 결정: 모델(프롬프트 v32)이 대사별로 고른다. 코드는 한 컷의 두 대사가 모두 특수 톤이면 뒤를 보통으로 바꾸는 안전망만 둔다(프롬프트에 금지했는데도 컷 8에서 점선 + 구름이 같이 나온 실측 때문).
- 노하우: 프롬프트 규칙은 어겨질 수 있으니 눈에 띄는 위반은 코드 안전망을 둔다. 규칙을 모델에만 맡기지 않는다.

### 2-4. 레퍼런스(네이버 웹툰) 분석과 "웹툰식 말풍선"

- 문제발견: 사용자가 레퍼런스 캡처를 공유("퀄리티 높아 보인다"). 우리 풍선은 스티커처럼 보였다.
- 분석(레퍼런스 공통 특징): (1) 말풍선이 그림 안이 아니라 흰 여백에 놓이고 경계에 걸치기도 함 (2) 선이 아주 얇음(약 1px) (3) 평범한 대사는 타원 + 보통 굵기 글꼴, 강한 대사만 각진/삐죽 + 굵은 기울임 (4) 꼬리가 짧고 뾰족하며 화자 머리를 정확히 가리킴 (5) 풍선이 서로 겹치며 읽는 순서를 이어 줌 (6) 효과음은 손글씨. 우리에게 가장 큰 차이는 1번(그림을 가리지 않는 배치)과 2·3번(선·글꼴)이었다.
- How: 그림 위에 흰 여백(그림 높이 30%, 표지는 +16%)을 붙이고 풍선을 그 여백에 두며 꼬리만 인물 머리로 내린다. 풍선은 타원(글자 덩어리를 감싸는 타원 크기 = 가로 ×1.36, 세로 ×1.56), 선 2px, 글꼴은 Pretendard 가변 굵기 430(Pillow `set_variation_by_axes`). 리서치는 웹 검색(AI 만화 말풍선 배치 연구·튜토리얼)도 병행: 가장 성공적인 방식은 "레이아웃 먼저, 그림은 나중" + 합성 후 검증(얼굴 가림·읽는 순서) + 사람이 고치는 편집 단계.
- 검증: 같은 원본 8장에서 클래식 vs 웹툰식 비교 — 웹툰식은 얼굴이 하나도 가려지지 않고 레퍼런스와 같은 구성이 됨. 사용자가 실제 사이트에서 "잘 보인다" 확인.
- 판정: CMS 토글 "웹툰식 말풍선"으로 채택(기본 꺼짐 → 프로덕션 켬).
- 트레이드오프: 컷이 3:2에서 약 1.17:1로 세로로 길어짐 → 서비스 갤러리를 컷별 비율로 바꿈. 목록/홈 썸네일은 3:2 중앙 크롭이라 표지 컷의 여백이 일부 잘릴 수 있음(첫 컷만 해당).
- 미검증 가설(성과 지표로 확인 필요): 웹툰식 배치가 독자의 읽기 완주율·다음 컷 도달률을 높인다. 측정 계획: 웹툰 탭에서 컷별 도달률(스크롤 깊이), 마지막 컷 도달률, "레터로 더 자세히 읽기" 클릭률을 켜기 전·후 비교. 현재 이런 지표는 수집하지 않으므로 먼저 계측을 넣어야 한다.

### 2-5. 정보가 빈약해 보인다 → 구성 설계(v33~v34)

- 문제발견(사용자): 대사 두 줄만으로는 내용이 빈약해 보인다. 하단 검은 나레이션이 사라졌다.
- 원인: v31이 "하단 전체 자막 바 금지"로 `narration`을 없앴다(QA 요청서 방침: 정보를 말풍선으로).
- 구성 원칙(3): 한 컷에 정보 하나 / 컷 끝마다 궁금증을 남겨 다음 컷이 풀어 줌(질문 컷 1·3·5·7, 답 컷 2·4·6·8) / 정보는 세 겹(대사=궁금증과 감정, 나레이션=확정 사실, 출처 박스=신뢰).
- 정보 충족 장치(모두 코드 합성, 이미지 모델 비용 없음): 나레이션 띠 속 핵심 숫자만 파랑 강조(정규식으로 숫자+단위 추출), 마지막 "핵심 정리" 카드(`key_numbers` 2~3개를 큰 파랑 숫자 + 라벨로).
- 검증: 더휴식 기사 재생성 — 스크립트가 컷마다 나레이션(수치 포함)과 key_numbers(650억 원·1817억 원·2028년)를 냈고, 컷 아래 띠에서 숫자가 강조됨, 카드가 마지막에 붙음. 사용자 확인 "잘 보인다".
- 한계: CMS 컷 생성기·미리보기는 8컷 단위라 카드(컷9)는 실제 자동 발행분에서만 보임.

### 2-6. 사람이 고칠 수 있게 — CMS 말풍선 편집

- 설계: 이미지 생성(비용)과 합성(무료)을 분리. 컷 생성 시 글자 없는 원본(`-bg.png`)을 S3에 따로 보관 → 편집 화면에서 말풍선 상자·꼬리 끝을 끌면 `recompose`가 원본 위에 다시 합성(몇 초, 비용 0). 화면의 그림은 서버가 실제로 그린 결과, 파란 상자와 빨간 점은 끌기용 손잡이(WYSIWYG).
- 보안: recompose는 버킷의 `media/webtoon-lab/*-bg.png` 키만 읽는다(임의 URL을 서버가 받아오지 않음). zip은 `media/webtoon-lab/` 접두어만, 24장 제한.
- 한계: 이번 세션에서 새로 만든 컷만 편집 가능, 발행된 컷은 원본이 없어 불가(Next: 발행 컷 원본 보관).

### 2-7. 화풍 일관성(요청서 3번) — 막힌 지점 기록

- 요청: 컷1을 승인하고 컷2~8을 image-to-image로 이어 그려 화풍·인물을 고정.
- 실측(Ultra, inference profile 경유, 약 $0.16): 4:5(896×1088), seed, negative_prompt는 모두 지원. image-to-image는 `Model ultra does not support image-to-image mode`. 요청서의 모델 ID(`stability.stable-image-ultra-v1:1`)는 비용태깅 규칙상 쓸 수 없고(베어 ID는 미태깅), 쓰는 것은 inference profile ARN.
- 대안과 판단: SD3.5 Large가 image-to-image를 지원하나 모델 교체는 화풍 변동 위험이 있어 사용자가 보류. 지금은 기사별 seed 고정·기록과 `negative_prompt`만 적용(분위기만 약하게 비슷해짐, 인물 고정은 아님). 문서의 "본문에 부정문 금지" 지적과 코드가 본문에 붙이는 "Do NOT render any text" 문구가 어긋나는 점은 실측 비교(약 $0.64) 후 판단하기로 보류.
- 교훈: 외부 요청서의 기술 주장(예: "Ultra로 image-to-image")은 구현 전에 가장 싼 실호출로 먼저 검증한다.

### 2-8. 사고: 표지(컷1) 글자 합성 누락

- 현상: 새 설정으로 재생성한 3개 웹툰의 컷1에 제목·풍선·나레이션이 전부 없었다. CMS 컷 생성기에서도 같은 증상.
- 원인: 표지는 제목 띠가 위를 크게 차지해서, 웹툰식 모드의 여백 한도 안에 풍선이 들어갈 자리가 없었고 계획기가 `best=None` 언패킹 오류를 냈다. 합성 예외를 파이프라인이 삼켜서 컷1이 글자 없이 올라갔다.
- 수정(개정 108): 표지 여백 +16%, 한도 안에 자리가 없으면 한도를 풀어 재탐색, 그래도 실패하면 고정 배치로, 웹툰식 합성 자체가 실패하면 기본 스타일로 재시도(3단 폴백).
- 복구: `scripts/recompose_cut1.py`로 3건의 컷1만 다시 합성(원본 그림 재사용, 비용 0). 한 건은 원본이 이미 기본 스타일로 합성돼 컷1 그림만 재생성(약 $0.08). 새 키 `-webtoon-cut001-v2.webp`로 올려 같은 URL 캐시 문제를 피함.
- 교훈: 새 모드의 극단 입력(표지, 사람 1명, 자리 없음)을 먼저 시험하고, 예외를 삼키는 지점에는 반드시 폴백 단계를 둔다.

## 4. 결정 목록

- 얼굴 감지는 Rekognition으로 되살린다(권한만 추가). 기본 꺼짐, CMS 토글.
- 말풍선 모양·여백·나레이션·카드는 모두 코드 합성(이미지 모델 비용 없음)으로 한다.
- 모델 교체(SD3.5)와 image-to-image 체인은 위험하다고 보고 보류.
- 프롬프트는 문서(`docs/prompt/webtoon/`)에 버전별로 보관하고, CMS 저장(관리자 로그인)은 사용자가 직접 한다.
- 새 스타일은 전부 토글(기본 꺼짐)로 도입해 테스트 카드에서 먼저 보고 프로덕션에 켠다.
