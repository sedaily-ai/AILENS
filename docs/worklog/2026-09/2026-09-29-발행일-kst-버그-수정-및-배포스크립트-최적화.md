## 배경

어제 배포한 mustknow_auto 하드컷 버그 수정(v1.7)이 실제 운영에서 잘
도는지 확인하려고 오늘 아침 07:00 KST 첫 회차를 CloudWatch 로그로
모니터링하다가, 사용자가 라이브 `/lens` 페이지 스크린샷을 공유하며
"다른 이슈" 목록에서 오늘 오전에 발행된 글이 "어제" 날짜로 묶여
보인다고 지적 — 조사 결과 전혀 다른, 더 파급력 큰 프로덕션 버그를
발견했다.

## 한 것

### 1. mustknow_auto 실행 모니터링

CloudWatch 로그로 어제 배포(리비전 86)한 하드컷 수정 회차를 추적.
결과: 배포 직후 도는 회차들은 이미 하루 누적 캡(24/20, 22/20)을
넘긴 상태라 `select_general_articles()` 자체를 호출 안 하고
스킵됐음 — 즉 새 코드(`overflow_keys` 분리)가 아직 한 번도 실행된
적 없음을 확인(정직하게 "아직 검증 안 됨"으로 남김). 오늘 첫 회차는
후보 86건으로 시작해 장시간(2시간+) 진행 — 원인은 콘텐츠 부족이
아니라 기사 하나당 레터+팟캐스트+웹툰+영상을 순차 생성하는 구조상
소요 시간이 김.

### 2. 발행일 KST 버그 발견·수정

**증상**: `/lens` 페이지 "다른 이슈"에서 09:07 KST 발행 글은 "가장
새로운 이슈"로 정상 표시되는데, 08:56·08:45 KST 발행 글은 "9월 28일"
아래로 묶여 보임.

**원인**: `cms_posts_repo.py::_row_to_post()`가 공개 API의 `date`
필드를 `row["published_at"].date()`로 뽑는데, Postgres 세션
타임존이 UTC라 이게 **UTC 달력일**이었다. 08:56 KST = 23:56 UTC(전날),
09:07 KST = 00:07 UTC(당일)라 09시를 기준으로 날짜가 갈렸다 — 매일
00:00~08:59 KST에 발행되는 글 전부(사실상 이 서비스의 새벽~오전
자동 발행 대부분)가 영향받는 구조적 버그였다. 실측: "런던 채링 크로스
로드..." 글의 슬러그는 `2026-09-29-...`로 정확했지만 공개 API가
반환한 `date`는 `2026-09-28`.

**수정**: `service/lens-cms-api/cms_posts_repo.py` +
`service/backend/clients/cms_posts_pg_client.py`(동일 로직 중복
구현, 둘 다 고침 — 파일 docstring이 명시하는 "쿼리·스키마를 바꾸면
같이 고친다" 원칙) — `published_at.date()` → `published_at.astimezone(KST).date()`,
날짜 필터 SQL도 `published_at::date = %s` → `(published_at AT TIME ZONE 'Asia/Seoul')::date = %s`로.

### 3. 배포 스크립트 최적화 (사용자 요청 — "배포 잦아질 텐데 효과적으로")

오늘 배포 4번(lens-cms-api·admin/backend·pipeline 이미지·admin/frontend)을
직접 돌려보고 나온 요청으로, 기존 스크립트 4개를 검토·평가 후 가장
낭비가 큰 지점 2개를 고침:

- **`admin/backend/deploy-admin-api.sh`** — `lens-cms-api/deploy.sh`와
  동일한 해시 비교 패턴 신설. 기존엔 매 배포마다 requirements.txt를
  무조건 `--upgrade` 재설치했다(오늘 배포 때 의존성 충돌 경고 다수
  발생 원인). `.pip-cache-admin/deps`에 영속 설치하고 해시 안 바뀌면
  재사용 — `.gitignore`에 캐시 디렉터리 추가. 격리된 로직 자체를
  별도 테스트(설치→스킵 순서)로 검증.
- **`pipelines/frontpage_auto/Dockerfile`** — 예전부터 알고 있었지만
  미뤘던 이슈(`COPY . .`가 `pip install`보다 먼저라 코드 한 줄만
  바뀌어도 매번 의존성 6개 전체 재설치). requirements.txt 6개만 먼저
  복사 → pip install → 그 다음 `COPY . .`로 순서 변경, npm 의존성과
  동일한 레이어 캐시 원칙 적용. 로컬 빌드(푸시 없음, `--platform
  linux/arm64 -t ...:local-test`)로 정상 빌드되는지 검증 후 이미지
  삭제.

## 결정

날짜 버그를 발견 즉시 배포하지 않고 "배포 스크립트 최적화부터"로
순서를 미뤘던 건 사용자 질문 흐름을 그대로 따른 것 — 이후 사용자가
"수정된거 배포됐나요?"로 직접 확인해 그제서야 배포 진행. 프로덕션에
실제 영향 있는 버그는 발견 즉시 배포 여부를 먼저 물었어야 한다는
교훈(다음 유사 상황엔 우선순위를 먼저 짚을 것).
