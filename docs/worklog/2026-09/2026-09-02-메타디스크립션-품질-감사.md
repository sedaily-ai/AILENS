## 리서치 — Google 공식 문서

- [Google Search Central: 검색결과 미리보기 제어](https://developers.google.com/search/docs/appearance/snippet) —
  각 페이지마다 고유한 설명, 키워드 나열식 금지, 페이지 내용과 무관한
  설명 금지.
- 실무 권장 길이: 데스크톱 150~160자, 모바일 110~120자(Google은 픽셀 폭
  기준으로 자름 — 데스크톱 약 920px, 모바일 약 680px). 핵심 메시지는
  앞 120자 안에.
- **Google이 검색 쿼리와 안 맞으면 62~70% 확률로 메타 디스크립션을
  자체 재작성한다** — 아무리 잘 써도 항상 그대로 노출되진 않음, 다만
  원본이 나쁘면 재작성 확률이 더 높아진다고 봐야 함.
- [Google Article 구조화 데이터](https://developers.google.com/search/docs/appearance/structured-data/article) —
  필수 필드 없음(전부 권장). 권장: headline, image(여러 화면비 권장:
  16x9/4x3/1x1), author, datePublished, dateModified.
- Google VideoObject — **필수**: name, thumbnailUrl, uploadDate,
  (contentUrl 또는 embedUrl) 중 하나. 없으면 리치 결과 자격 자체가 안 됨.

## Before — 실제 데이터 표본 확인 결과

메타 디스크립션의 원천(`excerpt`/`context`)은 원본 CMS 기사의
`subtitle`을 그대로 쓰는 구조(`cms_posts_shaping.py`:
`excerpt = post.get("subtitle") or ""`). 실제 표본(웹툰 8건, lens 15건)을
확인하니 두 가지 문제가 있었다:

1. **기자 바이라인이 그대로 노출**: "김남균 마켓시그널부 기자"(13자)가
   `/lens/2026-09-02-기자의-눈-금감원에-전문가가-사라진다면` 페이지의
   메타 디스크립션으로 그대로 나가고 있었음. lens 15건 표본 중 1건.
2. **신문 소제목이 개행 없이 이어붙음**: "■삼성 '훔볼트 카레'에
   체험공간차세대 TV·비스포크 AI 냉장고에Z 폴드8..." — 원본은 "■"로
   시작하는 여러 줄 소제목인데, subtitle 필드에 개행 없이 저장돼
   단어끼리 그대로 붙어버림. Google 가이드가 명시한 "키워드 나열식"
   패턴과 사실상 같은 모양.

## After

`shared/lib/seo/sanitizeDescription.ts` 신설:
- `sanitizeDescription(raw)` — 20자 미만이거나 "…기자"로 끝나는 짧은
  텍스트(바이라인으로 판단)는 `null` 반환, 호출부가 자기 폴백 문구를
  쓰게 강제. "■/□/▶/◆/●" 마커는 문장 구분(". ")으로 정규화.
- `trimToSnippetLength(s, max)` — Google 권장 길이(기본 155자)로 자르는
  기존 각 페이지 중복 `trimDescription()` 로직을 공용화
  (`buildPageTitle.ts`와 같은 정리 패턴).
- 적용 범위: letters/webtoon/video/lens/listen 상세 페이지 5곳 +
  webtoon 시리즈 페이지 + video/listen 목록 JSON-LD 2곳, 총 8개 파일.
- `letters/[id]/page.tsx`는 이미 자체 `usableSubtitle()`로 "■" 앞
  제거·stale subtitle 필터링을 하고 있어서, trim 함수만 공용으로 교체.

**실측 검증(배포 후 프로덕션)**: 문제였던 그 lens 페이지의 메타
디스크립션이 "김남균 마켓시그널부 기자" → "오늘의 이슈를 4가지
시선으로 짚어드려요."(정상 폴백)로 바뀐 것을 `curl`로 직접 확인.

## 리치 스니펫 감사 결과 — 이미 충족

Article/VideoObject 구조화 데이터를 Google 공식 요구사항과 대조:
- VideoObject 필수 4종(name/thumbnailUrl/uploadDate/contentUrl-embedUrl)
  전부 이미 존재.
- `duration` 필드는 의도적으로 생략돼 있었음 — 코드 주석에 "YouTube
  Data API 키 없이는 정확한 값을 못 구해서 추측값을 안 넣는다"고 이미
  기록돼 있었고, 이건 Google의 "구조화 데이터는 실제 페이지 내용과
  정확히 일치해야 한다" 정책과 부합하는 올바른 판단이라 추가 조치 안 함.

## 한계 (정직하게)

- "■" 마커가 없는데도 단어가 붙어버린 경우(예: "보류LP·야간",
  "커져거래량")는 원본 데이터 자체의 개행 손실이 원인이라, 어디서
  끊겨야 하는지 알 방법이 없어 정규식으로 완전히 복구 불가. 이번엔
  "확실히 나쁜 것"(바이라인, 너무 짧음, ■ 마커)만 걸러내고 이 부분은
  원본 데이터 품질 이슈로 남긴다.
- 원본 `subtitle` 자체를 고치는 건 이 레포 밖(원본 CMS/크롤링 소스)
  이라 스코프 밖.

## 다음

- 근본적으로는 `subtitle` 원본 데이터가 개행을 보존한 채로 넘어오게
  만드는 게 맞는 방향 — 원본 CMS 연동 쪽 조사가 필요하면 별도 세션.
- Search Console에서 실제 스니펫 노출 개선 여부는 크롤링·재색인에
  시간이 걸려 이번 세션에서 확인 불가.
