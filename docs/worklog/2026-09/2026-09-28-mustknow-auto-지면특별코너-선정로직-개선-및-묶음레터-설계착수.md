# 2026-09-28 mustknow_auto 지면특별코너 선정 로직 개선 + 묶음 레터 설계 착수

작성: 문영광 + Claude Code
관련: `pipelines/mustknow_auto/run.py`, `pipelines/discovery/pipeline.py`, `docs/product/4format-pipeline/08_BUNDLE_LETTER/`

## 배경

Play Store 앱 번들 업데이트 작업(`mobile-capacitor/` Capacitor 전환) 중, 대화가
"AI LENS 뉴스 선정 기준이 뭐냐"는 질문으로 넘어가 지면특별코너(전체/증권/산업/
시그널) 4탭의 실제 데이터 신뢰도를 전수 조사하게 됐다. 조사 중 두 개의 실제
버그/설계 결함을 발견해 당일 수정까지 진행했고, 이어서 "하루 발행 총량을 36건
(4탭×4 + 일반 20)으로 정의하자"는 새 컨셉과 "지면특별코너를 기사 1건=레터 1건이
아니라 4건을 묶어 레터 1개로 만들자"는 더 큰 제안까지 나왔다.

## 한 것

**1) 지면특별코너 4탭 선정 로직 — 지면 우선순위 + AI 폴백 하이브리드로 교체**

- 실측(9/18~9/27 daily-xml 10일): `paperNumber`는 날짜·카테고리별로 완전히
  들쭉날쭉해서("증권"이 어떤 날은 1·2면, 다른 날은 18·19면) "N면=증권" 식
  고정 매핑이 애초에 불가능. 대신 `paperNumber` 오름차순 + 같은 면이면
  `paragraph=="TOP"` 우선 정렬이 편집국의 실제 우선순위를 반영하는 신호로
  유효함을 확인(TOP은 페이지당 1개가 75% — 페이지 단위 "대표기사" 플래그).
- `pipelines/mustknow_auto/run.py`: `_rank_tab_candidates()` 신설 — 1차
  지면 정렬(점수 무관), 2차 지면 정보 없는 후보를 AI 점수 높은 순으로 폴백.
- 기존 `_TAB_CATEGORY` 딕셔너리(단순 `top_category` 매칭) 제거.

**2) 시그널 탭 분류 버그 수정 — "마켓시그널" 코너 40% 누락**

- `top_category`는 기사 하나에 여러 category 태그가 붙어도 XML에서 가장
  먼저 나온 것만 본다("증권" 태그가 "Signal" 태그보다 먼저 나오면 놓침).
  10일 표본 실측: 진짜 마켓시그널 코너 기사 58건 중 top_category=="Signal"로
  잡힌 건 35건(60%)뿐, 16건은 category 목록 어딘가엔 Signal이 있는데
  top_category가 아니라서 누락, 7건은 category 태그 자체엔 Signal이 없고
  제목의 "마켓시그널"/"[시그널]" 표시로만 식별 가능했음.
- `pipelines/discovery/pipeline.py`: `_is_market_signal()` 신설(category
  태그 전체 + 제목 패턴 확인), `_parse_item()`에 `is_market_signal` 필드
  추가, `classify()` 버킷 로직 반영.
- `pipelines/mustknow_auto/run.py`: `_tab_of()` 신설 — 시그널 판정을
  `is_market_signal` 우선으로, 증권/산업은 그 나머지만.
- 검증: 실코드(`discovery._parse_item`)로 10일치 재시뮬레이션 — 시그널 탭이
  지면 데이터만으로 정원(4건) 채워지는 날이 0/10일 → 6/10일로 개선.

**3) CloudWatch 로그로 실제 운영 데이터 확인**

- `/ecs/sedaily-lens-mustknow-auto` 로그 그룹에서 최근 10일 발행 집계 확인.
- **"탭당 4건 정원"은 회차(실행)당 상한이지 하루 총량이 아니었다** — 하루
  4~8회 도는데 매 회차 `tab_counts`가 0으로 초기화돼, 신선한 후보가 있으면
  회차마다 또 4건씩 채워짐. 실측: 9/23 증권 26건·산업 28건 누적 발행.
  "일반"(임계값 7.0, 캡 없음)은 평일 하루 16~48건.
- 일요일(9/20, 9/27) 4탭 전부 0건 확인 — `is_sunday` 스킵 로직 정상 동작.

## 결정

- **하루 총 발행 목표를 36건(지면특별코너 4탭×4=16 + 일반 20)으로 정의**한다.
  4탭도 "회차당 4건"이 아니라 "하루 누적 4건"으로 캡 방식을 바꿔야 함(미구현).
- **일반 20건 선정에서 AI 점수 기반 랭킹은 채택하지 않는다.** 실측(seen 테이블
  769건 스캔): 점수가 7.0~7.4 구간에 68.5% 쏠려 있어 사실상 "통과/미통과"
  이진 신호에 가깝다 — "점수 순 20개"가 "먼저 온 순 20개"와 실질적으로
  다르지 않을 가능성이 높다는 판단. **소거(제외)를 먼저 하는 쪽으로 방향
  전환**.
- **카테고리 소거 확정**: 연예·스포츠·피플·오피니언 4개 카테고리를 "일반"
  후보에서 제외(연예/피플은 개인 신상·명예훼손 리스크, 스포츠는 서비스
  컨셉과 결이 다름, 오피니언은 논쟁적 주장 재가공 리스크). 10일 표본 기준
  전체 물량의 30.6%(272/2741건) — 제외해도 남는 9개 카테고리(사회·정치·
  국제·경제·문화라이프·부동산·IT과학·금융·블록체인) 물량은 하루 평균 약
  193건으로 20건 캡엔 충분.
- **다이나모DB 신규 카운터 테이블 제안은 폐기.** 실제 발행 데이터는
  lens-cms-api Postgres(`publications` 테이블)에 있고, `published_at`
  파셜 인덱스로 "오늘+섹션별 COUNT" 쿼리가 가능(조사 완료, 쿼리 예시는
  이 세션 대화 로그 참고 — 아직 문서화 안 됨). 다만 지금 파이프라인은
  DB에 직접 안 붙고 `lens_cms_client.py`(HTTP) 경유라, COUNT 전용
  엔드포인트 신설이 필요(미구현).
- **AI LINK/Prism의 분류 프롬프트(`1_ai_link/prism/dev/DATA/Prompt/`)를
  참고**해 "소거 먼저 → 심층평가 → 다양성 메커니즘"이라는 3단계 깔때기
  구조를 벤치마킹하기로 함. 단, Prism의 평가 지표 내용(분석 깊이·데이터
  객관성 등)은 "글로벌 투자자" 페르소나 전용이라 그대로 못 가져오고,
  AI LENS "일반"은 published.md의 기존 5지표를 유지 — **구조만 이식,
  지표 내용은 유지**.
- **지면특별코너 4탭을 "기사 1건=레터 1건"에서 "기사 4건=레터 1건"(묶음
  레터)으로 바꾸는 안이 나옴.** "AI LENS — 같은 뉴스, 네 가지 시선"의
  "네 가지"는 스토리별 4관점이 아니라 4개 생성 포맷(레터/웹툰/팟캐스트/
  영상)을 가리키는 것으로 확인돼, 여러 기사를 묶는 것과 브랜드 충돌은
  없음. 사용자 목적: "독자 스타일에 맞는 뉴스를 친근한 형태로 전달"이
  핵심이지 "기사 1건" 자체가 원칙은 아니었음.
  - 현재 `service/backend/prompts/letters/published.md`(실제 운영,
    Postgres 경유)와 `docs/product/4format-pipeline/03_LETTER/README.md`
    (문서 정본, v10)는 둘 다 "기사 1건 → 구조화 레터 1건" 전제라 그대로
    재사용 불가 — 새 프롬프트 설계 필요.
  - 레터뿐 아니라 웹툰·팟캐스트·영상까지(`publish_utils.publish_article()`의
    "기사 1건 입력" 전제) 전부 영향받는 규모라, 기존 `03_LETTER/`에 끼워
    넣지 않고 **새 폴더 `docs/product/4format-pipeline/08_BUNDLE_LETTER/`를
    신설**해 독립적으로 버전 관리하기로 함(파일명 `vX.Y-YYYY-MM-DD-주제.md`
    형식 — 이 폴더는 기존 `NN-날짜-주제.md` 컨벤션 대신 시맨틱 버저닝 사용,
    사용자 명시 요청).

  - `_GENERAL_THRESHOLD` 제거(죽은 상수), 모듈 docstring·주석 갱신
- 둘 다 `py_compile` 통과. `select_general_articles()`는 실제 캡처한
  9/27 응답(버그 포함)으로 재검증 — 파싱 성공, 20건 정상 복구 확인.

### 결정

- 프롬프트는 admin CMS Postgres에 등록하지 않고 파일(`service/backend/
  prompts/selection/published.md`)로만 관리하기로 함 — "파이프라인 돌 때
  그냥 읽으면 되는 거 아니냐"는 사용자 판단, admin 편집 UI는 필요해지면
  나중에.
- 선정 안 된 general_pool 후보는 매 회차 seen 처리(선정된 것과 동일하게)
  — "일반" 후보 재평가를 회차마다 반복하지 않도록. 단, 이는 "하루 20건
  누적 캡"을 실제로 강제하는 것과는 다른 얘기 — 여전히 회차마다 새로
  유입되는 신선한 후보가 있으면 회차당 최대 20건씩 추가될 수 있다(지면
  특별코너 4탭이 회차당 4건씩 쌓여 하루 26건까지 갔던 것과 같은 구조적
  여지가 "일반"에도 남아있음 — "하루 누적 20건 캡"은 여전히 미구현).
