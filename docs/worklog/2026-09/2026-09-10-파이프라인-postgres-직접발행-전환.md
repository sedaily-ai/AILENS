# 2026-09-10 자동 콘텐츠 파이프라인 Postgres 직접 발행 전환 (v1.32)

작성: 사용자 + Claude Code
관련: `docs/architecture/db-changelog/postgres/v1.32-*.md`(작성 예정, mustknow_auto 정기 실행 완료 후), v1.29~v1.31(이번 작업의 전제가 된 직전 마이그레이션 버그 수정들)

## 배경

사용자가 "렌즈 파이프라인이 돌고 있나요? 9월 7일자가 마지막으로 돌고있는데?"라고
물어서 조사한 결과, `frontpage_auto`/`mustknow_auto`(EventBridge로 자동 실행되는
Fargate 파이프라인)는 스케줄대로 계속 정상 실행되며 하루 70~90건씩 콘텐츠를
만들고 있었지만, 전부 `sedaily-mbti-cms-posts-dev` DynamoDB 테이블에만 쓰고
있었다. 사이트 읽기(v1.20)·admin 쓰기(v1.21)는 이미 Postgres로 전환됐는데
이 자동 파이프라인만 전환 범위에서 빠져 있었던 것 — 그 결과 v1.4 이관
스냅샷 이후(2026-09-07 01:05 UTC) 파이프라인이 만든 글 240건이 DynamoDB에
고립돼 사이트에 전혀 반영되지 않고 있었다. 사용자가 "다이나모 안 쓴다고
한 거 아니냐"고 지적해 — 그건 CMS API·admin 얘기였고 이 파이프라인은
처음부터 이관 대상이 아니었다는 점을 설명한 뒤, "근본적인 걸 해결하는 게
목표"라는 요청에 따라 파이프라인 자체를 Postgres 직접 발행으로 전환했다.

## 한 것

### 설계 (plan mode, 승인받음)
- 직접 psycopg2 접속 대신 `service/lens-cms-api`의 기존 내부 HTTP API
  (`POST /admin/posts` 등, `X-Internal-Token` 인증)를 그대로 재사용하기로
  결정 — 이 서비스 자체가 "Postgres 접근을 이 서버 하나로 집중"한다는
  원칙을 이미 갖고 있고(admin 콘솔도 이 이유로 RDS에 직접 안 붙음), 그
  덕에 이번 파이프라인 전환도 네트워크(RDS 보안그룹 변경 불필요)·자격증명
  배포·admin_posts_repo.py의 검증된 트랜잭션 로직을 전부 공짜로 물려받았다.
- 형제 채널(webtoon/video/home_player) 별도 publications 행을 더는 안
  만들기로 결정 — v1.30 조사에서 이미 확인된 사실(channel=video/webtoon
  조회가 lens 번들의 rendition 포맷만 보고 걸러준다는 것)과 배치되는
  구조라, 형제 행을 계속 만들면 이번 세션 내내 고치던 것과 같은 중복
  publications 문제를 새로 만드는 것이었다.

### 구현
- `service/lens-cms-api/admin_posts_repo.py` — `find_by_source_url()` 신설
  (source_url 정확일치 조회, list_posts()의 admin_post_id 제한 없이
  v1.4 이관 글도 찾음 — 파이프라인 중복 발행 방지용).
- `service/lens-cms-api/main.py` — `GET /admin/posts/by-source-url` 라우트
  추가.
- `publications.source_url`에 btree 인덱스 신설(기존엔 없었음, EC2에서
  RDS 마스터 계정으로 직접 실행 — `lens_service_app`엔 DDL 권한이 없어
  사용자가 직접 시크릿 조회를 승인·실행).
- 새 파일 `pipelines/common/lens_cms_client.py` — `requests` 기반 얇은
  HTTP 클라이언트(`create_post`/`set_status`/`find_by_source_url`),
  `ddb_prompt.py`와 같은 `LENS_CMS_API_URL` env 재사용.
- `pipelines/common/publish_utils.py` — `already_published()`를 Postgres
  조회로 교체, `publish_article()`의 DynamoDB 4-item(`table.put_item()`)
  쓰기 구간을 lens-cms-api 발행 호출(`create_post`+`set_status`) 1건으로
  교체. 형제 채널 아이템 생성 코드 전부 제거.
- `pipelines/frontpage_auto/run.py`, `pipelines/mustknow_auto/run.py` —
  DynamoDB 테이블 생성/전달 코드 제거, 호출 시그니처 갱신. mustknow_auto의
  `sedaily-lens-mustknow-seen-dev`(기사 후보 중복 처리 캐시)는 사이트
  콘텐츠와 무관해 범위 밖으로 두고 그대로 DynamoDB 유지.
- 양쪽 `task-policy.json` — 이제 안 쓰는 DynamoDB CMS 테이블 권한 제거,
  새 SSM 토큰 파라미터(`/sedaily-mbti/admin/lens-cms-api-token`) 읽기
  권한 추가.

### 배포·검증
- lens-cms-api를 EC2에 먼저 배포(순수 additive, admin 콘솔 영향 없음).
- 파이프라인 Docker 이미지 빌드(`docker build --platform linux/arm64`)·
  ECR push·`aws ecs register-task-definition` 새 리비전 등록(frontpage-auto
  rev 37, mustknow-auto rev 2) — 두 파이프라인이 같은 이미지를 공유하므로
  한 번의 빌드로 둘 다 갱신됨.
- `aws ecs run-task`로 frontpage_auto 수동 1회 실행 — 지면 1면 후보 4건
  전부 `{"published": 4, "published_no_video": 0, "skipped_duplicate": 0,
  "failed": 0}`로 Postgres 경로 발행 성공 확인. DB 확인 결과 게시물당
  publications 1행 + rendition 4개(형제 행 중복 없음)로 설계대로 동작.
- EventBridge 정기 스케줄(mustknow-auto, 06:00 UTC)이 새 이미지로 자동
  실행되는 것도 확인 — 장시간(3시간+) 실행되며 순차적으로 여러 건 발행.

### 배포 중 발견·수정한 IAM 권한 갭 3건(전부 이번 전환과 무관하게 이미
있던 결함 — 자동 파이프라인이 실제로 실행돼본 적 없던 코드 경로라
지금까지 아무도 몰랐던 것)
1. **GPU 인스턴스 제어 권한 누락** — 웹툰 캐릭터 일관성용 GPU
   인스턴스(`i-02313c8c8285f9d91`, IP-Adapter)를 켜고 끄는 `ec2:Describe/
   Start/StopInstances`·`ssm:DescribeInstanceInformation/SendCommand/
   GetCommandInvocation`·전용 S3 버킷(`sedaily-webtoon-ipadapter-*`)
   권한이 두 태스크 역할에 아예 없었다. 웹툰 생성이 매번 실패하고
   "웹툰 없이 발행"으로 조용히 넘어가고 있었다.
2. **Bedrock 이미지 스타일 모델 권한 누락** — GPU까지는 켜지는데
   `stable-style-transfer`/`stable-image-remove-background` 모델
   호출 권한이 없어서 실제 컷 생성이 전부 실패.
3. **Bedrock cross-region 라우팅 미고려** — 2번을 us-west-2 ARN만
   허용해서 고쳤는데도 여전히 실패 — cross-region 추론 프로파일이
   us-east-1/us-east-2로도 라우팅될 수 있어, 3개 리전(us-east-1/2/
   us-west-2) × inference-profile/foundation-model ARN 전부를
   허용해야 했다. mustknow_auto 쪽은 이 확장으로 인라인 정책 용량
   10,240바이트 한도를 넘겨 `LimitExceeded` — 중복 정책(kebab-case/
   PascalCase 두 개가 같은 내용으로 존재했음)을 하나 지워서 해결.
- (미수정, non-blocking) `rekognition:DetectFaces` 권한도 없어 웹툰 컷
  QA의 얼굴 감지가 매번 실패하지만 "균등분할 폴백"으로 자동 우회돼
  발행 자체는 안 끊긴다 — 사용자에게 보고, 급하지 않다고 판단해 보류.

### 웹툰 재생성 백필(4건)
- frontpage_auto 수동 검증 실행 4건은 위 1번 권한 갭 때문에 웹툰 없이
  발행됐다 — 권한 수정 후 로컬(내 AWS 자격증명, 넓은 권한이라 IAM
  전파 지연과 무관)에서 웹툰만 재생성해 채워넣는 스크립트 실행.
  3건 8/8컷, 1건은 시스템 메모리 부족으로 스크립트가 한 번 죽었다가
  재시도해 5/8컷으로 완료.

### 부수 발견·수정 — 홈페이지 카드 버그 2건(오늘 작업과 무관하게 훨씬
전부터 있던 사이트 전체 버그, 사용자가 홈페이지 스크린샷으로 발견)
1. **웹툰 컷이 기사 카드 썸네일로 뜨는 문제** — `channel=letters` API가
   `admin_channel='letters'`인 글만 주는 게 아니라 letter 포맷
   rendition이 있는 모든 글(=거의 모든 lens 글, 실측 947/995건 겹침)을
   돌려주는데, 그 응답을 만드는 `shape_letter()`가 `photo_image_url`
   (진짜 기사 사진)을 아예 안 내려주고 `cover_image_url`(웹툰 첫 컷)만
   줬다 — v1.30이 `shape_video()`에서 이미 고쳤던 것과 똑같은 패턴.
   `shape_letter()`에 `photo_image_url` 필드 추가, 프론트
   `toTodayLetterCard()`가 그걸 `cover_image_url`보다 우선하도록 수정.
2. **같은 글이 카드 2번 중복 표시** — 1번과 같은 원인(letters·lens
   두 채널이 같은 글을 같이 돌려줌)으로, `buildArchiveItems()`가 letters
   목록과 lens 목록을 그냥 이어붙이기만 해서 카테고리 페이지(부동산 등)
   에 같은 글이 두 장 떴다. `buildArchiveItems()`에서 id(=post slug)
   기준으로 겹치면 lens 버전만 남기도록(letters 쪽 제거) 수정.
- 둘 다 lens-cms-api·frontend 재배포 후 실 프로덕션에서 재현·해소 확인.

## 결정

- HTTP API 재사용(직접 DB 접속 아님) — "Postgres 접근을 이 서버
  하나로 집중"한다는 기존 설계 원칙을 그대로 따름. 트레이드오프는
  사이트 쓰기 경로가 EC2 한 대에 의존하는 단일 장애점이 되는 것인데,
  admin 콘솔 발행도 이미 그렇다는 점에서 새로 만드는 리스크가 아니라고
  판단.
- 형제 채널(webtoon/video/home_player) 독립 publications 행을 이제
  안 만듦 — lens 글 1개(4포맷 전부 body_inline.lenses[]에) 로 충분.
- mustknow_auto의 seen-테이블(DynamoDB)은 전환 범위 밖으로 명시적으로
  제외 — 사이트 콘텐츠가 아니라 내부 중복 처리 캐시.
- IAM 정책 크기 초과는 중복 정책(다른 명명 컨벤션으로 두 벌 존재하던
  것) 하나를 지워서 해결 — 권한을 줄이는 대신 낭비되던 중복 리소스를
  정리하는 쪽을 택함.
