# 2026-09-02 4포맷 공용 팩트시트(0단계 사실추출) 실제 구현 — 기자 피드백 Step

작성: Claude Code (세션 기반, 사용자 지시 — "전체적으로 다 해야합니다, 차근차근")
관련: 브랜치 `feat/common-fact-sheet`(머지됨, main `4339052`), 파이프라인
배포(`sedaily-lens-frontpage-auto` 리비전 20), DDB `PROMPT#facts/published` v#1

## 배경

기자 피드백 2번 항목 — "포맷마다 설명 범위와 필수 정보가 달라질 가능성"
(공통 팩트시트 도입 제안). 확인해보니 이건 새 기능 추가가 아니라 **누락된
아키텍처를 실제로 만든 것**에 가깝다: 레터/웹툰/팟캐스트/영상 4개
프롬프트(DDB에 저장된 admin 편집 프롬프트) 전부 "## 설명" 섹션에 "입력은
0단계(사실 추출)에서 만든 facts.json"이라고 명시돼 있었다. 그런데 실제
파이프라인 코드(`frontpage_auto`/`mustknow_auto`의 `run.py`)를 확인하니
이 0단계는 어디에도 구현돼 있지 않았고, 4개 포맷 전부 기사 원문 텍스트를
그대로(각자 독립적으로) 받고 있었다 — 프롬프트가 존재하지 않는 입력을
전제로 쓰여 있던 것. 30초 핵심(같은 날 앞선 worklog)과 같은 패턴의
문제 — 문서화된 아키텍처와 실제 코드의 괴리.

## 한 것

- `pipelines/common/facts_extract.py` 신설 — `extract_facts(article_content)`.
  기사 원문에서 [기준일]/[핵심 숫자 3~5개, 비교기준 포함]/[핵심 용어]/
  [핵심 논지]/[출처]를 한 번만 뽑아 고정 텍스트로 반환. 실패해도
  빈 문자열(파이프라인 전체가 죽지 않게, 예전처럼 원문만 쓰던 동작으로
  자연 폴백).
- 새 Bedrock inference profile은 만들지 않고 `letters`의 것
  (`lens-letters-sonnet-46`)을 재사용 — 비용태깅 규칙(베어 모델 ID 금지)은
  지키면서 새 AWS 리소스 생성은 피함.
- DDB `PROMPT#facts/published` v#1 신설(신규 카테고리 — 기존에 없었음) +
  파일시스템 폴백 `service/backend/prompts/facts/published.md`. admin
  프롬프트 드로어에서 다른 포맷과 동일하게 관리 가능(단, admin
  프론트엔드의 카테고리 탭 목록에 "facts"가 아직 노출 안 될 수 있음 —
  확인 안 함, 아래 "다음" 참조).
- `frontpage_auto`/`mustknow_auto`의 `run.py` — `article_path`에 쓰는
  내용을 "원문"에서 "원문 + `\n\n---\n[공용 팩트시트]\n` + 추출 결과"로
  변경. 이 파일을 레터/웹툰/팟캐스트/영상 4개 `pipeline.py`가 전부 그대로
  읽으므로, 포맷별 코드는 하나도 안 건드렸다.
- 샘플 기사(오늘 자 "슈퍼 예산" 기사와 비슷한 내용으로 직접 작성)로
  실제 Bedrock 호출 검증 — "106조 원" 같은 비교 기준 누락 문제가 추출
  단계에서 정확히 해소되는 것 확인(예: "내년 국가채무는 올해 본예산보다
  106조 원 늘어난 1,519조 8,000억 원으로 전망된다"로 한 문장에 비교
  기준까지 고정됨).
- 파이프라인 Docker 이미지 재배포(리비전 20).

## 결정

- facts.json이 원문을 **대체**하지 않고 원문 뒤에 **추가**되는 구조로
  결정 — 프롬프트 문구상 "입력이 facts.json"이라고 돼 있었지만, 실제로
  원문 전체를 없애면 레터의 5개 소제목 심층 서술이나 웹툰의 장면·분위기
  묘사처럼 압축된 팩트시트만으로는 못 만드는 내용까지 잃는다. 원문(전체
  맥락) + 팩트시트(숫자·용어·논지 고정) 둘 다 주는 하이브리드가 실질적으로
  더 안전하다고 판단.
- 4개 포맷 프롬프트 자체(letters/webtoon/podcast/video)는 이번엔 수정
  안 함 — "입력은 facts.json"이라는 문구가 이제 실제로 맞는 말이 됐으니
  당장 급한 수정은 아니라고 판단, 문구를 "원문 + facts.json"으로
  더 정확히 고치는 건 사소한 문서 정합성 문제라 후순위로 미룸.
