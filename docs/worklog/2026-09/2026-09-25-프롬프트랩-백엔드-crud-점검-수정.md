# 프롬프트 랩 백엔드 CRUD 전수 점검 + 결함 5건 수정 (2026-09-25)

## 문제 발견

- "백엔드 개발자라면 필수로 체크해야 하는 것들 리서치하고, CRUD 제대로 되는지 봐주고 적용해달라"는 요청 — `prompts`/`prompt_lab_docs`/`prompt_lab_files`/`prompt_lab_threads`/`prompt_lab_thread_messages` 전 구간(라우트: `service/lens-cms-api/main.py`, 레포: 같은 폴더+`admin/backend/repo/`)을 코드로 직접 훑음

## 문제 정의

양호한 것(SQL 인젝션 방어 — 전부 파라미터 바인딩, 인증 게이트, 404 처리, FK CASCADE)과 별개로 5건의 실제 결함 확인:

1. **경쟁 상태(TOCTOU)** — `prompt_lab_repo._get_or_create_prompt_id()`가 SELECT 후 없으면 INSERT하는 2단계라, 동시 요청 둘이 동시에 "없음"을 보면 뒤에 도착한 쪽이 `prompts_category_name_key`(실측 확인한 실제 제약 — `UNIQUE(category, name)`) 위반으로 처리되지 않은 500이 날 수 있음
2. **필드 크기 무제한** — `content`/`description`/`instructions`/파일 `content`/메시지 `payload` 어디에도 크기 제한이 없음. 구조가 어제(2026-09-25) 고친 `admin/posts` 413 사고(무제한 JSONB가 목록 조회 응답을 6MB 넘김)와 동일
3. **메시지 40개 상한에 페이지네이션 없음** — 실측: thread_id 24가 59개로 이미 초과, 오래된 19개(그 안의 음성/영상 카드 포함)가 조회 불가 상태였음
4. **스레드 삭제 시 S3 정리 없음** — `delete_thread()`는 DB 행만 지움(메시지는 FK CASCADE로 같이 삭제되지만 S3의 실제 음성/영상/이미지 파일은 그대로 남아 계속 쌓임)
5. **ERD 오류** — 제가 어제 그린 ERD가 `prompts.name`을 단독 UNIQUE로 표기했는데, 라이브 `pg_constraint` 조회 결과 실제로는 `UNIQUE(category, name)` 복합 제약(2026-08-26 스키마 덤프 파일이 최신이 아니었음)

## 왜 그렇게 했는지

- 1번은 `INSERT ... ON CONFLICT (category, name) DO NOTHING` 후 재조회로 원자화 — 새 로직을 추가하는 대신 Postgres가 이미 갖고 있는 원자성 보장을 그대로 씀
- 2번은 `admin/backend/routes/posts.py::_MAX_PAYLOAD_BYTES`(340KB)와 같은 기존 관례를 `service/lens-cms-api` 쪽에도 동일 적용(200KB) — 이미 검증된 패턴 재사용
- 3번은 `chat_threads_repo.get_thread()`의 2026-09-20 주석이 이미 예고해둔 확장(`before_id` 커서)을 그대로 구현 — 새 설계 없이 예정된 자리를 채움. 프론트 "더 보기" UI는 이번 요청이 "백엔드"로 명시돼 있어 범위 밖으로 남김(백엔드는 커서 파라미터까지 완성)
- 4번은 S3 삭제 권한이 `lens-cms-api`(순수 DB 계층)엔 없고 admin Lambda에만 있어, 새 엔드포인트(`GET .../media-keys`)로 정리 대상 키만 lens-cms-api가 넘기고 실제 S3 삭제는 admin Lambda가 하도록 역할을 분리. 필드명(`imageUrl`/`audioUrl`/`videoUrl`/`thumbUrl`)을 하나하나 아는 대신 payload를 재귀적으로 훑어 버킷 URL 패턴과 일치하는 문자열을 전부 수집 — 새 preview 필드가 추가돼도 이 로직을 다시 안 고쳐도 됨
- S3 삭제 실패가 사용자가 요청한 "삭제" 자체를 막으면 안 된다고 판단해 fail-open(이 저장소의 `audit.log`/`notify.notify_content_changed`와 같은 원칙)

## 어떻게 달라졌는지

| | 이전 | 이후 |
|---|---|---|
| 동시 생성 요청 | 뒤에 온 쪽 500 가능(미확인 리스크) | `ON CONFLICT DO NOTHING` — 항상 200 |
| 필드 크기 | 무제한 | 200KB 초과 시 400(실측: 210KB 요청 → `"description too large: 210001 bytes (max 204800)"`) |
| 스레드 메시지 40개 초과 시 | 오래된 메시지 조회 불가 | `before_id` 커서로 이전 페이지 조회 가능(실측: 24번 스레드 40+19=59개 전부 커버 확인) |
| 스레드 삭제 | DB 행만 삭제, S3 잔존 | 삭제 전 미디어 키 조회(`GET .../media-keys`) 후 S3에서 먼저 삭제 — 종단 실측 완료(더미 파일 업로드 → 스레드/메시지 생성 → `handle_delete` 직접 호출 → S3에서 실제로 사라짐 확인) |
| ERD `prompts.name` 표기 | 단독 UK(오류) | `UNIQUE(category, name)`으로 정정, 라이브 조회 근거 각주 추가 |

- 5개 수정 전부 `pyflakes` 클린, 실제 프로덕션 엔드포인트에 curl로 직접 호출해 검증(테스트로 만든 `prompts` 행은 삭제해 정리)
- 배포 완료: `admin/backend`(Lambda) + `service/lens-cms-api`(EC2/PM2) 둘 다

## 결정

- 프론트엔드 "이전 메시지 더 보기" UI는 이번 범위에서 제외 — 요청이 명시적으로 "백엔드"였고, 백엔드는 이미 그 기능이 동작할 수 있는 API(`before_id`)를 완성해둠

## 후속 — IAM 권한 부여 완료 (같은 날)

`sedaily-mbti-admin-api-dev-role`의 `CmsMediaWrite` 정책에 `s3:DeleteObject` 추가(사용자 직접 실행, `s3:PutObject`와 동일 리소스 범위 `sedaily-mbti-cms-media-dev/media/*`로 한정). 적용 후 종단 재검증: 더미 파일 S3 업로드 → 테스트 스레드/메시지 생성 → `chat_threads.handle_delete()` 직접 호출 → S3에서 파일이 실제로 삭제됨을 `aws s3 ls`로 확인. 5개 결함 전부 완전히 해소됨.
