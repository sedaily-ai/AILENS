## 배경

이어지는 서사로 보이지 않는다."

## Before / After (구체적 예시 — 코드 레벨)

**Before** — 3단계 이미지 프롬프트에 인물 정보가 아예 없었다:
```python
prompt = build_background_prompt(s["camera"], s["scene"])
# → STYLE + "[SCENE] 회의실에서 마주앉은 두 사람" + 텍스트 금지 문구
# 8컷 전부 이 호출을 각자 독립적으로 실행 — 인물 생김새 정보 0
```
확산 모델은 "두 사람"이라는 말만 보고 매 컷 새로 인물을 그린다 — 컷1의
"30대 남성"이 컷5에선 "20대 여성"으로 바뀌어도 모델은 알 방법이 없다.

**After** — 1단계가 정한 인물 묘사를 8컷 전부에 동일하게 주입:
```python
characters = script.get("characters")
prompt = build_background_prompt(s["camera"], s["scene"], characters)
# → STYLE + "[CHARACTERS — keep consistent across all cuts]
#    A: 30대 남성, 캐주얼 셔츠, 피곤한 인상
#    B: 20대 여성, 정장, 또렷한 표정
#    setting: 사무실 회의실" + "[SCENE] ..." + 텍스트 금지 문구
```
8컷 모두 같은 `characters` 딕셔너리를 참조 — 완벽한 동일성 보장은
아니지만(확산 모델 한계), "정보가 아예 없던" 상태에서 "매번 같은 묘사를
참조하는" 상태로 바뀐 것이 핵심 개선.

## 한 것

- 원인 확인: `pipelines/webtoon/pipeline.py`의 1단계(스크립트) 출력에
  `characters: {A, B, setting}`(인물 묘사)가 기사당 한 번 정의되고,
  프롬프트도 "모든 컷에서 반복한다"고 지시하지만 — 이건 **1단계 텍스트에
  대한 지시일 뿐**, 실제 3단계 이미지 생성 호출
  (`build_background_prompt`/`build_image_prompt`)엔 `characters`가 인자로
  전달된 적이 없었다. 각 컷의 배경 이미지가 인물 생김새를 전혀 모른 채
  독립적으로 생성되고 있었음(현재 활성 경로는 `IMAGE_PROVIDER="bedrock"`
  — Stable Image Core, `build_background_prompt`).
- 새 헬퍼 `_characters_block(characters)` 추가 — 8컷 전부에 같은
  `characters` 딕셔너리를 `[CHARACTERS — keep consistent across all cuts]`
  블록으로 이미지 프롬프트에 주입. `build_background_prompt`(현재 활성
  Bedrock 경로) + `build_image_prompt`(OpenAI 크레딧 복구 대비 남겨둔
  휴면 경로) 둘 다 수정, 호출부(`characters = script.get("characters")`)도
  갱신.
- 인물 없는 소재(`characters: null`)는 빈 문자열 반환 — 기존 동작 그대로.
- 파이프라인 Docker 이미지 재배포(`sedaily-lens-frontpage-auto` 리비전
  19, mustknow_auto도 같은 이미지 공유).

파이프라인 배포 리비전 22, admin 웹툰 프롬프트 DDB v#5→v#6.

### 배경

위 "캐릭터 일관성" 수정을 배포한 뒤, 사용자가 "웹툰 샘플하나 출력해주시랠요?
변경된거. 활용해서"라고 요청 — 실제로 같은 "슈퍼예산" 기사로 8컷을 생성해
육안 검증했다.

### 발견 1 — 캐릭터 시트 주입 코드는 정상 동작, 그런데 그림은 딴판

컷1/4/8의 실제 이미지 프롬프트를 재조립해서 확인 — `[CHARACTERS — keep
consistent across all cuts]` 블록은 8컷 전부에 빠짐없이 들어가고 있었다.
코드 결함은 아니었다.

그런데 실제로 나온 그림(컷1/4/8)은 시나리오(`2_scenes.json`)의 지문과
전혀 달랐다. 지문은 "국무회의장 부감 샷, 정장 차림 인물들" / "A·B가
테이블 사이 마주 앉은 투샷" / "회의 끝난 빈 창가 테이블, 인물 없음"처럼
뉴스 맥락에 맞게 잘 쓰여 있었는데, 실제 그림은 **한옥 거리, 사극풍 의상,
여러 명의 군중**이었다.

### 원인 — STYLE 프롬프트의 "Kingdom/킹덤" 레퍼런스

`prompts.py`의 `STYLE`이 "Premium Korean webtoon illustration
(Kingdom/킹덤-level production quality)"로 시작했다. "그 정도 퀄리티"라는
의도였지만, "킹덤"은 조선시대 배경 넷플릭스 사극 좀비물이라 확산 모델이
문자 그대로 그 톤(한옥·전통의상)을 끌어온 것으로 추정. 같은 [SCENE]으로
그 레퍼런스만 빼고 재생성해서 실측 확인 — 사극 느낌이 사라졌다.

### Before / After (실제 이미지 비교, 컷1 기준)

**Before (Kingdom 레퍼런스 포함, 리비전 19)**: 한옥 거리 배경, 사극풍
의상을 입은 인물 1~2명, 지문("국무회의장 부감 샷")과 무관.

**After — 1차 수정 (Kingdom만 제거)**: 사극 톤은 사라지고 현대적 배경·
복장으로 바뀌었으나, 이번엔 "번화가 클로즈업 + 트렌디한 남녀 군중"이라는
전형적 K-웹툰 로맨스 구도로 회귀 — 여전히 지문과 다름.

**After — 2차 수정 (STYLE에 현대 배경/사극 금지/군중 금지 명문화 +
[SCENE] 직후 재강조 문구 추가, 리비전 22)**: 사극 오염은 완전히 해소.
다만 카메라 앵글(부감 요청 → 눈높이 샷)·인물 유무(컷8 "인물 없음" 지문에도
인물 등장)·특정 인물 반영(컷4 "A·B 마주 앉음" 지문에도 남성 1명 단독
클로즈업, A 부재)은 여전히 지문을 안 따라갔다.

### 결정

- Kingdom 레퍼런스 제거 + 현대 배경/사극 금지 명문화는 배포함(실측으로
  확인된 개선이므로). `pipelines/webtoon/prompts.py`, `pipeline.py`
  (`_SCENE_REINFORCEMENT`), admin DDB `PROMPT#webtoon/published` v#6
  전부 동기화.
- 카메라 앵글·인물 유무·특정 인물 반영 같은 장면 구성 자체의 지문
  이행력 문제는 **프롬프트 튜닝 2회차로도 해결 안 됨** — "[SCENE]에 없는
  인물 추가 금지"를 명문화했는데도 "인물 없음" 지문에 인물이 나온 걸
  보면, Stable Image Core가 이 정도로 복합적인 프롬프트(스타일+캐릭터
  시트+장면 지문)를 실제로 이행하는 능력 자체의 한계로 판단. 사용자
  확인 후 이 스코프는 여기서 마무리 — 더 파고들려면 다른 이미지 모델
  비교 테스트가 별도로 필요(이번엔 안 함).
- 이 발견으로 "컷 간 캐릭터 일관성"이라는 원래 문제의 우선순위가
  재평가됐다 — 캐릭터 얼굴이 컷마다 바뀌는 것보다, **장면 자체가 지문과
  무관하게 나오는 것**이 더 근본적이고 눈에 띄는 문제였다.

## 추가 기록 (같은 날 저녁) — 모델 비교 실험, 생성·검증·재시도 루프 신설

관련: 브랜치 `feat/webtoon-image-qa-retry`(머지됨, main `fa0a7c1`), 파이프라인
배포 리비전 23.

### 모델 비교 실험 (Bedrock Nova Canvas / SD3.5 Large / Stable Image Ultra)

- **Nova Canvas**: 계정 접근 자체가 막혀 있음(Legacy + 30일 미사용,
  콘솔 재요청 경로도 폐지됨) — 테스트 불가.
- **SD3.5 Large**: 짧은 단독 테스트 프롬프트로는 Stable Image Core보다
  극적으로 나은 결과(국무회의장 장면 정확히 재현)가 나왔으나, **실제
  파이프라인이 쓰는 전체 길이 프롬프트로 돌리면 이 우위가 사라짐** —
  완전히 동일한 프롬프트를 3번 돌려서 3번 다 결과가 판이하게 달랐다
  (회의실 → 달빛 발코니 → 로비 복도). 프롬프트 순서(SCENE을 앞/뒤로)를
  바꿔봐도 마찬가지 — 원인은 프롬프트 구조가 아니라 **확산 모델
  고유의 실행 간 변동성**이라는 결론.
- **Stable Image Ultra**: 최상위 등급이지만 콘텐츠 필터가 SD3.5보다
  민감해서, 완전히 정상적인 "국무회의장, 정장 인물들" 같은 프롬프트도
  간헐적으로 차단됨(`Filter reason: prompt`) — 프로덕션에 쓰기엔
  SD3.5보다 위험 부담이 큼.
- **negative_prompt**: "인물 없음" 위반이나 브랜드 로고 노출을 어느
  정도 억제하는 데는 도움이 됐지만 100%는 아님.
- **결론**: 모델 교체만으로는 해결 안 됨(테스트에 쓴 임시 inference
  profile 3개는 정리 완료). 실제 배포된 이미지 모델은 그대로 Stable
  Image Core 유지.

### 근본 대응 — 생성 → 비전 모델 검증 → 재시도, 말풍선 동적 배치

프롬프트로는 못 없애는 변동성이라는 게 확인됐으니, 방향을 "나쁜
뽑기를 걸러낸다"로 바꿨다.

**Before**: 배경 이미지 생성 후 검증 없이 그대로 사용. 말풍선은
`compose_text.py`가 화자 순서대로 상단에 좌→우 균등 분할로 그림 —
실제 인물이 어디 있는지 전혀 모른 채 배치(코드 주석에 이미 "화자
위치 데이터가 없어서... 타협"이라고 명시돼 있었음, 기자 피드백의
"말풍선이 허공을 가리키는 컷" 지적과 정확히 일치하는 원인).

**After**:
- `pipelines/common/bedrock_client.py`에 `call_vision()` 신설(이미지+
  텍스트 멀티모달 호출, 기존 `call_text()`의 자매 함수).
- `pipeline.py`: 배경 생성 직후 비전 모델(기존 웹툰 스크립트용
  inference profile 재사용, 신규 IAM 권한 불필요)로 이미지를 검사해
  `{sageuk, no_people_violated, faces_left_to_right_x}` JSON을 받는다.
  `sageuk`나 `no_people_violated`가 true면 같은 프롬프트로 1회
  재생성(확산 모델의 실행 간 변동성을 역이용 — 같은 프롬프트라도 다시
  뽑으면 다른 결과가 나온다는 걸 오늘 실측으로 확인했으므로).
- `compose_text.py`: `draw_dialogue()`가 감지된 얼굴 x좌표를 받으면
  (대사 수와 얼굴 수가 일치할 때만) 그 좌표에 말풍선을 앵커. 불일치
  시 기존 균등 분할 폴백 유지 — 안전망.
- 실측 검증: 사극 오염 이미지 → `sageuk:true` 정확히 판별, "인물 없음"
  위반 이미지 → `no_people_violated:true` 정확히 판별, 얼굴 좌표 지정
  테스트 → 말풍선이 지정 좌표(왼쪽/오른쪽)에 정확히 앵커됨.
- QA 호출 자체가 실패(네트워크 오류 등)하면 "문제 없음"으로 처리해서
  발행이 막히지 않게 함(가용성 우선 — QA는 품질 개선 장치지 발행
  게이트가 아님).

### 캐릭터 레퍼런스 이미지(img2img) — 조사만, 구현 안 함

Stability Bedrock API가 `init_image`+`image_strength`(SD3.5는 `strength`)
를 지원해 기술적으로는 가능. 다만 이건 "캐릭터 얼굴만 고정"이 아니라
"전체 이미지를 원본과 얼마나 비슷하게 유지할지"를 조절하는 뭉툭한
손잡이 하나뿐이라, strength를 높이면 배경·포즈까지 원본과 비슷해져
"다른 장면"이 안 되고 낮추면 캐릭터 정체성 유지력이 약해진다. 실제
웹툰 제작에서 쓰는 얼굴 고정 기법(IP-Adapter/InstantID/캐릭터 LoRA)은
지금 Bedrock 모델들엔 없음 — 시도는 가능하지만 별도 실험이 필요한
영역이라 이번엔 구현하지 않고 조사만 남긴다.

### 남은 한계 (정직하게)

- 재시도는 1회뿐이라(비용·시간 제약), 2번 다 나쁜 뽑기면 여전히
  문제 있는 이미지가 나갈 수 있음.
- 비전 모델의 판별 자체도 100% 정확하지 않음(별도 검증 안 함 — 이번
  세션 예시들로만 확인).
- 말풍선 동적 배치는 감지된 얼굴 수와 대사 수가 정확히 일치할 때만
  작동 — 군중 장면(얼굴 10개 이상)에서는 여전히 기존 균등 분할
  폴백으로 돌아감.
- "장면이 지문과 얼마나 맞는가" 자체는 QA 대상에 안 넣었다(사극·
  인물유무만 검사) — 카메라 앵글이나 소품 같은 세부 이행력은 여전히
  검증 안 됨.
