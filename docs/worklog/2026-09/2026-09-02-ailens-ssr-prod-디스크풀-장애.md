# 2026-09-02 ailens-ssr-prod 디스크 풀 장애 — 발생·복구

작성: Claude Code (사용자 지시 — "문제가 무엇이었는지 기록, why 던지고
before/after")
영향: `ailens.sedaily.ai` 약 30분간 502(완전 다운). 데이터 손실 없음.

## Why — 왜 터졌나

1. archive 재설계·페이지네이션 프론트엔드 배포(`service/frontend/deploy.sh`)
   실행 중, EC2(`ailens-ssr-prod`, 루트 볼륨 **8GB**)로 새 릴리스를 풀던
   SSM 명령이 7분 만에 타임아웃으로 실패했다.
2. 실패한 배포가 **비정상적으로 큰 릴리스 디렉터리(2.0G — 정상은 컷당
   ~385M)**를 `/opt/ailens/releases/`에 남겼다. `deploy.sh`의 옛 릴리스
   정리 로직은 **배포가 성공했을 때만** 실행되므로, 실패한 배포의
   잔해는 정리되지 않고 그대로 쌓였다.
3. 기존 릴리스 5개(~385M×5 ≈ 1.9G) + 이 잔해(2.0G) + OS 자체 용량으로
   **루트 디스크 8GB가 100% 꽉 찼다.**
4. 디스크가 꽉 차니 `cloud-init`이 상태 파일(`OSError: [Errno 28] No
   space left on device`)을 못 써서 실패 → **SSM 에이전트도 재연결이
   안 되고 PM2도 기동을 못 해** 사이트가 502로 떨어졌다.

**같은 원인이 2026-08-17에도 한 번 있었다**(`deploy.sh` 상단 주석에
기록됨, 당시는 정상 배포가 쌓이기만 해서 찼던 경우 — 이번은 "실패한
배포의 잔해가 청소되지 않는" 새 경로로 같은 8GB 한계에 다시 부딪힘).

## Before → After

**Before**
- 루트 볼륨 8GB, 여유 없음 — 배포 1~2번의 실패만으로도 100% 도달
- 배포 실패 시 잔해가 청소되지 않고 그대로 남음
- 디스크가 차면 SSM·cloud-init·PM2가 전부 동시에 멎어서, **원격
  명령을 실행할 방법 자체가 없어짐**(SSH도 막혀 있음) — 복구 수단이
  사실상 콘솔 접근뿐이었음

**After**
- 루트 볼륨 **20GB**로 증설(온라인 리사이즈, 데이터 손실 없음),
  파티션·XFS 파일시스템도 실제로 확장(`growpart` + `xfs_growfs`) —
  현재 8.4G 사용 / 12G 여유 (42%)
- 문제의 잔해 릴리스 삭제, 정상 릴리스 5개만 유지
- 재배포 성공 — archive 재설계·페이지네이션이 정상 반영됨
  (release `20260902-091850`)

## 복구 과정에서 겪은 것 (참고 — 다음에 같은 상황 대응 시)

- **재부팅만으로는 해결 안 됨**: 디스크가 이미 꽉 찬 상태에서 재부팅해도
  cloud-init이 다시 같은 이유로 실패해서 SSM이 재연결 안 됨 — 오히려
  PM2 프로세스까지 내려가서 200(구 릴리스로나마 서빙 중)이 502(완전
  다운)로 악화됨.
- **EBS 볼륨 온라인 증설**은 인스턴스를 멈추지 않고도 가능했지만,
  **파티션·파일시스템 자동 확장(`growpart`)이 부팅 시 자동으로 실행되지
  않았다** — 이 AMI/설정에서는 수동으로 `growpart` + `xfs_growfs`를
  SSM으로 실행해야 실제 여유 공간이 반영됐다.
- **SSM이 완전히 죽으면 셸 접근 경로가 없다**(SSH 인바운드 없음) —
  이럴 땐 **EC2 콘솔의 "시스템 로그 가져오기"**(SSM 비의존, 읽기 전용)로
  부팅 로그를 확인하는 게 원인 진단의 유일한 창구였다. 여기서
  `OSError: No space left on device`를 확인해 디스크 문제로 특정했다.

## 다음 (재발 방지, 이번엔 안 함 — 필요시 별도 작업)

- `deploy.sh`의 옛 릴리스 정리 로직을 "성공 시에만"이 아니라 **배포
  시작 시점에 실패한 이전 잔해까지 먼저 정리**하도록 바꾸는 게 재발
  방지에 더 확실할 것.
- 디스크 사용률이 일정 % 넘으면 배포 전에 미리 경고하는 사전 점검
  스텝 추가 고려.
- 이번에 8→20GB로 늘렸지만, 이 인스턴스가 원래 왜 8GB로 설정됐는지
  (비용 절감 목적이었는지) 확인 필요 — 볼륨 증설은 되돌릴 수 없는
  결정은 아니지만 비용 영향은 있음(gp3, 12GB 증가분만큼 소폭 증가).
