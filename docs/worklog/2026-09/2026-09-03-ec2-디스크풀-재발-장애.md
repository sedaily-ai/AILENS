# 2026-09-03 EC2 디스크풀 재발 장애 — SSM까지 마비, SSH로 직접 복구

작성: Claude Code
관련: `f968aab`(generateStaticParams 상한 근본 수정), `ea03a5c`(lens 채널 500 근본 수정)

## 배경

당일 세션에서 lens 채널 API의 목록 응답 limit을 100→1000으로 올렸는데
(별도 근본 원인 수정 — lens 채널이 300건 근처에서 500 에러 나던 문제
해결), 이게 `lens/[slug]/page.tsx`의 `generateStaticParams()`로 그대로
흘러들어가 최근 100건이 아니라 **741건 전부**를 정적 페이지로 미리
빌드해버렸다. standalone 산출물이 평소 ~680MB에서 897MB로 커졌고, 그
릴리스를 배포하다 EC2 루트 볼륨(20GB)이 100%까지 차서 SSM까지
마비되는 실제 프로덕션 장애로 이어졌다. 2026-09-02에 있었던 디스크풀
장애와 근본 원인은 다르지만(그때는 `deploy.sh`의 정리 로직 순서
문제) 증상은 동일했다.

## 한 것

### 1. 장애 진단
- CloudWatch `CWAgent` 네임스페이스의 `disk_used_percent` 메트릭으로
  디스크가 95%→98%→**99.999%**까지 오르는 걸 직접 확인(SSM이 이미
  마비돼 서버 안에서 `df -h`조차 못 돌리는 상태라 이 경로로 확인).
- SSM `send-command`가 `echo hello` 같은 최소 명령조차 즉시(0.001초)
  실패 — 디스크가 꽉 차서 명령 실행에 필요한 스크래치 공간도 못
  만드는 상태였다(2026-09-02 장애 때와 같은 "닭이 먼저냐 달걀이
  먼저냐" 패턴).

### 2. 시도했다가 부족했던 것
- EBS 볼륨 20GB→40GB 온라인 리사이즈(`aws ec2 modify-volume`) — API
  레벨로는 즉시 반영되지만, 파일시스템(XFS)이 `growpart`+`xfs_growfs`로
  실제로 늘어나지 않으면 OS는 여전히 꽉 찬 걸로 인식한다. 그 명령
  자체를 SSM으로 못 넣으니 이것만으론 부족했다.
- 소프트 리부트(`aws ec2 reboot-instances`) — 디스크가 꽉 찬 상태라
  종료(sync/unmount) 자체가 멈췄는지 몇 분째 반영이 안 됐고, 그 사이
  사이트가 CloudFront 504로 완전히 다운되고 SSH 배너 교환까지
  타임아웃되는 더 나쁜 상태로 진행됐다.

### 3. 실제로 복구한 방법 — SSH 직접 접속
- 로컬(`~/.ssh/ailens-ssr-prod`)에 인스턴스와 이름이 같은 키 페어가
  이미 있는 걸 발견 — 보안그룹(`sg-026385217d66ed9e1`)엔 80번
  포트(CloudFront 오리진 전용)만 열려있고 22번은 원래 안 열려있었다.
  사용자 승인 받아 내 IP만 22번 임시 허용(`authorize-security-group-
  ingress`, 작업 끝나고 바로 `revoke`로 원복) → SSH 접속 성공.
- **강제 정지(`stop-instances --force`) 후 재시작** — 소프트 리부트가
  안 먹혀서 하이퍼바이저 레벨에서 강제로 전원을 끊는 더 강한 조치.
  이후 SSH가 다시 응답했다.
- `/opt/ailens/releases/`에 릴리스 5개가 쌓여있는 걸 발견(정상 배포
  절차라면 최근 4개만 유지돼야 하는데, 오늘 실패한 배포가 정리 없이
  남긴 것으로 보임) — `current`가 가리키는 것 1개만 남기고 4개
  삭제해서 **디스크 사용률 100%→38%**로 즉시 확보.
- `growpart /dev/nvme0n1 1` + `xfs_growfs -d /`로 아까 리사이즈해둔
  40GB를 실제로 반영 → **38%→20%**(33GB 여유).
- PM2 — root 소유 PM2 데몬(`sedaily-mbti` 배포가 SSM=root로 실행되는
  것과 같은 이유)의 프로세스 목록이 재부팅으로 비어있던 것을
  `pm2 delete` 후 `PORT=3000 pm2 start server.js --name
  ailens-frontend`로 재기동, `pm2 save`로 재부팅 시 자동 복구되게
  고정.
- 복구 직후 한 번 `curl -o /dev/null` 측정에서 `size=0`으로 잘못
  읽혔는데, `curl -v`로 재확인하니 실제로는 476KB 정상 응답이었다 —
  측정 방식 문제였고 서비스 자체는 그 시점에 이미 정상이었다.

### 4. 근본 수정(코드) — 재발 방지
- `lens/webtoon/video/listen` 4개 `[slug]/page.tsx` 전부에
  `STATIC_PARAMS_LIMIT = 100` 도입 — 목록 API(`fetchLensPosts` 등)의
  응답 limit(100~1000, 채널마다 다름)과 "빌드 시점에 몇 건을 정적
  페이지로 미리 만들지"를 분리했다. 오래된 글은 이미 있는 단건 조회
  폴백(`fetchLensBySlug` 등, 오늘 앞서 만든 근본 수정)으로 요청
  시점에 정상 렌더링된다.
- 로컬 빌드로 검증: lens 정적 페이지 741→100, 전체 라우트 1805→939.
- 재배포 후 실측: 릴리스 832MB(897MB보다 작아짐), EC2 디스크
  12GB/40GB(28%) 사용, 여유 29GB.
- webtoon(706건 실존)도 같은 위험이 잠재해 있었다 — 오늘 새로 생긴
  버그가 아니라 다음에 706건을 넘기면 같은 장애가 재발했을 것이라
  같이 고쳤다.

## 결정

- 임시 SSH 접근은 최소 권한(내 IP만, 22번만)으로 열고 작업 끝나자마자
  즉시 원복 — 영구적으로 열어두지 않음.
- 강제 정지는 파일시스템 손상 위험이 있는 조치라 사용자에게 명시적으로
  알리고 승인받은 뒤 진행(리부트만으로는 부족하다는 게 확인된 뒤의
  마지막 수단으로).
- releases 디렉토리 정리는 `current`가 가리키는 릴리스만 남기고
  나머지 전부 삭제 — 롤백 여지보다 즉시 공간 확보가 우선인 상황
  판단.
