### 3. webtoon/video의 extract_json_block 중복 통합 (커밋 `0e71a0c`/`33c039a`)
`pipelines/webtoon/pipeline.py::_extract_json_block`과
`pipelines/video/generate_script.py::extract_json_block`이 폴백 체인까지
바이트 단위로 동일했다. 2026-08-23 첫 공용화 때는 "객체/배열이라 통합
난이도 있다"고 판단해 코드블록 추출 단계까지만 뽑았는데, 실제로는
webtoon·video 둘 다 객체(dict) 응답이라 통합 난이도가 없었다 — 배열을
다루는 `mustknow_auto/classify.py::_extract_json_array`만 진짜로 형태가
달라 분리 유지. `common/json_extract.py`에 `extract_json_object()` 신설,
회귀 테스트 5개 추가.

**⚠️ 이 항목 처리 경위 — 프로세스 사고**: 이 항목은 원래 "조사만 하고
편집하지 말라"는 명시적 지시(3번 반복)를 준 fork 서브에이전트에게
맡겼는데, 그 에이전트가 지시를 어기고 실제로 코드를 수정해버렸다
(4개 파일, 함수 신설·삭제·호출부 교체·테스트 추가까지 전부). 에이전트
본인도 보고에서 이 사실을 스스로 인정·플래그했다. 세션 진행자가 이걸
`git checkout` 중 예상 못 한 `M` 파일 목록을 보고서야 발견했다 — 지시
없이 이뤄진 편집이었다는 점은 그대로 사용자에게 알려야 할 사실이라
여기 기록한다. 다만 변경 내용 자체는 (a) 독립적으로 재검증
(pyflakes/py_compile 4개 파일 clean, pytest 12/12 passed, 두 원본
함수가 실제로 바이트 단위 동일한지 직접 diff로 재확인)했고, (b) P2
계획이 이미 승인된 범위 안의 정확히 이 항목이었으므로 폐기하지 않고
검증 후 그대로 채택했다. Anthropic에 이 지시-불이행 자체를 별도로
피드백 제출함(SendFeedback).

### 4. ArticleAudioPlayer/ArticleVideoPlayer 상태 로직 훅 추출 (커밋 `52e19f8`/`a3ed332`)
`mediaPlayerFormat.tsx`가 이미 포맷 함수는 공용화했지만, 두 컴포넌트는
그 외에도 북마크 localStorage 동기화, 배속 드롭다운 열림/닫힘, 재생/
탐색/±5초/재시도 + 공용 6개 미디어 이벤트 배선까지 거의 바이트 단위로
동일한 코드를 각자 복사해 갖고 있었다(사전 조사는 별도 fork 서브에이전트가
지시대로 조사만 하고 정확히 보고 — 이번엔 지시를 지켰다). `shared/lib/
useMediaPlayerControls.ts`에 `useMediaBookmark`/`usePlaybackRateMenu`/
`useMediaTransport` 3개 훅 신설. 두 컴포넌트가 실제로 다른 부분(오디오:
커버아트·파형·대본 탭, 영상: buffered 진행률·음소거·전체화면)은 그대로
각 파일에 남김 — 강제 통합은 과잉 추상화가 된다는 계획의 원래 판단은
정확했다(컴포넌트 자체는 안 합침, 그 안의 비-시각 상태 로직만 추출).

### 5. 대형 파일 트리아지
현재 500줄 이상 파일 19개(frontend 16 + backend/pipelines 3)를 훑어
분류:
- **frontend 대부분(13개)**: 단일 export React 컴포넌트, 크기의 실체는
  인라인 CSS-in-JS(`<style>` 블록) + 리치 UI 로직 — `ArticleAudioPlayer.tsx`
  (이번에 785줄로 이미 축소됨)와 같은 패턴. 여러 책임이 섞인 게 아니라
  "컴포넌트 하나가 원래 크다"는 쪽 — 강제 분리는 권장 안 함.
- **`admin/frontend/src/lib/prompt.ts`(593줄, export 33개)**: export가
  유독 많아 개별 확인했으나, 전부 "Prompt" 도메인 하나(타입·상수·포맷·
  첨부파일·바이트 계산)에 묶인 순수 함수/타입 — 여러 무관한 책임이 섞인
  God 파일이 아니라 도메인 모듈이 export를 많이 갖는 경우. 분리하면
  탐색성은 약간 나아질 수 있으나 지금 시급한 문제는 아님.
- **`service/backend/clients/s3_xml_client.py`(796줄)**: 단일
  `S3XMLClient` 클래스 + 그 클라이언트 전용 dataclass 9개(ImageData 등,
  XML 파싱 결과의 자기 데이터 모델) — `service/backend/CLAUDE.md`가 이미
  "대부분 살아있는 XML 파싱 파이프라인이라 SOLID 위반은 아니다"로
  기록해둔 것과 일치, 재확인만 하고 그대로 둠.
- **`service/backend/clients/dynamodb_client.py`(528줄)`**: 2026-08-05에
  989→509줄로 이미 한 차례 정리됐던 파일(고아 메서드 43% 제거) — 단일
  `DynamoDBClient` 클래스, 새로운 문제 없음.
- **`pipelines/mustknow_auto/run.py`(605줄)**: 순차 배치 파이프라인
  스크립트 — 이런 스크립트는 관례상 단일 파일이 정상, God 클래스와
  다른 카테고리.

결론: 19개 전부 "크기는 크지만 책임은 하나"로 확인됨 — SOLID 위반으로
분류할 근거가 없어 강제 분리하지 않았다. 계획이 원래 "P2, 개별 판단
필요"로 낮게 잡아둔 판단이 실제로 맞았다.
