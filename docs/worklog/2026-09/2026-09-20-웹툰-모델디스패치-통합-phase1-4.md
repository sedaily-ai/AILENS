# 2026-09-20 웹툰 모델 디스패치 통합 (정리후보 A+D) Phase 1~4 — GPU→Ultra 전환 완료

작성: 문영광 + Claude Code
관련: [`docs/architecture/webtoon_custom/`](../../architecture/webtoon_custom/README.md), [정리후보 A](../../architecture/webtoon_custom/02-정리후보/01-모델디스패치중복.md), [정리후보 D](../../architecture/webtoon_custom/02-정리후보/04-GPU경로결정미반영.md)

## 배경

같은 날 세션 초반에 admin 실험 패널(`admin/backend/routes/webtoon/generate.py`)을
"사용자 프롬프트 외 다른 영향 요인 없음" 원칙에 맞춰 정리하고 Stable Image
Ultra를 기본 모델로 확정했다. 그런데 "이게 실제 자동 발행에도 반영된 거냐"는
질문에 코드로 재확인한 결과, 실제 발행 파이프라인(`pipelines/webtoon/pipeline.py`,
ECS 배치 `frontpage_auto`/`mustknow_auto`)은 전혀 손대지 않은 상태였다 — 여전히
`IMAGE_PROVIDER = "bedrock-style-transfer"`(GPU IP-Adapter+Style Transfer) 코드
상수 그대로. admin과 발행 파이프라인이 모델 디스패치 로직을 한 줄도 공유하지
않는 게 근본 원인이라, Plan Mode로 이 갭을 메우는 계획(정리후보 A+D)을 세우고
사용자 승인을 받았다.

## 한 것

- **Phase 1** — `pipelines/common/webtoon_image.py`에 `generate_cut_image()`
  신설. admin의 `_generate_once()`/`_generate_composed_with_qa()` 본체를
  옮겨, 모델별 프롬프트 조립(`_generate_cut_once`)과 QA/재시도
  (`_validate_and_detect_cut`)를 admin·발행 파이프라인이 공유하는 단일
  정본으로 만듦.
- **Phase 2** — `admin/backend/routes/webtoon/generate.py`를
  `generate_cut_image()`를 부르는 얇은 wrapper로 축소(`openai_dalle3`만
  앞단에서 분기 유지). `deploy-admin-api.sh`로 배포, flat-copy import
  시뮬레이션 + pytest 144건 + 실헬스체크(401)로 확인.
- **Phase 3(구조 통합, 배포 완료)** — `pipelines/common/webtoon_image.py`에
  `generate_cut_image_to_file()` 추가(`generate_cut_image()` +
  `_retry_generate_and_write()`의 12/24/36초 백오프 파일쓰기 조합, 발행
  파이프라인 전용). `pipelines/webtoon/pipeline.py`의 `_validate_and_detect`/
  `_generate_and_qa_cut`/`_DEFAULT_VERDICT`와 개별 `build_*`/
  `generate_image_bedrock_*` 직접 호출을 전부 걷어내고, 컷 루프를
  `webtoon_image.generate_cut_image_to_file(...)` 한 호출로 교체. **이번
  phase 목표는 리팩토링이지 전환이 아니라 `IMAGE_PROVIDER`는 안 바꿨다**
  (여전히 `bedrock-style-transfer`). Phase 3-0(SD3.5·Ultra
  `bedrock:InvokeModel` ARN을 `frontpage_auto`/`mustknow_auto`
  task-policy.json에 추가, IAM role `frontpage-auto-access`/
  `mustknow-auto-access`에 `put-role-policy`로 적용)도 이때 같이 처리.
  ECS 이미지 재빌드·푸시·task definition 등록(revision 46) 후 수동
  RunTask 1회로 import 정상 확인(exit code 0, 발행 후보 0건이라 실제
  컷 생성 경로는 미검증).
- **Phase 4(모델 전환, 배포 완료)** — `IMAGE_PROVIDER`를
  `"bedrock-sd-ultra"`로 전환. `webtoon_image.py::generate_cut_image()`에
  `check_extra_people: bool = True` 파라미터 신설 — `sageuk`/
  `no_people_violated`(결과물 후처리 검사, "프롬프트 외 영향 없음"
  원칙과 무관, 안전망이라 유지)와 `extra_people`(고정 인물 수 초과 시
  재생성, "군중을 그려달라"는 정당한 지시와 충돌해 admin처럼 off)을
  독립적으로 켜고 끌 수 있게 분리. `pipeline.py`에 provider→model 매핑을
  `_PROVIDER_CONFIG` 딕셔너리로 정리(`bedrock-sd-ultra` → `model="sd_ultra",
  retries=3, with_qa=True, check_extra_people=False`). GPU 기동 분기
  (`IMAGE_PROVIDER == "bedrock-style-transfer"`)는 새 값이 안 걸려 자연히
  비활성화 — GPU EC2/IAM은 1~2주 안정화 확인 전까지 유지. ECS 재빌드·푸시
  (revision 47), `frontpage_auto`·`mustknow_auto` 둘 다 수동 RunTask로
  import 확인.
- **Phase 4-1(같은 날, 배포·검증 완료) — 배치 레벨 GPU 자동시작 제거**.
  Phase 4 검증 중 `mustknow_auto` RunTask 로그에서 `[gpu_ipadapter] 활성
  사용 태스크 13개`가 찍히는 걸 발견 — `IMAGE_PROVIDER`가 Ultra로 바뀌어
  `pipeline.py`의 GPU 분기는 더 이상 안 타는데, `frontpage_auto/run.py`
  (`if candidates:`)와 `mustknow_auto/run.py`(`if front_page or fresh:`)
  둘 다 배치 시작 시 **후보 유무만으로** `gpu_ipadapter.ensure_gpu_running()`
  /`stop_gpu()`를 무조건 호출하는 별도 코드가 남아 있었다(2026-09-10
  도입, `pipeline.py` 내부 로직과 별개) — 실제로 이날 GPU가 쓸 일이
  없는데도 켜져 시간당 $0.647가 새고 있었음. 두 `run.py`의 이 배치 레벨
  wrap을 제거하고, 개별 `_publish()`/`process_article()` 호출의
  `manage_gpu=False` 하드코딩도 기본값 True(`pipeline.py::run_article()`가
  기사 단위로 자체 관리)로 되돌려 GPU 경로 롤백 시 안전망은 유지. 같은
  이미지로 재배포(revision 48) 후 두 배치 다시 RunTask로 재검증 —
  `mustknow_auto`가 이번엔 fresh 13건이 있었는데도(직전 실행은 35건에서
  GPU가 켜졌었음) 로그에 `[gpu_ipadapter]` 줄이 전혀 안 나와 제거 확인.
- **Phase 4-2(같은 날, 배포·검증 완료) — "내일 당장 실사용" 요청으로
  `run_batch.py`(로컬, 실제 Bedrock 호출) 사전 점검 중 발견한 치명적
  버그 2건 수정**:
  1. **스크립트+장면 연출 생성이 항상 실패.** 2026-09-18 "1단계/2단계
     구분 제거" 프롬프트 개편으로 발행 프롬프트 문서에서 "1단계 출력"/
     "2단계 출력" 섹션 자체가 사라졌는데(문서엔 이제 "Stage 1 Script
     Output Format" 하나만 존재), `pipeline.py::run_article()`은 여전히
     그 섹션 이름을 참조해 2단계(장면 연출) 프롬프트를 조립하고 있었다
     — 모델이 스키마 없이 매번 다른(점점 장황해지는) JSON을 즉흥적으로
     만들다 `max_tokens=4000`을 넘겨 잘렸다(`Bedrock 응답에서 JSON을
     찾지 못했습니다`, 재현 확인). admin의 실시간 스크립트챗랩
     (`admin/backend/routes/webtoon/script.py::build_script_call()`)은
     이미 같은 문제를 단일 호출+`max_tokens=8000`으로 고쳐뒀던 걸(2026-
     09-15/18 그쪽 커밋에 기록) 발견 못 해 발행 파이프라인엔 반영이
     안 됐던 것 — `pipeline.py`에 `build_script_call`/`normalize_cuts`
     패턴을 그대로 이식(`_extract_chapters`/`_SCRIPT_CHAPTERS`/
     `_SCRIPT_OUTPUT_ADDENDUM`/`_normalize_cuts`, 두 배포 표면이 달라
     코드 공유 대신 포크)해서 1·2단계를 한 호출로 합치고 `call_json()`에
     `max_tokens` 파라미터를 추가해 8000을 넘겼다. `scene_map` 매칭
     로직도 걷어내고 컷이 이미 `camera`/`scene`을 갖고 오도록 단순화.
  2. **컷1(표지) 텍스트 합성 실패.** 새 스크립트 스키마의 `headline`
     필드가 줄바꿈(`\n`)을 포함해서 오는데(예: `"韓·佛, 영상산업\n5년·
     8000억 투자 선언"`), `compose_text.py::_wrap_text()`가 쓰는 PIL의
     `draw.textlength()`는 멀티라인 문자열을 받으면 즉시
     `ValueError: can't measure length of multiline text`를 던진다 —
     컷1 배경은 생성되지만 제목·말풍선 합성이 통째로 실패해 텍스트 없는
     배경만 남았다. `_wrap_text()` 진입 시 `\n`을 공백으로 치환해 폭
     기준 재줄바꿈에 맡기도록 수정(이 함수를 쓰는 8곳 호출부 전부 안전).
  3. 두 수정 후 로컬에서 같은 기사(뤼미에르파트너십) 전체 재실행 —
     스크립트 생성→8컷 Ultra 이미지 생성→QA→텍스트 합성→스티칭 전부
     성공(1216×6824 최종 이미지). 컷1 스크린샷 육안 확인(브랜드 라벨·
     헤드라인·말풍선 정상 렌더링). ECS 재빌드·푸시(revision 49), 수동
     RunTask로 import 재확인.
  4. **미해결(블로킹 아님)**: 컷8(마무리)이 새 스키마에 `closing_caption`
     필드가 없어(`new_conclusion`/`summary_line_1/2`만 있음)
     `compose_text.compose()`가 전용 남색 마무리 자막 스타일 대신 일반
     내레이션 스타일로 폴백함 — 내용은 정상 표시되나 디자인 의도와
     다름. 급하지 않아 보류.

## 결정

- **구조 통합과 모델 전환을 같은 배포에 안 싣는다.** `frontpage_auto`/
  `mustknow_auto`가 완전히 같은 `pipeline.py`를 `importlib`로 동적 로드해서
  배치 단위 카나리가 불가능하다 — 문제가 터지면 "구조 때문"인지 "모델
  때문"인지 구분이 안 되므로, Phase 3(구조만)과 Phase 4(모델 전환)를 분리해
  각 배포의 검증 질문을 하나로 좁힌다.
- Phase 3 코드 검증은 로컬에서 `generate_cut_image_to_file`을 모의(mock)로
  치환해 `run_article()`의 컷 루프가 리팩토링 전과 동일한 인자
  (`model="pipeline"`, `retries=2`, `has_dialogue` 판정)로 호출하는지
  확인하는 방식을 썼다 — 실제 이미지 바이트 단위 비교(`run_batch.py` 실사용
  기사 실행)는 안 함(비용·시간).
- IAM `put-role-policy` 적용 시 정책 이름을 `provision.sh` 주석의
  `FrontpageAutoAccess`(PascalCase)로 잘못 넣었다가, 실제 라이브 정책
  이름이 `frontpage-auto-access`(소문자-하이픈)인 걸 놓쳐 별도 정책이
  추가로 붙으면서 역할당 인라인 정책 합산 10,240바이트 한도를 넘겨
  `LimitExceeded` 에러가 남 — `list-role-policies`로 실제 이름 확인 후
  올바른 이름으로 재시도해 교체 적용(스트레이 정책 안 남은 것 확인
  완료). **provision.sh/deploy.sh의 정책 이름 주석이 실제 라이브 값과
  다르다는 게 이번에 드러남 — 다음에 이 role을 만질 때는 주석 대신
  `aws iam list-role-policies`로 먼저 확인할 것.**
- Docker 재빌드·ECS 배포 명령이 Claude Code 자동 모드 분류기에 "[Production
  Deploy]"로 차단돼, 사용자가 직접 터미널에서 `deploy.sh`를 실행함(Phase 3용
  1회, Phase 4용 1회).
- QA 정책(`check_extra_people`)은 사용자 확인 없이 계획 문서에 이미 적어둔
  추천안을 그대로 적용했다 — "다음 작업을 바로 진행" 지시에 따라 재확인
  없이 진행, 결정 근거는 위 계획 문서·이 파일에 기록.
- `mustknow_auto` RunTask가 두 번 다 exit code 1로 끝났는데, 이건 오늘
  변경과 무관한 **기존 의도적 설계** — `run.py`에 "후보가 있었는데 발행
  0건이면 CloudWatch 알람이 걸리도록 명시적 실패 코드를 반환한다"는
  주석이 있고, 실제로 두 실행 다 일요일이라 채점 대상이 전부 일반
  임계값(7.0) 미달이라 `published=0`으로 끝난 것 — 재조사 불필요.

# 같은 날 후속 — camera/scene→image_prompt 통합, 대본 프롬프트 v3 재설계, QA 전면 제거, 오늘자 레터 웹툰 백필

## 배경

위 Phase 4 이후 관리자 채팅(`PromptChatLab`)으로 "이미지 프롬프트만 넣었을 때
바로 컷 생성이 되는" 단순 워크플로를 실사용 전 검증하는 과정에서, 스크립트
스키마가 `camera`+`scene` 2필드로 나뉘어 있는 게 실은 22장 원본 문서엔 없던
"코드 보강"(2026-09-18 1/2단계 통합 때 남은 흔적)이라는 게 드러났다. 여기서
출발해 "화풍·인물 고정, 장면 포맷 메뉴, QA" 같은 하드코딩된 제약들을 하나씩
"진짜 필요한가"로 재검토하는 긴 라운드가 이어졌고, 마지막엔 "레터에 웹툰이
비어있는 게 많다"는 실사용 신고를 따라가 오늘자 레터 2건을 실제로 백필했다.

## 한 것

- **camera/scene → image_prompt 단일 필드 통합.** `admin/backend/routes/
  webtoon/script.py`·`pipelines/webtoon/pipeline.py` 양쪽의
  `_SCRIPT_OUTPUT_ADDENDUM`(모델에게 요구하는 필드)과 `normalize_cuts()`
  (파싱)를 수정 — camera(카메라 거리·앵글)+scene(구도·배경) 2필드가
  image_prompt 1필드(완성된 이미지 프롬프트 문장)로 합쳐짐.
  `webtoon_image.py`의 `build_background_prompt()`도 camera 파라미터를

## 결정

- **QA(검증 후 조건부 재생성)는 CMS 토글로 남기지 않고 완전히 삭제한다.**
  "admin 실험과 실제 발행이 100% 동일하게 동작해야 하고, 그 동작은
  CMS에서만 제어 가능해야 한다"는 원칙이 이번 세션 전체를 관통하는
  기준이 됨 — 코드에 하드코딩된 분기(모델별·경로별로 QA on/off가
  다름)는 전부 이 원칙 위반으로 간주하고, 새 설정을 추가하는 대신
  기능 자체를 없애는 쪽을 택함.
- **불확실하거나 검증 안 된 제약은 일단 추가했더라도 반문이 들어오면
  근거를 대거나 뺀다.** 이번 라운드에서 의상 고정·길이 캡·장면 포맷
  메뉴·캐릭터 외형 고정 등 여러 개가 "진짜 필요한가" 질문에 못 버티고
  제거됐다 — 유일하게 살아남은 scene_format_menu의 최초 방어 논리
  ("실측으로 다양성 확인됨")조차 사용자가 "이해가 안 된다, LLM 판단에
  맡기자"고 하자 최종적으로는 제거를 받아들임. 반대로 NEGATIVE의
  "not a photograph"·"no real public figures"·"lower abdomen 회피"
  세 가지는 전부 실측 실패 사례가 있어 살아남았다 — **이론적 추론보다
  실제 실패 재현이 항상 우선한다는 기준이 이번에도 반복 확인됨.**
- **자동 발행 파이프라인 배포(`ECS deploy.sh`, `run-task`)는 Claude
  Code 자동 모드 분류기가 매번 차단** — 이번 세션에서도 admin Lambda는
  자동 진행됐지만 ECS 쪽은 전부 사용자가 직접 터미널에서 실행.
- **백필 스코프를 "오늘 것만"으로 좁힌 건 사용자의 명시적 정정** —
  처음에 Claude가 frontpage_auto 전체 재실행(신규 기사 발굴)을 돌렸다가
  "기존에 올라간 레터 중 비어있는 것만" 채우는 게 원래 의도였다고
  바로잡힘. 5일치 200건 백필은 이번엔 진행하지 않음(스코프 밖).

이 중 웹툰 빈 레터는 198건이었다.

## 한 것

- **레터 paragraphs → 기사 텍스트 대용 + 기존 미디어 URL에서 article_name
  역추출하는 배치 스크립트 작성.** 오늘자 2건 백필 때 확립한 패턴
  (레터 렌즈의 `paragraphs`를 기사 원문 대신 사용, `channel="webtoon"`
  스코프 저장)을 일반화 — 각 레터의 팟캐스트/영상 렌즈 `media_url`/
  `video_url`에서 정규식으로 숫자 article_name과 log_prefix(`mustknow-auto`
  등)를 역추출해, 기존 3개 포맷과 같은 S3 키 규칙으로 웹툰 이미지를
  업로드(`media/{log_prefix}/{article_name}-webtoon-cut{n:03d}.png`).
  ThreadPoolExecutor(동시 6개)로 병렬 처리, 기사 단위 예외 격리(한 건
  실패해도 나머지 계속).
- **1차 배치(198건 타겟) 50건 처리 후 사용자가 스코프 정정** — "최신순
  100건까지만" 요청으로 실행 중이던 배치를 `kill`, `published_at`
  타임스탬프 기준 재정렬 후 이미 완료된 43건을 제외한 나머지 중 최신
  100건만 다시 타겟팅해서 2차 배치 실행(총 스코프 143건 = 43+100).
  2차 배치 완료: OK 83 / FAIL 17 (전체 합산 126 OK / 17 FAIL, 42분 소요).
- **첫 배치에서 "저장 실패(400)" 발견·수정** — 일반 글 편집 API
  (`posts_repo.update`, channel 없이 호출)가 "이 글은 자동 파이프라인이
  만든 '4가지 시선' 번들이라 이 편집기로는 저장 불가"로 거부. admin
  프론트(`webtoon/edit/page.tsx`)의 저장 로직을 읽고 올바른 방식(channel
  ="webtoon" + `body_inline={body:[], key_points:[], keywords:[],
  images:[...]}`)을 찾아 재시도 — 서버(`_update_lens_bundle_slice`)가
  이 형식을 받아 레터·팟캐스트·영상은 그대로 두고 웹툰 렌즈 항목만
  images로 교체하는 걸 확인.
- **실패 18건 근본 원인 규명 — 재시도가 무의미했던 이유.** 사용자가
  "재시도보다 오류를 정의하고 해결하라"고 요청 — 실패 로그를 다시 보니
  전부 `응답에 이미지 없음: ['Filter reason: prompt']`(Bedrock 콘텐츠
  필터 거부)였고, **같은 기사·같은 컷 번호가 서로 다른 배치 실행 두
  번 다 동일하게 실패**해 재시도가 원천적으로 무의미했다는 걸 확인.
  실패가 컷5·7(각 7건)·8(4건)에 몰려 컷1~4(0~1건)보다 훨씬 많은 것도
  확인 — 처음엔 토큰 예산 문제로 의심했으나, 실제 실패한 컷5의
  image_prompt 원문을 직접 읽어보니 표면적으로 전혀 위험해 보이지 않는
  문장("hand resting lightly on their chest, eyes cast slightly
  downward")이라 규칙 기반 사전 필터링으로는 못 잡는 케이스임을 확인.
- **콘텐츠 필터 거부 시 자동 프롬프트 순화 로직 신설.**
  `pipelines/common/webtoon_image.py`에 `_soften_scene_for_filter()`
  추가 — Bedrock 응답이 `Filter reason: prompt`면 텍스트 모델(재사용:
  기존 `_QA_MODEL` ARN, `lens-webtoon-script-sonnet-46`)에게 "실존 인물
  느낌·신체 부위·통증·갈등·폭력을 연상시키는 표현만 중립적으로 바꿔
  같은 형식으로 다시 써라"라고 요청해 받은 순화 버전으로 1회 재시도.
  `generate_cut_image_to_file()`의 재시도 클로저에 이 로직을 끼워 넣어,
  순화 후에도 실패하면 기존 백오프 재시도(12/24/36초)로 자연스럽게
  이어지게 함. **직접 검증**: 실패했던 실제 image_prompt로 `retries=1`
  단독 테스트는 실패했지만 `retries=3`(프로덕션 기본값)로는 성공 —
  순화가 재시도와 결합해야 효과가 난다는 것과, **Bedrock 필터가 완전히
  결정론적이지 않고 확률적**이라는 걸 실측으로 확인(같은 순화 문장도
  실행마다 통과/거부가 갈림). admin Lambda + ECS(`frontpage_auto`,
  revision 53) 배포.
- **실패 18건 재시도(순화 로직 적용 후) → 12건(67%) 복구.** 남은 6건
  중 재재시도로 1건(17%) 추가 복구 — 회수율이 급격히 떨어지는 수확체감
  패턴 확인, 자동 재시도로 100% 도달은 비현실적이라 판단하고 중단.

## 결정

- **"재시도보다 근본 원인"이라는 사용자 요청에 따라, 실패를 그냥
  다시 돌리는 대신 실패 메시지 원문을 직접 읽어 원인을 특정한 뒤
  코드를 고쳤다.** 이 판단(FileNotFoundError로 보였던 게 사실은
  콘텐츠 필터 거부였다는 것)이 없었으면 계속 의미 없는 재시도만
  반복했을 것.
- **콘텐츠 필터 거부에 대한 근본 해결책은 "사전 금지어 목록"이 아니라
  "거부 시점 즉석 순화"를 택했다.** "lower abdomen" 사례처럼 사후에
  문서(v3 프롬프트)에 금지어를 하나씩 추가하는 방식은, 이번 컷5
  사례처럼 표면적으로 안전해 보이는 문장도 거부되는 걸 막지 못한다
  — Bedrock이 거부 사유를 상세히 안 알려줘서 규칙화가 원천적으로
  불가능하다는 게 이번에 실측으로 재확인됨.
- **100% 성공률은 이 필터의 확률적 특성상 자동화만으로는 달성 불가로
  판단, 143건 중 138건(96.5%) 선에서 자동 백필을 마무리.** 남은
  5건은 사람이 직접 프롬프트를 검토하거나 다음 자동 실행 때 재시도되길
  기다리는 쪽으로 보류.
