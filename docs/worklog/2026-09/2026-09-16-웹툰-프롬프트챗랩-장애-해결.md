# 2026-09-16 웹툰 프롬프트 챗랩(PromptChatLab) 장애 해결 + nova식 프롬프트 로딩 전환

작성: 문영광 + Claude Code
관련: admin/backend/routes/prompts.py, admin/backend/routes/chat_ws.py,
admin/backend/repo/prompt_lab_repo.py, admin/frontend/src/components/PromptChatLab/,
pipelines/common/gpu_ipadapter.py

## 배경

`lensdb.sedaily.ai/webtoon`의 프롬프트 실험 챗봇(PromptChatLab)이 기사를 넣어도
응답이 아예 안 나오는 문제로 시작. 점검해보니 원인이 한 겹이 아니라 여러 겹
쌓여 있었다 — 토큰 낭비(105K자 프롬프트 통째 전송) 개선 요청을 먼저 처리하던
중, 실제로는 훨씬 더 근본적인 WebSocket 프레임 크기 장애가 숨어 있었다.

## 한 것

**1. 1·2단계 프롬프트를 챕터 단위로 분할 전송** (`prompts.py`)
- 발행된 웹툰 프롬프트(105,277자, `## N. 제목` 챕터 구조)에서 단계별로 필요한
  챕터만 추출하는 `_extract_chapters()` 추가 — 새 프롬프트 파일을 만드는 대신
  기존 발행 문서를 그때그때 슬라이싱.
- 1단계(스크립트) 호출은 35%(36,839자), 2단계(장면 연출) 호출은 23%(24,502자)만
  전송하도록 축소.
- 이 과정에서 발행 프롬프트 원본 자체의 결함도 발견: 0~21장이 문서 안에 통째로
  두 번 중복돼 있고(뒤쪽 사본이 최신), 맨 끝에 admin 편집 UI 라벨("### 파일 ·
  새 파일")과 테스트 텍스트("aaaa")가 발행 내용에 섞여 있었다. 코드에서
  방어적으로 우회 처리(마지막 등장만 채택 + 알려진 오염 마커 이후 절단)했지만
  **DDB 원본 자체는 아직 안 고쳤다** — 다음 항목 참고.

**2. 1·2단계를 실시간 스트리밍으로 전환 + human-in-the-loop 텍스트 선택지**
(`chat_ws.py`, `PromptChatLab.tsx`)
- 기사 도착 시 짧은 반응 문구 스트리밍(`_stream_reaction`)을 제거 — 바로 1단계로
  진입.
- 1·2단계 JSON 생성을 `converse_stream`으로 바꿔 생성 중 원문을 `step1_chunk`/
  `step2_chunk`로 실시간 중계, 프론트는 모노스페이스 "생성 중" 미리보기로 렌더.
- 1단계 완성 후 "(1) 다시 생성 / (2) 2단계 진행" 텍스트 선택지를 붙이고, 사용자가
  입력창에 숫자만 쳐서 보내도(버튼 대신) 같은 동작을 하도록 프론트에 라우팅
  로직 추가(번호 해석은 서버가 아니라 프론트가 담당).

**3. GPU 상태 조회 IAM 권한 수정**
- `AdminWebtoonGpuPipeline` 정책의 `ec2:DescribeInstances`가 특정 인스턴스 ARN으로
  스코프돼 있었는데, 이 액션은 리소스 단위 제한을 지원하지 않아(AWS 제약) 실제로는
  거부되고 있었다. `Resource: "*"`인 별도 statement로 분리해서 해결(Start/Stop은
  기존처럼 인스턴스 ARN으로 계속 제한).

**4. (핵심 원인) WebSocket 32KB 프레임 한도 초과로 연결이 반복적으로 끊기던 문제**
- 증상: 기사를 보내면 응답이 안 오고, 로그를 보면 연결이 몇 초 만에
  connect→disconnect를 반복.
- API Gateway WebSocket API 접근 로그가 꺼져 있어서(`LoggingLevel: OFF`) 그동안
  아예 안 보이던 구간이었다 — 로그 그룹(`/aws/apigateway/sedaily-mbti-admin-ws-dev`)
  만들고 스테이지에 access log + `LoggingLevel: INFO` 켜서 확인.
- 실제 원인: 우측 "지침" 패널이 편집 중(저장 여부 무관) 내용을 매 메시지마다
  `prompt_override`로 WebSocket에 실어 보내고 있었는데, 이 패널이 처음 로드될 때
  발행된 프롬프트 전체(105K자, ≈105KB)를 지침 칸 초기값으로 자동 채워 넣는
  동작이 있어서(`PromptSectionsPanel.tsx`), 그 상태로 아무 메시지나 보내면 매번
  API Gateway WebSocket 프레임 하드 리밋(32,768바이트)을 넘겨 서버가 code 1009로
  연결 자체를 끊어버렸다. 프론트의 close-event 진단 로그(`event.code`/
  `event.reason`)를 추가해서 code 1009 "Max frame length of 32768 has been
  exceeded"로 특정.

**5. 아키텍처 전환 — nova와 같은 방식으로 통일**
- 사용자 확인 후 "타이핑하는 대로 즉시 반영"(저장 없이 테스트) 기능을 폐기하고,
  `nova/backend/websocket/prompt_builder.py::load_engine_full_prompt` 패턴으로
  전환: 클라이언트는 프롬프트 원문을 아예 안 보내고, 서버(`chat_ws.py::
  _resolve_saved_draft`)가 저장된 지침(prompt_lab_docs)을 DB에서 직접 읽어와
  시스템 프롬프트로 합친다. `prompt_lab_repo.assemble_draft()`에 nova의
  `_get_engine_data`와 같은 60초 TTL 캐시 추가.
- 이제 WebSocket 프레임에 큰 텍스트가 실릴 일이 구조적으로 없다. 대신 지침을
  테스트하려면 타이핑 후 "저장"을 눌러야 한다(최대 60초 캐시 지연 후 반영).
- 죽은 코드 정리: `draftPromptRef`/`onAssembledChange` 연결 제거,
  `promptBlocks.ts`(프론트 조립 헬퍼, 서버로 로직 이전하며 무용지물) 삭제.

**6. GPU IP-Adapter 동시성 버그 수정** (`pipelines/common/gpu_ipadapter.py`)
- 위 문제들을 다 고친 뒤 "전체 컷" 생성을 처음 제대로 테스트하다가 발견 — 8컷을
  `ThreadPoolExecutor`로 동시 처리하는데, `gpu_ipadapter._clients()`가 ssm/ec2/s3
  세 전역변수를 순서대로 채우면서 가드는 `_ssm_client is None` 하나만 보고
  있었다. 한 스레드가 `_ssm_client`까지만 채운 순간 다른 스레드가 그 가드를
  통과해버려 `_s3_client`가 아직 None인 채로 반환되는 경쟁 조건 —
  `'NoneType' object has no attribute 'put_object'`로 여러 컷이 랜덤하게 실패.
  `threading.Lock()`으로 이중 검사 잠금(double-checked locking) 적용해 해결.
  오늘 다른 변경과 무관한 기존 버그였고, 동시 생성 경로가 처음 제대로
  실행되면서 드러난 것.

배포는 admin 백엔드(`deploy-admin-api.sh`)·프론트엔드(`deploy-admin.sh`) 각각
여러 차례(단계별 수정마다) 재실행.

## 결정

- **저장 안 해도 실시간 테스트되는 기능은 폐기.** WebSocket 프레임 크기 문제를
  구조적으로 없애는 쪽(nova식 서버 사이드 상시 조회)을 택했고, 그 대가로
  "저장 눌러야 반영"이라는 제약을 받아들이기로 사용자가 확인.
- **번호 선택지는 서버 상태 관리 없이, 프론트가 번호를 해석해서 기존 버튼과
  같은 동작으로 라우팅**하는 가벼운 방식으로 구현 — 별도 세션/스테이지 DB
  테이블은 만들지 않음.
- **발행 프롬프트 원본(DDB)의 중복·오염 텍스트는 이번엔 안 건드림** — 코드
  쪽에서 방어적으로 우회만 했다. 원본 정리는 별도로 사용자 확인 후 진행 필요
  (아래 "다음" 참고).

## 추가: 이미지 생성(컷 생성) "pipeline" 모델의 프롬프트를 DB 기반으로 통제

관련: `pipelines/common/webtoon_image.py`

### 배경

사용자가 "관리자가 화면에서 저장한 프롬프트만이 생성을 통제해야 하고, 화면에
안 보이는 곳에서 내용이 바뀌면 안 된다"는 원칙을 명확히 함. 점검해보니 기본
이미지 모델인 "pipeline"(GPU IP-Adapter + Style Transfer)의 실제 생성 경로에서
admin이 편집·발행하는 STYLE/CHARACTER_FEMALE/CHARACTER_MALE 텍스트가 전혀
안 쓰이고 있었다 — 코드에 박힌 별도 상수(`_STYLE_GUIDE_STYLE_HINT`)와
참조 이미지(사진)만으로 화풍·인물이 결정되고, admin이 그 텍스트를 고쳐 발행해도
결과물엔 아무 영향이 없었다.

### 한 것

1. **Style Transfer 호출의 `prompt`** — 하드코딩된 `_STYLE_GUIDE_STYLE_HINT`
   대신 `get_style()`(admin이 저장한 STYLE 텍스트)을 쓰도록 교체. "A는 여성,
   B는 남성" 역할 매핑 한 줄(`_STYLE_AB_ROLE_LINE`)만 구조적 배선으로 남김 —
   이건 화풍 콘텐츠가 아니라 참조 이미지 속 어느 쪽이 A/B인지 알려주는 용도라
   admin 편집 대상이 아니라고 판단.
2. **CHARACTER 텍스트를 실제 생성에 합류** — `_character_text_for(subject)`
   신설. 단일 인물 컷(GPU IP-Adapter)과 두 인물 동시 등장 컷(각자 solo 생성 후
   합성) 양쪽 모두, 인물 identity는 여전히 참조 사진(IP-Adapter)이 고정하되
   외형 텍스트는 이제 admin이 저장한 CHARACTER_FEMALE/MALE에서 가져온다.
   `_DUAL_SOLO_PROMPT_TEMPLATE`(포즈 지시문)는 admin 편집 대상 콘텐츠가 아니라
   R9 실측(공유 brief를 쓰면 두 인물 특징이 섞이는 문제)에 따른 기술적
   스캐폴드라 그대로 유지.
3. **장면(SCENE) 한→영 번역을 "압축"에서 "충실한 번역"으로** —
   `translate_scene_to_photo_brief()`가 쓰는 시스템 프롬프트가 원래 "compress"
   (요약)를 지시해서 admin이 SCENE에 적은 내용 일부가 조용히 생략될 수
   있었다. "생략·요약·창작 금지, 있는 그대로 번역"으로 지침을 바꿨다.
   인물이 몇 명 나오는 컷인지 분류하는 SUBJECTS 판단은 그림에 실리는 콘텐츠가
   아니라 내부 라우팅이라 그대로 유지.
4. 로컬 스모크 테스트(`get_style()`/`_character_text_for()`/
   `translate_scene_to_photo_brief()` 직접 호출)로 DB 값이 실제로 반영되는 것,
   번역이 내용을 안 빠뜨리는 것 확인. `py_compile`/`pyflakes` 클린.

### 결정

- **Style Transfer 프롬프트에 긴 STYLE 텍스트(약 3,100자)를 그대로 써도
  안전한가?** — 과거 실측(주석 참고)은 "장문 인물 묘사"를 이 프롬프트에
  섞었을 때 반실사화되는 문제였다. 현재 STYLE 텍스트는 화풍 묘사만 담고
  인물 외형 묘사가 없어 같은 문제가 재현될 가능성은 낮다고 판단해 진행 —
  다만 실제 컷 생성으로 화질 저하 여부를 아직 육안 확인 못 함(다음 항목).
- **시스템 프롬프트(번역 지시문) 자체는 admin 편집 대상으로 안 옮김** —
  이건 "무엇을 그릴지"의 콘텐츠가 아니라 "admin이 적은 내용을 그대로
  통과시켜라"는 코드 레벨 안전장치라 비우면 오히려 원칙에 역행한다고
  사용자에게 설명하고 동의 하에 유지.
