# 2026-11-03 CMS 목록 쿼리 튜닝 — 웹툰·영상·오디오 목록에서 컷 전체·본문 묶음 제거

## 배경

Aurora(`lens-postgres-migration-dev`, serverless v2 0.5~2 ACU)가 24시간 내내 5~10분마다 CPU 80~100%·ACU 상한을 찍었다.
11/2 Performance Insights(Database Insights Standard)를 켜고 nginx 접근 로그와 맞춰 본 결과, 프론트가 `channel=webtoon|video|home_player&limit=1000` 요청 3개를 같은 초에 보낼 때 봉우리가 생겼다.
11/3 Database Insights 상위 SQL 1위가 목록용 `_BASE_SELECT`(글마다 `webtoon_panels`·`rendition_blocks` 전체 `jsonb_agg`)로 확인됐다. 2위인 lens 목록(묶음 없음)의 약 3배.

## 한 것

- `cms_posts_repo.py`에 목록 전용 `_LIST_SELECT` 추가: 웹툰 컷은 첫 컷 1개만(`ORDER BY wp.position LIMIT 1`, 빈 URL 제외), 본문은 `NULL::jsonb`.
- `list_published_posts`에서 webtoon·video·home_player는 `_LIST_SELECT`, letters는 `_BASE_SELECT` 그대로.
- 근거: 목록 shaper가 웹툰 첫 컷(cover 폴백, `shape_webtoon`)만 읽는다. `shape_webtoon_summary`는 panels를 비우고, `shape_video`·`shape_home_player_summary`는 컷·본문을 안 읽는다. letters 목록은 본문을 쓴다(`shape_letter`).
- 배포: 이 PC 작업 사본이 CRLF라 `git archive`(LF) 사본에서 `deploy.sh`를 실행(PC 쪽 `/tmp` 경로만 scratch로 바꿈). 배포 전 서버 `*.py` 해시가 git HEAD와 전부 일치함을 확인. 서버 복구본 `/tmp/lens-cms-before-20261103T005850.tar.gz`.
- 검증: 배포 전후 `limit=1000` 응답(webtoon·video·home_player·letters) 1000건씩 글 단위로 비교 — 전부 동일. 서버 `cms_posts_repo.py` 해시가 배포본과 일치.

## 결정

- 프론트 `limit` 축소(B안: 홈은 4건만 씀, `toWebtoonPreviewSummaries`/`toVideoPreviewSummaries`의 `slice(0, 4)`)는 따로 한다. 원인을 하나씩 나눠 효과를 보려는 것.
- `transcript`는 목록에서도 아직 읽는다(home_player 목록은 받은 뒤 버림). 묶음 없는 컬럼이라 상위 SQL에 안 잡혀 이번엔 두었다.
