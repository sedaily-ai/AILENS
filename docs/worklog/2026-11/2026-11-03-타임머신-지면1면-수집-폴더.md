## 배경

타임머신에서 연월일을 고르면 해당 일자의 지면 1면 이미지와 1면 기사 데이터를 보여 주려 한다. 이미지는 1960년부터 로컬에 있었으나 텍스트 데이터는 없었고, 기존 타임머신은 1면 조회를 빅카인즈 실시간 호출(면 번호 시기만)에 의존한다.

## 한 것

- 네이버 서울경제 신문보기에서 2026-01-01~11-03 1면 기사 250일·1,171건을 수집했다(스크립트 `timemachine-data/collect/crawl_naver_front.py`).
- 이미지 현황을 집계했다: 1960-08-01~2026-11-02, 16,254장·21.3GB, 1978~87·1991~93 없음.
- 네이버 제공 시작 시점을 표본 조회로 확인했다: 2011-07-09 첫 제공, 2011-06 이전 표본은 0건.

## 결정

## 오후: 1면 이미지 저장소 설계와 인수 규격

작성: 도연 + Kiro
관련: 브랜치 `feat/timemachine-newspaper-intake`

### 배경

1면 이미지(1960-08-01~2026-11-02, 16,254장·21.3GB)는 확보돼 있어, 로드맵 1단계(데이터 구축 설계, 인수 규격 작성)를 진행했다. 이미지는 신문 비율을 지키려 원본 그대로 쓴다. 이 기기에는 AWS가 없어 AWS 설정은 AWS를 쓰는 기기에서 했다.

### 한 것

- 저장소·주소·폴더 구조·연도 파일 v1 형식을 `timemachine-data/README.md` "데이터 구조"에 적었다.
- 버킷 이름 `TIMEMACHINE_NEWSPAPER_BUCKET`을 `config/resources.env`에 생성 전 정본으로 등록했다. 아직 쓰는 스크립트는 없다.
- `timemachine-data/upload/check_images.py`(표준 라이브러리만): 올리기 전 점검(이름·날짜·JPEG·끝 잘림·내용 중복, 확인 항목은 공백 기간·1996-09-29 이후 일요일·작은 가로·가로형)과 올린 뒤 S3 목록 대조(빠짐·남음·크기·MD5). 가짜 폴더 18개 파일로 오류 9건·확인 5건이 기대대로 나오고, 요구사항 HTML의 실제 JPEG에서 408×560을 읽었다. Windows PowerShell 5가 UTF-16으로 쓴 목록도 읽는다.
- 이미지를 올릴 때 따르는 `timemachine-data/261103_타임머신_1면이미지_인수규격.md`를 썼다(저장소·형식·구조·업로드 명령·검증 기준).
- AWS를 쓰는 기기에서 버킷 `sedaily-lens-timemachine-newspaper`를 만들었다(us-east-1). 보고된 재조회 결과: 계정 일치, 태그 7개(`Service=lens` 포함), 공개 접근 차단 4개 모두 true, 버전 관리 Enabled, 수명 주기 `expire-noncurrent-versions-90d`(이전 버전 90일·미완료 멀티파트 7일), 소유권 `BucketOwnerEnforced`. 업로드 전용 정책 `lens-timemachine-newspaper-upload`를 만들었고 누구에게도 연결하지 않았다. 이 기기에는 AWS가 없어 직접 조회하지 못했고 실행한 쪽의 보고를 옮겼다.
- 신문 장면 표시 규칙을 `timemachine-data/261103_타임머신_신문장면_표시규칙.md`에 정리했다(구간별 자료, 기사 출처·순서, "1면" 문구, 지면 없는 날 대체, 안내 문구 9가지, 과제별 처리).
- 화면·백엔드·다른 타임머신 기능은 바꾸지 않았다.

### 결정

- 새 S3 버킷 `sedaily-lens-timemachine-newspaper`(us-east-1, 비공개, 버전 관리, 이전 버전 90일). 사이트 CloudFront `/timemachine-newspaper/*` → 버킷 `timemachine-newspaper/`(OAC). 태그 Service=lens(2026-10-01 이후 규칙). 요구사항의 `Service=atlas4`는 쓰지 않는다.
- 원본 이미지 `timemachine-newspaper/img/YYYY/MM/YYYYMMDD.jpg`, 자르기·크기 변경·재인코딩 없음. 연도 파일 `timemachine-newspaper/index/v1/YYYY.json`.
- 버킷·경로 이름은 개발(Kiro) 제안이다. 처음 고른 `front`가 '프론트(화면)'로 읽혀 '신문'(`newspaper`)으로 바꿨다(도연님 요청). '1면'을 영어로 옮기면 다시 front가 들어가 '신문'을 골랐다.
- 이미지는 날짜 주소로 직접 불러오고 연도 파일에는 기사만 둔다. 이미지 정보를 파일에 두면 이미지를 올린 뒤 파일을 다시 만들어야 해서 올리면 바로 보이지 않는다.
- 기사 데이터는 S3 연도 파일이다(DynamoDB 아님). 과거 날짜라 거의 바뀌지 않고 모든 사용자에게 같으며, 백엔드를 고치지 않고 사이트 주소로 바로 받는다. DynamoDB는 빅카인즈 결과 캐시 용도로 그대로 둔다.
- 기사는 최대 4건, 부족하면 있는 만큼. 네이버는 네이버 순서의 앞 4건에 1번만 크게 보이고 중요도는 말하지 않는다(두 날짜 확인에서 1번만 지면의 톱과 맞았다: 2015-01-02, 2026-11-02). 빅카인즈는 지금 방식 그대로다.
- "1면" 문구는 1면이 확실한 날(지면 사진, 네이버 1면, 빅카인즈 면 번호 시기)에만 쓴다. 빅카인즈 그날 기사는 "그날 서울경제 기사"로 부른다.
- 이미지가 있으면 그날 지면이 있었던 것으로 본다. 일요일(1996-09-29~)은 월요일자(없으면 토요일자), 명절·결측은 가장 가까운 지난 신문(최대 10일), 1990년 이전의 명절·결측은 안내만 한다.
- 기사 목록이 없는 시기(1960-08~1977, 1988-08~1989)는 글자 인식 없이 사진만 보여 준다.
- 화면은 이미지 보기를 끈 채 먼저 배포하고, 이미지 업로드를 확인한 뒤 켠다.

### 다음

## 저녁: 사이트 주소 연결과 e-Paper 1면 이미지 일일 수집

관련: 브랜치 `feat/timemachine-epaper-capture`

### 한 것

- 사이트 CloudFront에 `/timemachine-newspaper/*` 경로를 버킷과 연결했다(AWS를 쓰는 기기에서 실행하고 결과를 보고받아 옮겼다). 원본 접근 제어 `lens-timemachine-newspaper-oac`. 첫 화면과 `/birthday-market` 200, 시험 파일 4바이트가 200·`image/jpeg`로 열리고 확인 뒤 삭제, 없는 이미지는 404, 되돌림 없음. 사이트 배포의 `Service` 태그는 `atlas4`로 남아 있고 이번에 바꾸지 않았다.
- 사이트 CloudFront 표준 접속 기록은 꺼져 있다(`Enabled=false`, 새 방식의 delivery source 없음). 실시간 로그, WAF 로그, S3 데이터 이벤트 기록은 확인하지 않았다.
- e-Paper 첫 화면 구조를 확인했다. 최신호 정보가 화면에 박혀 있고(발행일, 1시간짜리 이미지 토큰, 면 목록), 토큰의 슬래시가 `\/`로 이스케이프돼 있어 풀어 쓰지 않으면 이미지가 403이다.
- `timemachine-data/collect/fetch_epaper_front.py`: 최신호 1면 이미지를 받아 폴더(`YYYY/MM/YYYYMMDD.jpg`) 또는 S3(`timemachine-newspaper/img/`)에 저장한다. 이미 같은 내용이 있으면 건너뛰고 다르면 그대로 두며, 토큰은 출력하지 않는다. 시험(네트워크·AWS 없이)이 통과한다.
- 2026-11-03 1면을 실제로 받았다: 2495×3507, 905,533바이트, 같은 명령을 한 번 더 돌리면 "이미 있음". 받은 파일은 `upload/check_images.py` 점검을 오류 0건·확인 0건으로 통과했다. 이미지는 저장소에 넣지 않는 폴더(`timemachine-data/local-capture/`)에만 있다.

### 결정

- 일일 수집은 e-Paper 첫 화면의 최신호 정보만 쓴다(로그인 불필요). 무료는 최신호 1면뿐이라 하루를 놓치면 그날 이미지는 로그인해야 받을 수 있다.
- 1면 기사 제목·영역(`pdfData`)도 이미지와 같이 저장한다(`timemachine-newspaper/epaper/YYYY/MM/YYYYMMDD.json`). 하루 약 1.5KB(들여쓰기 포함, 1면 기사 8개)로 비용이 거의 없고, 이것도 최신호만 무료라 놓치면 되돌릴 수 없다. 기사 저장이 실패해도 이미지 수집은 성공으로 본다.
- 일일 수집을 AWS에서 항상 자동으로 돌리기로 했다(이 PC의 예약 실행이 아니라 LENS의 다른 자동화와 같은 방식). Lambda `sedaily-lens-timemachine-newspaper-capture`를 EventBridge가 매시간 10분에 부른다. `collect/lambda_handler.py`, `aws/provision.sh`(리소스·태그 구성과 태그 재조회), `aws/deploy.sh`(코드 배포와 `CodeSha256` 확인)를 만들었고 시험은 25개(Lambda 진입점과 S3 저장 포함, 네트워크·AWS 없이)가 통과한다. `config/resources.env`에 함수 이름을 등록했다.
- S3 존재 확인은 `head_object`가 아니라 접두어를 제한한 목록 조회로 한다(없는 파일에 head를 하면 목록 권한이 없을 때 403이 와서 404와 구분되지 않는다).

### 한 것 (이어서)

- 일일 수집 Lambda를 AWS에 만들고 한 번 실행했다(AWS를 쓰는 기기에서 `aws/provision.sh`, 결과를 보고받아 옮겼다). 계정 일치, 리소스 네 곳(Lambda·IAM 역할·EventBridge 규칙·로그 그룹) 모두 `Service=lens`, 실행에 `FunctionError` 없음, 2026-11-03 1면이 `saved`(2495×3507, 905,533바이트)로 S3에 저장됐고 S3 크기와 사이트 주소 응답(200·`image/jpeg`·`content-length: 905533`·`max-age=2592000`)이 같다. 규칙은 `ENABLED`, `cron(10 * * * ? *)`, 대상 `CaptureLambda`. 회사 사이트가 AWS Lambda의 요청을 받는 것도 이때 확인됐다.
- 1면 기사 제목·영역 저장을 추가했다(`save_articles`, `lambda_handler.py`, 시험 37개). 권한은 `epaper/` 목록·저장을 더했다(`provision.sh` 정책).
- 권한 갱신(`provision.sh`)과 코드 배포(`deploy.sh`)를 AWS를 쓰는 기기에서 실행하고 결과를 보고받아 옮겼다. 권한 정책에 `epaper` 접두어 2곳, 배포 `CodeSha256` 일치, Lambda 실행 `status=exists`·`epaper=saved`, S3 `epaper/2026/11/20261103.json` 1,539바이트, 사이트 주소 200·`application/json; charset=utf-8`·`max-age=86400`, 내용 `2026-11-03` 기사 8개 2495×3507.
- `timemachine-data/build/build_year_files.py`: 1면 기사 CSV(`date`·`rank`·`title`·`url`)로 연도 파일을 만든다. 확인한 기간(`--covers`)을 선언받아 `text_covers`로 담고, 선언 밖의 행·중복 순서·잘못된 값은 오류, 기사 수 3~6건 밖·순서 끊김은 알림, 같은 입력이면 파일을 다시 쓰지 않는다. 시험 11개 통과.
- 네이버 신문보기 페이지 모양을 날짜 6건으로 확인했다: 2011-07-09부터 1면 목록이 있고 그 전날과 일요일·휴간일은 "발행된 종이신문이 없거나 신문게재 정보가 입력되지 않았습니다"이며, 2011·2013·2018년 모두 같은 구조로 읽혔다(기사 6·4·5건). `media.naver.com/robots.txt`는 모든 봇에 `Disallow: /`이고 AI 학습·RAG 수집 금지를 적고 있어(2026-11-03 확인) 대량 수집은 하지 않았다.

## 밤: 신문 장면 화면 구현

작성: 도연 + Kiro
관련: 브랜치 `feat/timemachine-newspaper-scene`, `timemachine-data/261103_타임머신_신문장면_표시규칙.md`

### 한 것

- 생일 타임머신 결과의 "그날 서울경제" 장면에 1면 사진, 네이버 1면 목록, 새 안내 문구, 일요일 월요일 우선 대체를 넣었다. 백엔드·"그날의 기사" 탭·`/timeline`·공유 카드는 바꾸지 않았다.
- `lib/birthdayNewspaper.ts`: 신문 장면 스위치, 날짜로 정해진 사진 주소, 연도 파일(v1) 읽기(https 주소와 순위만 받고 형식이 다르면 그 해를 버림), 일요일이면 월요일을 묻는 요청 날짜.
- `lib/birthdayNewspaperView.ts`: 사진·목록·안내·장면 이름·출처 줄을 정하는 규칙(화면은 이 결과를 그리기만 한다). 문구는 표시 규칙 4절과 같다.
- `lib/birthdayFrontPage.ts`: `loadFrontScene`(서버 답에 네이버 목록을 붙임, 연도 파일은 서버 요청과 함께 받음), 1990년 이전의 사진만 시도하는 상태(`image-only`).

## 밤 늦게: 날짜 종류별 개수표 스크립트

작성: 도연 + Kiro
관련: 브랜치 `feat/timemachine-day-counts`, `timemachine-data/upload/count_day_types.py`

### 한 것

- `upload/count_day_types.py`(표준 라이브러리만): 창간일부터 `--until`까지 날짜마다 1면 사진과 네이버 1면 목록이 있는지 세어 연도별 표를 만든다. 사진은 올리기 전 `newspaper_manifest.csv`(`--manifest`) 또는 올린 뒤 S3 목록(`--listing`, UTF-16도 읽음), 목록은 연도 파일 폴더(`--year-files`)에서 읽는다. 창간일·발행 중단 기간·일요일자 폐지일·사진 이름 형식은 `check_images.py`의 값을 불러다 쓴다.
- 날짜 종류: 발행 중단, 일요일 휴간(1996-09-29~), 옛 일요일(1996-09-29 전), 발행 예상일(사진+목록 · 사진만 · 목록만 · 둘 다 없음 · 목록 미확인). 사진이 이어서 없는 구간은 일요일을 건너뛰어 잇고 사진이 있는 날과 발행 중단에서 끊는다. 화면에는 긴 구간 15개만 보여 주고 전체는 `missing_runs.csv`에 둔다.
- `--out`: `day_types.csv`(날짜별), `year_counts.csv`(연도별), `missing_runs.csv`.
- 시험 18개(종류 판정, 연도 파일 읽기, 합계 일치, 두 입력 형식, 잘못된 입력, 옛 일요일 판정 문구, 구간 상한). 이미지·네트워크·AWS 없이 돈다.

### 결정

- 1996-09-29 전의 일요일을 발행 예상일에 섞지 않고 따로 센다. 일요일자가 나오던 시기라고 알려져 있지만(백엔드 `time_machine.py`) 사진이 있는지는 실제 목록으로만 알 수 있기 때문이다.
- 명절·휴간과 자료 누락은 구분할 수 없어 둘 다 "사진 없음"으로 세고, 짧은 구간(2일 이하)은 개수만 알린다.

### 확인한 것과 못 한 것

- 이 기기에는 사진 16,254장이 없어서 실제 개수표는 만들지 못했다. 가짜 입력(요구사항 HTML의 사진 현황과 같은 모양)으로 끝까지 돌려 표 합계가 일치하는 것을 확인했다(달력일 = 발행 안 함 + 옛 일요일 + 발행 예상일).
- 모델 점검: 요구사항 HTML의 "사진 없는 구간"을 빼고 일요일(1996-09-29부터)을 뺀 발행 예상일은 16,307일이고 HTML의 사진은 16,254장이라 차이가 53일이다(명절·결측으로 설명되는 크기). 1996-09-29 전 일요일 1,177일에도 사진이 있다고 보면 차이가 1,230일로 커진다. 그 시기 일요일에는 사진이 거의 없을 가능성이 크다.
- 위는 한 숫자로 세운 추정이다. 실제 목록으로 "옛 일요일 사진" 열이 거의 0인지 확인해야 한다. 그렇다면 신문 장면의 일요일 처리 시작일(`birthdayNewspaper.ts`의 `NO_SUNDAY_FROM`, 백엔드 `SUNDAY_CLOSED_FROM`)이 1996-09-29보다 앞서야 하는지 다시 본다. 지금 화면은 그 전 일요일에 사진을 찾다가 "사진을 찾지 못했어요"가 나온다.

### 다음

- 연도 파일이 생기면 `--year-files`로 목록 열을 채운다.

## 한밤: 네이버 일일 수집·누락 목록·알림·재처리

작성: 도연 + Kiro
관련: 브랜치 `feat/timemachine-daily-collect`, `timemachine-data/collect/{naver_daily,daily_handler}.py`, `aws/{provision_daily,deploy_daily}.sh`

### 한 것

- 이미지 수집 함수(`lambda_handler.py`)는 건드리지 않고 새 함수 `…-newspaper-daily`를 따로 만들었다(운영 중인 구성과 기존 시험 37개를 그대로 둔다). 매시간 25분에 돈다.
- `naver_daily.py`: 네이버 신문보기 1면 목록을 하루 단위로 받아 S3 연도 파일(`index/v1/YYYY.json`)에 이어 붙인다. 확인한 날만 `text_covers`에 넣고, 받기 실패와 아직 목록이 없는 오늘은 넣지 않아 다음 실행이 다시 받는다. 요청마다 3번 재시도, 403·429는 즉시 멈춤, 요청 간 0.7초, 수집기라고 밝히는 User-Agent. 있던 목록은 빈 화면이 와도 지우지 않고, 읽을 수 없는 기존 연도 파일은 덮어쓰지 않는다.
- `daily_handler.py`: 수집, 누락 목록(`ops/status/missing.json`, 공개 경로 밖), CloudWatch 임베디드 지표(`NaverSaved`·`NaverErrors`·`NaverBlocked`·`NaverMissingDays`·`ImageMissingDays`), 날짜 지정 재처리(`dates` 또는 `from`·`to`, 최대 31일, `force`).
- `aws/provision_daily.sh`: Lambda·EventBridge·IAM 역할(이미지 쓰기 없음)·SNS 토픽·알람 3개를 `Service=lens`로 만들고 마지막에 태그를 다시 조회한다. `aws/deploy_daily.sh`는 코드만 올리고 `CodeSha256`과 상태를 확인한다. `config/resources.env`에 이름 두 개를 더했다.
- 알람 3개: 새 함수 오류, 이미지 수집 함수 오류(지금까지 알림이 없던 구멍), 마감 정오 뒤에도 사진이 없는 발행 예상일이 3시간 연속.
- 시험 42개(받기·읽기·연도 파일 이어 붙이기·대상 날짜 고르기·수집·핸들러·누락 목록·지표 형식). 네트워크·AWS 없이 0.1초에 끝난다.

### 결정

- 네이버 수집은 환경 변수 `NAVER_DAILY=on`일 때만 요청하고 기본은 꺼짐이다. `media.naver.com/robots.txt`가 전체 접근을 막고 있어(2026-11-03) 하루 1~8건이라도 켜는 것은 별도 결정으로 둔다. 꺼져 있어도 이미지 누락 목록과 지표는 만든다.
- 켤 때는 `NAVER_DAILY_FROM`(일일 수집 시작일)이 필수다. 누락 기준이 없으면 2011-07-09부터 전부가 누락으로 잡혀 알림이 계속 울리기 때문이다. 시작일 이전은 `naver_backfill` 개수로만 적고 알림에 쓰지 않는다.
- 누락 날짜는 최근 것부터 60개를 담는다. 오래된 순으로 잘랐더니 최근 누락이 목록에 나오지 않았다.
- 알림은 기존 비용 알림(`cost_monitoring.sh`)과 같은 SNS 토픽 + 알람 방식이다. 받는 곳은 `ALERT_EMAIL`을 줄 때만 만들고, 주지 않으면 토픽까지만 만든다(알람 상태는 CloudWatch 콘솔에서만 보인다). 이메일은 쓰지 않기로 했다. 토픽은 나중에 받는 곳만 붙이면 된다.

### 확인한 것과 못 한 것

- 시험 42개 통과, 기존 이미지 수집 시험 37개 통과, 미사용 import 없음. 코드 묶음(세 파일)만으로 핸들러가 임포트되고 표준 라이브러리 밖 의존성은 `boto3`뿐이다. 3.12 문법으로 읽히고 3.13 전용 이름이 없다(3.12 인터프리터가 없어 시험은 3.13에서 돌렸다). 두 AWS 스크립트의 문법 검사 통과.
- 시험 중 실제 결함 하나를 고쳤다: `collect()`의 기본 인자로 받기 함수를 두었더니 시험에서 바꿔 끼운 가짜가 쓰이지 않고 진짜 네트워크를 시도했다. 호출 시점에 찾도록 바꿨다.
- 못 한 것: 이 기기에는 AWS가 없어 구성을 만들거나 실행하지 못했다. 네이버 페이지 요청도 하지 않았다(읽기 코드는 기존 수집 스크립트의 파서를 쓰고, 시험은 만든 HTML 조각으로 한다). CloudWatch 임베디드 지표가 실제 지표로 읽히는지, SNS 이메일 구독, 알람이 토픽으로 가는지는 AWS에서 확인해야 한다. macOS 기본 bash(3.2)에서의 `provision_daily.sh` 동작도 직접 확인하지 못했다.
- 마감 시각(정오)은 새 호가 올라오는 시각을 측정하기 전의 임시값이다.

## 2026-11-04: 1면 크게 보기 개선과 버튼 문구

### 문제
