# 선정(Selection) 프롬프트 — 설계 중

상태: **설계 중 — 아직 미구현, Postgres에 발행된 적 없음**

`mustknow_auto`의 "일반" 카테고리 기사 선정을 AI 채점(1~10점, 7.0 임계값)
방식에서 "LLM이 후보 전체를 보고 직접 고르는" 방식으로 바꾸는 프롬프트.

## 형제 폴더(`letters/`·`webtoon/`·`podcast/`·`video/`)와 다른 점

그 4개는 **지금 라이브로 쓰이는 프롬프트의 단일 스냅샷**이다(버전 이력 없이
Postgres에서 그때그때 다시 받아와 덮어씀 — `../README.md` 참고). 이 폴더는
아직 라이브가 아니라 **설계 중인 초안**이라, `docs/product/4format-pipeline/
08_BUNDLE_LETTER/`와 같은 방식으로 `vX.Y-YYYY-MM-DD-주제.md` 버전 이력을
쌓는다. 실제로 Postgres에 발행되는 시점이 오면 이 폴더도 `published.md`
단일 스냅샷 체계로 전환한다.

**규칙(2026-09-28 공식화)**: 새 버전 파일은 `_TEMPLATE.md`를 복사해서
시작한다. 핵심은 **가설을 먼저 쓰고, 정량 실험으로 검증하고, 판정을
명시**하는 것 — "왜 바꿨는지"가 아니라 "바꾸기 전에 뭘 예상했고 실제로
그랬는지"를 남긴다(볼트 `공통도구/`의 개인 기획 사이클 프레임워크와
같은 원칙: 문제발견→가설→검증→판정→Next). 프롬프트 내용이 이번
버전에서 안 바뀌었어도(예: 검증만 진행한 버전) 파일 맨 하단에 "## 전체
프롬프트 (vX.Y — ...)" 섹션은 반드시 포함한다 — 위쪽은 가설/검증/판정,
맨 아래만 보면 바로 실사용 가능한 프롬프트가 나오게.

## 배경

`service/backend/prompts/mustknow/published.md`(지면특별코너 4탭+일반
공용 채점 프롬프트)의 문제: 5지표 평균 점수가 7.0~7.4 구간에 68.5% 쏠려
있어(2026-09-28 seen 테이블 769건 실측) 사실상 통과/미통과 이진 신호에
가깝고, 애초에 "7.0"이라는 임계값 자체가 검증된 기준이 아니었다.

같은 사내 프로덕트 AI 프리즘(`1_ai_link/prism`)의 선별 방식을 참고 —
원본은 `docs/resources/prism-selection-reference/`에 저장해뒀다. 다만
평가 지표 내용(투자자 페르소나 전용)은 안 맞고, **다양성 메커니즘**(관심사
쏠림 방지) 구조만 참고 가치가 있다는 게 2026-09-28 결론.

## 버전 이력 — 가설·판정 요약

각 버전 파일 본문에 문제발견/근거/변경/검증이 더 자세히 있다 — 이 표는
"무엇을 예상했고 실제로 맞았는가"만 훑어보는 인덱스.

| 버전 | 가설(사전 예상) | 판정 | 근거 |
|---|---|---|---|
| v1.0 | 점수 채점 대신 LLM이 후보 전체를 직접 고르면, 소거·다양성 원칙을 점수보다 잘 지킬 것이다 | 보류(초안, 미검증) | — |
| v1.1 | Prism의 5개 자체검증 질문을 더하면 선정 품질이 오르고 사후 감사가 가능해질 것이다 | 부분채택 | v1.4에서 excluded_reasons가 실제로 유의미하게 출력됨을 확인 |
| v1.2 | "오늘의 흐름"을 먼저 파악하게 하면 시의성 판단이 개별 기사만 볼 때보다 정확해질 것이다 | 채택(단, 전제 조건 발견) | v1.4에서 today_context 품질 확인 → 단 v1.5에서 "후보만 보면 표본이 작을 수 있다"는 전제 결함 추가 발견 |
| v1.3 | "화제 자체"가 아니라 "화제×경제/생활 교차점"을 명시하면, 순수 이벤트 보도(추석 인파 등)는 배제되고 경제·생활 연관 기사가 우선될 것이다 | **채택** | v1.4 실험에서 선정된 20건 전부가 구체적 수치·정책·재정 기반, 순수 이벤트 보도 0건 |
| v1.4 | 위 v1.0~v1.3의 설계 전체가 실제 Bedrock 호출에서도 의도대로 작동할 것이다 | 부분채택 | today_context·다양성·화제교차점 전부 확인(채택) / JSON 파싱 버그 발견(예상 못 한 역효과) |
| v1.5 | 선정 후보(회차별 델타)와 별개로 전체 맥락(context_articles)을 주면, 델타가 작아도 today_context 품질이 유지될 것이다 | **채택** | "델타 12건+전체 맥락 221건" 시뮬레이션 — today_context가 하루 전체(147건)로 봤을 때(v1.4)와 동등 |
| v1.6 | (v1.0부터의 가설 재검토) 카테고리 다양성을 규칙으로 강제하면 더 나은 선정이 될 것이다 | **기각** | selection-harness가 "규칙을 LLM이 못 지킨다"를 먼저 보여줬고, 사용자가 "카테고리 쿼터 자체가 불필요하다 — 중복만 피하면 된다"고 직접 정정. 쿼터 삭제 후 재검증해도 자연스럽게 6~7개 카테고리에 걸쳐 선정됨(강제 규칙 없이도 결과는 비슷, 프롬프트 일관성만 개선) |
| v1.7 | `selected[]` 출력을 중요도순으로 정렬하라고 지시하면, 하루 캡 하드컷이 실제로 덜 중요한 기사부터 잘릴 것이다 | 보류(정량 검증 전) | 코드 리뷰(데이터가 아니라 프롬프트·코드 직접 판독)로 발견 — 하드컷된 기사가 "LLM 거절"과 동일하게 seen 테이블에 영구 기록되던 실제 버그를 같이 수정(`overflow_keys` 분리). 정렬 지시 자체의 효과는 아직 실측 없음 |

## 🛑 실제 런타임 파일은 여기가 아니다 (2026-09-28, 배포 직전 발견)

당초 계획은 `service/backend/prompts/selection/published.md`를
`ddb_prompt.load_prompt("selection")`이 읽는 것이었는데, 배포 직전
Dockerfile을 확인하니 **이미지 빌드 컨텍스트가 `pipelines/`로 한정돼
있어** `service/`가 컨테이너 안에 없다는 걸 발견했다. "selection"은
admin CMS(Postgres)에도 등록 안 돼 있어 API 호출이 항상 실패하고, 그러면
반드시 파일시스템 폴백을 타는데 그 파일이 컨테이너에 없어
`FileNotFoundError`로 `main()` 전체가 죽는 문제였다.

**실제 런타임이 읽는 파일은 `pipelines/mustknow_auto/selection_prompt.md`
다**(`run.py`가 `ddb_prompt` 안 거치고 직접 읽음). `service/backend/
prompts/selection/published.md`는 사람이 보는 문서 사본으로만 유지 —
내용 바꿀 땐 **두 파일 다** 갱신할 것.
